# MC-02 框架优化与融合路线图（板子已上车版 · 详细决策版）

> 适用范围：MC-02 已经装车，可以进行实车/半实物验证；目标机型为 RM 哨兵。
> 目标：在保证上车安全的前提下，把框架从“能编译、能跑”推进到“能闭环、能自主、可回归、好上手”，并吸收 RoboMaster 公开框架与哨兵相关开源项目的设计思路。
> 关联文档：[代码审查报告_MC-02.md](代码审查报告_MC-02.md)
> 阅读说明：第 0~4 节是框架优化与参考工程分析；**第 5 节起是“板子已上车”后新增的哨兵技术细节与分阶段推进图，当前优先级更高**。

## 0. 当前阶段的推进策略——我的建议

### 结论

**板子已经上车，第一优先级不再是重构框架，而是“安全上车 → 逐个执行器 bring-up → 整车闭环 → 接 NUC/视觉/导航 → 哨兵自主决策”。**

具体来说，按以下顺序推进：

1. **Phase 0 安全上电与 bring-up**：看门狗、急停、失能默认态、通信与传感器体检（第 6.1 节）；
2. **Phase 1 执行器逐个 bring-up + 标定**：CAN 扫描、电机方向/零位、单电机闭环、云台、发射机构（第 6.2 节）；
3. **Phase 2 整车闭环与安全**：全向底盘运动学、旋转模式、云台跟随/陀螺仪模式、发射安全、功率/热量限制（第 6.3 节）；
4. **Phase 3 NUC/视觉/导航一体化**：统一 VCP 协议、时间戳同步、自瞄接管、导航速度指令、失联安全（第 6.4 节）；
5. **Phase 4 哨兵自主决策与战术**：状态机/行为树、被击方向反应、目标优先级、前哨站模式、兑换/复活流程（第 6.5 节）；
6. **并行做框架优化**：A1-A3 + B1（构建、CI、主机测试）可以在 PC 上先做；C1/C2（消息中心并发、任务监控）、D1/D2（CLI、flash 参数）在上车调试过程中穿插；D3/D4、E1-E5 放在整车稳定之后。

### 理由

- 实车阶段任何“先重构再上车”的做法都会放大风险：执行器、功率、发射机构一旦失控就是硬件事故，必须先建立失能默认态、看门狗、急停和故障降级。
- 逐个执行器 bring-up 能把问题定位到单点（电机 ID、方向、零位、CAN 丢帧、电流环极性），比一次性上整车容易得多。
- 视觉/导航依赖 MCU 提供高精度、带时间戳的姿态和里程计；协议和时间同步不先做好，后面的自瞄和导航都会“看起来像算法问题，实际是通信问题”。
- 框架优化（构建、CI、主机测试、消息中心并发、CLI、flash 参数）与实车 bring-up 不冲突，可以并行推进，但不要阻塞安全与闭环。
- 框架级重构（例如整体 C++ 化）不在现阶段建议范围内，收益不确定、风险高，留到本赛季稳定后评估。

## 2. 详细工作项

> 标记说明：
> - [纯软件]：不依赖开发板，写代码 + 主机测试即可完成；

### A. 工程与构建

#### A1 统一构建系统（对应 BUILD-02/03）`[纯软件]`

**要解决的问题**：Makefile 与 CMake 的源文件集合不一致，导致两个构建产物行为不同（例如 Makefile 没编 `bsp/usb/`、`TFminiPlus` 等）；Makefile 的 `clean` 用 `rd /s/q`，不跨平台。

**具体做法**：

1. 以 CMake 为唯一事实来源，源文件清单只在 CMake 里维护；
2. Makefile 改为薄 wrapper：`make` 等价于 `cmake --build build`，`make clean` 等价于 `cmake --build build --target clean`（或 `ninja -t clean`）；
3. 删除 Makefile 里的 `rd /s/q` 和手动源文件列表，保留 `make` 入口只是为了兼容现有 CI 和习惯；
4. 清理 `CMakeLists.txt` 中不再使用的变量和重复包含。

**涉及范围**：`CMakeLists.txt`、`Makefile`、`.github/workflows/c-cpp.yml`。

**工作量**：S（半天）。

**收益/风险**：收益是构建行为唯一化，风险极低；唯一注意点是确认 CI 里 `make` 与 `ninja` 两条路径都还能通过。

**参考**：powerful_framework（CMake+Ninja 构建）。

#### A2 CI 增强 `[纯软件]`

**要解决的问题**：当前 CI 只验证“能编译”，不跑任何测试，也不做静态检查，回归靠人工。

**具体做法**：

1. 保留现有 make + ninja 两个编译 job；
2. 新增 `test` job：编译并运行 B1 的主机单元测试（CTest）；
3. 新增 `lint` job：跑 `cppcheck`（或 `clang-tidy`），先以“不新增告警”为门槛，再逐步清零；
4. 新增 `format` job：`clang-format --dry-run --Werror` 检查代码格式（如果团队统一使用 clang-format）；
5. 顺手把 `actions/checkout@v3`、`carlosperate/arm-none-eabi-gcc-action@v1` 等升级到受支持版本；
6. 编译时启用 `-Wall -Wextra`（配合 A3），CI 以告警为零为通过条件。

**涉及范围**：`.github/workflows/c-cpp.yml`、CMake 测试选项。

**工作量**：M（1~2 天）。

**收益/风险**：收益是每次 push 都有编译+测试+静态检查三层保护；风险是静态工具误报需要维护白名单，建议先跑通再逐步加严。

**参考**：librm 的 GitHub Actions（build、docs、CodeFactor）。

#### A3 编译告警清零 `[纯软件]`

**要解决的问题**：目前没有统一告警策略，潜在的类型转换、未使用变量、隐式截断等问题被静默放过。

**具体做法**：

1. 在 CMake 编译选项中先加 `-Wall -Wextra -Wpedantic`，记录现有告警清单；
2. 逐条修复：未使用参数加 `(void)param`、隐式转换显式 cast、比较类型不一致改类型等；
3. 修复后把 `-Werror` 只用于 CI（或本地可选），避免影响快速迭代；
4. 后续可逐步开 `-Wshadow -Wconversion -Wdouble-promotion`，嵌入式浮点代码尤其值得开 `-Wdouble-promotion`。

**涉及范围**：`CMakeLists.txt`、全部源码。

**工作量**：M（1~2 天，取决于现有告警数量）。

**收益/风险**：收益是编译期就能抓出一批隐藏 Bug（例如 `MOTOR-09` 的 int16 截断就是典型）；风险是告警多时修复需要耐心，建议按模块分批。

**参考**：librm 的 CI 和 `.clang-tidy`。

#### A4 源文件清单显式化 `[纯软件]`

**要解决的问题**：CMake 用 `GLOB_RECURSE` 收集源文件，新文件会自动进编译，但也可能把不该编译的骨架/死代码编进去（BUILD-01 的教训）；GLOB 结果不刷新时还会出现“改了文件但没重新 configure”的假象。

**具体做法**：

1. 把每个目录的源文件改为显式列表（`set(BSP_SRCS ...)`、`set(MODULE_SRCS ...)`）；
2. 若暂时保留 GLOB，至少加 `CONFIGURE_DEPENDS` 并写明理由；
3. 在 CI 里加一个“新增 .c 文件必须出现在 CMake 清单中”的检查脚本（防止忘加）；
4. 骨架/未启用模块（XM 电机、HC05、TFmini、OLED 等）用宏开关或独立目录控制，不让它们默认进构建。

**涉及范围**：`CMakeLists.txt`、`tools/`（检查脚本）。

**工作量**：M。

**收益/风险**：收益是构建行为可预测、新文件纳入受控；风险是显式列表维护成本略高，用检查脚本抵消。

**参考**：本项目 BUILD-01 的复盘结论。

### B. 测试与回归

#### B1 主机侧单元测试 `[纯软件]`

**要解决的问题**：PID、RLS、EKF、CRC16、消息中心这些纯逻辑模块目前只能在板子上验证，改一处要烧一次板，回归成本高。

**具体做法**：

1. 新增 `test/` 目录和 `BUILD_TESTS` CMake 选项，编译出在 PC 上运行的测试程序；
2. 把不依赖硬件的源码纳入测试编译：
   - `modules/algorithm/controller.c`（PID）
   - `modules/algorithm/QuaternionEKF.c`
   - `modules/algorithm/RLS`（若存在）
   - CRC16、`float_rounding`、`Float2Str` 等工具
   - `modules/message_center/message_center.c`（用 malloc 模拟，不依赖 RTOS）
3. 测试框架先用最简断言（或引入 Unity），不引入重量级依赖；
4. 每个算法至少覆盖：正常输入、边界输入（`dt==0`、`len==0`、全零向量、最大值）、已知答案校验；
5. 通过 CTest 接入 CI，`ctest --output-on-failure`。

**涉及范围**：`test/`、`CMakeLists.txt`、`.github/workflows/`。

**工作量**：M~L（3~5 天，视算法数量）。

**收益/风险**：收益是算法回归从此不烧板；风险是部分源码与 FreeRTOS/HAL 耦合，需要少量桩（stub）或把纯逻辑拆出来，这本身也是框架改进。

**参考**：librm `test/`（pid、trajectory_limiter、keyboard_handler、throttled_prio_queue 的 host 测试）。

#### B2 板载自测模式 `[板载]`

**要解决的问题**：没有电机时，改完底层代码只能“看日志猜”，缺少一个标准的、可重复的板级体检入口。

**具体做法**：

1. 新增 `SELF_TEST` 编译宏和 `RoboTest()` 入口，`main.c` 中 `#ifdef SELF_TEST` 走测试流程；
2. 实现以下板载测试项，每项打印 PASS/FAIL：
   - **USB CDC 回环**：PC 脚本向虚拟串口发数据，板子收到后原样回发；
   - **USART1 回环/收发**：接 CH340，PC 发已知模式，板子校验并回发；
   - **FDCAN 内部回环**：把 FDCAN 配成 internal loopback 模式，自发自收标准帧/扩展帧，不需要外部 CAN 总线；
   - **BMI088/IST8310**：读 ID、读原始数据、检查数据率；
   - **温控**：读取加热温度，验证 PID 输出随温度变化；
   - **ADC/WS2812/蜂鸣器**：依次点亮/发声，人工或光敏确认；
   - **任务健康**：打印所有任务栈水位、运行时间、CPU 占比；
3. 自测结果统一走 `bsp_log`，同时可经 VCP 输出结构化文本（`TEST START` / `PASS xxx` / `FAIL xxx`）；
4. 写 `tools/hil/selftest.py` 自动化执行和判定。

**涉及范围**：新增 `application/test/`、`main.c`、`CMakeLists.txt`、`tools/hil/`。

**工作量**：L（4~6 天，含脚本）。

**收益/风险**：收益是每次改动后 10 分钟内完成板级回归，修 Bug 有抓手；风险是部分外设（如 OLED、TFmini）当前无实际硬件，测试项要按板载资源裁剪。

**参考**：basic_framework 的 `BSPInit()` 单模块测试模式 + “硬件功能测试程序”理念。

#### B3 通信 HIL 扩展 `[板载]`

**要解决的问题**：视觉和裁判链路只做过“能通”的验证，缺少压力/异常注入测试，协议解析的边界（半包、粘包、坏 CRC、超长帧）没有系统覆盖。

**具体做法**：

1. 裁判侧：扩展现有 `tools/referee_sim/`，增加场景脚本：长时间灌包、随机帧间隔、坏 CRC 注入、截断帧、超大 data_len；
2. 视觉侧：新增 `tools/vision_sim/`，按 sp_vision_25 协议从 COM10（VCP）投喂模拟目标帧，同时接收下位机上行反馈做校验；
3. 增加“跑批模式”：PC 脚本连续跑 N 分钟，统计下位机日志中的错误计数、丢包率、解析失败次数；
4. 把 HIL 场景做成可重复的命令（`python tools/hil/run.py referee-stress`、`vision-stress` 等）。

**涉及范围**：`tools/referee_sim/`、新增 `tools/vision_sim/`、`tools/hil/`。

**工作量**：M~L。

**收益/风险**：收益是通信层健壮性可量化；风险是脚本工作量大，建议先做裁判 stress 和视觉 basic，再扩展。

**参考**：现有 `tools/referee_sim/`（已具备 pytest 单测和 GUI）。

#### B4 一键回归脚本 `[板载]`

**要解决的问题**：B2/B3 各自分散，无法“一条命令完成回归”。

**具体做法**：

1. 写 `tools/hil/run.py`，串联：构建 → 烧录 → 复位 → 进入自测/灌包 → 采集日志 → 判定 PASS/FAIL；
2. 输出一份 `report.txt/json`，记录固件 commit、测试项、耗时、失败原因；
3. 与 CI 可选联动（有板子接在 CI runner 上时跑真机回归）。

**涉及范围**：`tools/hil/`。

**工作量**：M。

**收益/风险**：收益是回归成本降到“一条命令”；风险是依赖探针稳定性（CMSIS-DAP 偶发断连），脚本要带重试逻辑。

### C. 框架健壮性（隐藏 Bug）

#### C1 message_center 并发与类型安全 `[板载]`

**要解决的问题**：当前发布/订阅全程没有互斥量或临界区，跨任务 `PubPushMessage` / `SubGetMessage` 存在数据竞争；注册时也不校验消息长度，长度不一致会静默踩内存。

**具体做法**：

1. 分析所有调用点，确认发布/订阅分别发生在哪些任务和中断里；
2. 给队列读写加保护：任务上下文用 `osMutex`（或 `taskENTER_CRITICAL`），中断上下文提供 `PubPushMessageFromISR` / `SubGetMessageFromISR`；
3. 注册时校验话题长度：发布者与订阅者 `data_len` 不一致直接返回 NULL 并打日志，而不是运行时破坏内存；
4. `QUEUE_SIZE` 从全局宏改为每个订阅者可配置（`SubRegister` 增加参数或提供 `SubRegisterWithQueue`），保留默认值兼容现有代码；
5. 用 B1 主机测试 + B2 板载压力测试（两个任务高频发布/订阅）验证。

**涉及范围**：`modules/message_center/`、所有调用方。

**工作量**：M。

**收益/风险**：收益是消除一类最难排查的偶发 Bug；风险是锁可能引入优先级反转或中断延迟，需要评估发布频率和临界区长度（建议临界区内只做 memcpy）。

**参考**：powerful_framework 的“严格跨任务数据读写保护”思路。

#### C2 任务监控封装 `[板载]`

**要解决的问题**：`robot_task.h` 只手工量了每个任务执行时间，FreeRTOS 的 run-time stats / trace facility 已打开但没有用起来，栈水位、CPU 占比都不可见。

**具体做法**：

1. 新增 `modules/task_monitor/`：登记任务句柄 + 名称 + 预期周期；
2. 周期（默认 1s）调用 `uxTaskGetStackHighWaterMark`、`vTaskGetRunTimeStats`，计算 CPU 占比和最大执行时间；
3. 超过阈值（如栈使用 >80%、执行时间 >周期 50%）时打 ERROR 并触发 daemon 告警；
4. 提供 `TaskMonitorDump()` 供 CLI（D1）和自测（B2）调用；
5. 移除 `robot_task.h` 里重复的手工计时（或改为调用监控模块）。

**涉及范围**：新增 `modules/task_monitor/`、`application/robot_task.h`。

**工作量**：S~M。

**收益/风险**：收益是任务健康状态一目了然，定位卡顿/栈溢出更快；风险小。

**参考**：powerful_framework `Core/sal/TaskManager.hpp`。

#### C3 剩余 P2/P3 修复 `[纯软件/板载/需实车]`

**要解决的问题**：审查报告里还有一批已定位但未修的缺陷。

**具体做法**：按报告逐项修，建议顺序：

| 编号 | 内容 | 硬件依赖 | 备注 |
|---|---|---|---|
| BSPCAN-01 | 过滤器计数 `>=` 且分总线判断 | 板载（CAN 回环） | 防止过滤器个数边界误判 |

# 第二部分：板子已上车后的哨兵技术细节

## 5. 需要补充的技术细节

### 5.1 NUC ↔ MCU 统一通信协议（最优先补充）

#### 现状

- 当前 `modules/master_machine/master_process.h` 只有视觉自瞄协议：`Vision_Recv_s`（控制/开火/yaw/pitch/速度/加速度）和 `Vision_Send_s`（q/yaw/pitch/弹速/弹计数）。
- 没有导航速度、底盘旋转模式、地图路径、兑换/复活、超电开关等哨兵自主决策所需字段。
- 没有消息 ID、序列号、时间戳，视觉侧无法做精确的图像-姿态对齐和延迟补偿。
- 现有发送协议缺时间戳；`sp_vision_25` 上位机实际采用“1kHz 姿态历史 + `imu_at(t - 1ms)` 插值”的方式做图像对齐，我们的协议需要支持这一点。

#### 推荐协议结构

统一帧格式（VCP 或 UART 通用）：

| 字段 | 长度 | 说明 |
|---|---|---|
| SOF | 2B | 固定 `'S','P'`（与现有视觉协议兼容） |
| ID | 1B | 消息类型 |
| LEN | 2B | 负载长度（小端） |
| SEQ | 1B | 递增序列号，用于丢包/乱序检测 |
| TIMESTAMP | 4B | MCU 侧 DWT 毫秒或微秒时间戳 |
| PAYLOAD | N B | 按下表定义 |
| CRC16 | 2B | 覆盖 ID~PAYLOAD |

消息类型建议：

| ID | 方向 | 名称 | 频率 | 关键字段 |
|---|---|---|---|---|
| 0x01 | PC→MCU | AIM_CMD | 100~200Hz | control/fire、yaw/pitch、yaw_vel/acc、pitch_vel/acc、target_id、target_state、shoot_mode、cmd_timestamp |
| 0x02 | MCU→PC | IMU_STATE | 1kHz | timestamp、q(w,x,y,z)、gyro[3]、温度 |
| 0x03 | MCU→PC | ROBOT_STATE | 20~50Hz | 比赛阶段、HP、热量/热量上限、功率/功率上限、缓冲能量、弹量、弹速、RFID、前哨站/基地 HP、被击事件 |
| 0x04 | MCU→PC | ODOM | 500Hz~1kHz | timestamp、vx、vy、wz、四轮编码器、yaw |
| 0x05 | PC→MCU | NAV_VEL | 50~100Hz | vx、vy、yaw_rate、chassis_mode、direction、supercap_enable |
| 0x06 | PC→MCU | SENTRY_CMD | 事件触发 | 确认复活、兑换复活、兑换弹量、远程兑换弹量/血量（bitfield） |
| 0x07 | PC→MCU | MAP_PATH | 事件触发 | intention、起点 x/y（dm）、delta_x/y[27]（dm，压缩路径） |
| 0x08 | 双向 | HEARTBEAT | 10Hz | 状态、超时计数 |
| 0x09 | MCU→PC | DEBUG_TELEMETRY | 可选 | 变量 ID + 值，用于 PlotJuggler 调试 |
| 0x0A | 双向 | CONFIG/CALIB | 可选 | 参数读写、标定命令 |

字段语义建议直接参考西电 2024 哨兵导航的 `NavVelocitySendPackage` / `DesicionRefereeReceivePackage`：

- `chassis_mode`：0=慢速旋转、1=随机旋转、2=快速旋转、3=保持（KEEP）；
- `direction`：0=正常、1=逆时针、2=顺时针；
- `capacitance`：0=超级电容关闭、1=开启；
- `sentry_cmd` bitfield：bit0=确认复活、bit1=兑换复活、bit2~12=兑换弹量、bit13~16=远程兑换弹量、bit17~20=远程兑换血量；
- `MAP_PATH`：起点 + 27 组 delta（单位 dm），把路径压缩到固定长度包；
- MCU→PC 的裁判信息：比赛阶段/剩余时间、双方全机器人 HP、前哨站/基地 HP、基地护甲状态、自身 ID/max HP、17mm 弹量、金币、已购弹量、RFID 状态、遥控器模式、小地图坐标。

#### 时间戳与延迟补偿

这是自瞄/导航能否打准的关键，建议按 `sp_vision_25` 的做法实现：

1. MCU 在 1kHz INS 任务里把 `{q, timestamp}` 推入环形缓冲（至少 1 秒历史）；
2. 每个 `IMU_STATE` 包携带 MCU 时间戳；
3. 上位机收到后按时间戳排序，建立本地时间映射（`steady_clock` offset）；
4. 相机取图后，用图像时间戳减去固定延迟，调用 `imu_at(image_ts - latency)` 做四元数插值；
5. `AIM_CMD` 携带命令生成时间戳，MCU 检查命令年龄；超过阈值（例如 20ms）则降级为“保持/停火”；
6. 延迟预算要单独测量：曝光 + 推理 + 通信 + 控制，建议用慢动作视频/示波器逐项测量，目标总延迟 < 20ms。

#### 协议落地策略

现有 `sp_vision_25` 上位机按固定 `VisionToGimbal` 结构解析，直接改成统一帧会破坏兼容。建议二选一：

- **方案 A（快速上车）**：视觉自瞄继续走现有 SP+CRC16 协议；导航/决策走第二条链路（UART 或 CAN），先保证上车可用。
- **方案 B（推荐长期）**：把 VCP 改成带 ID/SEQ/TIMESTAMP 的统一多路复用协议，同时修改 `sp_vision_25` 的 `io/cboard.cpp`、`io/gimbal.cpp` 解析代码，并把导航、裁判、IMU、自瞄统一到一条链路。

如果时间紧，先 A 后 B；如果本赛季就要做自主哨兵，建议直接上 B，避免两套协议长期维护。

### 5.2 自瞄与火控的嵌入式分工

#### 上位机（NUC）负责

- 装甲板检测、目标状态估计（EKF：x/y/z/vx/vy/vz/yaw/v_yaw/r 九维状态）；
- 目标跟踪状态机（LOST/DETECTING/TRACKING/TEMP_LOST）、装甲板跳变处理；
- 目标优先级、无敌装甲过滤、前哨站（3 装甲板）模式；
- 预测瞄准点、弹道解算（空气阻力迭代补偿）、开火决策；
- 通过 `AIM_CMD` 下发：控制开关、开火标志、yaw/pitch、yaw/pitch 速度与加速度前馈、目标状态、左右/双发选择。

参考：`sp_vision_25`（分布式自瞄、轨迹规划、开火决策）、`rm_auto_aim`（9 维 EKF + 跟踪状态机）、`SolveTrajectory`（空气阻力弹道模型）。

#### MCU 负责

1. **命令校验**：CRC、长度、数值范围、时间戳年龄；过期/越界命令直接丢弃；
2. **控制权仲裁**：手动遥控、视觉自瞄、导航自主三类控制源的优先级和切换条件必须显式化；
3. **云台控制**：绝对角度 + 速度/加速度前馈，多圈角度展开、pitch 限位、重力补偿、轨迹限幅；
4. **开火安全门**：目标状态为 READY、云台误差小于阈值、热量/弹量充足、摩擦轮转速到位、舱盖状态正确、裁判允许开火、弹丸计数反馈确认发射；
5. **弹速闭环**：从摩擦轮转速/裁判限速/标定曲线得到当前弹速，回传给 NUC；弹速变化时 NUC 的弹道解算要同步更新；
6. **延迟处理**：收到命令的时间戳与当前时间比较，命令过旧时停止追踪/停火，避免“追着旧目标打”；
7. **哨兵专有**：左右/双发选择、双云台目标分配（如果实际是双云台）、前哨站模式、被击后转向攻击者。

#### 火控安全条件（建议写成显式状态机）

```
ALLOW_FIRE =
  目标状态 == READY
  && 云台角误差 < FIRE_ANGLE_THRESHOLD
  && 当前热量 + 预计发弹热量 < 热量上限
  && 弹量 > 0
  && 摩擦轮转速在目标转速 ± 容差内
  && 舱盖/拨弹机构状态正常
  && 裁判系统允许开火
  && AIM_CMD 时间戳未过期
  && 未处于复活/兑换/离线和故障状态
```

每次开火后读取 `bullet_count` 反馈确认是否真正出弹；连续 N 次“命令开火但弹量不变”则判定卡弹并报警、停火、等待人工处理。

#### 弹道解算的补充细节

- 小弹丸参数：质量约 3.2g、直径约 16.8mm，25°C 标准大气压下空气阻力系数 `k1≈0.038`；
- 单方向空气阻力模型 + 迭代重力补偿（10~20 次迭代），输出炮台仰角；
- 弹速受摩擦轮转速、电池电压、温度影响，必须在线测量/标定；`AIM_CMD` 的 yaw/pitch 应基于当前弹速计算；
- 对移动目标，NUC 的预测瞄准点应包含弹丸飞行时间 `t_fly`；`sp_vision_25` 采用“射击轨迹 = 14ms 后的目标轨迹”的思路，并计算轨迹的速度/加速度作为前馈；
- 开火决策要考虑开火延迟 `t_fire`（从命令到出膛，摩擦轮掉速），不是简单看当前位置误差。

### 5.3 导航、决策与底盘旋转模式

#### 上位机（NUC）负责

- LIO/点云里程计、重定位（UWB/先验地图）、地形分析、全局/局部规划；
- Nav2 或自研规划器输出 `vx/vy/yaw_rate`；
- 行为树/状态机执行哨兵决策：巡逻、进攻、防守、撤退、补给、复活、前哨站；
- 通过 `NAV_VEL`、`SENTRY_CMD`、`MAP_PATH` 下发意图；
- 通过 `AIM_CMD` 下发云台/开火意图。

参考：`pb2025_sentry_nav`（Nav2 + point_lio + small_gicp + terrain analysis）、`sentry_navigation`（faster_lio + fast_gicp + far_planner + local planner + state_processing）、`pb2025_sentry_behavior`（BehaviorTree.CPP）、`tars_sentry_decision`、`rm_decision`。

#### MCU 负责

1. **速度执行**：把 NUC 的 `vx/vy/yaw_rate` 转成底盘运动学解算（全向轮/麦轮）；
2. **旋转模式**：慢速旋转、随机旋转、快速旋转、保持（KEEP）；平滑加减速、陀螺仪反馈、电流限制、模式切换去抖；
3. **云台跟随**：底盘跟随云台或独立控制；小陀螺时速度参考坐标系要正确；
4. **里程计输出**：四轮编码器 + IMU 融合，带时间戳回传 NUC，作为 LIO 的补充/降级输入；
5. **失联降级**：NUC 心跳超时 → 停止底盘、云台保持/回中、关闭摩擦轮/停火；
6. **安全状态机**：INIT → SAFE → MANUAL → AUTO_NAV → AUTO_AIM → EMERGENCY，状态切换必须有时延/滞回/原因日志。

#### 关键细节：坐标系与 `fake_vel_transform`

`pb2025_sentry_nav` 专门做了一个 `fake_vel_transform` 包，用来处理“云台扫描/小陀螺时导航速度参考系”的问题。对应到 MCU：

- NUC 规划出的速度通常是底盘/世界坐标系下的；
- 如果底盘在旋转、云台在扫描，速度指令需要按当前 yaw 偏差做旋转变换，否则会出现“边走边画圈”或控制器振荡；
- 建议明确三个坐标系：`world/map` → `chassis` → `gimbal`，每个速度指令包携带参考坐标系/时间戳；
- 旋转模式下，`yaw_rate` 与平移速度要解耦：平移由 NUC 控制，自转由 `chassis_mode` 控制；
- 补给、兑换、前哨站攻击时建议强制 KEEP 模式，避免姿态漂移影响操作。

#### 被击方向反应（哨兵很实用）

裁判系统 `0x0206 RobotHurt` 提供 `armor_id` 和 `hurt_type`。按 `pb2025_sentry_behavior` 的 `IsAttacked` 逻辑：

1. 检测到 `is_hp_deduced && hp_deduction_reason == ARMOR_HIT`；
2. 根据 `armor_id` 映射出被击装甲板相对车体的角度；
3. 输出云台 yaw/pitch（pitch 固定 0）或底盘旋转指令，让机器人转向攻击者；
4. 持续 N 秒后回到原决策状态；
5. 如果 NUC 离线，MCU 可以独立完成这个“最小反应”，作为降级策略。

#### RFID 与比赛阶段

- `0x0209 RfidStatus`：补给区、兑换站、基地等位置感知，供决策层使用；
- `0x0001 GameState`：比赛阶段/剩余时间；比赛未开始/已结束/机器人死亡时强制安全状态；
- `0x0003 GameRobotHP`、`0x0201 GameRobotState`、`0x020D SentryInfo`：双方 HP、前哨站/基地状态、哨兵状态；
- 这些数据建议以 `ROBOT_STATE` 包周期回传 NUC，NUC 决策层不直接解析裁判串口。

### 5.4 功率、热量与超级电容管理

#### 现状

- `modules/power/power_manager.h` 已有 `k1/k2/k3`、RLS 使能接口，但仍是骨架；
- 裁判系统已解析 `PowerHeatData`（底盘功率、缓冲能量、17mm 热量、热量上限等）和 `GameRobotState`（底盘功率上限、枪口热量上限、电源管理输出位）；
- 哨兵的热量/功率和弹量是最容易翻车的点，必须优先补齐。

#### 可借鉴的实现

- 西电 `librm` 的 `motor_power_model.hpp`：电机功率模型、电流-功率换算；
- `LIUYIXIEYANG/SuperCapcitor-Power-Controller`：双向 Buck-Boost 超级电容控制器，支持恒流/恒压/恒功率充电、与电源并联输出、最大化利用电源功率；
- `yssickjgd/robowalker_2025_power_sampler`：1kHz 功率采样板，USART 1Mbps/9e1 或 CAN 0x114 输出电流/电压/功率浮点帧，支持把标定参数写入 flash；协议中电流/电压/功率 + 校验和的格式可直接参考。

#### 建议实现

1. **功率模型**：`P = k1*I + k2*I²`（热量）+ `k3` 等模型项；用裁判系统实际功率与下发电流做 RLS 在线辨识；
2. **功率分配**：按优先级分配到底盘、摩擦轮、云台；先保证云台/发射，再限制底盘；限制要平滑（斜坡），不要突然掉电流；
3. **超级电容**：CAN/UART 读取电容电压/电流/状态；支持开启/关闭、充电/放电、故障降级；NUC 的 `capacitance` 位控制开关；
4. **热量管理**：读取 `shooter_17mm_barrel_heat`、`shooter_barrel_heat_limit`、冷却速率；估算每发热量，开火前做“热量预算”；接近上限时降低射频或停火；
5. **弹量管理**：读取剩余弹量/已购弹量；低弹量提醒 NUC 决策层去补给/兑换；
6. **电压/电流保护**：低压降功率、过流停电机、超电故障时切回直供；所有保护都要有日志和状态位；
7. **验证**：裁判模拟器投喂满热量/低热量/功率跳变/超电离线等场景；实车用电流钳/功率采样板记录，核对模型误差。

### 5.5 传感器标定与参数持久化

#### IMU

- 1kHz 姿态历史缓冲 + 时间戳（见 5.1）；
- 陀螺仪零偏温漂补偿：当前加热目标 45°C、实测约 42°C，可在温控稳定后再做零偏标定；
- 振动滤波：底盘高速/摩擦轮转动时给加速度计/陀螺仪加低通或陷波，避免 EKF 被振动污染；
- 安装矩阵/零位：IMU 与云台、底盘的安装角必须标定并可持久化；
- 上电静止检测：只有静止时才重新标定零偏，运动中拒绝标定。

#### 电机

- CAN ID 扫描、离线检测、方向、零位、减速比、电流零点；
- 单电机台架流程：小电流开环确认方向 → 编码器零位 → 速度环阶跃 → 位置环阶跃；
- 标定结果写 flash，启动时自动加载；电机更换后一键重新标定；
- 参考 `librm` 的 `motor_calibrator.hpp`、StandardRobot++ 的 `application/calibrate`。

#### 云台

- yaw 多圈零位、pitch 机械上下限、IMU-云台安装角、重力矩补偿系数；
- 限位要软硬双重保护：软件限位 + 机械/电流保护；
- 小陀螺/大陀螺时云台控制的坐标系和跟随策略要单独测试。

#### 弹速

- 摩擦轮转速 → 弹速曲线，至少标定 3~5 个转速点；
- 电池电压、温度、摩擦轮磨损都会影响弹速，建议在线估算 + 定期复核；
- 标定结果供 NUC 弹道解算和 MCU 开火安全门共用。

#### flash 参数区

- 先修 `BSPMISC-05`（扇区边界、擦除/编程返回值、静默截断）；
- 布局：magic + version + CRC + 数据 + 备份区；掉电/写坏时可回退默认值；
- 写入时机：只在机器人静止、非控制周期、电池电压正常时写；禁止在 ISR 中写；
- 提供 `ParamLoad/Save/Reset` 和 CLI 命令；参数结构体预留版本迁移字段。

### 5.6 可靠性与故障注入

#### 故障矩阵

| 故障 | 期望行为 | 恢复条件 |
|---|---|---|
| NUC 心跳超时 | 底盘停、云台保持/回中、停火 | 心跳恢复 + 重新使能命令 |
| CAN bus-off | 停用受影响电机、报警、尝试自动恢复 | CAN 恢复正常帧计数 |
| 电机离线/过流/过温 | 单电机失能、整车降级、报警 | 电机重新上线且错误清除 |
| IMU 超时/NaN | 切安全状态、停底盘、云台保持 | IMU 数据连续正常 N 秒 |
| 裁判系统离线 | 保留最后已知限制并降功率/停火 | 裁判帧连续恢复 |
| VCP 断连 | 停自主控制、切手动/安全 | USB 重新枚举 + 握手成功 |
| 电池低压 | 逐步降功率、禁止高功率动作 | 电压恢复 |
| flash 写失败/CRC 错 | 使用备份/默认参数、报警 | 重新标定/写入成功 |
| 云台卡死 | 关闭对应电机、报警、禁止继续发力 | 人工检查 |
| 车体倾倒（roll/pitch 超限） | 停底盘、停摩擦轮、保持云台安全 | 姿态恢复 + 人工确认 |

#### 建议实现

1. **看门狗分层**：IWDG（硬件）+ 任务监控（软件）+ daemon 离线监测；记录复位原因；
2. **失能默认态**：上电后所有电机默认失能，直到 IMU 有效、标定加载成功、遥控/NUC 明确使能；
3. **急停**：遥控器组合键/物理开关立即失能底盘和发射；NUC 也应有软件急停命令；
4. **黑匣子**：环形缓冲记录最近 N 秒的命令、姿态、功率、热量、故障事件；可经 VCP 导出或写 flash；
5. **故障注入脚本**：拔 CAN、拔 USB、kill NUC 进程、模拟裁判离线、注入 NaN/超范围命令，记录从故障到安全状态的时间（目标 <100ms）；
6. **日志规范**：错误码 + 模块 + 时间戳；重要状态变化（模式切换、使能、开火、保护触发）必须落日志。

## 10. 需要你决策的点

1. **协议路线**：视觉自瞄继续独立协议（方案 A，快速上车），还是直接统一到 VCP 多路复用协议（方案 B，长期更干净）？
2. **自瞄分工**：弹道解算放在 NUC（算力充足、易调参）还是 MCU（延迟低、但资源紧）？建议 NUC 算 + MCU 限幅/安全检查。
3. **决策层位置**：行为树/状态机放 NUC（推荐，迭代快）还是 MCU（抗断连，但资源紧）？建议 NUC 决策 + MCU 最小安全兜底（被击转向、失联停车）。
4. **导航方案**：是否已经确定用 NUC + ROS2/Nav2？如果 NUC 可能离线，MCU 是否需要一套简单的“巡逻路径回放”兜底？
5. **哨兵构型**：实际是单云台还是双云台？左右发射是两套拨弹盘还是单拨弹盘分弹？这决定 `shoot_mode` 和火控安全门的设计。
6. **超级电容**：实车是否已装超电板？型号/通信协议是什么？没有的话功率策略要先按无超电设计。
7. **裁判链路**：当前用 CH340 模拟，实车裁判串口是否已确定（USART1/PA10）？RFID/被击数据是否可用？
8. **视觉链路**：正式用 VCP（COM10）还是 USB2CAN？`sp_vision_25` 的 C 板通信是否直接复用，还是需要适配 MC-02 的 VCP？
9. **优先级**：本赛季目标是“先能安全跑起来打”还是“完整自主哨兵”？这决定 Phase 3 和 Phase 4 的投入比例。
