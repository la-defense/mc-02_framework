# 19 崩溃记录的可信度：magic、长度、版本、构建指纹与校验和（写给零基础）

> 本篇回答的问题：
> 1. 为什么"记录里放一个 magic 数字"这种常见做法**不够**？我们实测踩到了什么？
> 2. 长度、版本、构建指纹、校验和，各自挡住哪一类"假记录"？
> 3. 校验和用 CRC32 和用"简单异或/累加"到底差在哪？为什么这里选 CRC32？
> 4. 为什么这段代码在异常处理函数（handler）里必须写成**宏**，不能调用函数？
> 5. `.noinit` 的地址为什么会"漂移"？漂移之后会发生什么？
> 6. 为什么"复位前最后写的一条数据"可能丢？这是本次最意外的实测发现。
>
> 对应代码：`bsp/crash/bsp_crash.c/.h`、`modules/lcd/lcd_ui.c`（系统页显示）。
> 前情提要：崩溃现场怎么记录/怎么读，见《13-崩溃现场与异常处理入门》。

---

## 0. 一句话结论

**"这份记录是我们写的、而且是完整的"这件事，必须用"结构 + 内容"共同证明**，
而不是靠一个 4 字节的魔法数字：

```
magic(=OK)  +  len(=当前结构体大小)  +  version(=记录格式版本)
            +  fw_id(=本固件构建指纹)  +  crc32(对 payload 的校验和)
```

五个条件全中才算数；任何一条不符，启动时**一个字都不打印**。

---

## 1. 只靠 magic 为什么不够（实测反例）

最早的实现（`LOG-03`）是这样：记录开头放一个 `uint32_t magic = "CRAS"`，
写完最后写 magic，读到 magic 就认为"这份记录有效"。

这在"同一份固件、反复复位"的场景里够用，但它有一个致命前提：
**那块内存里除了我们，不会有别的数据**。而现实是：

| 场景 | 会发生什么 |
|---|---|
| 改了代码 → 记录结构变大/变小 → `.noinit` 的**地址变了** | 新地址上是上一版固件留下的**别的数据**；只要其中某 4 个字节恰好是 `"CRAS"`，就会被当成"上次崩溃现场"打印 |
| RAM 被其它模块/堆复用 | 同理 |

**实测现场**（2026-09-26，LOG-05 的起因）：

```
E:==== 上次运行崩溃现场(累计第 2261714040 次) ====
E:[crash] type=STACKOVF pc=0x0801705D lr=0x00000000 sp=0x24003AD0
E:[crash] 任务 '' 栈溢出
```

`累计第 2261714040 次`（0x86CF0478，纯垃圾数字）、任务名空白 —— 这份"现场"是假的。
它比"没有日志"更糟：会把人往错误方向带。

## 2. 四重判据：每个字段各管一类误判

| 字段 | 值 | 挡住什么 |
|---|---|---|
| `magic` | `"CROK"`（写完整）/ `"BUSY"`（正在写） | 挡住"从来没写过记录"（RAM 里全是 0 或随机值） |
| `len` | `sizeof(CrashLog_t)` | 挡住**换过记录结构**的旧记录（结构一改，大小几乎必然变） |
| `version` | 记录格式版本号，改布局就 +1 | 挡住"大小凑巧没变、但字段含义变了"的旧记录 |
| `fw_id` | 本固件的**构建指纹** | 挡住**别的固件**写的记录（PC 在新 ELF 上根本反查不出来，显示它只会误导） |
| `crc32` | 对 payload 的 CRC32-IEEE | 挡住**残留/写坏的字节**（随机数据命中 CRC32 的概率约 1/2³²） |

实现上沿用参数存储 `bsp/param` 的约定：**头部（magic/len/version/fw_id/crc32）+ payload**，
CRC 只算 payload。这样"发布"动作很清晰：**先算 CRC → 写 crc32 → 最后写 magic=OK**。

### 2.1 BUSY 标记：一条有价值的"负面线索"

记录**开始**时先写 `magic = "BUSY"`，全部写完才写 `"CROK"`。于是：

| 启动时看到 | 说明 | 处理 |
|---|---|---|
| `CROK` + 四重判据通过 | 完整记录 | 打印完整现场 |
| `BUSY` + `progress < 4` | **记到一半又崩了**（例如写到栈快照那步再次触发异常） | 只打**一行**提示：`上次崩溃记录写到一半就中断了(第 N 步)` |
| `BUSY` + `progress = 4` + 校验和正确 | 记录其实写全了，只是"发布那条 magic 写"丢了（见第 6 节） | **照常打印完整现场**（兜底判据） |
| 其它（找不到 magic / CRC 不符 / 旧固件 / 旧版本） | 残留数据或无记录 | **一个字都不打印** |

### 2.2 任务名为什么"内联"而不是"存指针"

栈溢出时 FreeRTOS 给的是"任务名字符串的地址"。这个地址指向 **TCB 里的 `char` 数组（RAM）**——
下次启动时那块内存可能已经被复用或重排，指针指向的内容早就不是任务名了（实测：打印出来是空的 `任务 ''`）。
所以记录时**把名字拷进记录本身**（`char task_name[16]`），拷贝时把不可打印字符换成 `.`，
这样无论后面是打印还是上 LCD，都不会吐出乱码。

## 3. 校验和：CRC32 与"简单异或/累加"的差别

对"RAM 里的残留垃圾"这个具体场景，两者的**误判概率都是约 1/2³²**——
因为垃圾数据是"随机"的，任何 32 位校验都一样。那为什么还是选 CRC32？

1. **本工程已经有两处用 CRC32**（参数存储 `bsp/param`、协议帧），统一一种"信任检查"少一份心智负担；
2. CRC 对**系统性位错**（连续多位翻转、整段位移、常见的通信错误模式）的检出能力
   明显强于异或/累加 —— 将来若把这套记录改成"写进 Flash 跨掉电保存"（待办 LOG-06），
   面对的就是存储介质的位错，CRC 才真正发挥长处；
3. 代价可忽略：本记录 payload 只有 52 个字，逐位算一遍约几万条指令（480MHz 下几十微秒），
   而且**只在崩溃那一刻算一次**。

### 3.1 为什么写成"宏"而不是函数

异常处理函数里有一条硬约束（见《13》）：**只做"读寄存器 → 写内存 → 复位"，
不调用函数、不碰外设**。原因是崩溃可能由总线/内存错误引起，此时任何函数调用都可能二次异常，
CPU 直接进 Lockup，连现场都保不住。

可是"校验和"这段逻辑在**写记录**（异常上下文）和**读记录**（正常上下文）两边都要用。
写成函数 → 违反约束；两边各写一份 → 容易改一处忘一处。**最终用宏解决**：

```c
#define CRASH_CRC32_WORDS(acc, p, n)  /* 展开成一段纯寄存器运算的循环, 不产生函数调用 */
#define CRASH_FW_ID_COMPUTE(out)      /* 同上: FNV-1a 逐字节算构建指纹 */
```

在 `-Og` 下验证过：`CrashLogRecord` 的反汇编里只有 `NVIC_SystemReset` 一个 `bl`，
CRC 的常数 `0xEDB88320` 就出现在函数体内（说明循环真的被展开在函数里）。

## 4. 构建指纹：`__DATE__` / `__TIME__` 能干什么、不能干什么

```c
static const char kCrashBuildStamp[] = __DATE__ " " __TIME__;   /* 例: "Sep 26 2026 21:33:07" */
#define CRASH_FW_ID_COMPUTE(out)   /* 对上面这串字符做 FNV-1a, 得到 4 字节指纹 */
```

**能干什么**：换一个固件（哪怕只改一行）指纹几乎一定变 → 上一个固件留下的记录不会被误认成本次的现场。
实测：烧完 CRASH_TEST 自测固件再烧正常固件，启动时**一条崩溃日志都没有**（旧记录的指纹不符）✓。

**不能干什么（要知道边界）**：

- 指纹只反映**本文件**的编译时间。如果只重编了别的文件（本文件没参与重编），指纹不变；
  这时靠 CRC 和 len/version 兜着（真正的"防篡改"要靠产物级的构建 ID，属于协议/发版话题）；
- 它与"可复现构建（reproducible build）"是矛盾的：`__DATE__/__TIME__` 让每次编译产物都不同。
  本工程目前不追求"逐字节可复现"，诊断收益大于这个代价。

**取舍（有意为之）**：换固件后**不显示**旧固件的崩溃现场。
因为旧记录里的 PC 在新 ELF 上反查不出来，显示它只会把人带偏 —— 宁可静默。

## 5. `.noinit` 的地址为什么会"漂移"

`.noinit` 段被放在 `.bss` 之后（链接脚本里 `>RAM`，不参与启动清零）：

```
0x24000de0  _sbss ──────────────────────── RAM 里的 .bss（所有全局/静态变量）
                  ... 变量增删、任务栈大小、日志缓冲大小 都会改变它的大小
0x2400fe98  _ebss = .noinit 起点 ───────── g_crash_log（跨复位保留）
```

任何一次"加个全局变量、改个数组大小"都会让 `_ebss` 变化 → `g_crash_log` **换个地址**。
于是新地址上躺着的是上一版固件在别处的数据 —— 这正是第 1 节那个假现场的来源。

有了 len/version/fw_id/crc32，地址漂移**不再是问题**：漂移后的内容不可能同时满足四个条件。

## 6. 本次最意外的发现：复位前"最后一条写"会丢

### 6.1 现象

改造完成后自测，记录**始终停在** `magic=BUSY、progress=4`，启动横幅一直在报
"上次崩溃记录写到一半就中断了"——但**其它字段（count、crc32、任务名、寄存器、栈快照）全都是写好的**。

### 6.2 排查（把每一步都变成证据）

| 步骤 | 结果 | 排除了什么 |
|---|---|---|
| 手工把 `magic` 改成 `CROK` 再复位 | 启动时**完整打印**了这份记录 | 读取与校验逻辑没问题 |
| 反汇编 `CrashLogRecord` | `... str crc32 → ldr OK → str magic → bl __NVIC_SystemReset`，顺序正确 | 代码顺序/编译器重排 |
| 硬件断点打在 `str magic` 上，看寄存器 | `r2 = 0x4B4F5243`、`r3 = &g_crash_log`，**值完全正确** | "存错了值/存错地址" |
| 单步跨过 `str` 后读内存 | `magic` 读出来就是 `CROK` | "存储没执行" |
| 读 `CCR`/`MPU_CTRL` | D-cache/I-cache 关闭、MPU 未启用 | 缓存/属性问题 |
| 反汇编 `__NVIC_SystemReset` | 复位前确实有 `dsb sy` | "缺屏障" |
| 在 `str magic` 之后插入一段有界空转 | **记录全部完整了** | ✅ 根因确认 |

### 6.3 结论

**系统复位会丢掉"还在总线上、尚未落到 SRAM"的写。**
`__DSB()` 只保证 CPU 自己的写缓冲排空，并不保证这笔写已经到达（并完成于）SRAM 控制器；
而复位请求恰好紧随其后时，最后一笔写就丢了 —— 表现就是"单步调试看得见、下次启动读不到"。

（这也是"日志/记录类代码"常犯的错：**写完就复位**。要留出让写落地的时间。）

### 6.4 修法（两层）

1. **写入侧**：发布 `magic=OK` 之后，`__DSB()` + 一小段有界空转（`CRASH_RESET_DRAIN_LOOPS`，
   约 0.1~0.2ms），等这笔写真正落地再 `NVIC_SystemReset()`；反正马上就要复位，代价为零。
2. **读取侧兜底**：把 "`BUSY` + `progress=4` + **校验和正确**" 也认作完整记录
   （见 2.1 表格第 3 行）。这样即使将来某块板子/某个优化等级下这笔写又丢了，
   记录依然可用 —— 校验和才是"内容完整"的真正证明，magic 只是"发布告知"。

## 7. 怎么验证（本项目实际跑过的流程）

### 7.1 崩溃自测（`-DCRASH_TEST=1` 单独构建）

自测按 `.noinit` 里的游标轮换三个阶段，每崩一次就主动复位、下一轮换下一个：

| 阶段 | 触发方式 | 实测结果 |
|---|---|---|
| 1 | 写 0xC0000000（无外设区） | `type=HARDFAULT`、`CFSR=0x00000400`(BFSR.PRECISERR)、`HFSR=0x40000000`(FORCED)、`R2=DEADBEEF R3=C0000000` —— 寄存器就是那条出错指令的操作数 |
| 2 | `configASSERT(0)` | `type=ASSERT` + `assert: D:/.../bsp_crash.c:458`（文件名:行号，指针经过"可打印字符串"检查） |
| 3 | 栈溢出钩子 | `type=STACKOVF` + `任务 'selftest' 栈溢出`（**内联的任务名**） |

### 7.2 反例注入（用 OpenOCD `mww` 改内存，再复位）

| 注入 | 期望 | 实测 |
|---|---|---|
| `magic=OK` 但破坏 payload（CRC 对不上） | 静默 | ✅ 零条崩溃日志 |
| `magic=BUSY` + `progress=3` | 只报一行"写到一半" | ✅ 一行，无现场 |
| 记录完整但 `fw_id` 改成别的固件 | 静默 | ✅ 零条 |
| `magic=BUSY` + `progress=4` + 校验和有效 | 完整打印（兜底） | ✅ 完整现场 |

命令形态（示例）：

```powershell
openocd -f interface/cmsis-dap.cfg -f target/stm32h7x.cfg `
  -c init -c halt -c "mww 0x2400fe9c 0x59535542" -c "reset" -c shutdown
python tools/rtt_dump.py --elf build-test\Basic_Framework_MC02.elf --seconds 2 --all
```

> 注意：注入后要**在 3 秒内**读日志（自测固件 3 秒后会再次崩并覆盖记录）。
> 正常固件不会崩，随时可读。

## 8. 速查表

| 症状 | 可能原因 | 怎么办 |
|---|---|---|
| 启动打印"累计第 2261714040 次"这种离谱数字 | 旧实现（只有 magic）把残留数据当记录 | 现在已被 len/version/fw_id/CRC 挡住；若还出现，说明某个字段没参与校验 |
| 启动一行"写到一半就中断了(第 N 步)" | 记录过程中又崩了（真的） | 看 N：1/2/3/4 分别对应头部/寄存器/栈帧/栈快照阶段 |
| 启动什么都不打印，但明明崩过 | 记录被判无效（CRC/len/version/指纹不符），或"最后一条写丢了" | 用 OpenOCD 读 `g_crash_log` 头部四字：`magic/len/version/fw_id`，再读 `crc32` |
| 任务名是空的 | 旧实现存的是 TCB 指针 | 现在内联拷贝，不会再空 |
| 换了固件后看不到上次崩溃 | **有意为之**：构建指纹不符 | 想看旧记录就用旧 ELF 反查，或用 OpenOCD 直接把 `fw_id` 改成当前值再复位 |
| 记录"看起来写全了"但 magic 还是 BUSY | 复位前最后一条写丢了 | 已有 `CRASH_RESET_DRAIN_LOOPS` 空转 + 读取侧兜底；若仍复现，先加大空转次数 |
