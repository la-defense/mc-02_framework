# 06 如何定位"只在特定条件下才出现"的故障（写给零基础）

## 0. 一句话总结

**不要猜，要测量。** 把"不确定的现象"变成"可观测的数字"，用最小的差异去逼近真相：
先固定其它变量 → 读寄存器/加探针看它到底停在哪 → 用二分法缩小到一个文件 → 找到"为什么这个文件在优化后语义变了" → 修掉 → 回归验证。
本文用本工程真实案例（同一份代码 `-Og` 能跑、`-O2` 起不来）把这套流程讲透。

---

## 1. 案例背景

本工程原来整机用 `-Og`（Debug）编译。为了省 CPU，加了 `-O2` 性能构建（见《01 编译优化入门》）。
结果：**`-Og` 固件正常启动运行；`-O2` 固件烧进去以后"死机"** —— 屏幕不亮、`lcd_heartbeat` 恒为 0、没有 HardFault。

这种"改一个编译参数就坏"的问题最容易被误判成"编译器有 bug"，其实绝大多数时候是**你代码里有依赖"碰巧"的地方**，
优化把它暴露出来了。下面的流程就是用来把这种"碰巧"抓出来的。

---

## 2. 思想一：先把变量固定成一个

排查任何故障的第一步不是看代码，而是**确认你能稳定复现，并且只有一个变量在变**：

| 固定住的 | 本次的做法 |
|---|---|
| 硬件 | 同一块板、同一根线、同一路供电（USB，不带 24V） |
| 工况 | 无电机、LCD 常开、同一份外设配置 |
| 软件差异 | **只有**编译优化等级不同（`-Og` vs `-O2`），源码完全一样 |

**为什么重要**：如果同时改了优化和别的代码，最后你分不清是谁的锅。工程上叫"最小可复现样本"。
如果没法固定（比如偶发故障），就要想办法**提高复现概率**（多跑、加压力、缩短周期），而不是凭印象下结论。

---

## 3. 思想二：先看"它停在哪"，不要先想"为什么"

### 3.1 静态定位：读 PC / LR

CPU 卡住时，最快的信息来源是寄存器：

- **PC（Program Counter）**：现在正在执行哪条指令；
- **LR（Link Register）**：是谁调用的（返回地址）。

本工程用 OpenOCD 读（halt → 读 → resume，不干扰运行）：

```powershell
openocd -f interface/cmsis-dap.cfg -f target/stm32h7x.cfg `
        -c "init" -c "halt" -c "reg pc" -c "reg lr" -c "resume" -c "exit"
```

拿到地址后，用 `addr2line` 换成"文件:行号"：

```powershell
arm-none-eabi-addr2line -f -C -e build-perf\Basic_Framework_MC02.elf 0x08014aeb
# 输出: BMI088CalibrateIMU  .../modules/BMI088/bmi088.c:344
```

**技巧**：采 **3~5 次**，看"哪一次最多"。本次 5 次里 4 次落在 `BMI088CalibrateIMU`（IMU 静止标定循环）里 → 立刻把范围从"整个固件"缩到"一个函数"。

### 3.2 拿一个"温度计"：为什么还要读寄存器

PC 只能告诉你"停在哪"，不能告诉你"为什么出不来"。这时要读**反映硬件真实状态**的寄存器，例如：

| 想知道 | 读什么 |
|---|---|
| 系统是不是在复位循环 | `RCC_RSR`（复位原因标志）、启动日志里打印的复位原因 |
| 看门狗配置对不对 | `IWDG->PR` / `IWDG->RLR`（分频 + 重装载值 → 实际超时） |
| 时钟/计数器活着吗 | `DWT->CYCCNT`（读两次看是否在走） |
| CAN 为什么收不到 | `CCCR.INIT` / `IE` / `ILE` / `PSI` / 错误计数 `ECR` |
| 故障类型 | `CFSR / HFSR / MMFAR / BFAR` |

本次就是靠读 `DWT->CTRL/CYCCNT` 确认"计数器是活的"，从而排除了"计时器坏了导致死等"这一大类假设。

## 4. 思想三：动态定位——给关键代码"打阶段标记"

### 4.1 什么是阶段标记

在长流程的关键节点写一个全局变量（`volatile`），出问题时直接读它就能知道"走到第几步"：

```c
volatile uint8_t lcd_init_stage = 0;   /* 0=未开始 1=Reset/Init 2=清屏 3=填充 4=画静态 5=刷数值 6=完成 */

void LCD_UI_Init(void) {
    lcd_init_stage = 1;  LCD_Init();
    lcd_init_stage = 2;  LCD_BufClearPanel();
    lcd_init_stage = 3;  LCD_BufFill(...);
    lcd_init_stage = 4;  LCD_UI_DrawStatic(0);
    lcd_init_stage = 5;  LCD_UI_UpdateValues(0);
    lcd_init_stage = 6;
}
```

本次用它一读就得到结论：`lcd_init_stage = 0` → **LCD 任务根本没进初始化**，于是问题从"屏幕不亮"变成"LCD 任务没被调度/没被创建"。

### 4.2 再加"计数器 + 耗时"，区分"慢"和"卡"

光有阶段还不够，要在循环里补三类量：

```c
volatile uint32_t cali_diag_outer;      /* 外层重试了多少次 */
volatile uint32_t cali_diag_inner;      /* 内层跑到第几轮 */
volatile uint32_t cali_diag_acq_us_max; /* 单次采集最坏耗时 */
volatile uint32_t cali_diag_delay_us_max;/* 单次延时的实际耗时 */
volatile float    cali_diag_acc_norm;   /* 采集到的物理量是否合理 */
```

本次这组量一次性回答了两个关键问题：

1. **数据是对的**：`|acc| = 9.687`（重力）、`gyro = 0.004 rad/s`（静止）→ 不是传感器/SPI 读错；
2. **单轮耗时正常**：`BMI088Acquire` 54µs、`DWT_Delay(0.5ms)` 实测 500µs → 标定循环本身没被"拖慢"。

**如果没有这两个读数，最容易被带偏的猜测是"SPI 变慢了"或"延时函数坏了"。**

## 5. 思想四：分清"卡死 / 反复复位 / 只是慢"

这三者现象很像（都是"没反应"），但方向完全不同：

| 现象 | 判据 |
|---|---|
| **卡死** | 两次读数（间隔若干秒）**完全一样**，且 CPU 的 PC 一直在同一小块代码 |
| **反复复位** | 两次读数的"启动阶段计数器"**变小**（`.bss` 变量每次启动会被清零，所以计数回退 = 复位） |
| **只是慢** | 计数器**单调变大**，只是比你预期慢 |

本次的判定方法（简单但非常有效）：

```
T0 : outer=01 inner=0f7 finish=00
T20: outer=01 inner=08c finish=00      ← inner 变小了！
T40: outer=01 inner=0fe finish=00
T60: outer=01 inner=067 finish=00
```

`inner` 在 247 → 140 → 254 → 103 之间来回跳 → **不是卡死，是在反复复位**。
（注意：这里的变量必须在 `.bss`/未初始化区，启动代码每次都会清零，所以"变小"能可靠地指示复位。）

## 6. 思想五：看门狗会把排查带偏（本次最大的坑）

### 6.1 现象

启动日志里反复出现：

```
I:[adc] VCC_IN sense started
E:[watchdog] reset reason: IWDG1
E:[watchdog] reset reason: NRST pin
I:[safety] state INIT -> SAFE
I:USB init success
```

也就是说：**每次启动都在跑到某个位置时被复位**，而"复位原因"指向看门狗。

### 6.2 为什么会变成"永远起不来"

- IWDG（独立看门狗）**上电后一旦启动，只有掉电才会停止**，普通复位不会把它清掉；
- 本工程的启动流程里有一步很耗时：**BMI088 在线标定**（6000 次采样，约 3.3s；标定环境不理想时会重试，最长约 12s）；
- 而运行期看门狗被设成 **200ms**（在 `RobotInit()` 末尾设置）；

于是出现"死亡螺旋"：某次运行触发了看门狗复位 → 复位后 IWDG 仍以 200ms 计时 → 而重新启动要 3~15s → **每次启动都被打断** → 永远起不来。

### 6.3 正确做法（本次已实现）

1. **启动阶段给足够窗口**：`BSPInit()` 一开始就用一个较长的超时（本项目 4000ms）启用/重配看门狗；
2. **在长耗时步骤里主动喂狗**：标定循环每 512 轮喂一次（约 285ms 一次）——这不是"作弊"，因为循环确实在前进；
3. **复位原因要记录**（并建议清除标志）：启动时打印 `RCC_RSR` 的复位来源；
4. 运行期再切回 200ms，由任务监控统一喂狗。

> 一句话：**看门狗是最后防线，不是调试工具**。它会把"偶发一次异常"放大成"再也起不来"，
> 所以启动路径必须能在看门狗超时内完成，或者主动报告进度。

## 7. 思想六：优化等级会暴露"未定义行为"和"竞态"

`-O2` 与 `-Og` 的差别不只是"快慢"，而是**编译器会做更多重排、内联、缓存**。以下写法在 `-Og` 下常常"碰巧能跑"，在 `-O2` 下就翻车：

| 隐患 | 为什么会崩 | 正确写法 |
|---|---|---|
| ISR 与任务共享的变量没有 `volatile` | 任务里的轮询循环被优化成"只读一次"，永远等不到变化 | 加 `volatile`（本工程 SPI 忙标志就是这样，已修） |
| 位域结构体被 ISR 与任务同时读写 | 位域常被编译成"读-改-写"，且可能被缓存 | 用 `volatile`，或改用普通变量 + 宏 |
| 依赖未定义求值顺序 / 类型双关 | 不同优化等级结果不同 | 拆成多条语句、用 `memcpy` 做类型转换 |
| 未初始化变量 | `-Og` 常常"恰好是 0" | 显式初始化 |
| 依赖"延时足够长"掩盖竞态 | 优化后代码更快，竞态窗口暴露 | 用标志/中断/信号量同步，而不是估算时间 |
| 栈使用量变化 | `-O2` 可能内联出更大的栈帧 → 栈溢出 | 看 `configCHECK_FOR_STACK_OVERFLOW` / 栈高水位 |

**排查套路**：用二分法把模块逐个换回 `-Og`，看问题在哪个模块消失：

```cmake
# 临时诊断: 只让可疑文件用 -Og, 其余保持 -O2
set_source_files_properties(${CMAKE_SOURCE_DIR}/modules/BMI088/bmi088.c
                            PROPERTIES COMPILE_OPTIONS "-Og")
```

本次用这个方法排除了 `bmi088.c`、`bsp_spi.c`、`ins_task.c`、`bsp_dwt.c`（换回 `-Og` 仍然卡），
说明问题不在这些文件自身的优化，而更可能在**启动/看门狗/调度**这条链路上。

## 8. 可复用的操作清单（照着做）

1. **固定变量**：确认"只有一个差异"（本次：只有优化等级），并确认能稳定复现；
2. **读 PC/LR**：采样 3~5 次 → `addr2line` → 缩到一个函数/循环；
3. **读寄存器**：复位原因、看门狗配置、DWT 计数器、故障寄存器；
4. **打阶段标记 + 计数器**：在长流程里写 `volatile` 阶段号、迭代数、最坏耗时、物理量；
5. **两次读数判趋势**：一样=卡死；变小=复位；变大=在跑只是慢；
6. **二分法缩小范围**：逐模块换回 `-Og`（或用编译开关隔离）；
7. **找语义变化的根因**：`volatile` 缺失 / 竞态 / 未定义行为 / 时序假设 / 栈；
8. **修复并回归**：修完必须重新跑一遍同工况实测，并把探针留在代码里；
9. **写下来**：把现象、判据、结论写进文档（就是现在这篇）。

---

## 9. 这些做法体现了什么"嵌入式开发思想"

1. **测量优先于假设**：把"我觉得"换成"我测到"。PC、寄存器、计数器都是客观证据；
2. **可观测性是一等公民**：探针、阶段标记、限速日志、占用率统计不是"调试残留"，而是长期资产；
3. **最小化差异**：一次只改一个变量（编译参数、单个模块），才能把因果关系钉死；
4. **防御式设计**：看门狗、超时、限流、断线自恢复——**假设"异常一定会发生"，并让它可控**；
5. **分层排查**：硬件 → 寄存器 → 中断 → 任务 → 应用逻辑，自下而上排除；
6. **尊重编译器的"自由度"**：`volatile`、内存屏障、原子访问不是可选项；
7. **把教训变成文档与工具**：踩过的每个坑都要变成下一个人的捷径。

## 10. 本次案例的"已知 / 未知"清单（诚实记录）

**已经确定（有实测证据）**

- `-Og` 固件正常启动运行（LCD 任务进入、heartbeat 递增、IMU 标定完成、温度正常）；
- `-O2` 固件启动阶段反复复位（`.bss` 计数器回零），没有 HardFault（CFSR/HFSR=0），CYCCNT 正常；
- 复位发生前，BMI088 标定循环每次只跑到约 150~250 轮（约 100ms 工作量），且**单轮耗时正常、采样数据正常**；
- LCD 任务从未进入初始化（`lcd_init_stage=0`）——因为它优先级最低，前面卡住它就永远排不上；
- `bsp_spi` 的忙标志缺 `volatile` 是一个真实隐患（已修），并补了超时（BSPSPI-04）；
- 看门狗"启动窗口不足"会形成"永远起不来"的死亡螺旋（已修：启动期长超时 + 标定循环喂狗）。

**尚未确定（下一步）**

- `-O2` 下启动被复位的**最终触发源**：需要在 `-O2` 启动过程中读 `IWDG->PR/RLR` 与 `RCC_RSR`，
  并尝试**完全关闭 IWDG**跑一次（确认是否还有别的复位源，例如 WWDG、欠压、栈溢出）；
- 是否还有其它 ISR/任务共享变量缺 `volatile`（建议全局搜一遍跨上下文共享的变量）；
- 是否因 `-O2` 栈帧变大导致某个任务/主栈溢出（可用 `-fstack-usage` 或栈高水位检查）。

> 结论：`-O2` 性能构建目前**不可用于生产**；生产固件仍使用 `-Og`。这个案例本身已经把"定位这类故障的完整方法"演示了一遍——**过程比结论更值钱**。
