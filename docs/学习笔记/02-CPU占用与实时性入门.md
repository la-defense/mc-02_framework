# 02 CPU 占用与实时性入门（写给 MC-02 工程）

## 0. 一句话版本

**"CPU 占用率"看的是"谁在什么时候把 CPU 抢走了、抢走多久"。** 本工程实测 `IDLE 只剩 5.9%`，意味着余量几乎耗尽；这篇文档讲清楚这些数字是怎么来的、中断算在谁头上、以及我们用什么工具测。

## 1. 我们为什么要测这个

实测基线（USB 供电、无电机、LCD 常开、5Hz 刷新）：

| 任务 | 占用 | 说明 |
|---|---|---|
| motortask | 48.2% | 名义 1kHz 电机控制（含被它"承接"的中断时间） |
| instask | 35.7% | 名义 1kHz 姿态解算（BMI088 读取 + 四元数 EKF） |
| lcdtask | 8.9% | 50ms 按键采样 + 5Hz 刷屏（需求其实是 19%，只拿到 8.9%） |
| IDLE | **5.9%** | 剩余余量 |

电机和 INS 两行的 1kHz 是任务声明的节拍，不是实测值。`PlatformTaskDelayMs(1)` 只是让任务跨过一个 1ms tick；执行时间小于 1ms 时循环周期约 1ms，超过 1ms 时会被推到后续 tick。实际周期和占用要用周期计数器确认。

结论有两条：① 整机接近饱和；② **LCD 被"饿着"**——它需要 19% 才能维持 5Hz，实际只拿到 8.9%，所以刷新率被拖到约 2.2Hz。

## 2. RTOS 里 CPU 是怎么被分配的

- **优先级**：数字越大越优先。我们的任务：`instask = osPriorityAboveNormal`、motor/robot/daemon/ui = `osPriorityNormal`、**`lcdtask = osPriorityLow`**、IDLE = 0。
- **抢占式调度**：高优先级任务一就绪就立刻抢 CPU（打断低优先级任务），所以**低优先级任务不会拖累控制**，它只能用"没人用"的时间片。
- **`osDelay(n)`**：主动让出 CPU，至少跨过 `n` 个 tick（我们 tick = 1ms）。`osDelay(1)` 是等到下一个 tick，不是调用后再等 1ms；执行时间小于 1ms 时循环周期约 1ms，超过 1ms 时会被推到后续 tick。
- **IDLE 任务**：优先级最低，别的任务都没事干时它才跑 → **IDLE 占用率就是"系统余量"**。IDLE 掉到个位数，就意味着任何新功能都可能顶不住。

> 由此得到两个重要推论：
> 1. LCD 慢一点不会影响控制回路（它被抢占）；
> 2. 但 LCD 要维持 5Hz 需要 19% 的预算，这部分会压缩后续功能（协议 v2、导航帧）的空间。

## 3. FreeRTOS 运行时间统计是怎么算出来的

原理（`tasks.c`）：

1. 每次**任务切换**时 FreeRTOS 调用一次 `portGET_RUN_TIME_COUNTER_VALUE()` 取当前计数器值；
2. 把"当前时刻 − 本任务被切入的时刻"累加到该任务的 `ulRunTimeCounter`；
3. `uxTaskGetSystemState()` 把每个任务的累计值、名字、优先级导出成一个数组。

所以 `ulRunTimeCounter` = **该任务真正占用 CPU 的累计时间**（精度取决于你提供的计数器）。

**我们踩过的坑（CORE-05）**：工程里 `getRunTimeCounterValue()` 是一个**空的弱实现**（`return 0`），于是所有 `ulRunTimeCounter` 恒为 0，`vTaskGetRunTimeStats()` 永远打印 0 —— 看着"统计已开启"，其实什么都没统计。

现在的实现：

```c
__weak unsigned long getRunTimeCounterValue(void)
{
    return (unsigned long)(DWT->CYCCNT / 1000u);   /* 480MHz 周期计数 → 约 2us 分辨率 */
}
```

- `DWT->CYCCNT` 是 CPU 的周期计数器（480MHz，分辨率 2.08ns）；
- 当前 `getRunTimeCounterValue()` 返回 `DWT->CYCCNT / 1000`，单位约为 2.08µs，但 DWT 源计数仍会在 480MHz 下约 8.94s 回绕。整数除法只改变单位，不会延长回绕周期；跨过 DWT 回绕计算任务时间差时，结果可能异常。4295s 和 8950s 都不适用于当前实现，回绕处理需要单独修正并验证。
- 占用率算法：**两次快照的差值之比**
  `占用率 = Δ(该任务累计) / ΣΔ(所有任务累计)`，不要用绝对值的百分比（含启动瞬态）。

## 4. 中断时间算在谁头上

这是最容易误读的一点：

- ISR（中断服务函数）抢的是"**当时正在运行的那个任务**"，因此 **ISR 的耗时会被记到那个任务名下**；
- 我们的 CAN 接收是每帧一次中断（电机反馈 1kHz × 每总线 5 个电机 ≈ 5k 帧/s），这些 ISR 时间就摊到了 motortask 头上；
- 所以 `motortask 48.2%` ≠ "PID 算了 48.2%"，里面包含：**自旋等待 + 中断服务 + PID + 组帧发送**。

怎么拆开？给 ISR 单独加计时累加（本次改造已加 CAN RX ISR 累计），再用"任务总时间 − ISR 时间"得到真正花在任务代码里的时间。

## 5. DWT 计时怎么做（本工程约定）

- 直接用 `DWT->CYCCNT`（480MHz），**不要**在热路径里用 `DWT_GetTimeline_us()`——它内部要做 64bit 除法（还有回绕处理），本身就是开销，会污染测量；
- 我们新增了轻量探针：`DWT_ProbeStart()` / `DWT_ProbeElapsedUs(start)`（两次 32bit 读 + 一次除法，约 0.1µs 级）；
- **回绕**：32bit @480MHz = 8.94s，探针区间远小于它，不需要处理回绕；
- **注意测的是墙钟**：如果任务在计时区间内被抢占，测出来的时间包含被抢走的部分。所以解释数字时要么结合"帧数/字节数"换算（例如 LCD 一帧 68.4KB ÷ 15MHz ≈ 36ms），要么同时统计 ISR/切换次数。
- **别乱加探针**：每字节/每帧都插探针会把测量对象变成探针本身。

## 6. 阻塞式等待的代价（以 CAN 为例）

改造前的 `CANTransmit()`：

```c
while (HAL_FDCAN_GetTxFifoFreeLevel(handle) == 0) {   /* 硬件 FIFO 满 */
    if (DWT_GetTimeline_ms() - start > timeout) { ... return 0; }   /* 自旋等超时 */
}
HAL_FDCAN_AddMessageToTxFifoQ(...);
```

为什么这很贵：

- CAN 帧按 1Mbps 发一帧约 130µs，还要等 ACK；**总线上没有其他节点（没接电机）时没有 ACK**，一帧要等约 150µs 才失败，FIFO 才有空位；
- `DJIMotorControl()` 每个 1ms tick 最多要发 9 组报文 → 最坏 **1.35ms 全在自旋**，而 tick 只有 1ms → 直接爆预算；
- 自旋里还在调用 `DWT_GetTimeline_ms()`（内部 64bit 除法），让空转更贵。

正确做法（本次改造）：

- **非阻塞**：先查 FIFO 空闲，满了就**丢帧并计数**，下一个周期自然重发（对电机控制没有影响，因为下一帧 1ms 后就到）；
- 用硬件 TX FIFO 当缓冲区（深度 4 → 16），发送完成用中断回调统计；
- 经典 CAN 的 TX **不需要 DMA**：FDCAN 外设自己从消息 RAM 读取数据，硬件队列 + 完成中断就是"DMA 化"的等价物；
- 加上总线错误恢复（BusOff/INIT 自动重启），否则空总线上跑一会儿 CAN 会彻底停摆（外设进了 BusOff/INIT 状态没人救）。

> 核心观念：**"等"也是一种 CPU 开销，而且通常是最容易消掉的那部分。**

### 6.1 高优先级任务的启动等待也会饿死看门狗

CPU 占用不只发生在周期任务里。INS 是高优先级任务；如果 BMI088 初始化失败后进入 `while (1)`，它会一直占着 CPU，daemon 就无法运行，负责检查任务心跳并喂 IWDG 的 `TaskMonitorTick()` 也就停了。板子看起来像“传感器坏了导致复位”，真正的直接原因却是失败分支没有让出 CPU。

本次 MC02-0042 的修复把短等待统一放到 `TaskMonitorDelayMs()`：调度器运行时按一个 tick 一次让出 CPU，并刷新调用任务的心跳；调度器未运行时才用 DWT 忙等。传感器初始化失败后，INS 任务保留无效姿态状态并继续有界运行，不用旧姿态假装有效，也不让加热恢复。

USB 裸板实测中，加速度计没有返回芯片 ID（`0x00`），BMI088 初始化以 `0xff` 失败；但 10 分钟内任务监控计数持续递增、IWDG 标志未置位，COM14 仍收到 CRC 正确的 43 字节状态帧。发送 1,000 个 `mode=0` 全零命令后，RX 计数增加 1,000、CRC 错误不变；停发超过 50 ms 后旧命令清零。这个结果说明故障降级路径、调度和双向通信保持运行，不代表传感器或自瞄已验收。详情见 [MC02-0042 实机回归](../workflow/tickets/MC02-0042.md)。

## 7. CAN 总线负载怎么估算

1Mbps 下，一个标准数据帧含位填充约 117~135 bit → **上限约 7.4k~8.5k 帧/s**。

DJI 电机的反馈是**电机自己按 1kHz 发的**，我们改不了：

| 总线 | 挂的设备（当前 config） | 反馈帧/s | 命令帧/s | 合计 |
|---|---|---|---|---|
| CAN1 | 4×底盘 M3508 + 拨弹 M2006 | 5000 | ~2000 | **≈7k** |
| CAN2 | yaw/mini_yaw/pitch GM6020 + 2×摩擦轮 | 5000 | ~3000 | **≈8k** |
| CAN3 | 无 | 0 | 0 | 0 |

也就是说：**总线已经贴在上限**。贴上限的后果就是丢反馈（误判电机离线）、TX FIFO 满（自旋等待）、错误计数上升。分摊到 CAN3、降低命令发送频率都能缓解；本次先做"软件侧不再自旋 + 总线可恢复"，接车后再做分摊。

顺带一提：**物理层**（终端电阻 120Ω、地线、双绞、屏蔽）经常是"总线错误"的假阳性来源，排查时不要只盯代码。

## 8. 从测量到修复的标准流程（本工程约定）

1. **记录基线**：同一工况（供电方式、LCD 开关、有无电机）先测一遍；
2. **分段定位**：把大块拆成"读取 / 计算 / 发送"，分别计时（例如 motor 分 PID、组帧、发送；INS 分 BMI088 读取、EKF）；
3. **一次只改一个变量**，改完立刻同工况复测；
4. **进报告**：把前后对比表写进 `docs/代码审查报告_MC-02.md`，然后 git 提交；
5. **仍不达标**再考虑有代价的手段（降频、改架构）——有代价的选项永远放最后。

## 9. 常见误区

| 误区 | 事实 |
|---|---|
| "占用率低就是好事" | 要看是不是"被饿着"：LCD 需求 19% 只拿到 8.9%，屏幕刷新就被拖慢 |
| "优先级越高越好" | 高优先级任务如果阻塞在不该等的地方，会拖垮全系统 |
| "加个 delay 就能省 CPU" | delay 只是把 CPU 让出去，单次耗时没变；真正要省的是"单次耗时 × 次数" |
| "采样一次就看到真相" | 占比必须用两次快照的差值；单次绝对值包含启动瞬态 |
| "任务占用率 = 任务代码的耗时" | 含被中断的时间；要拆开必须给 ISR 单独计时 |

## 11. 周期数与微秒的接口条件（MC02-0123）

[bsp_dwt.h](../../bsp/dwt/bsp_dwt.h) 的 ProbeStart 返回 CPU 周期数，ElapsedUs 才将周期差除以 MHz 频率得到微秒。
`DWT_Init(480)` 表示 480 MHz；计数超过 32 位最大值会回到 0，约每 8.94 秒一次。
无符号相减能处理跨过一次零点的短间隔，若两次读取相隔多个计数周期，单凭差值无法还原真实耗时。
累计时间也要在一个周期内至少更新一次，三个 Timeline 入口各自调用内部累计函数，并非调用 `DWT_SysTimeUpdate()`。
`DWT_GetDeltaT()` 会把传入的旧周期数改成当前读数，调用方要长期保留这份变量。

## 12. R25-12：任务栈和最大观测耗时

R25-12 在 `StartINSTASK()`、`StartMOTORTASK()`、`StartDAEMONTASK()`、`StartROBOTTASK()` 和 UART 发送任务中保留 `DWT_Probe_t`。其中 `max_us` 是本次上电以来、指定函数主体的最大观测耗时，单位为微秒；它不等于形式化 WCET，也不包含任务被更高优先级工作抢占的完整响应时间。LCD 另有采样、更新和绘制分段最大值。

`lcd_task_stats_snapshot()` 每约 5 秒发布一次 FreeRTOS 任务名、累计运行计数、优先级和历史最小剩余栈。`lcd_stats_generation` 在写入期间为奇数，写完后变为偶数；离线 GDB 先从匹配 ELF 找地址，运行中 OpenOCD 只读 RAM，并对照前后代号。`tools/probe_snapshot_live.py --rtos` 会拒绝布局不符、表格更新中、地址越界和栈剩余量大于已知配置的记录；任务超过12个时会明确报告截断，不能当作完整清单。

FreeRTOS 栈水位的单位是 `StackType_t` 个数，H723 每项4字节。本工程的 CMSIS-RTOS v1 `osThreadCreate()` 将 `stacksize` 原样传给 `xTaskCreate()`；FreeRTOS 把该参数解释为栈字数。因此本轮按实际传入的数值字数计算余量，并在票据中记录这一实现细节，不能只按 CMSIS 文档的“字节”注释推算。

FreeRTOS 运行计数由 `DWT->CYCCNT / 1000` 产生；480 MHz 时每个计数约为2.083微秒。它适合在不同快照间按任务名配对求差，不代表整数微秒。R25-12 的栈和耗时结论以已说明的 `bench_safe`、LCD＋DR16和本轮运行场景为边界；电机解析压力由生产 DJI 解码器主机测试覆盖，不把板上禁热配置说成电机实测。

详见 [R25-12 记录](../workflow/tickets/R25-12.md)、[探针工具](../../tools/probe_snapshot_live.py) 和 [LCD 任务快照](../../modules/lcd/lcd_task.c)。

本轮 `bench_safe` 裸板观察覆盖10个任务且任务表未截断；最少剩余值为 `defaultTask` 的48 word，即192字节。65.245秒内收到了13,047个CRC正确的SP状态帧，视觉模式保持0，IMU序号持续增加，加热占空比和看门狗复位标志保持0。任务主体最大观测值包括 INS 399µs、Motor 8µs、Daemon 48µs、Robot 64µs、UART TX 7µs。它们只对应本次禁热、无执行器的运行场景，不是WCET；剩余栈也没有被证明为所有负载下的安全阈值。完整任务表、调用计数、参数区逐字节对比和固件身份见任务票据。

## MC02-0100：可重算的只读观测

运行 `tools/probe_snapshot_live.py --performance` 可做默认30秒窗口；`--duration` 接受5～300秒，默认每秒采样。工具先比较所选 ELF 与板上固定身份记录，随后只从白名单地址读取运行中的 RAM。缺少身份、布局不匹配或读数失败时会保留原始失败记录，并将受影响结果标成不可计算。

每个五秒统计组各自带发布时间和编号。相同编号只记录一次；至少两份不同编号才计算窗口增量。超过两个发布周期（约10秒）未更新的组标为过期。任务按名称配对，CAN按总线显示，LCD当前统计和差值分开。`raw.jsonl` 可用于重算摘要；任务计数占比不代表精确 CPU 使用率，最大计时不代表 WCET。

## MC02-0086：任务创建使用平台接口

[任务创建流程](../../application/robot_task_create.c) 现在通过 [platform_os.h](../../bsp/os/platform_os.h) 提交名称、入口、栈字数和优先级。MC-02 后端仍调用原来的 CMSIS-RTOS 创建函数；INS 为高于普通，LCD 为低优先级，其他任务保持普通优先级。创建成功才写入不透明句柄，失败时按原核心／辅助分类记录；未启动的辅助模块不创建任务。任务循环仍使用原有等待周期，本次不改变任务拆分或调度频率。

主机测试使用可控的任务创建后端，检查栈、优先级及核心失败、辅助降级和禁用模块；这只能验证软件路径，不能代替板上调度、执行耗时和栈水位测量。

## MC02-0087：任务创建时暂停什么

启动协调者需要在调度器运行后创建任务。若新任务立即抢占，而任务句柄和服务就绪状态还没有发布，其他代码可能看到不一致的状态。`PlatformTaskBatchBegin()` 短暂暂停的是 FreeRTOS 任务切换，不是全局中断；创建并发布完成后，协调者调用 `PlatformTaskBatchEnd()` 恢复调度。

日志在调度器启动前也会接收启动事件。此时 FreeRTOS 的任务临界区嵌套计数尚未进入运行状态，不能用它保护日志后再假定中断已经恢复。日志端口在启动前保存并恢复原中断屏蔽状态，嵌套时只在最外层退出后恢复；调度器运行后继续使用任务临界区。主机测试分别检查原先开启、原先屏蔽和嵌套的情况，板上中断时序仍需验证。

基础启动会分别检查 RTT 日志出口和独立诊断串口。任一出口不可用时，在启动事件中记录对应资源的降级，并继续初始化其他功能；两个出口都失败时分别记录。若日志状态本身无法查询，则记录状态查询失败，不猜测哪个出口出错。运行期的实际可用状态仍由日志状态接口提供。

车型计划可能把日志列为核心模块，或让其他核心模块依赖日志。启动计划会计算完整依赖链：RTT 不可用或日志状态未知时，辅助日志保留降级状态；若日志处于核心依赖链，则阻止核心启动。诊断串口提供独立协议，不作为 RTT 日志正文出口的就绪条件；其故障仍单独记录。

这个批次只能由唯一协调任务持有，不能在其中延时、等待外设或做耗时初始化。UART 发送任务和日志静态任务在调度器运行时只接受批次内创建；普通运行任务和中断不能借此创建。日志创建失败时清除临时入口，协调者可在同一批次内处理失败或重试，成功后才允许新任务观察句柄。默认任务现已通过批次创建周期任务；主机测试通过模拟调度器检查配对、非法调用、失败重试和任务入口，真实中断和线程切换仍需后续裸板验证。

## MC02-0130–0137：可移植性能模板的调研结论

这次调研把“名义 1 kHz 与实际周期”和“平台可移植”放在同一份设计里。按 CPU 占用粗算，`osDelay(1)` 的电机任务约 518 Hz、INS 约 643 Hz；真实周期是执行时间加 1 ms，Cache 和热点优化前不能直接把周期改成 1 kHz。

H723 的主 RAM 99.8% 来自“只映射 128 KB AXI SRAM1”：AXI SRAM2 还有 128–192 KB，DTCM 只用了约 14.7 KB。方案是把 AXI1 留给 DMA 和崩溃记录，AXI2 放普通数据，DTCM 放栈和任务堆；I-Cache 先开，D-Cache 后开且默认关闭。

任务侧最终把全部任务改成静态栈/TCB，只留 newlib 堆；F407 先做 500 Hz、无 Cache、compile-only；C++ 最后用 `bsp/param` 试点。测量口径、风险、证据等级和 TODO 拆分见[调研文档](../workflow/specs/performance-portability-research.md)，本文只解释决策。

## MC02-0088 固定拍点、跳拍和超期

一轮工作花 2 ms，再调用 `osDelay(5)`，两轮开始之间就约有 7 ms。绝对时刻等待先选定 0、5、10、15 ms 等拍点。工作在 2 ms 完成时，只等到 5 ms。若任务到 19 ms 才获得处理器，且还没领取 5 ms 这一拍，就跳过 5 和 10 ms，只运行 15 ms 这一拍。再下一拍仍是 20 ms。见[周期计算](../../bsp/os/platform_periodic.c)和[FreeRTOS 等待适配](../../bsp/os/platform_periodic_freertos.c)。

执行预算和完成截止时间可以给出不同结果。19 ms 开始、21 ms 完成的工作只花了 2 ms。若预算是 2 ms，它仍满足预算，但已经过了 20 ms 的计划截止点。主机测试分别检查这两个结果，也覆盖计数回绕和提前唤醒。见[主机验证](../workflow/tickets/MC02-0088-evidence/README.md)。

裸板诊断用当前 FreeRTOS 的 1 ms 刻度维持名义 5 ms 周期，执行时间仍用 DWT 测量。可移植周期计算能接收更细的计数刻度。要在板上等待 500 μs 拍点，还需要提供能在该分辨率下唤醒任务的硬件后端。

### TIM5怎样唤醒任务

独立裸板自测把 TIM5 分频到 1 MHz。任务将下一个拍点写入比较寄存器后阻塞，由 TIM5 中断发出通知。有时计数在设置过程中已经到期，任务会直接复查这一拍，避免等待已经错过的比较。若中断比任务先到，信号量会保存通知，直到任务读取。见 [TIM5 后端](../../bsp/board/platform_periodic_tim5_stm32.c)。

等待通知依然有 RTOS 超时。定时器停摆或比较中断丢失时，本次拍点保持原值，诊断退出并释放资源。主机可以模拟这些顺序，实际计数误差和中断唤醒时延需要在裸板测量。见[本机验证](../workflow/tickets/MC02-0088-evidence/README.md)。

四个比较通道读取同一个 TIM5 计数值。每个任务把自己的下一拍写入独立的比较寄存器，ISR 将通知分别交给各自的信号量。第二个任务加入时沿用当前计数，否则重置 TIM5 会改变第一个任务的计划时刻。只有最后一个任务离开才停止计数。

TIM5 的状态位写 0 清除，写 1 保留。如果先读状态寄存器，再把读到的值改一位写回，两步之间刚到期的另一通道可能被写 0 清掉。程序清除本通道时给其他位写 1，也保留共享中断在 NVIC 中的挂起状态。主机测试模拟两个任务同时到期，以及一个任务超时退出时另一个仍有通知等待处理。见[后端代码](../../bsp/board/platform_periodic_tim5_stm32.c)和[本机验证](../workflow/tickets/MC02-0088-evidence/README.md)。

收到比较通知后，计数器仍可能在任务恢复执行前停转。任务会在领取拍点、打开比较中断和等待返回后检查外设时钟、计数开关以及 NVIC 中断开关。任一条件失效时，等待返回时钟错误，原计划时刻和上次出参保持原值。时钟已经关闭时，释放通道只处理还能访问的软件和 NVIC 状态。时钟恢复后若有已释放通道的比较请求，中断只清请求，其他通道继续处理。[失效注入回归](../../tests/host/platform_periodic_tim5_test.c)

### 为什么创建前先检查周期

周期和执行预算都得能用后端刻度精确表示。以 1 ms 的 RTOS 刻度为例，2 ms 的周期可表示，250 μs 的预算无法表示。允许自动选择的任务可以改用 1 μs 的硬件刻度，每个任务需要一个独立的比较通道。启动检查会统计整组请求，最后一个任务发现通道用完时，整组方案退回。见[周期计划](../../bsp/os/platform_periodic.c)。

禁热固件在创建任务之前检查配置，任务启动后读取同一份周期和预算。普通诊断指定使用 RTOS；专用固件的 500 μs 自测指定使用 TIM5，借此验证比较中断这条路径。预检只读取外设状态，开始等待的任务仍须实际申请自己的通道。见[诊断配置](../../application/robot_monitor_plan.c)。

### 任务做完才算完成一拍

姿态、通信派发、整车和设备维护任务使用 RTOS 固定拍点。正式、受限调试和禁热配置在启动业务设备前核对所选任务的周期和预算是否能用整刻度表示，失败时记录具体任务。未启用姿态的车型跳过姿态拍点。任务先等启动协调者放行，再建立自己的拍点。醒来后仍须取得任务监控许可才能执行本轮，完成时再用同一个时钟上报进度。时钟读数失效时，监控收不到新的完成报告。[周期检查](../../application/robot_monitor_plan.c) · [本机验证](../workflow/tickets/MC02-0055-evidence/README.md)

1 ms 的高优先级任务如果每次都做到下一拍，下一次等待可能立即返回，挤压低优先级任务的运行时间。诊断等软期限任务到达下一拍时会先让出一个 RTOS 刻度，醒来后从原计划取最近到期的一拍。主机测试注入恰好在下一拍完成、时钟出错和监控拒绝，检查任务是否应当工作或上报。[任务入口](../../application/robot_task.c) · [主机测试](../../tests/host/robot_task_cycle_test.c)

底盘等硬期限任务恰好在截止点完成时，直接按原计划等待下一拍。对 500 μs 的 TIM5 任务，额外让出一个 1 ms RTOS 刻度可能跨过下一拍。独立电机派发和其他硬期限任务用同一条故障路径：领到的拍点已漏拍时，先撤销许可，该轮不再运行；完成检查确认超预算时，立即撤销许可并停止上报完成。车型的周期和执行预算仍须按板上负载确认。[本机验证](../workflow/tickets/MC02-0055-evidence/README.md)

电机派发在接收和计算之后、进入 CAN 发送服务之前再看一次时钟。比如 2 ms 周期的任务晚 1 ms 开始，计算又占用 1 ms。执行预算还剩 1 ms，但下一拍已经到了，因此本轮不推进软件发送队列，且立即撤销运行许可。正常进入发送的轮次，结束时仍要检查实际耗时。发送前到达上限代表没有剩余时间，已经完成的工作则可以刚好用完预算。[电机派发入口](../../application/robot_task.c) · [回归记录](../workflow/tickets/MC02-0055-evidence/README.md)

发送服务可能轮流处理多条 CAN 总线，双板还会给桥接总线一次额外机会。第一帧提交后，本轮预算可能已经耗尽，所以普通发送和桥接都在每次交给 HAL 前重新检查时限。检查拒绝时，当前帧留在软件队列，原期限继续生效。队列退出保护后，电机任务才撤销运行许可并上报故障，不把本轮记为完成。主机回归观察 HAL 替身收到了哪些帧。已提交帧的硬件发送时刻、RTOS 刻度与实际停车时延仍需现场测量。[队列实现](../../bsp/can/bsp_can.c) · [主机回归](../../tests/host/lk_motor_bsp_can_test.c)

取得监控许可后，任务还可能在实际业务开始前被抢占。假设底盘任务的计划拍点在 0 ms，1 ms 领取，下一拍在 4 ms。如果获得许可后直到 4 ms 才继续执行，即使从领取时计算还有执行预算，也不能开始旧的一拍。底盘、电机派发和受限人工命令在业务入口用原时钟再检查一次，亚毫秒任务也检查 TIM5 是否仍可用。超期或时钟失效时先撤销输出，再上报故障，本轮不执行业务或推进完成计数。业务已经完成的轮次仍可正好用完预算。[任务入口](../../application/robot_task.c) · [主机回归](../../tests/host/robot_task_cycle_test.c)

### MC02-0055 底盘拆成独立任务

正式生成配置选用底盘时，启动阶段先读车型配置中的周期、预算、监控期限和栈字数。监控注册成功后保存只读副本，启动协调者核对设备已就绪再创建任务。底盘取得自己的拍点后从原话题读取新鲜命令，整车任务继续负责命令选择和状态汇总。拆分前后，底盘周期入口各有一个调用者。见[监控配置](../../application/robot_monitor_plan.c)、[任务创建](../../application/robot_task_create.c)和[周期入口](../../application/robot_task.c)。

底盘的任务时钟一旦失效，任务先撤销四轮速度参考，然后停止报告完成。这样即使后续监控尚未轮询到该故障，软件也已提交停机状态。这里验证的是参考值、进度和启动条件，实际停止时延需要上车测量。哨兵的周期和预算仍待确认，主机测试中的时间和栈配置仅用于触发各分支。见[验证记录](../workflow/tickets/MC02-0055-evidence/README.md)。

车型可指定 RTOS、TIM5 或自动选择。自动选择先检查 RTOS 能否精确表示周期和预算，必要时再使用 TIM5。启动预检通过后只保存实际选中的时钟。以 500 μs 的主机用例为例，任务仍按 500 μs 领取拍点，毫秒级存活监控把名义周期记为 1 ms。执行预算和下一计划拍仍用 TIM5 的原始计数判断。

TIM5 把周期状态的地址和任务绑定，因此状态对象保留在任务栈上。任务在原计数域检查完成时间。底盘超出单轮预算或错过下一计划拍时，先撤销轮组参考，再释放持有的通道，并停止报告完成。500 μs 是回归用例，哨兵车型的实际周期、预算和抖动仍待测量。[时钟检查](../../bsp/board/platform_periodic_tim5_stm32.c) · [底盘任务](../../application/robot_task.c)

任务自己已经确认拍点错误时，可以立即让监控锁存故障。底盘和电机任务先撤销速度参考或运行许可。底盘若持有 TIM5 通道，还要先释放通道，因为核心故障的直接关断入口会保持普通中断关闭。任务监控保留首次失败原因和完成次数，核心故障停止喂狗。对没有自行报告的任务，原有轮询仍会根据期限发现停顿。[任务监控](../../modules/task_monitor/task_monitor.c) · [联测记录](../workflow/tickets/MC02-0055-evidence/README.md)

受限底盘的整车任务负责发布人工命令，也使用这条故障路径。等待接口报告已跳过整拍时，任务在进入本轮工作前撤销运行许可。若工作已运行，直到检查完成时间才发现超期，任务随即撤销许可并上报原因，已发到总线的帧仍需现场测量其影响。两种情况都停止报告新的完成进度。普通裸板的整车任务仍使用诊断时序。[人工命令任务入口](../../application/robot_task.c) · [主机故障用例](../../tests/host/robot_task_cycle_test.c)

### 一个电机任务，两套拍点

计算和发送可以有不同周期，仍由同一个电机任务串行完成。用主机测试中的 2 ms 计算、3 ms 发送举例，第 2 ms 只计算，第 3 ms 只发送，第 6 ms 两者同时到期，就先计算再发送。每次轮询都先消费接收数据。若任务迟到，计算和发送各自跳过已经错过的工作。

发送拍点只能决定何时推进 CAN 队列。一帧能否送进硬件，还由它计算时所用的反馈期限和当前安全许可决定。这样即使计算与发送隔着几拍，新的反馈也不会延长旧结果的有效期。见[阶段顺序测试](../../tests/host/motor_profile_test.c)和[DJI 队列发送前复核](../../modules/motor/DJImotor/dji_motor.c)。

### MC02-0055 三类控制任务共享唤醒资源

正式固件为已启用的底盘、云台和发射模块分别创建任务。启动检查会一次提交所有周期请求。例如，平台只剩两个 TIM5 通道，而三个任务都要求亚毫秒拍点，第三个任务会报告资源不足，启动不会放行。如果其中一个任务的周期和预算都能用 RTOS 刻度表示，另外两个任务便可各用一个 TIM5 通道。各任务保存启动时选定的时钟和原始微秒值，监控显示可以向上取整到毫秒。

监控表按编入固件的任务数分配记录，通过任务编号查找记录。这样只增加一个独立任务时，表只多占一条记录，即使该任务的编号较大。标定和 Flash 维护只由 INS 任务申请，因此分别保留一条长操作记录。[任务监控](../../modules/task_monitor/task_monitor.c)

运行阶段由云台任务自己发布反馈。整车命令任务读取最近有效的反馈，继续按原始采样时间判定是否过期。独立任务遇到跳拍时跳过这轮业务，完成时钟错误或超预算时也停止对应输出。任务先执行关断和通道释放，再报告监控故障。哨兵的实际周期、预算、宽限期与栈容量待实测。[任务入口](../../application/robot_task.c) · [启动检查](../../application/robot_monitor_plan.c)

### MC02-0055 受限底盘的组合时限

一份人工输入刚好错过命令任务的拍点，就要再等一拍。底盘任务也可能刚执行完，随后电机计算和发送各有自己的拍点。启动时把这些名义等待和任务预算加起来。从输入可读取开始计时，要能覆盖整条路径。从命令发布开始计时，剩下的阶段还要落在话题期限内。两条时间线的起点不同，分别检查。

在主机用例里，命令任务的周期和执行预算各为 5 ms。底盘等待和执行各占 1 ms，电机计算和发送各等 1 ms，发送轮次再留 1 ms。输入阶段合计正好 15 ms，期限设为 15 ms 时通过，增加 1 μs 则被拒绝。这是启动时计算的名义值。接收排队、额外调度延迟和 CAN 仲裁还会影响实车结果。[组合检查](../../application/config/commissioning_chassis_config.c) · [主机回归](../../tests/host/commissioning_chassis_cmd_test.c)
