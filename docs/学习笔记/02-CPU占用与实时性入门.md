# 02 CPU 占用与实时性入门（写给 MC-02 工程）

## 0. 一句话版本

**"CPU 占用率"不是看任务写得漂不漂亮，而是看"谁在什么时候把 CPU 抢走了、抢走多久"。** 本工程实测 `IDLE 只剩 5.9%`，意味着余量几乎耗尽；这篇文档讲清楚这些数字是怎么来的、中断算在谁头上、以及我们用什么工具测。

## 1. 我们为什么要测这个

实测基线（USB 供电、无电机、LCD 常开、5Hz 刷新）：

| 任务 | 占用 | 说明 |
|---|---|---|
| motortask | 48.2% | 1kHz 电机控制（含被它"承接"的中断时间） |
| instask | 35.7% | 1kHz 姿态解算（BMI088 读取 + 四元数 EKF） |
| lcdtask | 8.9% | 1kHz 采样 + 5Hz 刷屏（需求其实是 19%，只拿到 8.9%） |
| IDLE | **5.9%** | 剩余余量 |

结论有两条：① 整机接近饱和；② **LCD 被"饿着"**——它需要 19% 才能维持 5Hz，实际只拿到 8.9%，所以刷新率被拖到约 2.2Hz。

## 2. RTOS 里 CPU 是怎么被分配的

- **优先级**：数字越大越优先。我们的任务：`instask = osPriorityAboveNormal`、motor/robot/daemon/ui = `osPriorityNormal`、**`lcdtask = osPriorityLow`**、IDLE = 0。
- **抢占式调度**：高优先级任务一就绪就立刻抢 CPU（打断低优先级任务），所以**低优先级任务不会拖累控制**，它只能用"没人用"的时间片。
- **`osDelay(n)`**：主动让出 CPU，至少 `n` 个 tick（我们 tick = 1ms）之后才可能再被调度。注意 `osDelay(1)` 的循环周期是"1ms + 本次执行时间"。
- **IDLE 任务**：优先级最低，别的任务都没事干时它才跑 → **IDLE 占用率就是"系统余量"**。IDLE 掉到个位数，就意味着任何新功能都可能顶不住。

> 由此得到两个重要推论：
> 1. LCD 慢一点不会影响控制回路（它被抢占）；
> 2. 但 LCD 把余量吃掉 19%，就压缩了后续功能（协议 v2、导航帧）的空间。

## 3. FreeRTOS 运行时间统计是怎么算出来的

原理（`tasks.c`）：

1. 每次**任务切换**时 FreeRTOS 调用一次 `portGET_RUN_TIME_COUNTER_VALUE()` 取当前计数器值；
2. 把"当前时刻 − 本任务被切入的时刻"累加到该任务的 `ulRunTimeCounter`；
3. `uxTaskGetSystemState()` 把每个任务的累计值、名字、优先级导出成一个数组。

所以 `ulRunTimeCounter` = **该任务真正占用 CPU 的累计时间**（精度取决于你提供的计数器）。

**我们踩过的坑（CORE-05）**：工程里 `getRunTimeCounterValue()` 是一个**空的弱实现**（`return 0`），于是所有 `ulRunTimeCounter` 恒为 0，`vTaskGetRunTimeStats()` 永远打印 0 —— 看着"统计已开启"，其实什么都没统计。

现在的实现：

```c
__weak unsigned long getRunTimeCounterValue(void)
{
    return (unsigned long)(DWT->CYCCNT / 1000u);   /* 480MHz 周期计数 → 约 2us 分辨率 */
}
```

- `DWT->CYCCNT` 是 CPU 的周期计数器（480MHz，分辨率 2.08ns）；
- **为什么要 `/1000`**：CYCCNT 是 32bit，480MHz 下 **8.94s 就回绕一次**；FreeRTOS 内部只用相邻两次切换的增量（很小，回绕在无符号减法下也正确），但**我们要跨几十秒比较"累计值"**，直接读原始周期数会回绕导致算错。除以 1000 后单位约等于 2µs，累计值要 4295s 才回绕。
- 占用率算法：**两次快照的差值之比**
  `占用率 = Δ(该任务累计) / ΣΔ(所有任务累计)`，不要用绝对值的百分比（含启动瞬态）。

## 4. 中断时间算在谁头上

这是最容易误读的一点：

- ISR（中断服务函数）抢的是"**当时正在运行的那个任务**"，因此 **ISR 的耗时会被记到那个任务名下**；
- 我们的 CAN 接收是每帧一次中断（电机反馈 1kHz × 每总线 5 个电机 ≈ 5k 帧/s），这些 ISR 时间就摊到了 motortask 头上；
- 所以 `motortask 48.2%` ≠ "PID 算了 48.2%"，里面包含：**自旋等待 + 中断服务 + PID + 组帧发送**。

怎么拆开？给 ISR 单独加计时累加（本次改造已加 CAN RX ISR 累计），再用"任务总时间 − ISR 时间"得到真正花在任务代码里的时间。

## 5. DWT 计时怎么做（本工程约定）

- 直接用 `DWT->CYCCNT`（480MHz），**不要**在热路径里用 `DWT_GetTimeline_us()`——它内部要做 64bit 除法（还有回绕处理），本身就是开销，会污染测量；
- 我们新增了轻量探针：`DWT_ProbeStart()` / `DWT_ProbeElapsedUs(start)`（两次 32bit 读 + 一次除法，约 0.1µs 级）；
- **回绕**：32bit @480MHz = 8.94s，探针区间远小于它，不需要处理回绕；
- **注意测的是墙钟**：如果任务在计时区间内被抢占，测出来的时间包含被抢走的部分。所以解释数字时要么结合"帧数/字节数"换算（例如 LCD 一帧 68.4KB ÷ 15MHz ≈ 36ms），要么同时统计 ISR/切换次数。
- **别乱加探针**：每字节/每帧都插探针会把测量对象变成探针本身。

## 6. 阻塞式等待的代价（以 CAN 为例）

改造前的 `CANTransmit()`：

```c
while (HAL_FDCAN_GetTxFifoFreeLevel(handle) == 0) {   /* 硬件 FIFO 满 */
    if (DWT_GetTimeline_ms() - start > timeout) { ... return 0; }   /* 自旋等超时 */
}
HAL_FDCAN_AddMessageToTxFifoQ(...);
```

为什么这很贵：

- CAN 帧按 1Mbps 发一帧约 130µs，还要等 ACK；**总线上没有其他节点（没接电机）时没有 ACK**，一帧要等约 150µs 才失败，FIFO 才有空位；
- `DJIMotorControl()` 每个 1ms tick 最多要发 9 组报文 → 最坏 **1.35ms 全在自旋**，而 tick 只有 1ms → 直接爆预算；
- 自旋里还在调用 `DWT_GetTimeline_ms()`（内部 64bit 除法），让空转更贵。

正确做法（本次改造）：

- **非阻塞**：先查 FIFO 空闲，满了就**丢帧并计数**，下一个周期自然重发（对电机控制没有影响，因为下一帧 1ms 后就到）；
- 用硬件 TX FIFO 当缓冲区（深度 4 → 16），发送完成用中断回调统计；
- 经典 CAN 的 TX **不需要 DMA**：FDCAN 外设自己从消息 RAM 读取数据，硬件队列 + 完成中断就是"DMA 化"的等价物；
- 加上总线错误恢复（BusOff/INIT 自动重启），否则空总线上跑一会儿 CAN 会彻底停摆（外设进了 BusOff/INIT 状态没人救）。

> 核心观念：**"等"也是一种 CPU 开销，而且通常是最容易消掉的那部分。**

## 7. CAN 总线负载怎么估算

1Mbps 下，一个标准数据帧含位填充约 117~135 bit → **上限约 7.4k~8.5k 帧/s**。

DJI 电机的反馈是**电机自己按 1kHz 发的**，我们改不了：

| 总线 | 挂的设备（当前 config） | 反馈帧/s | 命令帧/s | 合计 |
|---|---|---|---|---|
| CAN1 | 4×底盘 M3508 + 拨弹 M2006 | 5000 | ~2000 | **≈7k** |
| CAN2 | yaw/mini_yaw/pitch GM6020 + 2×摩擦轮 | 5000 | ~3000 | **≈8k** |
| CAN3 | 无 | 0 | 0 | 0 |

也就是说：**总线已经贴在上限**。贴上限的后果就是丢反馈（误判电机离线）、TX FIFO 满（自旋等待）、错误计数上升。分摊到 CAN3、降低命令发送频率都能缓解；本次先做"软件侧不再自旋 + 总线可恢复"，接车后再做分摊。

顺带一提：**物理层**（终端电阻 120Ω、地线、双绞、屏蔽）经常是"总线错误"的假阳性来源，排查时不要只盯代码。

## 8. 从测量到修复的标准流程（本工程约定）

1. **记录基线**：同一工况（供电方式、LCD 开关、有无电机）先测一遍；
2. **分段定位**：把大块拆成"读取 / 计算 / 发送"，分别计时（例如 motor 分 PID、组帧、发送；INS 分 BMI088 读取、EKF）；
3. **一次只改一个变量**，改完立刻同工况复测；
4. **进报告**：把前后对比表写进 `docs/代码审查报告_MC-02.md`，然后 git 提交；
5. **仍不达标**再考虑有代价的手段（降频、改架构）——有代价的选项永远放最后。

## 9. 常见误区

| 误区 | 事实 |
|---|---|
| "占用率低就是好事" | 要看是不是"被饿着"：LCD 需求 19% 只拿到 8.9%，屏幕刷新就被拖慢 |
| "优先级越高越好" | 高优先级任务如果阻塞在不该等的地方，会拖垮全系统 |
| "加个 delay 就能省 CPU" | delay 只是把 CPU 让出去，单次耗时没变；真正要省的是"单次耗时 × 次数" |
| "采样一次就看到真相" | 占比必须用两次快照的差值；单次绝对值包含启动瞬态 |
| "任务占用率 = 任务代码的耗时" | 含被中断的时间；要拆开必须给 ISR 单独计时 |
