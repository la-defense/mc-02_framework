# 03 非阻塞通信与 CAN 收发技术细节（写给零基础）

## 0. 一句话总结

**非阻塞 = "能发就发，发不了就记一笔、下个周期再来"，绝不在原地干等。**
CAN 外设内部有一块自己的 RAM 和硬件发送队列，配合"发送完成中断"，就能做到几乎不占 CPU 的发送；而"原地等"会把控制任务的时间预算吃光——我们在 MC-02 上实测到 motor 任务 98.9% 的时间都耗在等 CAN 上。

---

## 1. 先建立直觉：三种 I/O 模型

任何"和外部设备打交道"的操作，CPU 只有三种参与方式：

| 模型 | 做法 | 生活类比 | CPU 占用 | 实时性 |
|---|---|---|---|---|
| **阻塞式 / 轮询（blocking / polling）** | CPU 反复检查"好了没"，好了才继续 | 站在银行柜台前一直等到办完 | 100% 被占住 | 简单但最差 |
| **中断式（interrupt, IT）** | 交出控制权，硬件完成后打断 CPU 去执行一小段处理函数（ISR） | 拿号去旁边坐着，叫号再过去 | 只在事件发生时占用 | 好 |
| **DMA** | 交给专门的搬运硬件，CPU 完全不参与数据搬移 | 找代办，你连椅子都不用坐 | 几乎为 0 | 最好（但要硬件支持） |

关键概念：

- **ISR（中断服务函数）里不能做耗时的活**：不能 `printf`、不能 `malloc`、不能长时间循环。ISR 只适合"搬运 + 置标志"，复杂计算留给任务。
- **"等"也是 CPU 开销**：`while(...)` 空转和真正算东西一样吃电、一样占时间片，只是没产出。
- **非阻塞的本质**：把"等"从代码里删掉，改成"试试看 + 记状态 + 下次再来"。

## 2. STM32 的 FDCAN 外设到底长什么样

新手最容易卡在"我不知道硬件帮我做了什么"。把 FDCAN 想成**一个独立的小电脑**：

- 它有**自己的寄存器**（配置、状态、中断）；
- 它有**自己的内存**，叫**消息 RAM（Message RAM）**，是 MCU 内部专门划给 CAN 的一块 RAM；
- 它**自己会按 CAN 的位时序把帧一位一位发到线上**，不需要 CPU 逐位参与。

消息 RAM 被分成若干区（H7 的 FDCAN 是这样）：

```
标准滤镜(Filter) | 扩展滤镜 | RxFIFO0 | RxFIFO1 | RxBuffer | TxBuffer | TxFIFO/Queue | TxEventFIFO
```

### 2.1 发送一帧，硬件做了哪些事

1. CPU 把**帧头 + 数据**写进消息 RAM 里的某个 TX 槽位（HAL 里叫 `AddMessageToTxFifoQ`）；
2. CPU 置位该槽的**发送请求位**（TXBAR）；
3. 外设按位时序把帧送上总线，然后在帧尾等接收方的 **ACK 位**；
4. 收到 ACK → 该槽标记完成 → 触发**发送完成中断**（TCE）；如果整个 FIFO 空了 → 触发 **Tx FIFO Empty**（TFE）；
5. 如果没人 ACK（总线上没有其他节点），这次发送**失败**，错误计数增加（见第 7 节）。

**重要**：第 1 步只是"把信投进信箱"，**不等待发送成功**。真正的等待发生在硬件内部。所以 CPU 完全可以投完就走人——这才是"非阻塞发送"能成立的根本原因。

### 2.2 三种发送缓冲组织方式

| 方式 | 行为 | 我们用哪个 |
|---|---|---|
| **Dedicated Tx Buffer** | 每个 buffer 固定绑一个消息 ID，优先级最高 | 不用 |
| **Tx FIFO** | 先进先出，按写入顺序发送 | ✅ 我们用这个 |
| **Tx Queue** | 按**消息 ID 优先级**发送，ID 越小越先发 | 不用 |

可以配置缓冲深度（我们原来是 4 个槽位，本次改成 16 个）。深度越大，突发情况下越不容易"信箱满"。

### 2.3 接收一帧，硬件做了哪些事

1. 总线上的帧先过**滤镜（Filter）**：滤波器决定"这帧我要不要"；
2. 要 → 写入 **RxFIFO0** 或 **RxFIFO1**（硬件队列），然后触发 `RX_FIFO0_NEW_MESSAGE` 中断；
3. CPU 在 ISR 里用 `HAL_FDCAN_GetRxMessage()` 把帧**取走**（这一步千万不能忘：不取走 FIFO 会满，之后新帧全部丢失）；
4. 取走之后，CPU 根据 ID 找到"这帧属于哪个设备"，调用对应的解析函数。

### 2.4 中断源为什么要"能不开就不开"

FDCAN 的接收侧可以开这些中断：`NEW_MESSAGE`（来了新帧）、`WATERMARK`（FIFO 填充达到阈值）、`FULL`（FIFO 满）、`MESSAGE_LOST`（因为 FIFO 满丢过帧）。

我们原来的代码**四个全开**，而中断处理函数把 `NEW_MESSAGE / WATERMARK / FULL` 当成同一件事处理 → **同一个事件会进好几次中断**，白白多花 CPU。这就是"中断源精简"的动机：只留

- `NEW_MESSAGE`（真正需要的事件）
- `MESSAGE_LOST`（丢帧诊断）

## 3. 为什么经典 CAN 的发送"用不上 DMA"（很常见的误解）

DMA 的工作模型是：**内存 ↔ 外设数据寄存器（DR）**逐字节搬运。UART、SPI 都是这种模型（数据必须一个个写进 DR），所以它们用 DMA 非常划算。

**FDCAN 不是 DR 模型**：数据放在消息 RAM 里，外设自己去读。CPU 只需要"写消息 RAM + 置请求位"，然后就没事了。

所以当有人说"把 CAN 发送改成 IT/DMA"时，落到 STM32 上真正的意思是：

> **用硬件 Tx FIFO/Queue 当缓冲区 + 发送完成中断做统计 + 调用处绝不阻塞。**

这三件事合起来，效果就等价于"发送不占 CPU"。

## 4. 我们原来的写法为什么把系统拖垮（真实数据）

改造前的代码（简化）：

```c
while (HAL_FDCAN_GetTxFifoFreeLevel(handle) == 0) {      /* 信箱满就一直等 */
    if (DWT_GetTimeline_ms() - start > timeout) {        /* 1ms 超时 */
        LOGWARNING("CAN MAILbox full! ...");
        return 0;
    }
}
HAL_FDCAN_AddMessageToTxFifoQ(handle, &conf, buf);
```

### 4.1 时间账

- CAN 1Mbps，一帧（8 字节数据 + 位填充）约 **130µs** 上线；
- 总线上**没有其他节点 → 没有 ACK → 这一帧失败**；只有失败之后，那个槽位才会释放（约 150µs）；
- motor 任务每 1ms 要发 **2~3 帧**（底盘一组、云台一组、摩擦轮/拨弹一组）；
- 一旦信箱被塞满，之后每次调用都要**等满 1ms 超时**才返回 → 一个 tick 白等 **2~3ms**（而 tick 只有 1ms）。

### 4.2 实测（30 秒窗口）

| 指标 | 数值 |
|---|---|
| CAN 发送段耗时 | **3068µs / 次**（占 DJIMotorControl 的 98.9%） |
| 真正的 PID 计算 | 34.2µs / 次 |
| 30 秒内发送次数 | 22698 次，**全部超时失败** |
| 自旋轮数 | 462 万轮 |
| 后果 | motor 任务只能跑到 250Hz（期望 1kHz），整机 58% CPU 被"等"吃掉 |

### 4.3 更糟的一层：BusOff 死循环

失败会让错误计数疯狂增长，很快把节点打进 **BusOff**（见第 7 节）。BusOff 之后外设**彻底停止发送** → 信箱永远不空 → 每次调用必然 1ms 超时 → 死循环自我放大。
同时每次超时都打一条 `LOGWARNING`，把只有 1KB 的 RTT 日志缓冲刷爆（日志格式化 + 写缓冲本身也吃 CPU）。

## 5. 改成非阻塞：具体写了什么

### 5.1 发送：满了就丢，绝不等待

```c
uint8_t CANTransmit(CANInstance *ins, float timeout /* 保留但不再使用 */)
{
    probe_start = DWT_ProbeStart();

    if (HAL_FDCAN_GetTxFifoFreeLevel(handle) == 0u) {   /* 信箱满 */
        stats->tx_drop++;                                /* 记一笔 */
        LogRateLimited(...);                             /* 限速打印, 不刷屏 */
        DWT_ProbeDone(&can_prof_tx, probe_start);
        return 0;                                        /* 立刻返回, 不等待 */
    }
    if (HAL_FDCAN_AddMessageToTxFifoQ(handle, &conf, buf) != HAL_OK) {
        stats->tx_error++;
        return 0;
    }
    stats->tx_ok++;
    return 1;
}
```

**为什么"丢一帧"比"等 1ms"好？**

- 丢一帧的后果：这个电机在接下来的 1ms 里继续执行上一帧的指令（电流/速度给定是连续的），几乎没有影响；下一周期会自动重发；
- 等 1ms 的后果：整个 motor 任务这一轮延迟 1~3ms，**所有**电机一起被拖慢，还能把更高层的控制节奏打乱；
- 一句话：**丢一帧是局部小损失，等待是全系统大损失。**

### 5.2 缓冲深度与发送完成统计

- TX FIFO 深度 4 → 16：突发时多给硬件一点缓冲；
- 打开 `FDCAN_IT_TX_FIFO_EMPTY`（队列清空）与 `FDCAN_IT_TX_COMPLETE`（单帧完成）中断，在回调里只做计数：

```c
void HAL_FDCAN_TxFifoEmptyCallback(FDCAN_HandleTypeDef *hfdcan) { bus->tx_complete++; }
void HAL_FDCAN_TxBufferCompleteCallback(FDCAN_HandleTypeDef *hfdcan, uint32_t indexes)
{ bus->tx_done += __builtin_popcount(indexes); }
```

**注意**：这两个回调在**中断上下文**执行——只允许加法、赋值这类操作。不能打印、不能调用可能阻塞的东西。

### 5.3 接收：中断源精简 + O(1) 查表派发

**问题一**：原来四个接收中断源全开，同一个事件进多次中断 → 只留 `NEW_MESSAGE | MESSAGE_LOST`。

**问题二**：原来每收到一帧，都要遍历所有已注册 CAN 实例，比对"句柄 + rx_id"才找到归属：

```c
for (i = 0; i < idx; ++i)                       /* 9 个实例就是 9 次比较 */
    if (handle == inst[i]->handle && id == inst[i]->rx_id) { ... }
```

每总线 5 个电机、1kHz 反馈 = 每秒 5000 帧 → 每秒 45000 次比较，全在中断里做。

**改法**：注册时建一张查找表，用"ID 的低 9 位"做下标：

```c
static CANInstance *rx_lookup[3][512];          /* [总线][rx_id & 0x1FF] */
...
CANInstance *ins = rx_lookup[bus][id & 0x1FF];
if (ins != NULL && ins->rx_id == id) { 回调(ins); }   /* 命中: 1 次索引 + 1 次校验 */
else { 回退线性查找 }                                  /* 极少数别名冲突才走这里 */
```

- 为什么不做成 2048（11 位完整 ID）的直表：`2048 × 4B × 3 总线 = 24KB`，RAM 太贵；
- 512 张 × 4B × 3 = 6KB，可以接受；低位相同的不同 ID（别名）用"完整 ID 再校验 + 回退线性查找"解决；
- 效果：常见路径从"9 次比较"变成"1 次索引 + 1 次比较"，且**不含循环分支**，更快更稳。

**问题三（顺带修的 bug）**：原来的 ISR 找到匹配实例后**直接 `return`**，FIFO 里剩下的帧这一轮就不处理了 → FIFO 很快满 → 开始丢帧（`MESSAGE_LOST`）。现在处理完一帧**继续排空 FIFO**，直到队列真的空。

## 6. 任务与 ISR 的分工原则（本工程约定）

| 工作 | 放在哪 | 理由 |
|---|---|---|
| 把帧从 RxFIFO 取走、拷进实例缓冲 | ISR | 必须尽快腾空 FIFO，否则丢帧 |
| 按 ID 找设备、调用解析回调 | ISR（但必须 O(1)） | 延迟敏感（控制用 1kHz 反馈） |
| 电机 PID、状态机、决策 | 任务 | 需要时间，放 ISR 会拖垮系统 |
| 日志打印、参数保存、BusOff 恢复 | 任务（低频） | 耗时、可能阻塞 |

### 6.1 IST8310 回调中的等待和失败处理（MC02-0121）

[ist8310.c](../../modules/ist8310/ist8310.c) 收到数据就绪引脚的中断后，调用 `IICAccessMem()` 读取6字节，在这个调用返回后直接执行 `IST8310Decode()`。底层当前使用阻塞式 HAL 访问，传入的超时参数为100ms；配置表中的 `work_mode` 不会让这条路径改为中断或 DMA 读取。HAL 超时还依赖毫秒计数推进，不能只凭这个参数保证中断中的等待一定按时结束。

`IICAccessMem()` 没有把 HAL 返回状态传给模块，因此读取失败后仍会解析当前缓冲区，三轴结果可能带有旧内容。6字节复制为三个 `int16_t`，再分别乘 `MAG_SEN=0.3`，得到 x/y/z 轴磁场，单位 µT（微特斯拉）；换算系数与 [iSentek 数据手册](https://isentek.com/userfiles/files/IST8310Datasheet_3DMagneticSensors.pdf) 的0.3µT/原始计数一致。当前实例没有采样时间或单独的数据有效标记，`ist_module_callback` 字段也未被此文件设置或调用。

[ist8310.h](../../modules/ist8310/ist8310.h) 的初始化行为按阶段区分：

| 位置 | 当前代码的动作 |
|---|---|
| 参数和实例分配 | 拒绝空配置；检查实例分配结果，分配成功后清零对象 |
| I²C 登记 | 先复制局部配置并登记；失败时释放实例并返回 `NULL`，不改写调用方配置，也不注册 GPIO 或访问设备 |
| GPIO、复位和读 ID | I²C 登记成功后改写三个 `id` 和两个回调字段；复位脚拉低、拉高后各等待50ms；读回 ID 不等于0x10时返回 `NULL`，此后续失败的资源回收仍未解决 |
| 写配置并读回 | 四项依次写入，每项读回同一配置寄存器；不符时反复打印该项编号，不返回错误码 |

I²C 地址在配置中填写未左移的0x0E，由底层登记函数左移。配置表在登记返回后可释放，HAL 句柄和登记对象需继续有效。配置表保留原有四项写值，实际工作模式和输出频率仍需在启用前核对。I²C 注册分配、重复拒绝及失败回退见 [BSPIIC-01 任务记录](../workflow/tickets/BSPIIC-01.md)。

本机测试直接调用生产 `IICRegister()`、`TFMiniRegister()` 和 `IST8310Init()`，只替换 HAL、GPIO、DWT 与日志。测试覆盖 I²C 注册失败回滚；IST8310 后续 ID/配置失败、GPIO 生命周期和读取状态仍不在本任务范围内，外设启用前还需继续处理，参见 MC02-0051。

### 6.2 接口说明里的完成、时间和地址（MC02-0123）

[bsp_can.h](../../bsp/can/bsp_can.h) 的发送返回 1 只表示写入硬件队列，空间满则立即返回 0，
旧的 `timeout` 参数已忽略。发送完成统计记录的是回调次数，一次通知可能包含多帧，不能直接等同于帧数。
当前回环自测默认使用外部回环，会发出测试帧，旧注释中的“不驱动总线”不能沿用。

UART、USB 都是中断复制数据、任务派发，超过 50 ms 的排队数据不再回调。
UART回调接收`USART_RxBlock_t`，USB仍使用`VCPGetCurrentRxData()`。
两种数据地址都只借用到回调返回，不能继续保存使用；时间取原接收通知时刻，不能用派发时刻代替。
USB 的初始化入口只设置回调和接收地址，不证明设备已经完成枚举。

[bsp_spi.h](../../bsp/spi/bsp_spi.h) 的三个收发入口共用总线占用和错误处理。阻塞模式最多等总线1000μs，再使用2ms的HAL传输超时；IT／DMA遇忙立即返回。异步数组须保留到查询确认已释放，错误通知本身不代表DMA已经停止，详见第13节。
I²C 寄存器访问仍按标记选择 8 位或 16 位地址，阻塞等待参数为 100 ms；传输状态没有通过接口返回，失败时也不会自动清接收数组。注册路径已检查配置、7位地址、模式、重复项、容量和分配结果；对象准备好后才发布，容量固定为 `MX_IIC_SLAVE_CNT=8`。GPIO 注册检查仍需后续核实。

### 6.3 I2C 注册失败为何不能留下半个设备（BSPIIC-01）

`IICRegister()` 接收调用方配置，但注册成功后实例由注册表长期持有。它先检查配置指针、HAL 句柄、未左移的7位地址（`0x00`～`0x7F`）和工作模式，再检查同一句柄与地址是否已登记以及8个设备槽位是否已满。回调和 `id` 可以为空；不同地址可共用句柄，不同句柄也可使用相同地址。

只有全部检查通过才申请一个 `IICInstance`。对象清零后复制配置并将地址左移一次；最后在短临界区内发布指针并增加计数。因而参数错误、重复、满表或内存分配失败均返回 `NULL`，不替换既有对象，也不占注册槽位。注册仅在启动阶段串行调用，成功对象不得由调用方释放；配置表可以在返回后释放，但 HAL 句柄必须保持有效。

TFmini 和 IST8310 先申请各自候选实例，再调用生产注册接口。注册失败时释放候选实例并立即返回；IST8310 使用局部 I²C 配置，所以失败不会改写传入配置，也不会继续等待或登记 GPIO。验证由独立主机进程执行：注入分配失败、重复地址和满表，统计分配/释放并检查地址转换、初始接收字段和回调路由。I²C 传输状态、GPIO 生命周期、IST8310 登记后的设备校验失败及 TFmini 接收长度问题仍由其他任务处理。

## 7. CAN 的错误状态机：TEC / REC / Error Passive / BusOff

### 7.1 两个计数器

- **TEC**（Transmit Error Counter）：发送错误计数
- **REC**（Receive Error Counter）：接收错误计数

粗略规则（够用版）：

- 发送失败（超时/错误帧）：TEC **+8**
- 发送成功：TEC **-1**
- 接收失败：REC +1；接收成功：REC -1（如果 REC > 127 则 -1 也要满足条件）

### 7.2 三个状态

| 状态 | 条件 | 行为 |
|---|---|---|
| Error Active | TEC、REC ≤ 127 | 正常收发，发现错误时发"主动错误帧" |
| Error Passive | 128 ≤ TEC 或 REC ≤ 255 | 仍能收发，但只能发"被动错误帧"（不打断总线） |
| **BusOff** | TEC > 255 | **停止收发**，从总线上"退出" |

### 7.3 BusOff 之后会发生什么

标准（ISO 11898）规定：节点进入 BusOff 后，要**监听 128 次"11 个连续隐性位"**才允许重新上线（防止一个坏节点一直干扰总线）。
STM32 的实现里，如果 `CCCR.INIT` 被置位（比如协议异常、或软件 `HAL_FDCAN_Stop()`），节点会**停在初始化状态**，必须由软件把它拉回来。

**我们板子的真实情况**：空总线上每帧都失败 → 30 多次失败就 BusOff → 而固件里**根本没有恢复代码** → CAN 永久死掉（LCD 第 4 页那两个 `OFF` 就是这么来的）。

### 7.4 我们的恢复策略

在 100Hz 的 daemon 任务里挂一个 10Hz 的健康检查：

```c
void CANHealthMonitor(void)
{
    for (每个总线) {
        HAL_FDCAN_GetProtocolStatus(h, &ps);
        if (ps.BusOff) {
            bus->busoff++;                        /* 计数 */
            HAL_FDCAN_Stop(h);                    /* 置 CCCR.INIT, 复位错误状态 */
            HAL_FDCAN_Start(h);                   /* 清 INIT, 重新上线 */
            重新使能接收中断;                       /* Stop 之后中断使能可能丢失 */
            bus->busoff_recover++;
            限速打印;
        }
    }
}
```

- 为什么放 10Hz 任务：恢复动作要动好几个寄存器，放 ISR 不合适；10Hz 足够快，也不会自己造成抖动；
- 为什么要计数：BusOff 频繁发生本身就是"总线有问题"的信号（终端电阻、地线、波特率、线缆）；
- 为什么限速打印：BusOff 可能每 100ms 一次，不限速日志会把 CPU 和 RTT 缓冲吃光（我们已经吃过这个亏）。

### 7.5 AutoRetransmission（自动重传）的取舍

| 设置 | 行为 | 适合 |
|---|---|---|
| **开** | 一帧没 ACK 会由硬件一直重发，直到成功或 BusOff | 点对点可靠链路 |
| **关（我们用）** | 失败一次就放弃，下一周期由软件自然重发 | 多节点控制总线：**不会让一个失败帧把 FIFO 占死** |

我们原来的灾难 = **自动重传关闭 + 软件又自己自旋等待超时**：硬件不重传，软件却死等，两头都不对。现在硬件不重传（保持）、软件也不等（改成丢帧计数），才是自洽的组合。

### 8.1 本机那台 USB-CAN 适配器的实测结论（2026-09）

- **它不是 slcan/CANable**：对 `\r`、`C\r`、`S8\r`、`O\r` 等 ASCII 命令零响应，而是持续输出**私有二进制协议**；
  帧长 16 字节、同步字 `55 AA`，实测格式（由观测推断）：

  ```
  55 AA | 11 08 | ID_L ID_H | DATA0..7 | xx xx
  ```

- 因此 **python-can 不能直接驱动它**（python-can 支持 pcan/kvaser/slcan/canalystii/… 但都要求厂商规定的协议或 DLL）。
- 但它**能当"只听"的监视器用**：`tools/usbcan_serial_monitor.py` 就是按上面的格式解帧的，
  实测能看到 MCU 发出的 `0x200` 帧（约 1.2~2.2k 帧/s）；**把 MCU 暂停后数据流几乎归零**，
  这条实验反过来证明了"它报的就是总线上的真实帧、且波特率/接线都是对的"。
- 它**不回 ACK**：MCU 侧 TEC 一直涨到 200+（接近 BusOff），说明它要么处于"通道未打开/静默"状态，
  要么就是纯监听设计。要让它参与收发（ACK、发帧），需要厂商上位机/协议文档里的"打开通道"命令。
  这也说明：**用一台不回 ACK 的适配器做验证时，"发送失败/BusOff"不一定是 MCU 的问题。**

## 11. UART的块和协议帧要分开（BSPUART-03U1）

UART空闲或DMA接收完成时，HAL通知了一段字节。这段字节可能是半帧，也可能含两帧。`recv_buff_size`只是接收容量；业务不能据此假定完整协议帧已经到齐。新[接收描述符](../../bsp/usart/usart_rx.h)把只读地址、实际长度、原通知毫秒值和连续性编号一起交给`callback(context, block)`。

DMA一直复用实例中的数组。中断先复制到队列，任务直接读队列槽，直到业务回调返回才释放槽。即使回调期间又发生接收，新DMA字节也不会盖掉正在解析的数据。业务要留下半帧时，把所需字节复制进自己的固定数组，同时保存来源时间，不能保存block或data地址。

每路四个槽实际可放三块，满时丢新块。编号在通知、丢块、错误和显式重启时都会前进；相邻编号不连续，协议就清残帧。正常重装DMA不额外推进编号，因此可以拼接正常分段。编号从UINT32_MAX回到0仍然连续。

派发入口记录各路当时的末位置，每路最多三块；回调期间新到的块留给下一轮。这个数量限制让单次工作范围清楚，但不保证1ms以内完成。板上物理耗时仍要实测。

[队列回归](../../tests/host/usart_snapshot_test.c)在解析时模拟DMA写入、再次入队和递归派发，检查当前数据未变、新数据下一轮处理。它还验证启动尚未返回就发生中断，以及启动失败、中止也失败时不会释放硬件可能仍在用的内存。[完整证据](../workflow/tickets/BSPUART-03U1.md)只涉及本机软件。

## 12. LK 电机注册与跨总线组帧（MOTOR-04/05）

LK 的 `can_init_config.tx_id` 在 `LKMotorInit()` 入参中表示电机编号 **1～4**。驱动将反馈 ID 设置为 `0x140 + 编号`，把真正发送 ID 和 HAL 帧头都设为 `0x280`；编号另外保存在电机实例里，所以它不会再被拿来计算 CAN ID 与帧偏移。每条物理总线最多四个 LK 实例，三条 H723 总线合计最多十二个。相同编号可以出现在不同总线上，同一总线的重复编号会在资源申请前拒绝。

注册顺序也决定了资源清理是否可靠。PID 配置先在局部候选中检查；正式实例创建后，再按 LK 对象、Daemon、CAN 的顺序准备资源。Daemon 失败释放 LK 对象；CAN 失败先从 Daemon 表移除回调，再释放 LK 对象。CAN 是最后一个可能失败的资源步骤，全部成功后才把实例加入总线编号槽并选为该组发送对象。

控制任务每轮先清零三条总线的候选帧，再逐个计算已注册电机。编号决定固定的两个字节，输出以小端顺序写入；未注册的槽、停止电机和计算失败项自然保持零。浮点结果经过方向处理后若无法表示为有符号16位命令，也按数值失败清除 PID 历史并置零，不做饱和猜测。随后每条已注册总线各提交一帧，FIFO 忙或 HAL 报错只影响该总线的本轮提交；失败帧不排队，下一次会重新计算。CAN 统计中的 `tx_ok` 表示成功放入本机 FIFO，不能解释成对端已经收到。

[LK 驱动说明](../../modules/motor/LKmotor/LK_motor.md)列出编号、反馈 ID、帧位置、初始化限制和仍未处理的闭环问题。主机测试以不同编号注册到不同 CAN 句柄，检查三个槽位的帧结果和有符号16位边界；另有集成目标链接真实 `LK9025.c`、`daemon.c` 与 `bsp/can/bsp_can.c`，只替换 HAL、时间和日志，注入滤波注册失败、FIFO 忙和 HAL 错误。没有连接电机或开发板，测试结论限于软件资源及帧路由。

## 13. SPI 超时后，为什么不能立即交给下一个设备（BSPSPI-03）

SPI上的多个设备共用时钟和数据线，通过各自的片选区分。设备A正在接收时，设备B必须等A结束或收到忙状态，不能先拉低自己的片选。原先只有`SPITransRecv()`登记总线使用者，`SPITransmit()`和`SPIRecv()`也能直接启动HAL，两套规则会互相覆盖。现在三个入口共用同一流程：检查配置，取得总线，取得HAL计时使用许可，再记录数组并拉低片选。

注册表的容量是SPI1、SPI2合计4个设备。配置表可在注册返回后释放，实例、HAL句柄和数组则有不同的使用期限。注册对象由模块持有，调用方不能直接改模式或释放；`SPISetMode()`只允许空闲时修改，`SPIUnregister()`会拒绝仍在传输、回调、恢复或隔离的总线。

| 情况 | 本次行为 | 数组何时可复用 |
|---|---|---|
| 请求在启动HAL前被拒绝 | 不动旧片选和接收字段 | 新请求没有借出数组 |
| 阻塞传输 | 最多等总线1000μs，HAL等待参数2ms；等待他人到期不会取消他人 | 函数返回后；失败接收字节不能使用 |
| IT／DMA已接受 | 保留占用，返回HAL_OK | 查询`buffers_released=1`后 |
| 收到错误或已到期限 | 不发布接收数据，等任务停止HAL／DMA | 停止确认且查询已释放后 |
| 停止失败 | 保留占用及计时许可，其他设备不能复用本总线 | 系统重新初始化前不可复用异步数组 |

异步`HAL_OK`只表示启动被接受。接收和全双工成功完成时才调用一次接收回调，纯发送不会调用它。回调前片选拉高，但总线一直占用到用户回调返回，这样回调读到的`rx_buffer`、`rx_size`不会被下一份请求盖掉。回调通常位于中断；若完成比HAL提交函数返回还早，则延后到提交函数中交付，所以业务不能依赖它只会在中断中执行。无论在哪执行，都不能在回调里等待、再次提交同总线或注销实例。

`async_timeout_ms=0`使用20ms默认值，也可配置1～`INT32_MAX`毫秒。现有Daemon任务约每10ms调用`SPIProcessTimeouts()`。当经过时间大于或等于期限，便标记超时；即使完成回调先于下一次检查到达，也不会把过期数据当成功。时间用HAL毫秒值，无符号相减处理一次回绕。计时许可在异步期间一直保留，避免HAL tick暂停让期限不再推进。

错误中断只标记失败，不在中断里执行阻塞停止。任务先调用`HAL_SPI_Abort()`，再检查SPI状态、使能／DMA请求／中断位及本次DMA stream，清理相关标志与待处理中断后才释放。HAL返回成功或者状态写成READY，都不能单独证明DMA已经停止。若仍无法确认，就保持隔离，不反复停止，也不自动接收新请求。10ms检查间隔还要加上任务调度和HAL停止耗时，不能将20ms配置解释为物理停止时间保证。

HAL的完成通知没有事务编号。当前实现会拒绝空闲期、传输类型不符和恢复期间的回调；新事务安全复用依靠旧硬件已停止及中断已清理，不能声称任意旧通知都能靠软件编号识别。

当前BMI088仍在SPI2使用阻塞收发；LCD在SPI1直接使用HAL。两条总线分别使用，没有把LCD迁入本封装，也没有启用BMI088异步采样。仅设置`SPI_DMA_MODE`不代表外设、中断和DMA已配置；入口会检查必要条件，真实引脚、IRQ处理函数和缓存一致性仍需启用硬件前核对。

[生产接口测试](../../tests/host/bsp_spi_status_test.c)用HAL寄存器模型验证三种操作、三种模式、起始失败、回调抢先到达、期限边界、回绕和停止失败；WSL额外用真实线程竞争同一总线、交错超时和完成。[任务记录](../workflow/tickets/BSPSPI-03.md)保存本机证据。本轮没有开发板，未验证SPI波形、实际DMA停止时序或物理耗时。

## 14. UART先复制，再由专用任务发送（MC02-0061）

DMA发送时借用的数组必须一直存在。以前调用者可能修改在途数组；现在由[`USARTSubmitTx()`](../../bsp/usart/bsp_usart.h)把完整报文复制到每路固定存储。每路最多4条，**包含排队、在途和等待通知的报文**；每条1～128字节，数据32字节对齐，普通`.bss`由当前链接脚本放在DMA可访问的AXI RAM。TX四条都能使用，与本篇第11节RX四槽可用三槽的环形实现不同。

```c
// 该回调由发送任务调用，context若非NULL必须一直保留到通知结束。
static void Sent(void *context, const USARTTxEvent_t *event)
{
    (void)context;
    // 按event->id记录结果；event只在本次回调期间可读，不等待对端。
    (void)event;
}

static USARTSendStatus_t Submit(USARTInstance *uart)
{
    uint8_t bytes[] = {0x11, 0x22};
    USARTTxRequest_t request = {
        .data = bytes, .length = sizeof(bytes), .mode = USART_TRANSFER_DMA,
        .timeout_ms = 50u, .complete = Sent
    };
    uint32_t id;
    return USARTSubmitTx(uart, &request, &id);
    // ACCEPTED时bytes可以立即复用；拒绝不会产生通知，也不会写id。
}
```

先完成HAL、DMA和中断配置，注册UART，再在调度器启动前调用`USARTTxTaskInit()`。专用任务为Normal优先级、512个`StackType_t`，约1ms执行一轮，并纳入30ms任务监控。创建失败保留接收注册，但不接受发送。普通业务只提交、取消和查询；禁止直接HAL发送混用，也不自行调用发送推进入口。关中断或中断上下文会被拒绝。

成功提交返回非零编号。总期限从入队时开始，1～`INT32_MAX`毫秒，**达到期限就过期**；它与裁判接收组“边界仍新鲜”的规则不同。排队及恢复期间保留HAL tick使用许可，避免计时暂停。视觉默认20ms、裁判100ms、舵机和HC05各50ms。HAL_BUSY且尚未启动时继续排队；启动报错、在途报错或超时后本条结束，已经开始的报文不会自动重发。

DMA搬完只说明内存搬运结束，UART的TC通知才说明本机这次发送完成。ISR仅登记结果，专用任务按提交顺序回调一次，再收回名额。回调可以非阻塞提交新报文，但必须短小，不能等待。每轮每路最多通知一条、启动一次，全局最多停止一路；停止路由轮转，其他串口照常推进。任务调度和HAL停止仍有耗时，1ms轮询不构成物理时限保证。

取消排队帧不会启动硬件；取消在途帧先停止TX和对应DMA，已经送出的字节无法收回。普通TX超时不会主动停止RX。确认停止、清完发送标志后才复用内部数组；若无法确认，隔离该路并保留仍可能被DMA访问的数组和计时许可，拒绝新提交，等待系统重新初始化。共享UART的接收中断pending位不被整体清除。HAL错误可能提前清DMAT，因此停止还会检查TX DMA，必要时单独停止它，不能只凭UART状态READY就释放。

`USARTGetTxState()`只复制统计与最近通知，不推进队列。HAL回调没有事务编号，安全复用依靠停止和清理完成；软件编号不能识别任意伪造的旧硬件通知。当前工程未启用DCache；将来启用缓存时，需要重新核对DMA数组的清理策略。

四类调用方都提交局部帧：备用UART视觉、裁判、总线舵机和HC05；默认USB视觉路径未改。HC05只接受4字节内容，仍编码6字节；总线舵机仍保留16字节旧命令及固定设备编号，不代表注册和设备协议问题已解决。各调用方记录最近完成结果和失败计数；HC05及舵机通过复制查询读取，视觉合入`VisionGetStatus()`，裁判用`RefereeGetTxState()`读取本路统计。

[`uart_tx_backend_test.c`](../../tests/host/uart_tx_backend_test.c)直接运行生产H723后端，HAL／寄存器由模型替代；[`uart_tx_callers_test.c`](../../tests/host/uart_tx_callers_test.c)核对四字节HC05内容、舵机固定命令和43字节SP帧。测试区分DMA完成与UART完成，验证取消、计时回绕、停止失败、线程交错及运行期不分配。实际串口波形、DMA物理停止和吞吐没有实测，证据见[任务记录](../workflow/tickets/MC02-0061.md)。


## 15. 队列有空位，为什么仍要等待（REF-03）

四条UART复制队列解决了数组归属，但裁判协议还限制发送频率和目标接收字节数。现在UI和机器人交互都经过[`RefereeSubmit()`](../../modules/referee/referee_tx.h)：发送者来自新鲜机器人状态，内容、接收者和长度检查后统一组帧、计算真实CRC，再复制到原UART队列。成功入队才递增线上序号；不再开放原始帧提交或可写`UI_Seq`。

队列严格按成功入队顺序处理。发送任务在启动前调用注册时固定的检查：允许就尝试HAL，暂缓就保留队首、内容和最初期限，拒绝就取消本条。后面的短帧不能越过暂缓的长帧。本次没有添加第二份帧队列或新任务，最多四条仍包含在途和待通知项。

所有`0x0301`共用至少34ms启动间隔，保守满足合计30Hz；机器人目标还按滚动1000ms累计完整帧字节。普通机器人上限3720字节，哨兵／雷达5120字节，记录年龄恰好1000ms时不再计入。这个计数只覆盖本机发送，不能知道其他机器占用了目标多少接收额度。

举例：29帧满长127字节合计3683字节。第30帧将达到3810字节，超出普通机器人额度；即使34ms已经满足，也必须等待最早的记录满1000ms。换目标可以使用另一份字节额度，但仍共用34ms。改变本机身份和重新初始化UI都不会清空这些历史。

计费依据实际启动时间；已开始后出错不会退回额度。HAL启动报错也按整帧保守计费。确认尚未启动的取消或超期不计费。完成观察先于请求回调，且在下一条启动前完成，因此旧帧的额度不会被下一条绕过。固定30条时间记录足以覆盖34ms间隔下的1000ms窗口，检查不分配内存。

[`RefereeGetTxState()`](../../modules/referee/referee_tx.h)复制UART容量、累计事件及最近限流原因；它不推进发送。UI仍保留115ms实际启动节奏和100ms总期限。限流计入期限，尚未启动即超期的UI帧保留刷新标记和初始化步骤，下轮用最新内容再尝试；启动错误、已经开始后的错误／超时或串口隔离仍需显式重新初始化。

[`referee_budget_test.c`](../../tests/host/referee_budget_test.c)运行真实CRC、裁判解析、UI、UART队列与H723后端模型，覆盖FIFO、窗口边界、身份切换、超期、隔离及线程提交。专用[`采集工具`](../../tools/referee_budget_capture.py)保存完整线上字节和MCU只读记录；PC到达时间不作为线端精确时序。具体软件与裸板证据分开记录在[REF-03](../workflow/tickets/REF-03.md)。
