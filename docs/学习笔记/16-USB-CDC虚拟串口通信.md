# 16 USB CDC 虚拟串口通信（写给零基础）

本文说明 MC-02 的 USB 接收、发送和重新连接。先认识主机、端点和 CDC，再读生产接口。MC02-0062 的实施与验收依据集中在[任务记录](../workflow/tickets/MC02-0062.md)；文中介绍代码规则，不能据此认定板上验收已经完成。

主要入口：[usb_transport.h](../../bsp/usb/usb_transport.h)、[传输核心](../../bsp/usb/usb_transport.c)、[H723后端](../../bsp/usb/usb_transport_port_stm32.c)、[CDC回调](../../USB_DEVICE/App/usbd_cdc_if.c)和[SP解析](../../modules/master_machine/vision_protocol.c)。调用方先初始化，再由普通任务推进；中断不运行协议解析或用户完成回调。

## 1. USB 和物理串口的本质区别

UART 两端各自按约定波特率发送。USB 则由电脑这个主机安排传输，MC-02 作为设备准备数据和接收存储。电脑不读取 IN 端点时，设备准备好发送也不一定能完成。

端点表示设备上的传输通道。IN 方向是板到电脑，OUT 是电脑到板。当前工程使用 USB OTG HS 控制器的内置 PHY，实际配置为 Full Speed，且未启用 USB DMA；名字中的 HS 不表示当前以 High Speed 运行。

单个 USB 包、一次 CDC 接收回调和一份 SP 业务帧是不同概念。电脑一次写入29字节，不能据此要求每次回调恰好29字节。解析器必须接受跨块、同块多帧和噪声。

## 2. CDC 是怎么把 USB 变成串口的

CDC ACM 描述让操作系统把设备呈现为 COM 或 ttyACM。程序仍可以通过串口库打开端口、读写字节，但实际传输由 USB 端点完成。

本工程没有把 CDC 的波特率转换成 UART 时钟，也不以 DTR、端口打开或枚举成功授予控制许可。是否能使用命令，还取决于新鲜合法业务帧及当前 safety 许可。USB 承担上下位机业务；诊断目前使用类型化日志、RTT及只读记录，独立诊断 UART 由 MC02-0004 跟踪。

## 3. 接收：为什么要“重新武装”

设备先把数组交给 OUT 端点。收到数据后，回调取得实际字节数；要继续接收，必须重新设置接收数组并调用 `USBD_CDC_ReceivePacket()`。

生产回调先调用 `USBTransportOnReceive()` 复制数据，然后重新武装。端点数组可能马上被下一包覆盖，因此队列不能只保存端点指针。重新武装失败也要登记错误，交由任务处理。

接收队列固定8项，每项最多128字节。超长块整块拒绝，队列满也丢弃新块并计数；这些丢弃仍推进连续性编号，后面的解析器才能发现中间缺了数据。长度在检查前保留原宽度，不先转成较小整数。

## 4. 为什么回调里不能久留

中断负责复制和登记事件，`USBTransportProcessRx()` 负责普通任务中的派发。它每轮最多处理4块，每块最多128字节，不使用“只要还有输入就一直循环”的处理方式。

回调得到 `USBRxBlock_t`：只读数据、字节数、原接收毫秒值、连续性编号和连接代号。回调返回后不能继续保存数据指针。原时间允许为0，不能用“时间非零”判断是否收到过数据。

USB 与备用 UART 共用 `VisionProtocolStreamFeed()`。它保存最多29字节的候选，同时保存每个字节属于哪一次原接收时间；CRC正确后按顺序交付全部完整帧。50ms边界允许；来源过期、组帧过期、缺块或连接代号变化时放弃旧候选。

例如一帧在0ms收到前10字节，在20ms收到剩余19字节，帧的来源时间仍为0ms。若任务到51ms才处理，不能以20ms或51ms让它重新变得有效。

## 5. 发送：`USBD_BUSY` 是怎么回事

公开提交入口为 `USBTransportSubmit()`，使用自有返回状态。`USB_ACCEPTED` 表示复制内容并被本机接受；它不等于电脑应用已经读取或执行。

```c
uint32_t id;
USBStatus_t status = USBTransportSubmit(bytes, length, &id);
// 成功后可复用bytes；真正完成由初始化时登记的回调通知。
// 忙时不保存等待项，下一周期重新组装最新状态。
```

一份报文最多128字节，只保留一份在途内容。提交成功后原数据可以是已经准备好的局部数组；真正需要长期保存的发送数组由模块自己管理。忙时不复制、不覆盖在途内容、不修改编号输出。

从接受起达到100ms仍未完成即超时。接收完成中断和发送完成中断不同，只有 CDC 的真实发送完成入口登记完成。用户回调在普通任务执行一次，不能等待。

启动时报错也不能假定硬件从未取得数组。若不能证明未启动，模块保留数组直到确认停止；这次提交没有被接受，不给它编号，也不发送完成通知。

## 6. VCP 与物理串口的取舍（为什么视觉选 VCP）

板载 USB 可以直接接电脑，不额外占用 UART 及电平转换器。备用 UART 仍可通过构建配置选择，两种传输保持相同 SP 字节格式。

不能根据接口名称或理论带宽推断实际延迟。主机调度、读取速度、操作系统缓冲和解析周期都会影响结果；本轮没有给出物理吞吐或线端延迟保证。

USB 暂停、复位、取消配置和重新连接会让旧连接代号失效。消费者据此撤销旧命令，重新连接后等待首份新鲜合法命令，不用旧数据自动恢复控制。当前没有启用 VBUS 检测，拔线不能只依靠一个断连回调识别，业务的50ms来源检查仍然必要。

## 8. 三次恢复额度与60秒正常通信（MC02-0062）

已接受的发送到100ms仍未完成，或出现明确传输错误时，任务可重建整个 USB。先撤销旧命令、停止并核对清理结果，再保持软断开至少250ms并启动设备；等待主机配置最多5秒，两次重建尝试至少相隔1秒。等待跨多轮任务执行，不在控制任务内等待主机。

最多连续尝试3次，开始重建就消耗一次。重新枚举不清次数。只有连续60秒命令年龄不超过50ms、发送完成持续推进、且没有错误或连接中断，才补满额度；仅有新接收或仅有发送完成都不够。

额度耗尽后不再主动重启。后端仍可响应主机时，主机重新配置可恢复通信，但次数保留。无法确认停止的硬件故障则保持隔离，保留仍可能被外设借用的数组，等待系统重新初始化。USB恢复失败不进入整板 `Error_Handler()`。

实际停止和枚举依赖后端及主机。主机模型验证状态变化、归属与次数规则；裸板测试另外验证实际重新枚举和通信恢复。已有[CDC练习](../课程/自瞄链路/exercises/02-usb-cdc/solution/main.cpp)帮助理解异步缓冲，它不替代生产回归或设备实测。

裸板采集入口为 [`tools/usb_lifecycle_capture.py`](../../tools/usb_lifecycle_capture.py)。它先调用只读快照工具核对板上身份与所选 ELF 的 Build ID，再打开指定 CDC 端口；身份或布局校验失败时不会发送。采集过程中仅发送 mode=0 的六浮点零值帧，并保存原始字节、解析后的状态和主机侧错误。主机侧时间不代表线端时序，也不代替烧录前整片 Flash 备份及参数区回读。

Windows串口采集要保留一个短时读请求。零超时读取会立即返回；这次MC02-0062回归中，零超时工具写入成功却没有收到状态字节。将读取超时设为20ms后，主机能持续请求IN端点并收到状态帧。若固件重建让COM句柄失效，工具在10秒内按USB序列号重新打开同一块板；失败的写操作只记错误，不把可能只发出一部分的帧再次提交。

USB-only诊断回归中，挂起读取配合SWD复位后的有限重枚举采集得到1001个CRC正确、数值有限的状态帧。具名固件随后按计划抑制4次完成通知、执行3次重建并进入等待主机重新配置；60秒窗口后保持运行，但普通COM重开没有恢复已耗尽状态。这个结果验证了本次有限故障注入和主机读请求，不能替代耗尽后由主机发送重新配置请求，也不能代替USB数据线断开时保持板供电的测试。

后续在没有限流主电源时，测试保持USB-only，不连接TB47S也不拔USB。恢复普通`bench-debug`前先只读备份整片Flash和参数区；烧录日志确认ELF编程、verify和复位成功，回读参数区与烧录前逐字节一致。普通固件的Build ID匹配，目标在60秒只读窗口内持续运行且没有看门狗复位。COM14重新出现后，重新打开端口并发送33份固定中性帧仍未收到状态字节；后续只读快照显示33块均被接收路径丢弃、没有一块进入队列，USB状态仍为`exhausted`、重建额度3/3。生产接收入口只在`READY`入队，因此串口重新打开不能代替链路配置恢复。由于板子仅由USB供电，本轮没有通过禁用设备或拔线制造总线重枚举。WSL USB专项在Debug和Release各25/25通过，但真实主机重新配置和双向恢复仍待安全的供电／总线测试条件，MC02-0062继续开放。详见[本轮实施记录](../workflow/tickets/MC02-0062.md#2026-10-24-usb-only-下恢复普通固件与被动观察)。
