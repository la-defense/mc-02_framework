# 04 IDLE 余量是什么，它体现了哪种设计方式（写给零基础）

## 0. 一句话总结

**IDLE 余量 = 单片机的"空闲时间占比" = 这套系统还能承受多少新负载的度量。**
在 RTOS 里，它是"当所有正经任务都没事干时，CPU 在跑的那个最低优先级任务（IDLE 任务）所占的时间比例"。
它不只是个数字，而是一种**设计方式**：把 CPU 时间当成稀缺资源，按优先级分配，并且永远留出余量。

本工程实测过的两个极端，正好说明它的意义：

| 状态 | IDLE 余量 | 结果 |
|---|---|---|
| CAN 自旋等待（改造前） | **148‰（14.8%）** | LCD 任务被"饿死"到 0.5‰，屏幕冻结不刷新；控制任务也只剩勉强够用 |
| CAN 非阻塞（改造后） | **509‰（50.9%）** | 同样的功能，多出一半 CPU 余量 |

## 1. 先看一个生活化的类比

想象一家餐厅：

- **顾客** = 需要 CPU 的任务（电机控制、姿态解算、LCD 刷新……）
- **服务员** = CPU（480MHz 的 H723，一秒钟能"服务"4.8 亿个时钟周期）
- **IDLE 余量** = 服务员"站在那儿没事干"的时间占比

如果服务员 99% 的时间都在忙，会发生什么？

1. 来了一个临时需求（比如裁判系统发来一大包数据、USB 插入事件），**没人手** → 只能等 → 响应变慢（实时性变差）；
2. 某个顾客点菜比平时慢一点（某个任务偶发慢 2ms），整条队伍立刻堵住 → 连锁延迟；
3. 只要再加一个菜（新功能），就直接崩盘（任务错过截止时间）。

所以 IDLE 余量不是为了"好看"，而是**衡量系统还有没有抗风险能力**。

## 2. 什么是 IDLE 任务（RTOS 的基础设施）

### 2.1 调度器的硬性要求

RTOS 的调度器本质上在一遍遍问："现在哪个任务可以跑？"

如果**所有**任务都在等待（等待延时、等待信号量、等待消息），那 CPU 该干什么？总不能停在哪里不管——中断还得响应、时间必须继续走。于是每个 RTOS 都必须提供一个**永远可以运行**的任务：

> **IDLE 任务：优先级 0（最低），永远处于"就绪"状态，没事干时它就无限循环。**

在 FreeRTOS 里它是 `prvIdleTask`，启动调度器时自动创建。它的循环大致是：

```c
for (;;) {
    /* 1. 释放被 vTaskDelete() 删掉的任务残留的内存(TCB/栈) */
    /* 2. 如果启用了低功耗(tickless)，判断能不能把心跳停下来省电 */
    /* 3. 如果用户注册了 vApplicationIdleHook()，在这里执行 */
}
```

注意两点，新手最容易误解：

1. **IDLE 不是"什么都不做"**：它负责回收被删除任务的资源（这也是为什么 `vTaskDelete` 之后不能立刻释放自己的栈内存，要等 IDLE 来收）。
2. **IDLE 任务永远不能阻塞**：如果 IDLE 也被阻塞（比如调用了 `vTaskDelay`、等互斥锁），系统就会出现"没有任务可运行"的致命错误（FreeRTOS 会直接报错卡死）。

### 2.2 优先级与"填充"关系

在抢占式调度里，CPU 永远是"当前优先级最高的就绪任务"在跑。于是：

```
CPU 时间轴（示意）

 电机控制(1kHz) ██  ██  ██  ██  ██  ██        ← 高优先级，需要就跑，随时抢占
 姿态解算(1kHz)   ███   ███   ███   ███       ← 次高
 决策/命令(200Hz)        ██          ██        ← 更低
 LCD 刷新(低优先级)              █            ← 最低，只能用"别人都不要的时间"
 IDLE            ░░░░░░░░░░░░░░░░░░░░░░░░    ← 所有任务都没事干时才跑
```

**关键推论**：

- 高优先级任务**不会**被低优先级任务拖慢（低优先级任务随时被打断）；
- 反过来，**低优先级任务只能捡剩下的时间**——所以"IDLE 变少"最先受害的往往是低优先级任务，而不是控制任务。
  这正是本工程 LCD 屏幕被"饿死"的原因（它是最低优先级的 `lcdtask`）。

## 3. 怎么量出"IDLE 余量"

### 3.1 原理：让 RTOS 记账

FreeRTOS 提供"运行时间统计"：每次**任务切换**时，它读一次"当前计时器"的值，把"从上次切进来到现在"的这段时间，累加到被切出去的任务头上：

```c
/* 伪代码, 见 tasks.c */
pxCurrentTCB->ulRunTimeCounter += ( 现在的时间 - 上次切进来的时间 );
```

于是每个任务都有一个"累计占用 CPU 时间"的账本。IDLE 任务的账本除以"总时间"，就是 IDLE 余量。

前提：你必须给 RTOS 一个**高精度、会一直走的计数器**。本工程用的是 Cortex-M7 自带的 DWT 周期计数器（480MHz，精度 2.08ns）：

```c
__weak unsigned long getRunTimeCounterValue(void)
{
    return (unsigned long)(DWT->CYCCNT / 1000u);   /* 单位≈2us */
}
```

### 3.2 三个新手必踩的坑（本工程都踩过）

| 坑 | 现象 | 原因与修法 |
|---|---|---|
| 计时回调是空实现 | 所有任务占用率恒为 0 | 工程模板里 `getRunTimeCounterValue()` 是 `return 0` 的弱符号。本工程的 **CORE-05** 就是这样：宏开了、数据全是 0。修法：接 DWT |
| 计数器回绕 | 隔几十秒读两次，算出的增量是错的 | 32bit 周期计数器 480MHz 下 **8.94s 就回绕**；把它除以 1000 变成"约 2µs 单位"后，累计值 4295s 才回绕，跨分钟比较才安全 |
| 任务顺序会变 | 某次测量某个任务突然占 99% | `uxTaskGetSystemState()` 返回的任务顺序不保证稳定；**必须按任务名配对**再求差，不能按下标。本工程工具 `tools/probe_snapshot.py` 为此专门修过一次 |

### 3.3 一个重要细节：中断时间算在谁头上

ISR（中断服务函数）没有自己的"任务身份"，它抢的是"当时正在跑的那个任务"，所以**ISR 的耗时被记到被中断的任务名下**。

含义：

- 如果 IDLE 正在跑时被中断，那段时间会计到 IDLE 头上 → 所以 **IDLE 占比是"空闲"的上界**（真实空闲可能略少）；
- 如果电机任务正在跑时被 CAN 接收中断打断，那段时间算电机任务 → 所以"电机任务占了 48%"不一定是它自己在算，可能是"它运行期间中断很多"。

想拆清楚，就必须给 ISR 单独加计时（本工程的做法：在 CAN 接收派发和发送路径上加 DWT 探针）。

## 4. 怎么解读这个数字（经验区间）

以下经验值针对"机器人主控"这类每 1ms 都要干活、且随时可能有突发中断的系统：

| IDLE 余量 | 含义 | 该怎么办 |
|---|---|---|
| **> 50%** | 宽裕，能再加 1~2 个中等负载功能 | 保持，别浪费 |
| 30% ~ 50% | 正常但不算多 | 加功能前先评估；关键路径不要新增轮询 |
| 15% ~ 30% | 偏紧 | 先把已有的浪费（阻塞等待、无用轮询）清掉 |
| 5% ~ 15% | 危险区：突发（日志、总线错误、USB）就可能顶不住 | 必须优化，别再叠加功能 |
| < 5% | 已经饱和：低优先级任务会被饿死、抖动明显 | 立刻处理，否则隐藏的时序 bug 都会冒出来 |

补充两条：

1. **平均值不等于最坏值**。平均 IDLE 30%，但如果每 10ms 就有一次 3ms 的突发阻塞，控制抖照样会有问题。工程上更关心"最坏执行时间（WCET）+ 峰值负载"。
2. **IDLE 余量高，不代表不会被偶发事件拖垮**：要看"谁在什么时候突然要很多时间"。

## 5. 它体现了哪些设计方式

### 5.1 分层优先级 + "用最低优先级任务填充空闲"

设计的核心：**把实时性要求高的放在高优先级，把"晚一点也没关系"的放到最低优先级**，让它们自动使用空闲时间。本工程的分层：

| 任务 | 优先级 | 频率 | 实时性要求 |
|---|---|---|---|
| instask（姿态解算） | AboveNormal | ~1kHz | 最高：姿态晚了，控制就抖 |
| motortask（电机控制） | Normal | ~1kHz | 高：直接决定手感 |
| robottask（决策/命令） | Normal | 200Hz | 中 |
| daemontask（监控/蜂鸣器） | Normal | 100Hz | 低 |
| uitask（裁判 UI） | Normal | 不定 | 低 |
| **lcdtask（仪表盘）** | **Low** | 5Hz | 最低：晚一点无感 |
| IDLE | 0 | — | 兜底 |

**这就是为什么 LCD 慢一点不会影响控制**，也是为什么"给 LCD 加功能"风险很低——但前提是 IDLE 还有余量，否则它会最先被饿死（屏幕卡住不动）。

### 5.2 余量预算（Headroom Budgeting）

工程上不是"能跑就行"，而是**预留**：

- 设计时按"最坏情况"估算总占用，并给自己留 20%~30% 余量应对：
  - 突发中断（总线错误、USB 事件）；
  - 调试期开的日志（RTT printf 本身要花时间）；
  - 未来要加的功能（本工程后面还有协议 v2、导航帧、裁判完整转发）。
- 没有余量的后果不是"慢一点"，而是**偶发失效**：某些帧丢了、某个任务偶尔超时、看门狗误复位——这类问题最难查，因为平时看不出来。

### 5.3 "等待即浪费"：非阻塞设计

IDLE 余量最容易被吃掉的不是"计算太多"，而是**在等**：

```c
while (硬件没准备好) { }        /* 轮询等待: CPU 100% 在空转 */
vTaskDelay(10);                /* 主动让出: 这些时间会自动变成 IDLE 余量 */
```

本工程最典型的例子：CAN 发送原来是"自旋等 1ms 超时"，每个 tick 白等 2~3ms，motor 任务被拖到 250Hz、占 58% CPU。
改成"硬件队列 + 满了就丢帧"后，同一功能只占 5.9%。**这就是"非阻塞"和"IDLE 余量"的直接关系**：等的时间变成了真正空闲的时间。

### 5.4 事件驱动 vs 周期轮询

| 方式 | 特点 | 对 IDLE 余量的影响 |
|---|---|---|
| 中断/事件驱动 | 有事才醒 | 空闲多，余量高 |
| 固定周期轮询 | 无论有没有事都跑一遍 | 空闲少，余量低 |
| 阻塞等待信号量 | 没数据就挂起 | 余量高（但要小心优先级反转） |

"能中断就中断、能挂起就挂起"是提升余量的通用手法。反过来，把一切塞进 1kHz 循环里"顺手做一下"，是余量杀手。

### 5.5 优雅降级（Graceful Degradation）

余量不足时，**牺牲顺序必须事先定义**：

- 先牺牲最低优先级、最不影响安全的功能（屏幕刷新节流、日志降频）；
- 关键功能（姿态、电机、安全状态机）永远不降级；
- 严重不足时进入"安全模式"（停下来、报警），而不是随机丢功能。

本工程的落地方式：`lcdtask` 是 `osPriorityLow`，系统忙它就慢下来（甚至暂停刷新）；`TaskMonitor` + IWDG 负责"真的没人喂狗"时的兜底复位。

### 5.6 可观测性设计（把余量做成"仪表盘"）

余量是"看不见的资源"，所以要主动度量：

- RTOS 运行时间统计（本节 3.1）；
- 分段 DWT 探针（把"某任务占 58%"拆成"PID 35µs + CAN 发送 3068µs"）；
- 本工程每 5s 输出一行 RTT 汇总：

  ```
  I:[cpu] win=6425ms lcdtask=148 IDLE=517 motortask=58 defaultTask=4 robottask=11 daemontask=1 uitask=0 instask=256 Tmr Svc=0
  ```

  （数字是千分比，`IDLE=517` 就是 51.7% 余量）

把余量做成常态指标，才能"在加功能之前就知道够不够"。

### 5.7 是否该用 IDLE 任务本体干活

FreeRTOS 允许注册 `vApplicationIdleHook()`，在 IDLE 里做后台工作（例如某些 RTOS 里做 LCD 刷新、统计）。**注意**：

- IDLE hook 运行在 IDLE 上下文（优先级 0），**绝对禁止阻塞**（不能 `vTaskDelay`、不能等信号量、不能长时间不返回），否则调度器会报错；
- 它还会影响 tickless 低功耗（IDLE 不"空"就没法停机省电）。

所以本工程的做法是：**不开 IDLE hook，而是建一个低优先级的独立任务 `lcdtask`** —— 它可以自由地 `osDelay`、可以阻塞式刷 SPI，行为更可控，效果上"等价于用空闲时间干活"。

## 6. 想提高 IDLE 余量，按这个顺序做

1. **测量**：先看 `[cpu]` 汇总，找出"谁最占"（本工程一度是 motortask 58%）；
2. **分段定位**：把它拆成小段（PID / 组帧 / 发送 / 读取），找出真正的大头（本工程：CAN 发送段占 98.9%）；
3. **删除"等"**：自旋、无超时阻塞、过长的 `HAL_Delay` → 改非阻塞/中断/队列；
4. **减少中断开销**：精简中断源、把重活搬出 ISR、降低中断频率；
5. **减少重复劳动**：缓存、只在变化时更新（例如 LCD "值不变就不重绘"）；
6. **降低频率/精度**：能 500Hz 就别 1kHz，能用 int 就别用 double（这是有代价的选项，放最后）；
7. **换编译器优化**：本工程原来整机 `-Og`，换 `-O2` 通常能直接省一大截（见《01 编译优化入门》）。

## 7. 新手常犯的 6 个错

| 错误认知 | 事实 |
|---|---|
| "IDLE 占比就是 CPU 空闲" | 它包含"IDLE 运行时被中断打断"的时间，是空闲的**上界** |
| "平均够就行" | 要看最坏情况；峰值负载才是压垮系统的原因 |
| "低优先级任务慢点无所谓" | 余量耗尽时它会被**完全饿死**（我们的 LCD 曾 30s 刷新 0 次） |
| "加个 delay 就等于省 CPU" | delay 只是把时间让出去；真正要省的是"单次耗时 × 次数" |
| "余量高就可以随便加功能" | 要看新功能的**峰值**需求和调用频率，以及它会不会带来新中断 |
| "串口打印不花时间" | `printf`/RTT 格式化很贵；本工程的热路径日志曾把 CPU 和 1KB RTT 缓冲一起刷爆 |
