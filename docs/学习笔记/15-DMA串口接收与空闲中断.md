# 15 DMA 串口接收与空闲中断：怎么收"一包不知道多长"的数据（写给零基础）

> 本篇回答的问题：
> 1. 为什么串口接收要用 DMA？不用会怎样？
> 2. 收到一串字节，怎么知道"这一包收完了"？
> 3. `HAL_UARTEx_ReceiveToIdle_DMA()` 到底做了什么？为什么它触发的回调会被调用好几次？
> 4. 为什么"解析完立刻清零缓冲再重启 DMA"能工作？改成任务里解析后为什么必须拷贝？
> 5. ORE / NE / FE / PE 是什么？为什么串口出错后必须 Abort？
> 6. 为什么"阻塞版 Abort"不能放在中断里？
>
> 对应代码：`bsp/usart/bsp_usart.c`。并发模型部分见《12》，互斥保护见《14》。

---

## 1. 为什么串口接收要用 DMA

最朴素的接收方式是**每来一个字节进一次中断**：在回调里把字节存进数组，
然后再开一次接收。问题在于**中断次数太多**。按 115200 波特率、每字节 10 位（含起止位）算：

| 波特率 | 每字节时间 | 每秒中断次数 | 光收数据的 CPU 开销 |
|---|---|---|---|
| 115200 | 86.8 µs | 11520 次 | 每次 2µs 的话就是 2.3% |
| 921600 | 10.8 µs | 92160 次 | **约 18%**——光收数据就把 CPU 吃掉一大块 |

**DMA 的解法**：告诉 DMA"串口收到的字节你直接搬到我指定的内存里"，CPU 完全不参与搬运。
上表的 CPU 开销直接变成 **0**，只在"一包收完"时进一次中断。

代价是要多占一个 DMA 通道，并且要处理一个新问题：**怎么知道一包收完了？**

---

## 2. 不定长数据的四种"判包"方案

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **固定长度** | 收满 N 个字节算一包 | 最简单 | 只适合定长协议 |
| **超时判断** | 连续一段时间没新字节就算结束 | 通用 | 要额外占一个定时器，"多久算超时"难定 |
| **空闲中断 IDLE** | 串口硬件自带：总线空闲一个字符时间就触发中断 | 不用额外硬件、反应快 | 两帧之间**没有间隙**时（连续发送）分不开 |
| **协议自带边界** | 靠帧头/长度字段/帧尾自己找 | 最可靠 | 得先收到数据才能判断 |

**本工程是"IDLE + 协议边界"组合**：IDLE 负责"把这一批数据交上来"，
模块回调里再用帧头 + 长度 + CRC 把真正的帧切出来（裁判的 `JudgeReadData()` 就是这样：
在收到的字节里滑动找 `0xA5` 帧头，逐帧校验 CRC8/CRC16，一批里可能含多帧）。

> **为什么不能只靠 IDLE**：如果上位机把两条帧连着发、中间没有空闲间隔，
> IDLE 只会触发一次，交上来的是一整坨。所以解析必须能"一批里切多帧"。

## 3. `HAL_UARTEx_ReceiveToIdle_DMA()` 做了什么

这一句同时做了三件事：

1. 启动 DMA，把串口收到的数据搬进 buffer，最多 `size` 个字节；
2. **使能 IDLE 中断**（总线空闲就触发）；
3. 使能 DMA 的**半传输**和**传输完成**中断。

于是有三种情况会进**同一个回调** `HAL_UARTEx_RxEventCallback()`：

| 触发源 | 什么时候 |
|---|---|
| DMA 半传输完成 | 收了 `size/2` 个字节 |
| DMA 传输完成 | 收满了 `size` 个字节 |
| **IDLE** | 总线空闲了一个字符时间 |

**问题**：收一包数据可能进回调 2~3 次。半传输那次尤其讨厌 ——
它拿到的只有一半数据，按它解析只会失败或把一帧切成两截。

本工程的解法（代码注释里说的"HAL 库的一个设计失误"）：

```c
__HAL_DMA_DISABLE_IT(huart->hdmarx, DMA_IT_HT);   /* 关掉半传输中断 */
```

关掉之后只剩"收满 buffer"和"IDLE"两种情况，语义就清楚了。

## 4. 同一个缓冲区的复用陷阱（本次改造的核心）

DMA 接收的特点是：**它一直往同一块内存里写**，不会给你第二份干净副本。

### 改造前：解析完立刻清零 + 重启 DMA

触发 IDLE 时 DMA 已经停了，此时解析是安全的；解析完 `memset` 清干净、再重启 DMA。
这个顺序**是对的**，但它把"数据安全"和"解析"绑死了：
解析（裁判要在 255 字节里滑动找帧 + 逐帧 CRC 校验）**必须全在中断里做完**。

### 想搬到任务？只存指针会出事

如果中断只是"记下数据在哪，让任务去解析"，那就是只存了个指针，
紧接着又调了 `HAL_UARTEx_ReceiveToIdle_DMA()` —— **DMA 立刻开始往同一个 buffer 写**。
任务还没跑，新数据已经把旧数据盖掉，任务读到的是半新半旧的垃圾。

**正确做法是拷贝**：中断里把这一段数据 `memcpy` 进队列的独立槽位，
先写数据、`__DMB()`、再发布队列索引（见《12》），然后才重新武装 DMA。
这样 DMA 后面怎么写都不影响已经拷走的数据。

代价是多一次内存拷贝（一包最多 255 字节）。相比"把几微秒的中断变成几十微秒、
还可能被 CRC 校验拖到上百微秒"，这次拷贝非常划算。

> **一句话**：只要数据的"生产者"是 DMA/外设、"消费者"是任务，中间就必须有一份
> **拷贝**（或队列、双缓冲这类等价机制）。指针传递只适用于"生产者也停下来等你"的场景。

## 5. 串口错误：ORE / NE / FE / PE

| 标志 | 名称 | 什么情况 |
|---|---|---|
| **PE** | Parity Error | 校验位不对 |
| **NE** | Noise Error | 采样到的电平有毛刺（线太长、干扰、波特率不匹配） |
| **FE** | Frame Error | 停止位不对（**波特率不匹配的典型表现**） |
| **ORE** | Overrun Error | 上一个字节还没取走新的又来了（接收来不及） |

**关键点：出错之后接收往往就"停"了**。HAL 会把接收状态机复位，
`RxState` 不再是 READY，不处理的话这个串口就**永久收不到数据**（直到重新上电）。

所以必须"出错 → 中止当前接收 → 重新武装"：

```c
HAL_UART_AbortReceive(huart);                     /* 清错误标志 + 把状态机复位 */
HAL_UARTEx_ReceiveToIdle_DMA(huart, buf, size);   /* 重新开始收 */
__HAL_DMA_DISABLE_IT(huart->hdmarx, DMA_IT_HT);
```

**为什么要重试**：Abort 或重启偶尔会失败（比如 DMA 卡在某个状态），
所以本工程加了"最多重试 3 次"，连续失败就置一个 `recover_failed` 标志供观测。

## 6. 为什么阻塞版 Abort 不能放在中断里

`HAL_UART_AbortReceive()` 是**阻塞版**：它关掉 DMA 和 UART 之后，会**轮询等待**
状态回到 READY（带超时）。正常情况这个等待只有几十微秒，但：

- 如果 DMA 因为某种原因卡住（总线错误、外设异常），它会**一直等到超时**；
- 在中断里等几百微秒甚至几毫秒，意味着**这期间其它中断全被推迟**，
  1kHz 的控制任务会被拖垮，严重时看门狗直接复位。

**本工程的改法**：

```
中断里(几微秒):
    err_count++            // 累加计数
    need_recover = 1       // 只置一个标志

任务里(1kHz):
    if (need_recover) {
        重试最多 3 次 { Abort; 重启 DMA; }
    }
```

这和《12》里 CAN 接收的思路完全一样：**中断只记账，重活交给任务**。
代价是恢复延迟从"立刻"变成"最多一个任务周期"（本工程 1ms）——
对"出错恢复"这种异常场景完全够用。

## 7. 顺便算一下：一包数据要多久

知道这个数才好判断"任务周期够不够"：

| 波特率 | 每字节 | 裁判一包 255 字节 | 遥控一帧 25 字节 |
|---|---|---|---|
| 115200 | 86.8 µs | **22.1 ms** | 2.17 ms |
| 921600 | 10.8 µs | 2.76 ms | 271 µs |

裁判一包要 22ms——**远大于 1ms 的任务周期**，所以：

- 用 DMA 收是必须的（否则 22ms 里要进 255 次中断）；
- 1kHz 的任务去消费队列，一次处理一整包完全来得及；
- 队列深度 4 足够：正常情况下同一时刻最多积压一包。

## 8. 速查表

| 问题 | 答案 |
|---|---|
| 串口为什么用 DMA | 解放 CPU：每字节一次中断 vs 每包一次中断 |
| 怎么判断一包收完 | IDLE 中断最省事；协议有帧头/长度的再自己切帧 |
| 回调为什么进好几次 | HAL 把"半传输/传输完成/IDLE"接到同一个回调 → 关掉 `DMA_IT_HT` |
| 能不能只把指针给任务 | **不能**，DMA 会立刻覆盖；必须拷贝（或双缓冲/队列） |
| 出错后为什么收不到数据了 | HAL 把接收状态机复位了，必须 Abort + 重新武装 |
| 为什么 Abort 不能在中断里 | 阻塞版会轮询等待，最坏卡到超时 → 中断延迟爆炸 |
| 恢复延迟 1ms 能接受吗 | 能。出错本身就是异常事件，1ms 恢复完全够 |
| 怎么验证改造有效 | 用错误波特率持续灌数据制造错误，量中断耗时是否恒定 |
