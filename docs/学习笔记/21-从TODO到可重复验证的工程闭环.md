# 从 TODO 到可重复验证的工程闭环

本工程有固件和视觉两个 Git 仓库。各自的 TODO 是任务状态的唯一来源；规格、代码、验证结果和教学文档通过稳定任务编号相互链接。跨仓库工作在两个 TODO 中各有一条对应任务，并在两个仓库分别提交。

本文依据 **MC02-0043** 和用户于 2026-10-08 确认的新流程更新。流程的权威规则在 [issue-tracker.md](../agents/issue-tracker.md)，这里解释每一步解决什么问题。

## 一次改动怎样交付

```text
明确验收 → 查源码和 TODO → 相关改动共用分支
         → 定位与实现 ↔ 统一验证
         → 教学文档和 TODO → Git 提交 → 简短复盘交付
```

大功能或跨模块改造先写规格和依赖任务；修复一个地址边界判断等小问题，直接在 TODO 写可观察的验收条件即可。规格的作用是减少设计歧义，内容应随问题复杂度变化。

分支保存一组相关改动的代码状态，TODO 保存每个问题的验收状态。两者无需一一对应：例如一次改造涉及 SPI 错误传播和 IMU 快照发布，可以在同一分支实现两个相互关联的任务，分别记录它们的验收结果。默认交付结束于本地提交和说明，代码审查、重复代理复审、推送和 PR 已从常规链条移除。

## 为什么先找一个可运行的检查

修复一个问题时，先找到能触发并识别它的最小检查，再改代码。MC-02 的主机测试直接调用 `VisionProtocolFindCommandFrame` 和 `VisionControlInputIsUsable`，可以在没有 STM32、USB 或云台的情况下检查帧长、CRC、超时和非有限数值。视觉的 `sp_vision_protocol_test` 检查 43/29 字节帧、CRC、禁火瞄准帧及无目标、失联、无效规划时生成的中立帧。

这些测试覆盖的是纯 C/C++ 逻辑边界。硬件收发、相机时序和实际电平需要连接设备才能观测，因此按验收需要选择验证路径。

## 一个验证阶段，两种证据

测试先行、构建、回归和上板调试都属于统一验证阶段，验证可与实现交替进行。

| 改动例子 | 验证方法 | 得到的证据 |
|---|---|---|
| SP 帧 CRC、失联清零、地址白名单 | 本机运行生产接口测试或假 OpenOCD 服务 | 逻辑是否满足输入、输出和错误处理约定 |
| STM32 固件改动 | 本机交叉编译相应配置 | 代码能否生成目标固件，以及编译、链接问题 |
| USB 实际收发、SWD 在线观察、VIN 精度 | 需要时连接裸板，记录固件 SHA、供电和观测方法 | 接口或实物在这次条件下的行为 |

TDD 是需要新增行为回归时的一种方法：先让检查在实际故障上失败，再修复并使它通过。简单重构优先复用现有行为测试。例如移动一个对齐计算不必断言内部属性名称，应该由“非对齐读取被拒绝”这样的外部行为检查保护。

本机测试通过并不会证明 VIN 测量准确，SWD 寄存器读数也不能代替 PB1 波形测量。尚缺仪表的物理验收继续留在 TODO，避免把软件证据当成实物证据。相关检查已经通过时结束验证；新改动、失败或明确剩余风险才需要重复检查。

## CMake 和 CTest 如何连起代码与证据

每组主机测试由 CMake 描述：哪些源文件组成测试程序、需要哪些头文件、测试的名字是什么。构建目录放在仓库之外或被忽略的 `build/` 中，避免生成物混入提交。

`ctest` 根据构建目录中的测试清单运行程序并汇总退出状态。CI 执行相同的配置、构建和测试步骤，因此开发机和 GitHub Actions 共享同一套可复现检查。

视觉协议测试必须在 Release 配置下也保留检查。标准 C `assert`/C++ `assert` 会在定义 `NDEBUG` 时被移除；所以测试使用 `CHECK`，条件失败时打印表达式并以非零退出，而不依赖构建类型。

```sh
cmake -S tests/host -B build/host-tests -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build/host-tests --parallel 2
ctest --test-dir build/host-tests --output-on-failure
```

视觉仓库的离线 CPU 测试用 CTest 运行固定长度的演示视频片段，不打开 GUI，也不加载工业相机 SDK。回放汇总报告处理帧数、有目标帧数，以及同一批有目标帧中产生有限瞄准输出的帧数。

## 教学文档与 teach 的区别

每次改动必须提交一份新增或实质更新的教学文档，内容至少说明改了什么、为什么、工程中的具体例子、如何验证及证据局限。已有文章涵盖主题时更新原篇，并维护索引；本次流程变更直接更新第 21 篇。

teach 用于需要互动讲解的情形：你要求学习、表示没理解，或者概念影响眼前的设计决定。普通交付文档无需额外生成 HTML 课程和练习。课程或文章写出来只表示有可复习材料，学习记录仍只在你通过回答或练习展示理解后增加。

## Git 提交怎样描述改动

提交采用 Conventional Commits 的常用形式：`类型: 中文摘要`。类型保留 fix、feat、docs、chore 等原文，摘要和正文用中文。

```text
fix: 修复视觉超时后的旧指令残留

在接收有效期结束时清除控制状态，并保持禁止开火。
生产接口回归覆盖正常接收、停发和计时回绕。
教学资料：docs/学习笔记/22-失联安全与有界等待.md
```

fix 适用于故障修复，feat 适用于新增功能，docs 适用于文档，chore 适用于工具或工作流维护。本次统一代理指引和 skills 采用 chore 类型。类型是帮助读者理解改动性质的约定，正文记录原因、验证和教学入口。

任务结束时，TODO、提交 SHA、验证结果和学习文档应能互相追溯。交付中的简短复盘说明实际教训，例如“旧规则散布于多个 skill，因此本次同时修正路由和实施入口”；正式 retro 留给重大故障、阶段结束或明确请求。

## 任务清单与资料文档的分工

本仓库只在 `.Doc/TODO.md` 维护任务状态。审查报告保留问题背景、证据和修复过程；规格与票据记录设计和验收细节；学习笔记解释技术概念。这些资料可以链接到任务编号，但不再各自保留待办勾选框或第二份状态。

合并旧清单时先对照当前 TODO。已经被新任务覆盖的旧编号只保留映射，例如 `CORE-10` 与 `CORE-04` 归入 `R25-12`，`APP-07`、`APP-08` 分别归入 `R25-15`、`R25-07`，`VISION-07` 归入 `R25-09`。旧报告中的其他未完成项先标记 `needs-triage`，核对当前源码后再决定修复、关闭或废弃；这样不会把过时的审查结论误当作当前缺陷。

旧条目把多个缺陷写在一个编号下时，应拆成各自可验收的事项，例如 LK/HT/DM 电机、舵机和 OLED 问题分别管理。`tools/workflow/check_todo.py` 可以检查未完成条目的编号、类别、状态和验收描述是否齐全，但它不能判断旧问题今天是否仍存在，所以迁入项先进入 `needs-triage`。格式合规与技术事实核验是两件不同的工作。

归档文件也要有明确用途。当前安全审查、硬件依据、部署记录和学习资料放在 `docs/`；旧的重复导出、无效模板和过期路线图应从入口移除。整理文件时先核对是否有有效信息只存在于待删除文件中，并修正指向旧路径的链接。共享账号、密码和令牌不应写入仓库；如果历史提交曾包含仍有效的凭据，应轮换凭据，因为删除工作树文件不会清除 Git 历史。

## Release 回归如何证明检查仍在执行（R25-13、MC02-0053）

主机测试不使用会受 `NDEBUG` 影响的标准 `assert`。统一 `TEST_CHECK` 在所有构建类型计算表达式，失败时打印位置和条件并返回非零。单独的负向控制把一条检查故意设为失败；CTest 只有在程序确实以预期状态退出且输出诊断时才判该控制用例通过。这样能验证“测试框架会发现错误”，而不是只看所有业务测试进程是否意外地以 0 退出。

对有副作用的接口，先执行、再检查：例如注册话题、入队、获取快照或初始化 USB 的返回状态应存入局部变量，再交给 `TEST_CHECK`。若把调用直接写入 `assert`，Release 会连生产接口调用一并删掉。故障注入也要观察优化后的调用边界；编译器把 `malloc()+memset()` 合并为 `calloc()` 后，测试替身必须拦截这两种入口，确保优化构建仍触发相同的失败情形。

复查旧任务时应保留旧结果和新证据的区别：R25-10、R25-11 原记录中的 Release 计数保留为当时的历史信息，同时注明断言式检查失效的范围；以修复后的当前全套 Debug／Release 结果作为有效验收证据。本次两种配置各 102/102，负向控制都确认错误条件会令测试失败。固件六配置、Windows／WSL 增量构建测试和文档检查各自提供不同证据，不能互相代替。

## 讨论方案怎样转成实施范围（2026-10-15）

本轮先逐文件讨论，再由用户筛选功能。139 个文件不能直接变成 139 个待办：多个文件往往共同完成一个行为。例如 safety 发布故障、alarm 选择模式、RGB 和蜂鸣器分别输出，验收对象应是“当前故障被准确、及时地表示”，而不是“每个头文件增加了几个字段”。

[范围规格](../workflow/specs/robomaster-framework-evolution.md)把 23 个获选主题映射到稳定任务编号，[文件讨论记录](../workflow/maps/framework-file-discussion-20261015.md)保留上下文；任务的分诊与完成状态仍只在 [TODO](../../.Doc/TODO.md)。本轮新增 MC02-0054～MC02-0085，并更新 15 个原有条目。登记表示需求和验收已记录，不表示算法、驱动或硬件功能已经实现。

### 选中上层，不会自动选中所有下层改造

用户选了 R28 姿态模块和 Fusion，暂缓 R27 多 BMI088／异步采样。两个选择可以通过接口分层兼容：采样模块先提供现有完整样本，姿态模块声明时间来源、单位、坐标和有效性，QuaternionEKF 与 Fusion 分别作为同一接口上的 Adapter。姿态输出保持统一，业务不需要了解每个算法的内部状态。

若现有样本只有读取时间，不能把它写成已精确获得硬件采样时刻；精度不足时，应记录缺失能力，让相关任务保留待补信息。这样也不会为了让 Fusion 的验收看起来方便，就悄悄实施本次暂缓的 SPI 事务系统、DRDY 采样或全局时基平台。实际补偿还依赖安装几何和可信运动反馈，单纯换一个姿态库不会补齐这些信息。

这对应 [MC02-0005、MC02-0082、MC02-0083](../../.Doc/TODO.md)：统一接口、后端适配和运动补偿分开验收。纯算法检查可以使用固定数据验证数值，但通用主机回放调试平台仍是后续内容。

### 安全状态由一处决定，多个输出共同表达

RGB 与蜂鸣器联动对应 [MC02-0025、MC02-0084](../../.Doc/TODO.md)。安全模块拥有故障和运行许可；告警模块读取其一致快照，根据配置选择颜色、闪烁周期、蜂鸣节拍和优先级。告警不能通过“恢复绿色”反向清掉核心故障。

| 职责 | 工程位置 | 接口应表达的事实 |
|---|---|---|
| 故障和运行许可 | [robot_safety.h](../../modules/safety/robot_safety.h) | 当前故障集合、运行许可、恢复信息 |
| 告警模式和仲裁 | [robot_alarm.h](../../modules/alarm/robot_alarm.h)、[robot_alarm_policy.c](../../modules/alarm/robot_alarm_policy.c)、[sentinel_config.c](../../application/config/sentinel_robot/sentinel_config.c) | 配置故障／状态映射、优先级、节奏和静音等级；策略纯逻辑从一致 safety 快照选当前事件 |
| 光与声音输出 | [ws2812.h](../../bsp/ws2812/ws2812.h)、[led.h](../../modules/alarm/led.h)、[buzzer.h](../../modules/alarm/buzzer.h) | 返回底层提交结果；灯声在 Daemon 任务中按共同事件起点、各自时间线推进 |

多个故障同时存在时，低优先级事件不会覆盖最高优先级；最高项清除后下一项接替。完整故障集合仍由 safety 快照保留。哨兵配置中的颜色和节奏是软件默认提示值，不是实测的亮度、声压或车辆安全等级标定。

“闪烁频率”与“任务调用频率”分别定义：Daemon 每10ms推进一次，但闪烁和节拍依据 HAL 毫秒时间差计算，允许调用间隔轻微变化与 `uint32_t` 回绕。RGB 或蜂鸣器初始化和运行错误只使对应辅助通道降级，不设置 safety fault，也不改变使能许可。异常关断路径仍由原有 safety／硬件保护处理。

### 告警仲裁、播放与静音怎样分别验收（第140–145项）

策略和运行桥接分别位于 `robot_alarm_policy.c`、`robot_alarm.c`；车型表在 `sentinel_config.c`。不为每种故障创建任务：Daemon 每轮复制一次 safety 快照，选择一项并计算 LED 与蜂鸣器当前输出。输出只有在请求值变化时才触发底层写入。

仲裁持续表达最高优先级故障，清除后显示下一项。A 高于 B 时同时存在只表达 A，诊断仍可看到全部故障；A 清除后转为 B。临时静音只让当前故障的声音停下来，灯光仍表达 A，安全许可不改变。静音等级、最长时限由车型配置，排队期间告警变化会使旧请求失效；到期恢复声音与故障恢复是两个不同状态。

灯光与声音共用告警起点，不要求每段长度相同。光可设为短闪、停顿、再次短闪和长停顿，声音可使用另一种节奏；切换到 B 时撤销 A 的输出并使用 B 的新起点。任务按当前时间算出所处段落，不依赖固定调用次数，也不忙等。分段数最多8段，单轮时间最多10秒。无更高优先级故障时，STOP／INIT／SAFE／CALIB／READY／FAULT／ESTOP 状态使用配置灯效。

生产策略回归覆盖 A 优先、清除后转为 B、故障／状态切换、常亮／闪烁／呼吸／分段时间、时钟回绕、静音到期、初始化和运行失败。适配层回归还检查 snapshot 失败保持旧状态、身份代次变化使旧静音请求失效、处理期间拒绝并发重复请求。WS2812 主机用例核对 BDMA 缓冲、SPI 完成事件、超时隔离和目标变化；HAL 替身不能证明灯珠实际波形，PWM 映射也不能证明蜂鸣器物理频率。SPI6 异步路径使用固定 SRAM4 缓冲与协作式超时，物理验收仍归 MC02-0025。

`RobotInit()` 现在先选择长期车型配置，再初始化告警。RGB 或蜂鸣器初始化失败不会上报整车初始化故障；Daemon 调用 `RobotAlarmTask()` 推进唯一策略。驱动删除了旧多实例报警 API，`OCTAVE_8` 对应1046Hz并由生产 PWM 映射测试覆盖。`buzzer.md` 已改成新接口和实际验证边界说明。

PID 原 MC02-0015 曾建议统一分配实例，本轮选择调用者提供存储，因此更新原编号和验收。RGB 原 MC02-0025 的 PWM 候选路线改为现有 SPI 单灯修复，LOG-06 从“是否需要归档”改为已确认需求但介质／分区待补。这样保留讨论历史，也避免同一目标出现两条相互冲突的任务。

### 一条需求如何找到自己的编号

### 消息有效、对时有效和恢复握手分别判断

[MC02-0089／0090／0091](../../.Doc/TODO.md)的例子能说明这三个事实。导航仍有效而瞄准过期，正式自主在许可正常时可继续平移，同时禁发射并本地索敌；不能用一份新导航帧续期旧瞄准，也不能仅因为目标丢失就断言USB整条链路断开。

### 真实算法与测试替身提供的证据不同

[MC02-0099](../../.Doc/TODO.md)固定同源DSP源码和头文件，是为了让“代码声明了什么”和“实际链接执行了什么”一致。本轮固件与主机使用[同一份九文件清单](../../cmake/mc02_dsp.cmake)，来源是CMSIS_5 5.7.0提交`a65b7c9a3e6502127fdb80eb288d8cbdf251a6f4`中的DSP1.7.0。文件、许可和SHA256留在[第三方目录](../../Middlewares/Third_Party/CMSIS-DSP-1.7.0/README.md)，构建无需联网。Core、HAL、RTOS保持原版本，实际使用的Core编译器头另记指纹。

旧KF测试中“只返回成功、不计算”的矩阵替身已经删除。现在[dsp_numeric_test.c](../../tests/host/dsp_numeric_test.c)比较固定答案、独立双精度求逆以及`A×A⁻¹`残差；三角函数用`−8π～8π`网格对照标准数学函数，允许绝对误差为`3×10⁻⁵`。矩阵失败测试仅在指定步骤返回失败，其余步骤继续调用真实DSP。采样、USB和SWD仍可以使用各自的硬件替身，它们提供的证据范围不同。

该版本的[求逆实现](https://github.com/ARM-software/CMSIS_5/blob/a65b7c9a3e6502127fdb80eb288d8cbdf251a6f4/CMSIS/DSP/Source/MatrixFunctions/arm_mat_inverse_f32.c)还说明一个容易忽略的问题：输入描述符为const，不代表其指向的数据不会被修改。算法会在工作区消元，失败时也可能留下中间状态。因此要先复制到独立工作区，完整成功且数值有效后才接受新结果。这与统一数值接口“失败保留旧有效结果”的约定一致。

[DSPMatrixInverseF32](../../modules/algorithm/dsp_matrix.h)需要`2*n*n`个float：一半保存可改写的输入副本，一半保存候选输出。方阵尺寸、容量、对齐、重叠和有限数值全部检查通过才调用厂商求逆；失败时原输入和旧输出保持。只在适配层保护输入，并不改变第三方源码。

MC02-0078把KF改为调用者长期保存实例及工作区。主机验证回答的是数值、容量和失效规则是否正确；六种固件构建回答的是头来源、链接、ABI和配置隔离是否正确；裸板被动观察回答的是这次固件能否启动并保持IMU、禁热和输出隔离。三种证据各自记录在[本轮任务详情](../workflow/tickets/MC02-0099.md)，不能用裸板上一次正常姿态代替20ms／2倍方差的软件边界测试。

同样，USB业务测试用“发送总成功”替身能检查命令队列，不能证明CDC在途缓冲未被覆盖；空临界区替身不能证明抢占读取一致；寄存器模型也不能证明板上灯珠波形。后续按实际改动选择生产接口回归和必要裸板测量，不为了填满测试数量复制实现。

## 唯一构建入口怎样保持角色隔离（BUILD-02）

固件和主机测试是两个独立 CMake 工程。根目录只接受 `CMakePresets.json` 中的 Ninja 固件配置；Windows VSCode 任务把工作区路径作为独立参数交给 `wsl.exe`，由 WSL 中的 CMake 和 ARM GCC 执行构建。`tests/host/CMakePresets.json` 单独提供主机 Debug／Release。构建产物统一放在 `build/wsl/<预设名>/`，避免 Windows 本机缓存与 WSL 编译器混用。

`cmake/mc02_firmware_sources.cmake` 按平台、BSP、当前公共依赖和应用角色登记固件 `.c`。单板含 RobotCMD、底盘、云台和发射；底盘板只含底盘应用；云台板含 RobotCMD、云台和发射。裁判 UI 与视觉 USB／UART 另由明确配置选择。新增源码要登记到所属清单，清单改动会触发已有目录重新配置；未登记文件不自动参与构建。没有替保留模块逐个增加开关，当前清单之外的驱动仍可留在仓库供后续任务使用。

“参与编译”不等于“保留在最终 ELF”：`compile_commands.json` 证明某源码有编译命令，Ninja 链接命令证明其对象被交给链接器，ELF 符号再说明哪些入口最终留下。角色验收应联合检查这几份证据。单板、底盘板和云台板虽然复用 CANComm 及当前通信格式，但本机编译和链接成功只证明代码可构建，不证明跨板控制已具备真实总线和业务验证。

配置失败也属于可复现证据：裸板启热、裸板选择双板角色、云台板开启裁判 UI、手工注入冲突板级宏或视觉宏均应在配置阶段拒绝。已有构建目录变更清单后，增量回归会把它的编译源与干净配置比较，并检查退出清单的对象不再链接；不自动删除旧 Windows 构建缓存，使用新的 WSL 预设目录即可避免误用。

详细的预设、角色矩阵、工具链结果和资源统计见 [BUILD-02 任务记录](../workflow/tickets/BUILD-02.md)。

## 怎样锁定一次构建实际用到的依赖（MC02-0020）

版本说明和构建证据要对得上：文件夹里存在一个库，只能说明它被保存进仓库；`compile_commands.json`列出实际编译的源文件，Ninja依赖记录列出编译时读取的头文件，二者合起来才能说明这个配置真正用到了哪些第三方文件。`capture_build_baseline.py`按这些输入计算逐文件SHA-256和组件摘要，并同时核对ELF、HEX、BIN、map是否生成。

## 固件归档怎样绑定到一次构建（MC02-0103）

本地与 CI 都调用 [`archive_firmware.py`](../../tools/workflow/archive_firmware.py)，输入是 CMake 预设已经生成的 ELF、HEX、BIN、map 和 `mc02-selected-sources.txt`。脚本先核对 CMakeCache、预设、源码选择摘要、禁热配置和 ELF GNU Build ID，再生成 ZIP；缺少文件或身份不匹配时返回失败，不输出貌似成功的包。

包内 `build-info.json` 记录完整 Git 提交、是否有已跟踪改动、改动路径及其清单指纹、构建预设、车型／板卡角色、视觉传输、协议、姿态后端、Debug／RelWithDebInfo、工具链版本、工具链文件 SHA-256、源码清单散列和 Build ID。路径指纹只标识哪些文件有改动，不哈希工作区文件内容；构建产物自身的 SHA-256 则准确检查归档中字节。清单不记录本机绝对路径；ELF 和 map 保留现有调试路径以便定位匹配源码。文件名带预设、提交短 SHA、Build ID 和清单指纹；归档名冲突且内容不同时拒绝覆盖。

在 WSL 完成构建后运行 `python3 tools/workflow/archive_firmware.py --preset bench-debug`，默认输出到 `build/firmware-archives/`。CI 对十种常规禁热预设逐个调用同一脚本，并上传这些 ZIP；本地运行能核对打包过程和内容，只有工作流真正运行后才能确认 GitHub 下载行为。本任务不推送或手动触发远端 CI，因此远端下载仍按 TODO 记录为待证据。

Build ID 关联 ELF 的链接映像，SHA-256 检查文件字节，Git SHA 标识仓库提交，三者不能互相替代。`.vscode/launch.json` 与公共 Ozone 项目默认指向 `bench-debug`；选择其他角色时，需从同配置包中使用 ELF 和 map。ZIP 仅整理产物，不能证明它已写入开发板或整片 Flash 与文件相同。

## 只读观测的身份与证据闭环（MC02-0100）

观测记录能解释现场读到的字段，前提是它来自所选固件。链接时生成的 GNU Build ID 保留在 Flash；启动早期将它和 profile、角色、模块位图写入固定 RAM 身份记录。主机工具从 ELF 离线解析身份、字段地址和 RAM 范围，连接后先比较板上身份，再允许读取业务字段。它验证的是映像身份与布局一致，不是整片 Flash 逐字节校验。

每个观测会话保存在独立目录，包含参数、ELF SHA-256、配置、身份、原始 JSONL 和摘要。Build ID 用来关联链接映像，SHA-256 用来确认本地 ELF 文件没有被替换；两者用途不同。失败或 Ctrl-C 时仍保存已取得的原始记录，并用不同退出码表示不完整结果。

JSONL 的性能样本保留事件外层字段，统计快照放在 `decoded` 子对象中。汇总器既要能读取运行时保留的完整样本，也要能从保存的 JSONL 样本重算；测试应直接把实际序列化后的样本交给汇总器，不能先手工摊平字段，否则会掩盖生产数据形状和汇总输入不一致的问题。`session`、`identity`、`sample` 等事件各有用途，重算统计时只取样本记录。RTOS 任务表和计时、CAN、LCD 统计组都带发布代号；只读读取恰逢短暂写入时，工具会在该次采样总超时内重读，不把半份统计当成有效结果。

本次字段来自已有五秒统计发布，不新增任务或运行期分配。身份记录和观测字段只用于诊断，不进入控制许可。MC02-0100 的实现、验证边界和板上证据见[任务记录](../workflow/tickets/MC02-0100.md)。

## 崩溃记录怎样绑定到正确固件（MC02-0068）

崩溃记录里的 PC 不是单独可信的答案。当前 v4 将完整 GNU Build ID 和角色配置写入固定 336 字节记录；记录放在链接脚本保留的 512 字节 `.crash_record (NOLOAD)` 区域。异常入口的栈读取范围由链接脚本提供，先检查地址、长度、对齐、`EXC_RETURN` 和相关 CFSR 状态，再复制现场。CRC 只证明已写字段与记录内容一致，不能证明它们由哪份固件写入；Build ID 才把 v4 记录绑定到某个链接映像。

离线工具先核对版本、长度、进度和 CRC。v4 记录只有在完整 Build ID 与 ELF 相等时才允许 `addr2line` 处理 PC/LR；归档时将原始记录、对应 ELF、map 和文件 SHA-256 一起保存。v3 旧记录仍可校验和查看稳定头部，但其弱 `fw_id` 不足以唯一识别 ELF，所以工具只输出原始负载字，不推测寄存器含义或故障位置。不能为了得到熟悉的符号结果，手工改写旧记录里的身份字段。

有限异常自测使用独立 `crashdiag-debug` bench_safe 禁热构建。工具核对当前 ELF、构建配置和板上身份，只向固定 RAM 许可地址写一个测试编号和校验值；任务消费许可后只触发一次异常。普通构建不包含这个许可入口。主机负例能证明工具拒绝错误 ELF、缓存配置或任意 OpenOCD 命令；它们不能代替裸板上的真实异常、复位和记录回读。实现、测试证据及未完成的硬件验收见 [MC02-0068 任务记录](../workflow/tickets/MC02-0068.md)。

## 整车健康快照怎样保持只读（MC02-0065）

健康聚合器每50ms从现有模块快照读取状态，再一次性发布版本、时间和各组数据。`enabled_modules`表示当前固件角色编入的模块；`available_modules`表示来源确实提供了有效状态；`degraded_modules`记录已选但不可用或带故障的模块。三者不能用一个“在线”标志代替。数据源自各模块自己的采样／接收时刻，聚合发布时间不会刷新这些时刻；读取者只复制快照，不能顺便清故障或更新控制许可。

初始化诊断另有16项固定事件环，记阶段、失败、READY、HAL毫秒时刻、模块、原因、资源和严重程度。查询按先后顺序复制，不消费记录；满后覆盖最旧事件，但已有首次失败摘要和累计次数继续保留。系统复位额度尚未实现，所以用known位表达未知；温度有效、编译允许加热、PWM比较值非零、温稳判据和故障也是不同字段。没有物理电流或温升测量时，不把PWM命令说成实际热输出。

用户选择复用USART10的等级命令链路，增加按需`GET_HEALTH`结构化应答。它沿用`D3 6C`和CRC，返回最近一次已发布快照；不会周期发送，也不会把类型化日志镜像到串口，日志仍只走RTT。软件回归验证序列、长度、字段小端顺序和CRC，不能证明USART10的实物电平、线路或波特率质量。完整事件环可由固件只读API复制，当前串口命令只导出固定健康快照，不包含事件分页。

这些边界由[MC02-0065任务记录](../workflow/tickets/MC02-0065.md)、[`vehicle_health.h`](../../application/vehicle_health.h)和[健康快照主机测试](../../tests/host/vehicle_health_test.c)共同说明。主机线程测试能检查复制一致性，ARM构建能检查角色选择和链接；二者都不替代裸板串口观测。

## 怎样验证 RobotCMD 每轮确实少做了工作（MC02-0028）

先从生产任务调用链确认数据用途，再选择能说明变化的指标。单板 `RobotCMDTask()` 原来每轮从消息中心复制9字节底盘反馈到 `chassis_fetch_data`，双板路径也复制同一数据；全仓只有这次写入，没有消费者。因此移除这次反馈数据复制不会改变控制计算，还能少做一次复制和相应临界区操作。测试保留消息发布、遥控／云台输入、RobotCMD、Safety 和控制输出的生产代码，双板回归确认仍发送安全零输出。

测量时需要区分两件事：链接器包装 `memcpy` 能精确统计每轮复制量，但包装器本身会增加调用开销；不包装的独立测试才用于计时。两类测试都使用相同预热和固定输入，耗时测试测量当前线程 CPU 时间，降低被其他进程抢占造成的墙钟噪声。基线与改后程序固定在同一 WSL CPU 上交错运行。

本次主机样本每批包含50,000次任务调用，共100批。P50／P95按最近秩法分别取100个批次均值的第50项和第95项，再对五轮结果取中位数。基线到改后的每轮复制量为51字节到42字节；五次交错运行的批次均值P50中位数为79ns到59ns，P95中位数为96ns到76ns，100个批次均值最大值的中位数为101ns到83ns。这些是同一主机环境的可比较结果；批次均值最大值不是单次函数最坏执行时间，主机纳秒值也不能外推成H723上的周期或实时上界。可用[对比脚本](../../tools/workflow/compare_robot_cmd_performance.py)指定基线提交复跑，原始配对样本保存在`build/mc02-0028-comparison.jsonl`。实现、完整回归和构建证据见[MC02-0028任务记录](../workflow/tickets/MC02-0028.md)。

## 复杂代码和配置怎样写注释

学习工程时，复杂逻辑中的每一步都需要能沿着代码读懂。例如通信恢复、矩阵计算和并发状态切换，逐行说明每条有效语句的作用、原因和前后关系；函数开头的概述帮助理解整体，但不能替代各步说明。较长的配置列表也逐项说明对应对象和用途，有单位、取值意义或选择原因时一并写出。实物参数没有确认时写明待确认，不从示例值推测真实配置。

这些要求写入 [student-code-comments 技能](../../.agents/skills/student-code-comments/SKILL.md)，供后续源码、测试、脚本和构建配置改动使用。简单代码仍使用简明注释；核对时把注释与实际执行路径和配置来源一起检查。

## 独立编译目标和真实依赖（MC02-0086）

`mc02_portable_framework` 独立编译 Daemon 和消息中心，仅提供框架自己的头文件目录。只看源码里的 `#include` 还不够：[check_firmware_profile.py](../../tools/workflow/check_firmware_profile.py) 同时核对编译命令、Ninja 实际头文件依赖，以及最终 ELF 链接命令中的对象。检查会拒绝厂商目录、强制包含和只编译却没有链接的对象，避免构建配置掩盖不小心引入的依赖。

同一工具链、同一 Debug 配置还可用 `-fstack-usage` 比较单个函数的静态栈：例如本轮事件任务初始化从 64 B 变为 56 B，但它新增调用的任务适配函数自身使用 40 B。单函数数字不能直接当作完整调用链的峰值；还要考虑被调函数和中断嵌套。具体基线、测试和其余未迁移范围见 [MC02-0086 记录](../workflow/tickets/MC02-0086.md)。

初始化诊断也进入这一独立目标。[init_diagnostic.c](../../application/init_diagnostic.c) 通过 `PlatformIrqSaveAndDisable` 保存调用前的中断状态，再用 `PlatformIrqRestore` 原样恢复；如果外层已经屏蔽中断，内层结束时不会提前打开。事件时间通过 `PlatformTimeNowMs` 获取，H723 后端仍读取原来的 HAL 毫秒计数，因此单位与 32 位回绕规则保持一致。主机测试分别检查原本开启和已屏蔽的情况，以及事件顺序和首次失败记录；禁热裁判诊断固件的实际编译依赖和链接输入也通过检查。这些结果不代表其他业务文件已经完成隔离。

整车健康信息的组装和诊断应答同样编入独立目标：前者通过 `vehicle_health_source.h` 读取各项状态，后者编码只读应答；芯片相关的数据采集仍由板级后端实现。这样更换板卡时可以保留健康信息格式，同时为新板卡提供对应的数据来源。现有五种车型角色的主机检查和禁热裁判诊断固件的头依赖、链接检查覆盖了当前接入，不能证明新平台的后端已经实现。

原来的 `robot_task.h` 同时声明并定义任务循环，任何包含它的源文件都会编译这些实现。现在任务入口声明留在头文件，循环移入 [robot_task.c](../../application/robot_task.c)，任务创建通过声明引用入口；[robot.c](../../application/robot.c) 只调用任务创建接口。移动前后的任务函数体逐字比较一致，任务创建测试仍覆盖核心失败和辅助降级。移除不再使用的芯片和设备头后，任务实现进入不提供厂商／RTOS 头路径的框架目标。普通禁热、LCD 诊断和裁判诊断固件均完成实际依赖与链接检查；另外使用明确标记的测试配置编译 UI、DJI 注入、温控和崩溃诊断分支，未生成生产机器人固件，也未验证实物调度。

整车启动和周期协调也进入框架目标。它只需要调用底盘、云台和发射的初始化及周期入口，因此这些声明集中在 `robot_control_tasks.h`；原有业务头继续包含该声明供其他调用者使用。编译器对普通禁热、LCD 和裁判诊断配置检查实际头依赖与最终链接；单板、底盘板和云台板的机器人条件分支使用测试配置做 ARM 单文件编译及头依赖检查。后者不证明整车能够完成链接、上板或通过机械参数门槛。

裁判界面状态和发送额度、电机反馈与 PID、LCD 按键事件及裁判数据行也按车型选择进入框架目标。这些文件的实现无需芯片或 RTOS 头；禁热裁判诊断固件的检查同时确认它们被编译并进入链接。遥控安全手势同样被纳入可选清单，因该固件未选择遥控，另用测试配置编译其 ARM 对象并检查实际依赖。主机回归覆盖裁判、遥控、电机和 LCD 相关行为；这一步只改变编译归属，未增加硬件验证。
