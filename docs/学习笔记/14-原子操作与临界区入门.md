# 14 原子操作与临界区入门：为什么"检查完再动手"会出事（写给零基础）

> 本篇回答的问题：
> 1. "原子"到底是什么意思？为什么它在单片机里这么重要？
> 2. 上一篇文章《12》里那段 `__disable_irq()` 包起来的代码，到底在防什么？
> 3. 为什么说 `volatile` **不等于**原子？（这是最常见的误解）
> 4. Cortex-M 上哪些操作天生就是原子的，哪些不是？
> 5. 有几种办法保证原子性？各自代价是什么？什么时候不需要它？
>
> 对应代码：`bsp/can/bsp_can.c` 的 `CANProcessRx()`、`bsp/dwt/bsp_dwt.c` 的
> `DWT_CyclesUpdate()`、`bsp/crash/bsp_crash.c`。

---

## 1. 从一句话说起：什么叫"原子"

**原子（atomic）** 的原意是"不可分割"。

在并发编程里它的含义是：

> **一个操作要么完全做完、要么完全没做，中间状态永远不会被别的执行者看到。**

在单片机上，"别的执行者"通常是这几种：

- **中断服务函数（ISR）**：随时可能插到任何两条指令之间；
- **另一个任务**：RTOS 会在中断里切换任务，所以任务之间也会互相打断；
- **DMA**：不打断 CPU，但会在你不知道的时候改内存。

如果一段逻辑需要"不被任何人打断地做完"，这段逻辑就叫**临界区（critical section）**。

## 2. 一个真实的例子：CAN 接收的"双消费者保护"

《12》里出现了这段代码，我们把它完整写出来：

```c
void CANProcessRx(void)
{
    static volatile uint8_t processing = 0;   /* 当"锁"用 */

    uint32_t primask = __get_PRIMASK();       /* ① 存下当前中断开关状态 */
    __disable_irq();                          /* ② 关中断 */
    if (processing)                           /* ③ 检查锁 */
    {
        __set_PRIMASK(primask);               /*    已经有人在处理, 恢复后直接走 */
        return;
    }
    processing = 1u;                          /* ④ 上锁 */
    __set_PRIMASK(primask);                   /* ⑤ 恢复原来的中断状态 */

    ... 遍历三条总线, 把队列里的帧逐帧派发给模块回调 ...

    processing = 0u;                          /* ⑥ 放锁 */
}
```

**这段代码要解决的问题**：

`CANProcessRx()` 是"接收队列的消费者"，它靠一对 `head`/`tail` 索引来读队列。
这个设计的前提是**只有一个人消费**。但本工程启动期的自测跑在 daemon 任务里，
而那时 motor 任务已经在跑了 —— 于是两个任务会同时调用它。

两个人同时读同一个 `tail`、各自往后推，后果是：

```
同一帧被解析两次        → 多圈角度多加了一圈
或者中间几帧被整段跳过  → 多圈角度算错
```

所以需要一把"锁"：**谁先进来谁干活，另一个直接返回**（返回是安全的，
队列里的帧不会丢，干活的那个会处理掉）。

---

## 3. 关键问题：为什么不能光写 `if (processing) return; processing = 1;`

因为 `③检查` 和 `④上锁` **之间可以被中断打断**。

看这条时间线（两个任务 T1、T2，中间发生了一次任务切换）：

```
T1: 读 processing → 0        ← 检查通过
    ┌──────── 中断来了, 调度器切到 T2 ────────┐
T2: 读 processing → 0        ← 也检查通过!
T2: processing = 1           ← T2 上锁
T2: 开始遍历队列 ...
    └──────── 切回 T1 ────────┘
T1: processing = 1           ← T1 又上了一次锁(它以为自己拿到了)
T1: 也开始遍历队列 ...        ← 两个人同时消费! 锁完全失效
```

**根本原因**："检查"和"上锁"是**两步**，而这两步之间可以被别人观察到中间状态。

这种模式有个专门的名字：**check-then-act（先检查再动作）**，
它是并发 bug 里最常见的一类。

要让锁真正起作用，**"检查 + 上锁"必须是一步——也就是必须是原子的**。

---

## 4. 关中断为什么能保证原子

Cortex-M 上**任务切换是靠中断完成的**（SysTick 产生 tick，PendSV 做上下文切换）。
所以只要把中断关掉：

- SysTick 进不来 → 调度器不会把 CPU 切给别的任务；
- 别的 ISR 也进不来 → 不会插队改内存。

于是**关中断期间的这几条指令之间，时间上不可能插入任何别的东西** ——
"检查 + 上锁"就变成了事实上的原子操作。

```c
    __disable_irq();          /* 从这里 */
    if (processing) { ... }
    processing = 1u;
    __set_PRIMASK(primask);   /* 到这里, 中间没有任何人能插进来 */
```

### 为什么是 `__set_PRIMASK(primask)` 而不是 `__enable_irq()`

这是很容易写错的地方。`PRIMASK` 是个"状态保存寄存器"：
bit0 = 1 表示**当前中断被屏蔽**。

正确做法永远是"**存 → 改 → 恢复**"：

```c
    uint32_t primask = __get_PRIMASK();   /* 存: 记下"进来之前"是开还是关 */
    __disable_irq();                      /* 改: 关掉 */
    ... 临界区 ...
    __set_PRIMASK(primask);               /* 恢复: 原来开着就开, 原来关着就保持关 */
```

**为什么不能无脑 `__enable_irq()`**：调用你的这段代码的人，可能**本来就在关中断**的上下文里
（比如它自己也在做临界区，或者干脆是在某个 ISR 里）。如果你直接把中断打开，
就破坏了调用者的假设 —— 它外层保护的临界区突然失效了，bug 会出现在离你很远的**别人**的代码里，
非常难查。

这条规则叫"**锁的对称性**"：谁关的谁开，别人关的不能替他开。

## 5. `volatile` 不等于原子（必须纠正的误解）

很多人以为给变量加了 `volatile` 就"线程安全"了。**完全不对。**

`volatile` 只做一件事：

> **"每次用到这个变量，都必须真的去内存里读/写，不许优化掉、不许缓存到寄存器里。"**

它**不保证**操作的原子性。举几个例子：

| 代码 | `volatile` 后原子吗？ | 为什么 |
|---|---|---|
| `a = 5;`（a 是 32 位对齐） | ✅ 原子 | 就是一条 `str` 指令 |
| `b = a;`（同上） | ✅ 原子 | 一条 `ldr` |
| `a++;` | ❌ **不原子** | 实际是"读 a → 加 1 → 写回 a"**三条**指令 |
| `a \|= 0x1;` | ❌ | 同样是读-改-写 |
| `flag = !flag;`（当开关用） | ❌ | 读-改-写 |

**`a++` 就算加了 `volatile`，中间照样能被中断切开**：

```
任务: 读到 a=5  ── 中断进来, ISR 也执行 a++, 把 a 改成 6 ── 回到任务
任务: 5+1=6, 写回 a=6     ← ISR 那次的 +1 被"吃掉"了!
```

所以"用 `volatile` 变量当锁/当计数器"是**典型错误**：
它保证了"你每次看到的都是内存里的真值"，但没保证"你的读-改-写不会被打断"。

**在《12》的代码里，`processing` 之所以加了 `volatile`**，只是为了
① 让编译器别把它优化进寄存器、② 让调试器/其它上下文能看到它的变化；
**真正保证原子性的是那对 `__disable_irq()/__set_PRIMASK()`**。

## 6. Cortex-M 上哪些操作天生就是原子的

这一点想清楚了，很多问题就不用再纠结。

**32 位 Cortex-M 的规则**（近似说法，足够日常使用）：

| 操作 | 原子？ | 说明 |
|---|---|---|
| 一次 `ldr` 读 32 位对齐的 `uint32_t`/指针 | ✅ | 单条指令, 总线读一个"字" |
| 一次 `str` 写 32 位对齐的 `uint32_t`/指针 | ✅ | 同上 |
| `uint8_t`/`uint16_t` 的单次读写 | ✅ | 包含在 32 位总线里 |
| `uint64_t` 的读或写 | ❌ | 编译器会生成两条 32 位指令 |
| `float`/`double` 的读写 | `float` ✅（单条 `vldr`/`vstr`）；`double` ❌ | |
| `a++`、`a += x`、`a \|= mask` | ❌ | 读-改-写 |
| 结构体的整体赋值 | ❌ | 会拆成多次拷贝 |
| "一组相关的字段"（比如 `total_round` 和 `total_angle`） | ❌ | 两次独立的写，中间可能被别人看到不一致的组合 |

**注意"对齐"两个字**：非对齐访问在 Cortex-M7 上会触发 `UsageFault`（默认禁止），
详见《09》。所以"原子"的前提是**地址是 4 字节对齐的**。

## 7. 保证原子性的三种手段

### 手段 A：关中断（临界区）—— 本工程的主力

```c
    uint32_t primask = __get_PRIMASK();
    __disable_irq();
    ... 就几行代码 ...
    __set_PRIMASK(primask);
```

| 优点 | 缺点 | 适用 |
|---|---|---|
| 最简单、最可靠、没有任何副作用 | 中断会被延迟；临界区长了会影响实时性 | **临界区只有几~几十条指令**时首选 |
| 在 ISR 里也能用（只是退化成无操作） | 只能防本核的中断，防不了 DMA | |

**代价量化**：一次 `__disable_irq/__set_PRIMASK` 大约几条指令（十几纳秒），
本工程 `CANProcessRx()` 在 1kHz 下每次调用一次，开销完全可以忽略；
真正要小心的是**临界区里别放大循环**。

### 手段 B：用一条指令完成 test-and-set

Cortex-M 提供 `LDREX`/`STREX`（独占访问）指令，可以用一条指令原子地完成
"读旧值 + 写新值"：

```c
    if (__atomic_test_and_set(&lock, __ATOMIC_ACQUIRE) == 0) { /* 拿到锁 */ }
    /* 或者用 __atomic_exchange_n / __LDREXW/__STREXW 自己实现 */
```

| 优点 | 缺点 |
|---|---|
| 不用关中断，对实时性影响最小 | 要理解内存序（acquire/release），写错了很难查 |
| 适合"多核/多主"或高频竞争场景 | 本工程是单核，收益不明显 |

本工程没用它 —— **能用简单办法解决就不要上复杂工具**。

### 手段 C：RTOS 的互斥量（Mutex）

```c
    osMutexWait(mutex, osWaitForever);   /* 拿不到就让出 CPU, 等别人放 */
    ...
    osMutexRelease(mutex);
```

| 优点 | 缺点 |
|---|---|
| 拿不到锁时**会让出 CPU**，不会空等 | **不能在 ISR 里用**（ISR 不能阻塞） |
| 支持优先级继承，能避免优先级反转 | 有内核开销（几十~上百周期）；语义更重 |

**本工程为什么没用它？** 两个原因：
1. `CANProcessRx()` 的两个调用者里有一个是**启动期的自测**，
   我们希望"被挡的那个直接返回"，**而不是阻塞等待**（等下去会把实时性拖垮）；
2. 临界区极短，关中断的代价远小于一次内核调用。

## 8. 本工程里真正用到"原子性"的三处

### ① CAN 接收的双消费者保护（`bsp_can.c`）

就是本文开头那段：**用关中断保护 "检查+上锁"**。

### ② DWT 时间轴的 64 位累加（`bsp_dwt.c`）

```c
static void DWT_CyclesUpdate(void)
{
    uint32_t primask = __get_PRIMASK();
    __disable_irq();

    uint32_t cnt_now = DWT->CYCCNT;
    s_cycles_total += (uint64_t)(uint32_t)(cnt_now - s_cycles_last);  /* ← 64 位累加! */
    s_cycles_last = cnt_now;

    __set_PRIMASK(primask);
}
```

**为什么这里也要关中断**：`s_cycles_total` 是 `uint64_t`，它的 `+=` 是
"读低 32 位 → 读高 32 位 → 加法 → 写回两次"，**不是原子的**。
如果两个任务同时调用（INS 任务算 dt、其它地方读时间轴），
就会出现"同一段增量被加两次"或者"`s_cycles_last` 倒退导致时间跳变"。

### ③ 崩溃现场记录（`bsp_crash.c`）

那里反而是**刻意不做任何保护**的：因为 handler 里一旦再出问题就是 Lockup，
所以它只写内存、不做同步（崩溃时整个系统已经停了，没有"别人"会和它竞争）。

**这是一个重要提醒**：不是"所有共享变量都要加锁"，而是
"**先问清楚有谁会并发访问它**，再决定要不要保护"。

## 9. 有时候根本不需要锁：靠"所有权约定"

本工程的 CAN 接收队列（《12》）用的是 **SPSC 环形队列**：

```
   head 只由中断(生产者)写, 任务只读
   tail 只由任务(消费者)写, 中断只读
```

**这个约定本身就是一种"无锁设计"**：

- 两个索引各自只有一个写者 → 单次 32 位写原子 → 不需要加锁；
- 剩下的只是"顺序问题"：生产者**先写数据再发布 head**，
  消费者**先读完数据再推进 tail**，各加一条 `__DMB()` 内存屏障即可。

> **设计原则**：能用"所有权约定"（谁写谁读）消除竞争的，就不要上锁。
> 锁会带来延迟、优先级反转、死锁风险；而"约定"什么都不花。

## 10. 常见误区清单

| 误区 | 事实 |
|---|---|
| "加了 `volatile` 就线程安全了" | `volatile` 只保证"每次都真读真写"，不保证读-改-写不可打断 |
| "两个任务不会同时跑，所以不用管" | RTOS 会让它们在任何两条指令之间切换；抢占式调度下"同时"是常态 |
| "在 ISR 里用 mutex 等锁就行" | ISR 里不能阻塞，只能用"关中断"或"直接返回"这类非阻塞手段 |
| "关中断会严重影响性能" | 几~几十条指令的临界区，开销在纳秒级；真正贵的是**长临界区** |
| "`a++` 是一步操作" | 它是读-改-写三步，必须保护 |
| "`uint64_t` 也是 32 位单片机的原生类型" | 32 位机上一次只能动 32 位，64 位操作必然拆成多条指令 |
| "只要没人写就不用保护" | 还要看**有没有人写一部分、别人读另一部分**（多字段一致性） |

## 11. 速查表：遇到共享变量该怎么做

```
有一个变量会被"不止一个执行者"访问?
│
├─ 只有一个写者, 其它都是只读, 且是"单次 32 位对齐读写"
│     → 天然原子, 不用保护 ✓
│
├─ 多个写者, 或者要做"读-改-写"
│     │
│     ├─ 临界区只有几~几十条指令, 且不涉及阻塞
│     │     → 关中断临界区(存 PRIMASK → disable → 干活 → 恢复) ✓ 本工程首选
│     │
│     ├─ 需要"拿不到就让出 CPU", 且只在任务上下文
│     │     → RTOS mutex
│     │
│     └─ 需要"拿不到就直接放弃"
│           → 原子 test-and-set(LDREX/STREX 或 __atomic_*), 或关中断 + 标志位
│
└─ 一组字段要"配套更新"(比如角度+圈数)
      → 用序号(seqlock)、双缓冲, 或者干脆整份快照 + 临界区拷贝
```

---

## 12. 一句话总结

**"原子"就是"不可被打断"，而单片机里几乎所有打断都来自中断；
所以最朴素的 `__disable_irq()` 临界区，往往就是最对的答案 ——
前提是你要搞清楚三件事：谁在写、谁在读、以及你保护的到底是"一个变量的读改写"
还是"一组字段的配套更新"。**
