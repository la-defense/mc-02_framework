# Ozone 辅助 PID 调参

> 本篇整理历史调参笔记中的阶跃响应和模型辨识思路。Ozone 中改写参考值可能直接驱动执行器；MC-02 的裸板联调边界禁止驱动执行器。任何真实机构调参都必须先满足 `.Doc/TODO.md` 中对应的安全验收条件，并由受控台架单独安排。

Ozone的实时变量可视化监测(示波器)功能可以很好地帮助我们观察控制器在时域的表现，典型的有上升时间、超调量和稳态时间等。

## 调试顺序

先内环，后外环。若有已知的外部扰动如阻力、重力等可以在**保持kp不变**的情况下添加积分环节，并查看达到稳态时积分的输出，该输出值可以作为**前馈**作用通过feedforward_ptr一同送入下一个串级控制器。在没有模型的时候，计算前馈一般通过**数据驱动**的方法，如稳态误差-参考值关系拟合。

经典的经验式整定方法有简单的Ziegler-Nicols法和Cohen-Coon法，还有需要一定的系统辨识的Chien-Hrones-Reswick、Tyreus-Luyben和Skogestad法。这些方法在网络上或提出方法的论文中都有详尽的说明，这里不再赘述。

我们可以使用上述方法确定一套参数的初值，再根据时域表现进行精细的参数调整。

## 电机方向标志与 PID 符号（MC02-0018、MC02-0019）

方向设置要放在明确的控制位置。MOTOR-01/02 记录的 LK、HT 兼容行为仍保留在对应历史实现说明中；当前 DJI、LK9025 和 HT04 的输出轴方向由 `output_axis.direction` 统一处理，旧 `motor_reverse_flag` 与 `feedback_reverse_flag` 必须保持 `NORMAL`。输出轴测量和目标使用相同方向映射，闭环结果再映回驱动方向。XM 仍未接入真实通信，不据其骨架代码推断设备能力。

直接电流／力矩输出仍是设备侧数值，不由输出轴角度方向自动换算；需要方向适配时必须由应用配置明确处理。当前初始化拒绝非 `NORMAL` 的旧方向标志，避免同一电机重复施加两套方向规则。软件测试验证输出轴转换和固定控制结果；实际电机转向还受接线及机构定义影响，本轮没有连接或驱动电机，不能用主机测试证明物理正方向。

以笔者个人的纯调参无模型云台调试经验，可以进行如下步骤：

1. 首先整定P参数，使用二分法确定大致范围。将电机参考速度和实际速度在Ozone示波器同一窗口中打开以观察时域表现。把pid的ref值添加到变量观测，方便修改（只要修改ref值，每次就可以触发阶跃信号输入）。当P达到欠阻尼且波动只有一个周期（只有超调一个峰）时，开始添加D参数。
2. 添加微分参数。务必打开微分滤波器，并根据你的闭环带宽（速度环要跟随的频率）设置滤波系数。目前使用的是一阶低通滤波，后续考虑增加高阶滤波器和特殊的带宽滤波器（切比雪夫、巴特沃斯等）。调节D参数至P进入临界阻尼或过阻尼的状态（没有超调）。
3. 交替增大比例系数和微分系数，直到出现不可控的微分抖动，然后减小两者的值直到出现一个合适的平衡（调个大概即可，没有模型的情况下很难达到均衡）
4. **固定PD参数**，查看不同目标值的**静差**。如果没有对云台进行建模，则拟合目标值与静差的关系（线性、多项式、指数、对数），并将该值作为前馈加入系统，以补偿PD无法影响的扰动项。
5. 增加额外的积分控制以消除前馈模型不准确带来的影响。务必使用积分分离和变速积分。参数不要求精细，一般来说大致即可。

## model-based控制

无模型的控制显然存在其劣势和效果上限，为了提高性能，我们需要对云台进行建模。

建模的方式包括动力学方程推导和数据驱动的系统辨识。

动力学方程的推导即分析系统的输入（电机的扭矩）和输出（速度/角度）的关系，得到系统动态的微分方程，然后使输入等于微分方程中除输出外的项，从而让输出的动态变为简单的一阶线性常微分方程，以最快的方式到达期望位置。此时再额外增加PID控制器，用于补偿建模得到的系统和实际不匹配造成的误差。建模考虑的因素越全面，建模的效果可能会越好。

系统辨识的经典方法是伯德图法即频域分析。通过给定一系列的正弦输入，观察系统的输出表现得到系统的相频曲线和幅频特性曲线，并选择一个特定结构的系统对曲线进行拟合（最小二乘或极大似然估计），对得到的系统应用超前-滞后补偿控制器以确定合适的PID参数，在裕度和带宽之间权衡，使得系统的频率响应满足设计要求。

Ozone可以非常方便的获取系统的频率响应数据。


## 电机参考值和反馈量要按驱动分别看（MC02-0123）

调用 `SetRef()` 时先查具体驱动怎样使用参考值。DJI、HT04 和 LK9025 的角度／速度环统一用输出轴 rad、rad/s 作为参考、反馈和 PID 输入；协议原始字段可能仍是转子 deg、deg/s 或设备量纲，由驱动边界显式换算。电流及力矩保持设备侧数值，不因字段名推断为 A 或 N·m。DM 电机先按方向反转并把参考限制在协议数值范围内，再编码发送；DM 的 `−18～18` 是当前协议范围，不代表已确认的实际力矩单位。

舵机也有两种不同的输入：总线舵机直接发送位置整数，实际角度范围由舵机决定；PWM 舵机直接使用 0 到 1 的占空比。XM 驱动当前只保存软件对象和标志，还没有接上电机通信。使用这些接口前要看对应驱动的单位和当前实现。

多个驱动的停止接口只设置停止标志或发送停止命令，DJI 的停止标志不会清掉已保存的参考值。DM 的 Stop 会清除本地参考并停止采用目标；应用层重新使能后仍需等待使能发送结果，再提交新参考。其他驱动仍要按各自的接口和状态流程处理旧参考。

### DM 只在显式使能后发送力矩（MOTOR-03）

`DMMotorInit()` 只准备实例、Daemon 和 CAN 接收对象，不会发送使能、编码器置零或控制帧，也不再等待固定时长。注册成功的实例初始保持停止，参考为零；调度器启动前最多串行注册4个实例，全部电机任务创建成功后不再接受新注册。注册配置按只读输入处理：直接力矩模式必须关闭闭环和前馈，同一总线上的发送 ID 或接收 ID 不能重复，底层分配或登记失败会回收本次对象。

`DMMotorEnable()` 和 `DMMotorCaliEncoder()` 只把请求放入单个命令槽，由对应电机任务发送一次。`QUEUED` 表示请求已排队；查询到命令结果为 `ACCEPTED`，只表示本机 CAN 接口接受报文，不表示电机已执行。使能帧被接受后会清掉此前所有参考，调用方应先读状态，再提交新参考。Stop 会取消尚未提交的命令；已进入 CAN 提交的报文无法撤回，提交结束后也不会重新打开本地运行状态。置零前要由调用方确认机械静止，置零后电机仍保持停止。

力矩处理每轮只读取一次参考和方向，先执行反向，再限制到 `−18～18`，最后才写入12位字段。对应的固定编码是 `+9 → 0xBFF`、`−9 → 0x3FF`、`−18 → 0x000`、`+18 → 0xFFF`；零力矩为 `0x7FF`。停机控制帧仍保留位置和速度字段，不能把8字节整帧清零。NaN／Inf 不会沿用旧目标，本轮采用零力矩，后续重新提交有限参考后可恢复。

主机回归链接生产 DM、FDCAN 注册和 Daemon，只替换 HAL、RTOS、时间与日志。测试覆盖注册失败回退、任务创建回收、忙／拒绝／取消、停止与提交交错、正反向和限幅编码、多实例及并发接口。仓库验收使用 WSL 主机测试和 ARM 固件构建，不要求 Windows 原生编译；当前固件没有调用 DM 电机，ELF 中的 DM 目标节由链接器移除。本轮没有连接开发板或电机。实际型号、固件、物理力矩单位和电机响应仍需确认，见 [MOTOR-03 验证记录](../workflow/tickets/MOTOR-03.md)。

### LK9025 与 HT04 如何选闭环反馈（MOTOR-01、MOTOR-02）

三环串级时，每一步结果会成为下一环的目标。现在 DJI、HT04 和 LK9025 的角度／速度闭环统一使用**输出轴 rad、rad/s**：参考值、反馈值以及对应 PID 的输入使用相同单位。电流环仍使用驱动自身的电流数值，设备反馈里的电流、力矩或电压不会因为字段名称而自动成为 A、N·m 或 V。

每个电机配置 `output_axis.gear_ratio` 和 `output_axis.direction`。减速比定义为转子转数／输出轴转数，方向用来把转子测量换成输出轴坐标，并把输出轴控制结果映回驱动方向。DJI 的原始编码器总角度仍是 deg、转子速度仍是 deg/s；驱动在反馈快照中统一转换。LK 的角度和速度原始字段单位并不相同，转换时分别处理，不能套用一个角度系数。应用层的单位转换留在明确的边界：云台命令从 deg 转成 rad，底盘运动学结果从 deg/s 转成输出轴 rad/s，拨弹盘每发角度按槽数计算为 rad。

外部反馈和前馈通过只读回调提供完整快照，不再保存裸 `float *`。配置声明单位、参考系和最大年龄；快照包含有限数值、采样时刻、非零序号和有效标记。控制周期会检查这些字段，过期或不匹配的数据会让本周期输出零并清除该实例 PID 历史。回调需要由调用方用合适的同步方式复制数据；“只读”接口本身不提供跨任务一致性。

DJI 的单圈编码器反馈不能独自说明停机期间错过了多少整圈。首次收到有效样本时先建立多圈基准；若反馈中断后无法证明跨圈变化可信，多圈位置会失效，不能继续作为内部角度环反馈。需要新的可信机械参考时，应用显式调用 `DJIMotorRebaseReference()` 后才能恢复；外部角度来源则按自己的有效期判断。

LK 仍分别选择 `angle_feedback_source` 和 `speed_feedback_source`，速度环使用独立 `speed_PID`；HT04 也独立选择角度与速度来源。反馈源切换不会串用不同环的积分和微分历史。前馈仍在原有串级位置加入，单位需与该处目标一致。初始化只要求实际会运行的 PID 和来源有效，未使用的环可保持空配置。

迁移 PID 单位时，增益、积分限幅、输出限幅和死区也要按输入／输出单位变化换算，不能只把反馈数字乘一个系数。MC02-0072 的配置和主机固定答案验证了软件换算关系，但本机当前没有连接电机，本轮没有做机械方向核对、增益整定、物理单位标定或动态响应验收。实现与边界见 [MC02-0072 记录](../workflow/tickets/MC02-0072.md)、[MOTOR-01/02 记录](../workflow/tickets/MOTOR-01-02.md) 与 [MC02-0017 记录](../workflow/tickets/MC02-0017.md)。

## PID 调用间隔、死区和输出（MC02-0015、BSPMISC-02）

[controller.h](../../modules/algorithm/controller.h) 要求 `measure` 和 `ref` 使用同一单位；实际输出单位由增益和被控对象决定。现在由调用模块测量真实间隔，再以秒传给 `PIDCalculate()`。算法不再读取 DWT，也不会把过小间隔改成10微秒。`DtMin_s`、`DtMax_s`、`Output_LPF_RC` 和 `Derivative_LPF_RC` 都以秒表示。

误差绝对值不大于 `DeadBand` 时，输出、本次积分增量和累计积分都清零。打开堵转检查后，`ERRORCount` 按调用次数累计，参考值接近0或输出很小时不计数；误差比例连续超过95%，计数大于500后标记堵转。这个数字表示调用次数，换算成时间要结合 PID 实际调用频率。

## 云台模式的实际行为（APP-09）

`GimbalTask()` 读取最多保存50 ms的云台命令。没有新命令、命令过期或读取失败时，本地命令会清零并进入 `GIMBAL_ZERO_FORCE` 分支。

`GIMBAL_GYRO_MODE` 和 `GIMBAL_FREE_MODE` 当前执行相同动作：使能 yaw、pitch 电机，把角度环和速度环的反馈来源设为 `OTHER_FEED`，并将命令中的度换成弧度后设置参考值。外部角度反馈来自 INS 的 yaw 总角度和 pitch 角度，速度反馈分别使用 Z 轴和 X 轴陀螺仪；数据单位为 rad、rad/s，反馈允许年龄为5 ms。`FREE` 目前没有独立的底盘跟随行为，不能按名称推断它改用编码器。

零力和未知模式都会调用 `DJIMotorStop()` 并把两路参考设为零。停止接口设置软件标志，后续电机发送周期据此清零对应发送槽；任务返回不能证明 CAN 已完成发送或电机机械运动已经停止。生产状态转换由 [gimbal_mode_test.c](../../tests/host/gimbal_mode_test.c) 检查，模式说明见 [gimbal.md](../../application/gimbal/gimbal.md) 与 [APP-09 记录](../workflow/tickets/APP-09.md)。本机测试不验证真实电机响应、方向或物理停止时间。

### 时间由谁测量

电机使用 [motor_pid.c](../../modules/motor/motor_pid.c) 保存每个电机的控制调用时刻；驱动读取现有微秒时基，一轮串级计算只取一次 dt。反馈接收的间隔仍单独保存，不能拿它代替控制任务的调用间隔。电机当前允许10微秒到50毫秒，两端都允许。

温控在 [imu_heater.c](../../modules/imu/imu_heater.c) 中用现有毫秒计数测量间隔，允许大于0且不超过20毫秒；其计时精度仍是1毫秒。首轮只记录时刻，输出保持0；得到下一次允许范围内的间隔后才计算。关闭或恢复温控时重新建立起点，不能把标定或 Flash 操作期间的长时间拿来累计积分。

换算秒数采用除法。例如20毫秒除以1000后与配置中的0.02秒比较，避免乘以单精度0.001时引入额外舍入，误把允许的上限当成超时。

### 返回错误时怎样处理

`PIDInstance` 由调用者长期保存，首次使用前清零。`PIDInit()` 检查整份参数，成功才接受；未启用的电机环可以保持未初始化。原来声明但没有实现的 `PID_Proportional_On_Measurement` 会被明确拒绝。

```c
PIDInstance pid = {0};
PID_Init_Config_s config = {
    .Kp = 2.0f, .Ki = 3.0f, .Kd = 0.1f,
    .MaxOut = 1000.0f,
    .DtMin_s = 0.00001f, .DtMax_s = 0.05f,
};
float output = 0.0f;
PID_Status_e status = PIDInit(&pid, &config);
if (status == PID_OK)
    status = PIDCalculate(&pid, 1.0f, 3.0f, 0.01f, &output);
if (status != PID_OK)
    output = 0.0f; // 调用模块本周期只采用零输出。
```

这组正常输入得到 P=4、I=0.06、D=20，输出为24.06。dt 若为0、负数、NaN/Inf或超出允许范围，计算返回错误。参数及中间结果也检查是否为有限数值。

算法先在局部数据上计算，成功才保存。失败时实例和输出参数保持原值，因此业务不能把旧输出当成这次成功结果。电机驱动将本轮发送数值置0并清除各环历史；温控直接关闭 PWM。`PIDReset()` 清除全部计算历史并保留参数；`PIDGetState()` 复制最近成功的数据，修改副本不会改变控制器。同一实例仍须顺序使用，不能由两个任务同时修改。

### 为什么两个电机不能共用临时变量

原积分限幅函数中的两个 `static float` 由所有 PID 实例共用。如果另一个任务在计算中途进入该函数，临时值可能被覆盖。现在每次调用使用自己的局部变量，积分、微分和堵转计数也只保存在对应实例中。

[PID 回归](../../tests/host/pid_test.c) 用手算数值、不同 dt、非法输入及不同实例交错调用检查行为；Linux 额外运行两个线程，比较它们与分别运行时的结果。[电机回归](../../tests/host/motor_pid_integration_test.c) 运行生产 DJI 驱动，检查串级环共用 dt、首轮零输出、初始化拒绝和计算失败后的 CAN 字节。温控回归每毫秒提供新样本来检查五分钟边界，不用一次超长 dt 跳过持续加热。

验证命令、工具限制及裸板证据见 [MC02-0015 记录](../workflow/tickets/MC02-0015.md)。禁热裸板只能检查启动、通信和输出关闭，不能据此判断真实闭环响应或加热性能。

2026-10-17用软件提交`1b10845`完成本机和裸板检查：WSL Debug／Release各112项通过，Windows两种配置的可移植子集各14项通过，六种禁热固件及ELF检查通过。板上连续60.22秒收到12,042个CRC正确且四元数有限的状态帧，发送0帧；参数区逐字节保留，IMU数据递增，加热和输出保持关闭。

这次IMU初始化阶段为READY（9），整车状态为ESTOP（6）、使能请求为0。两种状态说明不同的事情：前者表示传感器完成启动，后者表示整车仍不允许执行输出。检查记录要分别保存，不能只看到一个“READY”就认为机器人已经使能。

## 云台和拨弹时钟的平台接口（MC02-0086）

云台读取消息时的有效期检查，以及发射命令和电机反馈的时间检查，改用 `PlatformTimeNowMs()`；H723 后端仍读取原 HAL 毫秒时钟。拨弹间隔仍按原来的浮点毫秒时间判断，`PlatformProbeTimelineMs()` 在该板上转发给原 DWT 计算，不改变 150／300 ms 等待条件。Debug、Release 和 ASan／UBSan 主机回归检查云台模式及发射命令过期后的重新使能；两份生产源码也用测试车型配置完成无厂商头路径的 ARM 单文件编译和依赖检查。

这些检查不代表发射机构已经完成实物验收。当前生产哨兵配置仍受机械参数和云台能力门槛阻止；未在本次构建中链接、启动或驱动机器人执行器。
## LK 电机计时与任务锁（MC02-0086）

LK 驱动通过框架接口读取毫秒和微秒时间、计算反馈周期，并进入任务临界区。MC-02 后端沿用原有 HAL 毫秒时钟、DWT 微秒累计时间和 FreeRTOS 任务锁；目标值、PID 运算顺序和 CAN 报文格式没有变化。来源数据时间仍来自接收队列，调用时钟不刷新来源期限。

Debug、Release 和 ASan／UBSan 的 LK 注册、跨总线发送、闭环、前馈和反馈失效共15项主机回归通过。默认禁热固件不选择 LK，因而该固件通过链接检查不能证明 LK 已参与固件链接；驱动仍持有板级 CAN 实例，接口隔离尚未完成，也没有驱动电机。

LK 后续已改用逻辑 CAN 端点：注册时保留原来的每电机反馈 ID 和每总线 `0x280` 组发送 ID，接收任务交付只读帧及中断入队时间；错误长度不会更新反馈。每条逻辑总线使用长期保存的组标识提交最新周期帧，注册失败仍撤销已申请的 Daemon 并释放对象。LK 源码可只带框架头路径编译成 ARM 对象；这还不是完整机器人固件。

新增主机测试经过生产 CAN 入队、端点适配和 LK 解码，核对入队时间与任务派发时间不同、短帧不能刷新反馈；连同既有注册、回退和分组发送共16项在 Debug／Release／ASan＋UBSan 通过。默认禁热诊断固件不包含 LK；未验证板上通信或实际电机。

HT 驱动的反馈周期、毫秒／微秒时间和任务临界区也改为框架接口；每电机的控制任务通过平台创建，继续使用普通优先级、128 栈字及每轮 1 ms 等待。旧 CMSIS 宏实际生成的任务名是 `ht_task_name`，这里沿用该名称。初始化时发送模式及置零命令的顺序没有变化；当时任务创建失败上报和 CAN 端点隔离尚未完成，后续改动见下文。

生产任务适配器配合 CMSIS 替身，检查任务入口、名称和栈大小，并通过19项 HT 反馈、闭环、前馈、异常恢复与方向回归；Debug、Release、ASan／UBSan 均通过。这些测试不会向真实电机发命令，也不证明任务调度时限。

HT 的 CAN 接收和发送现在使用逻辑端点，帧长度不足 6 字节时不更新反馈；有效反馈保留接收时刻。模式与置零命令交给原有的一次性发送队列，周期控制仍提交最新帧。初始化阶段的 5 ms 和 50 ms 忙等经专用板级接口保留原行为，尚未改造启动流程。

HT 的19项主机回归覆盖模式命令、延时顺序、短帧及原始接收时间；生产 CAN 队列测试检查未绑定总线和有限重试。驱动另行通过 ARM 单文件编译及头依赖检查；默认禁热固件未选择 HT，不能据此证明完整机器人固件链接或真实电机运行。

HT 控制任务创建现在返回结果：无电机返回成功，某个任务创建失败时立即返回失败，已经创建的任务不删除。启动阶段再次调用只补建缺失任务，避免同一电机出现两个控制任务。整车任务初始化收到失败后记录电机任务故障并返回失败，由原有启动失能路径处理；其他核心任务已失败时不创建 HT 任务。

主机回归注入第二个 HT 任务创建失败，核对结果、重试及重复调用；另用真实整车任务创建流程检查故障上报。Debug、Release 与 ASan／UBSan 的相关 HT 和整车创建测试通过。这些检查不启动真实调度器，不能证明板上资源足够或电机停止时限。
