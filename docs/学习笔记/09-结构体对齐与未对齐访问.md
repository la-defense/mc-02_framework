# 09 结构体对齐、`#pragma pack(1)` 与"为什么 -O2 一上电就 HardFault"（写给零基础）

> 本篇回答的问题：
> 1. "对齐"到底是什么？为什么硬件会关心变量放在哪个地址？
> 2. `#pragma pack(1)` 有什么好处，为什么它差点害死我们？
> 3. 同一份代码 `-Og` 跑得好好的，为什么 `-O2` 一上电就 HardFault？
> 4. 现场拿到一个 HardFault，怎么在 10 分钟内定位到出错的函数？
>
> 对应代码：`bsp/can/bsp_can.h`（本轮修复点）、`dji_motor.c`、`bsp/dwt/bsp_dwt.c`。

---

## 1. 什么叫"对齐"

CPU 访问内存时，**地址本身**会影响能不能"一次读完"。

以 32 位（4 字节）的 `uint32_t` 为例：

| 地址 | 4 字节对齐？ | 说明 |
|---|---|---|
| `0x2000_0000` | ✅ | 地址能被 4 整除 |
| `0x2000_0004` | ✅ | |
| `0x2000_0002` | ❌ | 这个 4 字节数据"跨"在两个 4 字节格子之间 |

为什么硬件在意？因为内存总线一次只能搬运一个"格子"（比如 4 字节）。
如果一个数据跨了两个格子，硬件要么：

- 拆成两次访问再拼起来（慢，而且有些指令根本不支持）；
- 直接报错（就是我们要讲的 **UsageFault: UNALIGNED**）。

**编译器正常情况下会自动帮你对齐**：它给每个类型规定对齐要求
（`char`=1、`short`=2、`int`/`float`/指针=4、`double`/`long long`=8），
然后通过**在结构体成员之间插入填充字节（padding）**来保证每个成员都落在自己的对齐边界上。

例如：

```c
struct A { uint8_t a; uint32_t b; };   /* 自然对齐下: 1 字节 a + 3 字节填充 + 4 字节 b = 8 字节 */
```

那 3 个填充字节看起来"浪费"，但它们保证 `b` 一定在 4 的倍数地址上。

## 2. `#pragma pack(1)` 做了什么，为什么有人喜欢它

`#pragma pack(1)` 的意思是：**"别插填充了，成员紧挨着排"**。

```c
#pragma pack(1)
struct P { uint8_t a; uint32_t b; };   /* 5 字节, b 落在 offset 1 —— 非对齐! */
#pragma pack()
```

为什么有人用？

1. **省 RAM**（嵌入式里字节也是钱）；
2. **协议/报文结构体必须紧凑**：比如裁判系统协议里"第 3 个字节是血量低 8 位"，
   如果编译器插了填充，收发两边就对不上了；
3. 有些老代码的"把结构体整个 cast 成 `uint8_t*` 发出去"的写法依赖紧凑布局。

**结论**：`pack(1)` 用在"**只当作字节数组来收发**"的结构体上是合理的；
用在"**会被 CPU 按成员类型直接读写**"的结构体上是危险的。

## 3. 编译器会做一件很关键的事：把多次字节访问"合并"

看 HAL 里的一段真实代码（`stm32h7xx_hal_fdcan.c: FDCAN_CopyMessageToRAM`）：

```c
for (ByteCounter = 0; ByteCounter < DLCtoBytes[...]; ByteCounter += 4U)
{
    *TxAddress = (((uint32_t)pTxData[ByteCounter + 3U] << 24) |
                  ((uint32_t)pTxData[ByteCounter + 2U] << 16) |
                  ((uint32_t)pTxData[ByteCounter + 1U] << 8)  |
                  ((uint32_t)pTxData[ByteCounter]));
    TxAddress++;
}
```

人的理解是"读 4 个字节拼成一个 32 位字"。
但编译器（尤其是 `-O2`）会想：**小端机器上，这正好等于"从 `pTxData+ByteCounter` 读一个 32 位字"**——
于是它把 4 条字节读**合并成一条 `ldr r3, [r1, r2]`**。

这条优化本身完全正确，而且更快。**但它要求 `pTxData+ByteCounter` 是 4 字节对齐的**：

- 对得上 → 一切正常；
- 对不上 → **UsageFault(UNALIGNED)** → 因为 UsageFault 是"可配置优先级故障"，
  没有被单独使能处理时会被升级成 **HardFault** → 程序挂死/复位循环。

`-Og`（我们日常开发用的优化级别）**不会做这个合并**：它老老实实读 4 个字节。
于是就出现了最难受的一类现象：

> **同一份源码，`-Og` 正常，`-O2` 崩溃。**

这不是"编译器有 bug"，而是**我们的代码在 `-Og` 下"侥幸正确"，在 `-O2` 下暴露了真正的未定义/未对齐行为**。

## 4. 本轮的真实案例（完整复盘）

### 4.1 现象

切到 `-O2`（`build-perf`）烧录后：

- 日志打到 `[bmi088] 使用 Flash 标定记录` 就没了；
- 每 ~4 秒复位一次，复位原因 `IWDG1`；
- 无 `HardFault` 打印（`HardFault_Handler` 里只有 `while(1)`，没打印）。

一开始我们以为是"卡死"，因为现象确实是"不动 + 看门狗复位"。

### 4.2 第一步：不要猜，先读故障寄存器

Cortex-M7 有三个"出事报告"寄存器（地址固定）：

| 寄存器 | 地址 | 作用 |
|---|---|---|
| CFSR | `0xE000ED28` | 可配置故障状态：MemManage / BusFault / **UsageFault** |
| HFSR | `0xE000ED2C` | 硬故障状态；bit30 = FORCED（由别的故障升级而来） |
| BFAR / MMFAR | `0xE000ED38` / `0xE000ED34` | 出错的**地址**（只对 BusFault/MemManage 有效） |

用 OpenOCD 直接读：

```bash
openocd -f interface/cmsis-dap.cfg -f target/stm32h7x.cfg \
  -c "init" -c "halt" -c "mdw 0xE000ED28 1" -c "mdw 0xE000ED2C 1" -c "reg pc" -c "shutdown"
```

读到的结果：

```
0xe000ed28: 01000000     ← CFSR
0xe000ed2c: 40000000     ← HFSR
pc: 0x08001ca0
```

解读：

- `CFSR = 0x01000000` = **bit24 = UFSR.UNALIGNED** → 「执行了非对齐访问」；
- `HFSR = 0x40000000` = **bit30 = FORCED** → 「这是被升级上来的硬故障」；
- `pc = 0x08001CA0`：用 `arm-none-eabi-addr2line` 一查 → `HardFault_Handler`。

**到这里，"卡死"变成了明确的一句话：有代码做了非对齐访问。**

### 4.3 第二步：找出"是谁做的"

`HardFault_Handler` 只是终点，要看**从哪跳进来的**。两种办法：

**办法 A（推荐）：让 GDB 打回溯**

```bash
python skills/debug-gdb-openocd/scripts/gdb_debugger.py \
  --elf build-perf/Basic_Framework_MC02.elf \
  --interface cmsis-dap --target target/stm32h7x.cfg \
  --mode crash-context
```

输出（截取关键部分）：

```
#0 HardFault_Handler ()
#1 <signal handler called>
#2 FDCAN_CopyMessageToRAM (hfdcan=..., pTxHeader=0x24000331 ..., pTxData=0x2400035d "", ...)
#3 HAL_FDCAN_AddMessageToTxFifoQ (...)
#4 CANTransmit (bsp_can.c:534)
#5 DJIMotorControl (dji_motor.c:404)
#6 MotorControlTask ()
#7 StartMOTORTASK ()
```

**一眼就定位到了：CAN 发送。**

**办法 B：手动解栈**

`HardFault` 时 CPU 会把出事现场的 `R0-R3/R12/LR/PC/xPSR` 压到栈上，
`LR` 若是 `0xFFFFFFEx` 形式就是异常返回标记，据此判断用 MSP 还是 PSP，
再 dump 栈（`mdw <sp> 22`）并找其中那个 `0x08xxxxxx` 的值就是出错 PC。
不如 GDB 舒服，但在没有 GDB 的场合能用。

### 4.4 第三步：看 `pTxData` 的地址

回溯里最扎眼的是：

```
pTxData = 0x2400035d      ← 结尾是 ...5d，不是 4 的倍数!
pTxHeader = 0x24000331    ← 同样非对齐
```

一个**本该 4 字节对齐的缓冲区，地址却是奇数**。查 `bsp_can.h`：

```c
#pragma pack(1)                      /* ← 元凶 */
typedef struct _ {
    FDCAN_HandleTypeDef *can_handle; /* 4B */
    FDCAN_TxHeaderTypeDef txconf;    /* 36B */
    uint32_t tx_id;                  /* 4B */
    uint32_t tx_mailbox;             /* 4B */
    uint8_t  tx_buff[8];             /* ← 从 offset 48 开始 */
    ...
} CANInstance;
#pragma pack()
```

再看谁在用它（`dji_motor.c`）：

```c
static CANInstance sender_assignment[9];   /* 9 个元素 */
```

`pack(1)` 让 `sizeof(CANInstance) = 77`（不是 4 的倍数），于是：

```
sender_assignment[0] @ 0x240002E0
sender_assignment[1] @ 0x240002E0 + 77 = 0x2400032D   ← 非 4 字节对齐!
sender_assignment[1].tx_buff = 0x2400032D + 48 = 0x2400035D  ← 就是它!
```

**完整因果链**：

```
CANInstance 被 pack(1)
  → 结构体对齐要求变成 1 字节、sizeof = 77
    → 静态数组 sender_assignment[1..8] 元素地址非 4 对齐
      → tx_buff / &txconf 非 4 对齐
        → -O2 下 HAL 把 4 次字节读合并成一条 32bit ldr
          → UsageFault(UNALIGNED) → HardFault → 死循环 → IWDG 复位
```

而 `-Og` 下 HAL 逐字节拷贝，**非对齐也不会报错**，所以这个问题藏了很久。

### 4.5 修复

```c
/* 去掉 #pragma pack(1)，让编译器自然对齐 */
typedef struct _ { ... } CANInstance;   /* sizeof 77 → 80 */

/* 加编译期兜底: 谁再加回 pack(1)，直接编译不过 */
_Static_assert((sizeof(CANInstance) % 4u) == 0u, "CANInstance 大小必须是 4 的倍数");
_Static_assert((__builtin_offsetof(CANInstance, txconf)  % 4u) == 0u, "txconf 必须 4 字节对齐");
_Static_assert((__builtin_offsetof(CANInstance, tx_buff) % 4u) == 0u, "tx_buff 必须 4 字节对齐");
```

代价是每个实例多 3 字节填充（9 个实例 = 27 字节），换来的是"物理上不可能再非对齐"。

**修复后实测**：`CFSR/HFSR = 0`，EKF `dt ≈ 1.0014ms`，系统稳定运行，
`-O2` 从"一上电就复位"变成"可正常使用"。

## 5. 怎么预防同类问题（按性价比排序）

### 5.1 搞清楚 `pack(1)` 的使用边界（最重要）

| 结构体用途 | 要不要 `pack(1)` |
|---|---|
| 直接当字节数组收发（裁判协议、视觉协议、CAN 报文净荷结构） | **要**（否则两端字节位置对不上） |
| 会被 CPU 按成员直接读写的驱动/实例结构体 | **不要**（CANInstance 就是反例） |
| 里面含指针 / `float` / `double` 的结构体 | **强烈不要** |

**本项目要注意的清单**：`application/robot_def.h`、`modules/referee/referee_protocol.h`、
`modules/master_machine/master_process.h`、`modules/can_comm/can_comm.h` 里都有 `pack(1)`，
它们大多是"协议结构体"，属于第一类；但**只要有人把它们的某个成员指针直接交给 HAL/DMA
按 32 位访问，就会重演今天的故障**。查的时候问自己一句：
"这个结构体的成员，会被某个库函数当 `uint32_t*` 用吗？"

### 5.2 用 `_Static_assert` 把约束写进代码

编译期就能挡住的错误，绝不留到运行时。除了上面的对齐断言，还可以断言
"协议结构体的大小必须等于多少字节"——这一招在协议对接里特别好用：

```c
_Static_assert(sizeof(RefereeFrame_t) == 12, "协议长度变了?!");
```

### 5.3 需要紧凑、又需要对齐时怎么办

如果确实要"紧凑布局 + 成员对齐"，可以让编译器"结构体内部紧凑、结构体本身仍对齐"：

```c
struct __attribute__((packed, aligned(4))) Foo { ... };
```

或者干脆把热字段放到结构体开头（偏移 0 一定对齐）。

### 5.4 关键：把 `-O2` 纳入日常验证

这个 bug 之所以藏了这么久，就是因为**平时只跑 `-Og`**。
现在工程有两套构建（见《01》）：

```bash
cmake -S . -B build      -G Ninja -DCMAKE_BUILD_TYPE=Debug           # -Og: 日常开发/调试
cmake -S . -B build-perf -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo  # -O2: 每个里程碑至少跑一次
```

**建议把它变成习惯：每次改完底层驱动（CAN/SPI/UART/Flash/DMA），
至少烧一次 `-O2` 跑 10 分钟再算完成。**

### 5.5 兜底：把 HardFault 变成"能说话"

当前 `HardFault_Handler` 是 `while(1)`，什么都不打印，只能靠调试器。
可以升级成"把 CFSR/HFSR/BFAR 和出错 PC 存到 RAM 里 + 打印"，
这样即使不接调试器也能事后分析（记得 RAM 里的现场在复位后可能被清掉，
可以考虑放到不参与初始化的段或直接写 RTT）。

## 6. 速查表

| 现象 | 可能原因 | 快速检查 |
|---|---|---|
| `-Og` 正常、`-O2` HardFault | 非对齐访问被优化暴露 | 读 CFSR 看 bit24（UNALIGNED） |
| CFSR=0x01000000, HFSR=0x40000000 | UsageFault(UNALIGNED) 升级为 HardFault | 用 GDB `bt` 找调用链 |
| 某个"本该对齐"的指针地址是奇数 | 结构体被 `pack(1)` / 数组元素大小非 4 倍数 | 查 `sizeof` 与 `offsetof` |
| 只在某些元素上出错 | 数组第 0 个对齐，第 1 个开始错位 | 手算 `base + n*sizeof` |
| 只在调用 HAL 时出错 | HAL 内部把字节读合并成 32 位读 | 看该缓冲区是否 4 字节对齐 |

---

## 7. 一句话总结

**"对齐"不是编译器的洁癖，而是硬件总线的物理约束；
`#pragma pack(1)` 只在"纯字节协议"上安全；
而 `-O2` 会把"侥幸正确"的代码变成"明确错误"——
所以底层驱动改完，一定要用 `-O2` 再验一次。**
