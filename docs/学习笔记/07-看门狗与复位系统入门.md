# 07 看门狗与复位系统入门（写给零基础）

## CubeMX 重新生成后的人工核对（MC02-0087）

重新生成会影响启动顺序、失败处理和中断接入。先保存当前提交、`.ioc` 和实际使用的 CMake 配置，在可比较的工作副本中生成，再逐项检查差异。不要仅凭 `USER CODE` 标记判断定制代码已经保留。

1. 检查 `Core/Src/main.c`：早期直接关断和复位记录仍先执行；主时钟经过固定期限保护，外设之前建立看门狗。车型校验先于业务外设准备，CAN 控制器复用 `RobotCollectCanDemands()`，未恢复无条件 OSPI、TIM1／TIM2 初始化。`RobotInit()` 不以整段中断屏蔽包围设备等待。
2. 检查 `Core/Src/freertos.c`：默认任务仍用既定的静态存储，由 `RobotStartupRun()` 完成业务初始化、诊断、任务创建和放行。USB 空配置兜底在业务注册之后执行，随后继续维护 USB 生命周期。周期任务等待统一放行，启动等待不能被当作任务已完成工作。
3. 检查时钟及外设受检查入口：VOS、时钟切换、外设准备共享既定总期限；轮询或切换设备不延长期限，停表仍有次数上限。SPI、PWM、ADC、UART、CAN 的失败应返回给启动计划，不能重新变成一律调用 `Error_Handler()`。`HAL_GetTick()` 的工程定义及启动等待保护仍保留。
4. 检查中断与退出：FDCAN 共享时钟使用计数和独立过滤器配置；UART 退出先禁用并清除自身 IRQ／DMA，I²C 错误 IRQ 同样处理；共享 EXTI 入口逐引脚派发。同步 BMI088 配置不恢复数据就绪 EXTI。重入或重复退出不能关闭其他控制器的资源。
5. 检查受控输出：三路电源与加热输出仍先写关闭值；电源阶段和使用模块来自车型声明。普通裸板配置保持禁热、禁火和失能，未确认的生产电源或机械条件仍拒绝构建。初始化完成不等于 safety 已允许控制。
6. 检查构建与内存：继续使用仓库 CMake 工具链、硬浮点和非 `fast-math` 设置；启动汇编、链接脚本、参数分区、`.noinit`、CAN 工作区及 DMA 缓冲位置不被生成配置替换。核对新 ELF 的 Build ID、源码清单、头依赖和实际链接输入，记录 Flash／RAM／栈帧变化。
7. 在 WSL 运行 Debug／Release 完整主机回归，构建普通禁热、遥控诊断和裁判诊断各两种配置。用 `check_firmware_profile.py` 核对每份 ELF 及其构建目录，并复查 UART、Fusion 和关闭辅助显示的选择。主机和编译检查通过后，真实上电、时基、IRQ／DMA、复位输出与 CAN 过滤仍按 MC02-0128 的裸板条件验收。

这是一套人工流程。本轮没有执行 CubeMX 重新生成，也没有用软件检查代替物理验收。

## 分阶段启动时怎样看待看门狗（MC02-0087）

启动协调者需要先确认计时和看门狗可用，再按车型依赖初始化设备。一次设备等待有固定截止时间；即使循环不断检查状态，也不能把总期限重新开始。调度器启动前后的等待条件不同，不能假设 HAL 毫秒中断在所有阶段都能运行。

启动任务的进度与控制任务的周期心跳分别记录：控制任务还没有放行时，启动协调者不能替它报告周期已完成。核心失败先关闭输出并保存原因，再按既有复位额度处理；辅助设备失败则按依赖关系报告降级。此段描述本轮约定，具体实现和本机结果以 [MC02-0087 规格](../workflow/specs/h723-staged-startup.md)及后续任务记录为准，不能据此推断板上时序已验证。

当前配置已把三路受控电源标为待确认；生产构建不能用未确认声明继续，板级阶段执行器尚未完成时也保持拒绝。共享 EXTI 组将 10 至 15 号线逐一交给 HAL：HAL 只处理各自待处理的线，回调因此收到单个引脚号。即使以后同组增加设备，其待处理位也不会因入口只检查 IMU 使用的 10、12 号线而遗留。同步 IMU 采样不启用该 IRQ。主机模型检查了六路同时、单路及重复进入，真实板上中断行为仍需 MC02-0128 验证。

MC02-0087 开始按功能选择板载外设：在 GPIO 和 DMA 准备后，`PlatformFeaturePeripheralsInit()` 只为启用的告警、LCD、IMU 和温控分别初始化 TIM12、SPI1、SPI2 和 TIM3；LCD 诊断也会请求 SPI1。关闭温控时不初始化加热 PWM。随后读取车型配置，为启用的裁判、遥控和 UART 视觉选择串口，并保留 USART10 诊断。电机和双板通信使用的 CAN 总线也由配置选出；旧超级电容仍固定使用 CAN2，显式启用回环自测时准备全部三条总线。板级入口先检查全部编号，再初始化所需串口和 CAN 控制器；重复声明只调用一次，无效编号当前按启动失败处理。主机测试用替身检查开关、重复和非法编号，固件构建检查实际链接；这还不能证明板上外设时序。除下文所述的 SPI1、SPI2、TIM3 和 TIM12 外，尚未改造的 CubeMX 生成入口遇错仍进入致命处理。重新生成工程时，应核对 `main.c` 仍使用功能选择入口，且没有恢复这些外设的无条件调用。

LCD 的 SPI1 和板载 IMU 的 SPI2 已接入分级处理：启动时先检查时钟配置，再初始化 SPI；失败时只释放对应控制器已配置的引脚和时钟，并将相应功能标为未就绪。模块启动计划按功能的核心或辅助身份处理失败，辅助 LCD 失败不创建 LCD 任务；核心 IMU 失败则不放行控制。主机测试注入两路时钟及 SPI 初始化失败，检查 SPI2 失败不释放 SPI1；HAL 时钟等待的统一时限、其他外设的降级和板上验证仍待完成。CubeMX 重新生成时，还须核对两个 `MX_SPIx_InitChecked()`、MSP 回调与失败清理没有被覆盖。

车型参数检查现在先于 SPI 和 PWM 功能初始化，检查失败不会继续准备这些设备。当前业务没有使用 TIM1、TIM2，启动入口不再无条件配置它们；将来有设备需要时，必须在车型资源声明及板级启动计划中补充绑定。CubeMX 重新生成后也应确认这两个入口没有重新加入默认启动顺序。

受控电源的车型声明除阶段外，还要列出使用该路电源的模块。构建时检查模块是否属于车型，并筛选出当前板卡启用的使用者；当前板没有使用者时，该路生成关闭状态。裸板无论车型声明如何都生成关闭状态和零模块位图，板级后端也拒绝开启。开启的电源没有声明使用者、关闭的电源却声明使用者，都会被拒绝。哨兵实际三路负载仍未确认，生产配置因此不能构建。

启动协调先执行设备前电源，再初始化独立模块；设备后电源开启前，直接使用它的模块及其下游保持等待。阶段准备失败只影响相关模块；核心电源失败时先直接关断并锁存故障，再记录失败，第一阶段已有核心失败时不会执行后续电源阶段。准备时在同一短临界区内检查急停和核心故障，再写入电源引脚；模块初始化前重新检查 GPIO 输出锁存。GPIO 高电平只说明开启命令仍在，不代表已测得电源电压。若前置辅助模块已失败，其全部使用者都受阻的后阶段电源不会开启。主机测试覆盖顺序、共享电源、核心失败、辅助降级、急停和关断后重新检查；真实上电、电压和中断时序仍需 MC02-0128 验证。

TIM3 和 TIM12 的受检查初始化依次检查定时器、主模式和 PWM 通道，全部成功后才配置输出引脚。任何一步失败都释放对应时钟并使句柄无效；温控因此无法注册失败的 TIM3，蜂鸣器失败时告警模块仍可使用 RGB。主机测试逐步注入三处失败并检查另一控制器不受影响；加热引脚低电平和电源安全仍需真实板验收。重新生成时应核对受检查入口和失败分支。

温控被车型计划判定为辅助失败后，姿态任务仍需读取 IMU，但不再初始化或周期更新该温控模块；强制关闭入口仍保留，以便在故障路径撤销加热。标定和参数 Flash 维护不再向已失效的温控申请新保护，但仍受任务监控的固定时限约束。如果操作已经取得温控保护，即使过程中模块降级，也要结束这次保护。Flash 维护使用准备、已开始和收尾状态拒绝重叠调用；参数层仍单独检查维护授权和看门狗。主机测试覆盖温控预先降级、保护取得后降级、监控拒绝、超期及准备阶段重入，不能替代 Flash 板测。

## 0. 一句话总结

**看门狗是一个独立计时的"死人开关"**：程序必须周期性地告诉它"我还活着"，否则它就复位整个系统。
它救的是"程序跑飞/死锁"这种情况；但用错会把系统变成**永远起不来**——本篇把 IWDG/WWDG、复位原因寄存器、
启动期设计、以及本工程踩过的坑一次讲清。

---

## 1. 为什么需要看门狗

嵌入式设备无人值守：程序可能因为以下原因"卡住"：

- 死循环（逻辑写错、等一个永远不来的标志）；
- 死锁（任务互相等锁）；
- 跑飞（数组越界/野指针破坏了返回地址或数据）；
- 硬件异常（总线卡死、外设不再响应）。

这时软件自己已经救不了自己了。看门狗是**独立于 CPU 的硬件计时器**：只要软件没有在超时时间内"喂狗"，
它就直接把 MCU 复位，让系统重新开始。**它是最后一道防线。**

---

## 2. STM32 上和"复位"有关的几个东西

| 名称 | 时钟源 | 能不能关 | 特点 |
|---|---|---|---|
| **IWDG**（独立看门狗） | LSI（≈32kHz，内部低速、精度差但独立） | **一旦启动就不能关** | 最常用、最可靠；CPU 停了它还在跑 |
| **WWDG**（窗口看门狗） | APB 时钟 | 复位后关闭 | 要求"在时间窗口内喂"，太早也会复位；用于严格时序监控 |
| **RCC_RSR**（复位原因寄存器） | —— | —— | 记录"上一次为什么复位"，排查必备 |

STM32 的复位来源包括：上电/掉电复位（POR/PDR）、欠压复位（BOR）、外部引脚复位（NRST）、
**看门狗复位（IWDG1/WWDG1）**、软件复位（`NVIC_SystemReset()`）、低功耗复位。

## 3. IWDG 深入（本工程用的就是它）

### 3.1 超时怎么算

```
超时 = (RLR + 1) × 预分频系数 / f_LSI
```

- `PR`（预分频）：可设 /4、/8、/16、/32、/64、/128、/256；
- `RLR`（重装载值）：12 位，0~4095；
- `f_LSI ≈ 32kHz`（**不精确**，所以超时只能当"数量级"，别拿它当精确计时）。

例：本项目运行期 200ms → 需要 `(RLR+1) × 分频 / 32000 = 0.2s`。
实际读寄存器验算的例子（本项目实测）：

```
IWDG->PR = 6（÷256）, IWDG->RLR = 2500
→ (2500+1) × 256 / 32000 ≈ 20.0s      ← 启动期长超时
```

**技巧**：排查时不要猜配置，直接读 `IWDG->PR/RLR` 反推超时（这就是《06》里"读寄存器"的具体应用）。

### 3.2 配置流程（必须按顺序）

当前实现先向 `KR` 写 `0xCCCC` 启动 IWDG1，让看门狗时钟工作，再执行下面的配置：

1. 等待上一次寄存器更新结束。
2. 向 `KR` 写 `0x5555` 允许修改配置，写入分频 `PR` 和重载值 `RLR`。
3. 再等待新配置更新，向 `KR` 写 `0xAAAA` 重载计数。

两次等待分别计时，每次按 CPU 频率估算 20ms。程序使用 DWT 的 `CYCCNT`，不依赖由中断更新的 HAL tick；检查次数也有上限，计数停止时仍能退出。MC02-0087 改为在写前或写后等待失败时立即返回错误，禁止继续喂狗；硬件看门狗一旦启动仍无法用软件停止。

### 读懂看门狗接口和等待循环（MC02-0116）

第九批注释整理对应检查清单060、061，接口见 [bsp_watchdog.h](../../bsp/watchdog/bsp_watchdog.h)，实现见 [bsp_watchdog.c](../../bsp/watchdog/bsp_watchdog.c)。阅读时注意软件保存的信息与寄存器操作各自表示什么。

- `BSP_WatchdogInitChecked()` 和 `BSP_WatchdogSetTimeoutChecked()` 返回配置结果；请求按 LSI 32 kHz 估算，最大 32760 ms，0 按 1 ms 换算。超范围参数保留原配置，寄存器等待失败则禁止喂狗。旧的不带 `Checked` 入口保留但忽略结果。
- `BSP_WatchdogGetTimeout()` 返回最近一次确认完成的请求值，初始为 200 ms；实际时限受 LSI 频率及分频影响。`BSP_WatchdogFeed()` 仅在软件记录配置已完成时重载；`BSP_WatchdogIsRunning()` 返回这一软件状态，不能证明硬件实际时限。
- 基础启动和运行窗口切换会检查配置结果；参数 Flash 维护在看门狗窗口未确认时不开始擦写，恢复窗口失败时报告维护失败并执行保护收尾。
- `BSP_WatchdogLogResetReason()` 先读出硬件复位标志，逐项打印，保存发现过的 IWDG1 信息，再清除硬件标志。应在日志初始化后、其他代码清除标志前调用。`BSP_WatchdogWasIwdgReset()` 在尚未读取时也返回 0；一旦记录为 1，本次启动中再次读取不会将它清零。

生产代码主机测试检查调试冻结位、写前／写后超时、DWT 停滞、配置范围和维护窗口失败。模拟寄存器不能证明实际 IWDG 时钟、硬件更新时序或复位行为，板上验证仍由 MC02-0128 跟踪。

CAN 容量预检可能在设备初始化前拒绝辅助模块。启动协调把拒绝位图交给电源计划：如果某路电源只供这些模块或其下游使用，就跳过开启；如果还有核心模块需要同一路电源，仍会开启，但被拒绝的模块不会因此获得就绪状态。设备前电源自身失败时，后续电源也会排除已受影响的下游。主机测试使用实际 CAN 容量规划结果检查这些分支，真实电源输出仍需裸板验收。

### 3.3 三个致命特性（本次故障的两条根因都在这里）

1. **启动后不能关闭**：只要没断电，IWDG 一直在计时；
2. **普通复位不会停止它**：软件复位、NRST 引脚复位之后，IWDG **仍然按原来的配置继续计时** → 于是出现
   "一次看门狗复位 → 复位后启动还没做完又被它打断 → 永远起不来"的**死亡螺旋**；
3. **LSI 精度差**：别用它做毫秒级精确判断（本项目只拿它做"死机兜底"）。

### 3.4 喂狗

```c
IWDG->KR = 0xAAAA;      /* 把计数器重装载 → 相当于"我还在正常前进" */
```

**喂狗的语义非常重要**：喂狗应当代表"系统在正常前进"，而不是"我还没死"。
本工程的做法是：**由 daemon 任务里的 TaskMonitor 统一喂狗**，且只有
`INS / Motor / Robot / Daemon / UART_TX` 五个关键任务都被标记为"活着"时才喂（见 `TaskMonitorTick`）。
这样任何关键任务卡死都会在 200ms 内触发复位，而不是被"某处随手喂一口"掩盖掉。

## 4. WWDG 深入（窗口看门狗，本工程未启用）

WWDG 与 IWDG 最大的区别是"**窗口**"：

- 计数器从初值递减到 `0x3F` 就复位；
- 但如果在计数器还**很高**（窗口之外）时喂狗，也会复位；
- 也就是说：喂狗既要"别太晚"，也要"别太早"。

它适合监控"必须在确定时间内完成"的流程（例如通信握手）。本项目在
`stm32h7xx_hal_conf.h` 里把 `HAL_WWDG_MODULE_ENABLED` 注释掉了，即**没有使用**；
`bsp_watchdog.c` 仍然保留了打印 WWDG 复位原因的代码，方便将来排查。

## 5. 复位原因寄存器（RCC_RSR）：必读、必清

```c
uint32_t rsr = RCC->RSR;
if (rsr & RCC_RSR_IWDG1RSTF)  /* 看门狗复位 */
if (rsr & RCC_RSR_PORRSTF)    /* 上电/掉电 */
if (rsr & RCC_RSR_PINRSTF)    /* NRST 引脚（下载器复位、复位按键） */
if (rsr & RCC_RSR_BORRSTF)    /* 欠压 */
if (rsr & RCC_RSR_SFTRSTF)    /* 软件复位 */
...
RCC->RSR |= RCC_RSR_RMVF;     /* ⚠️ 必须清除, 否则标志会"粘住" */
```

**为什么要清**：这些标志是**累积**的，如果不在启动时清掉，你会看到"每次启动都同时报 IWDG 和 NRST"，
从而误判复位来源。本工程在 `BSP_WatchdogLogResetReason()` 末尾已经加了清除。

**排查时的用法**：

1. 打印/记录复位原因到日志（本项目会打 `[watchdog] reset reason: ...`）；
2. 看到一个"周期性的 IWDG 复位"→ 说明系统在稳定地卡死，而不是偶发跑飞；
3. 看到 POR/PDR → 说明是供电问题（比如电机启动导致的电压跌落）。

## 6. 启动期 × 看门狗：本工程最有价值的一课

### 6.1 冲突从哪来

- 运行期看门狗 = **200ms**（要求所有任务都健康）；
- 启动后最耗时的一步 = **BMI088 在线标定**：6000 次采样，正常约数秒；最多三轮，DWT 期限约 12s，任务监控总窗口为 15s；
- 而 IWDG 一旦启动、复位也不停 → 于是：

```
第 1 次运行: 某处卡死 → 看门狗复位
第 2 次启动: IWDG 仍按 200ms 计时, 而启动要 3~15s → 又被复位
第 3 次启动: 同上 ... → "永远起不来"
```

现象上它看起来像"换了优化等级就起不来"；实际触发源是非对齐访问（见《09》），看门狗把 HardFault 放大成周期复位，让排查一度偏离。

### 6.2 当前启动和后续协调

```c
uint8_t BSPInit(void) {
    DWT_Init(480);
    if (!BSP_WatchdogInitChecked(4000)) return 0; /* 启动窗口必须确认 */
    ...
}

/* 任务创建完成后切回短超时；失败进入失能路径 */
if (!BSP_WatchdogInitChecked(200)) goto init_failed;
```

启动标定由默认协调任务执行，运行中的人工标定仍由 INS 任务执行。启用温控时，标定入口先关闭并锁定加热器，再向 `TaskMonitor` 申请最多 15s 的 INS 期限。运行期标定时 daemon、motor、robot 等任务仍要按时报告健康；标定循环会让出 CPU，超时或其他任务故障时监控停止喂狗，由 IWDG 负责复位。

MC02-0087 在延迟放行期间按成功读取并完成数值检查的 BMI088 样本报告启动标定进度：编号必须递增，且至少经过 100 ms 才重载一次看门狗；标定的 15 秒总期限保持不变，时钟不前进或重复样本不会反复喂狗。超期时记录故障并按现有路径关断。普通运行中的手动标定仍由任务监控统一喂狗。

现有主机测试分别验证任务监控和 BMI088 的生产代码，后者使用监控替身核对只对有效样本报告进度。协调者已启用延迟放行，但这些测试不证明完整启动流程或板上时序；硬件看门狗和实际采样由 MC02-0128 验证。

`RobotInitializeIns()` 把 INS 初始化后的处理整理成一个单独步骤：姿态传感器失败时按车型依赖判断是辅助降级还是核心关断；已启用温控失败时先关热，只有温控影响核心时才关断整车。启动协调者调用它后决定是否创建周期任务。主机测试分别注入这两类故障，不能证明真实设备和输出电平。

任务监控也使用同一份车型依赖：`RobotConfigureTaskMonitor()` 先检查依赖并计算核心模块包含的前置模块，再将 INS 标为核心、辅助或不启用。辅助 INS 的任务未能创建时，启动流程可以在周期运行前移除它的监控；核心任务不可用这种方式跳过。辅助任务运行故障会通知模块依赖图，便于停用受影响模块。整车协调者已接入该流程，实际调度与硬件时序仍需验证。

长操作窗口里一旦观察到其他任务超时，故障会一直锁存到复位。任务后来恢复并再次调用 `TaskMonitorFeed()`，只能更新它的心跳时间，不能撤销这次故障；长操作结束仍会失败，监控也不会恢复喂狗。这样可以避免一次短暂失活被后续心跳“洗掉”，从而错误地恢复加热。

设计原则总结成一句话：

> **短期限用于发现故障；长操作只能获得有限豁免，不能自行喂狗把故障盖住。**

### 6.3 调试时的注意

原先 `BSP_WatchdogInit()` 会设置 `DBGMCU_APB4FZ1_DBG_IWDG1`，让 IWDG 在 CPU halt 时冻结。MC02-0034 已移除这项固件设置；现在 halt 时 IWDG 仍计数，但它到期前 CPU 不会执行软件关断，PWM 也可能保持原输出。连接调试器本身不等于停核。**不要把 IWDG 复位当成 PB1 已经低电平的物理证明。** 裸板 `bench_safe` 构建从启动阶段禁用加热；受控台架上的停核／探针故障电平仍未验收。

## 7. 常见误区（都是血泪）

| 误区 | 后果 | 正确做法 |
|---|---|---|
| 把喂狗放在定时器中断里 | 任务卡死但中断照跑 → 看门狗形同虚设 | 由"能代表系统健康"的任务喂（本工程：TaskMonitor） |
| 喂狗周期贴着超时 | LSI 精度差 + 任务抖动 → 偶发复位 | 留 2~5 倍余量 |
| 启动期忘了喂 | 启动长 → 死亡螺旋 | 启动期长窗口 + 长步骤按进度喂 |
| 不清 `RCC_RSR` | 复位原因误判 | 打印后立即 `RMVF` |
| 用 LSI 做精确计时 | 误差大 | 精确计时用 DWT/TIM |
| 只靠 IWDG 而不做任务监控 | 卡死一个任务却不复位，或反过来频繁复位 | IWDG + 任务级健康检查组合 |
| 断电靠"复位"清 IWDG | IWDG 不会被普通复位清掉 | 记住：只有掉电才清 |

## 8. 一套可复用的排查动作（看门狗相关问题）

1. 上电后先读/打印 `RCC_RSR`，判断上次复位来源，然后清除；
2. 读 `IWDG->PR/RLR` 反推当前超时，确认和设计一致；
3. 用"两次读数比较"区分卡死/复位（见《06》第 5 节）；
4. 若怀疑看门狗是干扰项：**把长耗时循环改成逐轮喂狗**再测——若仍然复位，就说明复位源不是看门狗；
5. 排查完把复位原因打印保留在启动日志里（这是长期资产）。

## 9. 提交参数到内部 Flash 时，看门狗怎么办（2026-09-22 新增）

这是本工程最典型的一次"看门狗和长耗时操作打架"，值得单独记下来。

### 9.1 冲突是怎么产生的

- 运行期 IWDG = **200ms**，由 `TaskMonitorTick()` 在 daemon 任务里喂；
- 把参数写进内部 Flash 需要**先擦一整个 128KB 扇区**，H7 单 bank 下实测
  擦 1 个扇区 ≈ **0.83s**、擦 2 个 ≈ **1.66s**；
- 单 bank 擦写期间 **CPU 取指被硬件暂停** → 所有任务一起停 → 没人喂狗。

结论：**200ms 的看门狗必然先超时复位**，而且复位后重新启动、重新提交，形成复位循环。

### 9.2 本工程的做法：先验证健康，再建立限时保护

`bsp/param/bsp_param.c` 的 `ParamCommit()` / `ParamReset()`：

`ParamCommit()` 和 `ParamReset()` 先调用 `RobotInit()` 注册的保护回调。回调先锁定加热，再由 `TaskMonitorBeginLongOperation(INS, FLASH)` 确认所有任务当前健康。获准后参数层保存原 IWDG 超时、切到最多 8s 并喂一次，然后执行擦写和回读。返回后恢复原超时，由任务监控继续决定是否喂狗；Flash 成功且窗口未超时，才清理任务时间戳，为恢复调度留出期限。成功结束也不会立刻恢复加热，温控必须收到操作之后的新鲜 IMU 样本。

如果保护回调未注册、入口发现已有任务故障、Flash 失败或窗口超时，参数操作失败，加热器保持锁定。Flash 窗口结束后没有直接喂狗，所以任何已记录的任务故障仍会导致 IWDG 复位。

### 9.3 三个容易忽略的细节

1. **IWDG 的 `PR`/`RLR` 有更新等待位**（`PVU`/`RVU`）：写进去后硬件要几个 LSI 周期才能生效，
   期间写新值会被忽略。本工程 `IWDG_WaitForUpdateFlags()` 会等这两个位清零再写、
   写完再等一次，避免"改了超时其实没生效"。
2. **Flash 是全核停顿**：所以入口要先确认任务健康，并只允许通过带 8s 上限的保护回调；任务时间戳只在成功返回后重置。
3. **不要在中断里提交**：ISR 里擦 1.7s Flash 会阻塞整个系统，
   而且 IWDG 的放长/恢复也需要任务上下文才安全。

### 9.4 更彻底的方案（本项目暂未采用，留作后续）

| 方案 | 代价 | 收益 |
|---|---|---|
| 后台"预擦"非活动区（SAFE 状态时提前擦好） | 需要状态机管理 | 真正提交时只需写入（~1ms），完全不碰看门狗 |
| 换外部 Flash / FRAM | 增加硬件 | 彻底避开"擦写停 CPU" |
| 用双 bank 的 H7（如 H743/H750 部分型号） | 换芯片 | 可以边执行边擦写另一个 bank |

## 11. 6S 上电时：停核、复位和断电是三件事（2026-10-04）

本节对应 [TB47S／6S 安全审查](../6S上电安全审查_2026-10-04.md)，源码基线 `0965d031ad60c5f1c1eeeac63c728dc44f7d4338`。具体任务状态见 [TODO](../../.Doc/TODO.md) 的 MC02-0034～0041、LCD-09 和 HIL-10；本节没有新增硬件测试或学习掌握记录。

### 11.1 为什么暂停程序还可能继续加热

CPU 的工作是读取 BMI088 温度、检查 VIN，再把输出写到 `TIM3->CCR4`。TIM3 是另一个硬件单元，会反复执行最后设置的 PWM；CPU 暂停并不会自动把 CCR4 写成 0。

例如 `IMUHeaterUpdate()` 刚写入一个非零占空比，随后调试器 halt：温控和五分钟软件超时都不再执行，TIM3 仍可能重复旧 PWM。现在 IWDG 不会因固件调试冻结位而停计数，但它只能在超时后触发复位，不能证明这段时间 PB1 已失能。**“我暂停了程序”不能推导为“加热已经关闭”。** 旧 `tools/probe_snapshot.py` 已退役；运行态读取使用先核对 Build ID 的 [只读观测工具](../../tools/probe_snapshot_live.py) 和 [OpenOCD 配置](../../tools/openocd_running_inspection.cfg)。身份不匹配或读取失败会停止，不改用 halt 继续读取。

OpenOCD 官方的[运行态内存检查说明](https://openocd.org/doc/html/GDB-and-OpenOCD.html#using-gdb-as-a-non-intrusive-memory-inspector)要求目标支持 background memory access，并关闭默认的 GDB attach halt 行为。配置文件清空 attach/detach 事件；脚本使用 `--nx`、关闭 interrupt-on-connect，只对 ELF 全局 RAM 值发出 `printf` 读取，并对每个 GDB 子进程设硬超时。主机测试验证工具命令与分类逻辑，但不能代替 CMSIS-DAP 实测。

软件准备妥当后，在已烧录的运行态目标上分开启动 OpenOCD 服务和快照读取：

```powershell
openocd -f tools/openocd_running_inspection.cfg
python tools/probe_snapshot_live.py --elf build/bench-safe/Basic_Framework_MC02_bench_safe.elf --samples 5 --interval 1 --timeout 5
```

这里不执行 `halt`、`reset`、`resume` 或目标写入。若 GDB 连接失败或超过 5 秒，工具报告 `probe_io_error` 并退出；没有连接设备前，仅可验证脚本和命令构造，不能据主机测试宣称 CMSIS-DAP 不停车读取已实测。

仅冻结 TIM3 计数也不够：PWM1 的输出取决于当前计数和比较值，停在有效阶段可能保持高电平。要关闭加热，应确保输出实际失能，而不是只让某个时钟停止。ST 的 [RM0468](https://www.st.com/resource/en/reference_manual/dm00603761.pdf) 第 3231～3234 页分别定义 TIM3 和 IWDG 的调试冻结；主供下验证关断需受控供电，不能用无限流电池做停核实验。

### 11.2 为什么 5% 和 0.30W 仍有前提

PWM 占空比 `D` 是导通时间的比例。电阻平均功率近似为：

```text
P平均 ≈ (输入电压² / 等效电阻) × D
```

以 [官方原理图条件](../硬件定位/MC02-6S供电依据.md) 的 47Ω 为例，25.2V 全导通约 13.51W；要按 0.30W 限制，占空比需约 2.22%。当前代码按 VIN 计算这个限值，再受 5% 上限约束。

这依赖 VIN 新鲜且准确、电阻与图纸一致、Q9 受控及温度采样可信。ADC 缓存停更时，公式可能用错电压；SPI 失败但仍返回“成功”时，温控可能用错温度；Q9 损坏短路时，写 CCR4=0 也不能断开电流。因此软件限幅、看门狗和外部故障能量限制需要各自验证。

### 11.3 复位为什么也不能替代限流

看门狗复位主要解决程序不继续工作的情况，不能检测所有局部过热，更不能切断板外短路线。参数 Flash 操作会临时使用最多 8s 的窗口；标定只为 INS 任务申请最长 15s 的受限期限，daemon、motor、robot 等其他任务仍持续受监控。标定循环会让出 CPU，不直接喂狗。加热器在这些操作入口先关断并保持锁定，成功后也要等到操作完成后的新鲜 IMU 样本；监控期间发现的任务故障仍会锁存。软件关断和看门狗不能代替外部限流及实测。

USB 也可能继续给低压系统供电。停止上位机、复位 MCU 或只断开电池，分别改变不同部分，不能笼统称为“整套设备已经断电”。本次采用的交付边界是先审查和修复、在无加热能量的模拟中验证异常，再由受控供电核验实际电平和温升；电池上电单独验收。

### 11.4 加热故障为什么需要锁存和新样本恢复

这里的“锁存”表示故障发生后保留记录，温度下降也不自动清除。可用温度达到 **50°C** 时关闭加热并记下过温；手动清除要求温度严格低于 **42°C**，等于42°C也不允许。

`IMUHeaterClearFault()` 先关闭输出，再检查是否允许清除，返回1表示通过，0表示拒绝。需已初始化、最近一次更新没有要求强制关闭，也没有进行中或失败的耗时操作；不能处于等待新数据的状态。最近一次温度检查需通过，所用 IMU 数据未超过5ms，温度至少-20°C且严格低于42°C，不能出现 NaN/Inf。当前 ADC 数据需有效、未超过20ms且换算设置可用，VIN 在10～30V之间，两端均允许。

已有故障时，还要求清除所用数据的序号晚于首次故障记录的序号，采样时间不早于故障时刻。成功当次仍保持零输出，并记下本次所用的数据；后续序号需更新，采样时间不能早于它，才继续温控检查。序号和毫秒计数用无符号差值比较，可处理计数超过最大值后继续的情况。当前 LCD、串口和遥控器没有调用此清除接口的入口。

连续加热从 **PWM 非0** 时开始计，归0就结束这一段；达到300000ms（5分钟）时记录超时。即使本次温度已达到目标加2°C，也先检查连续加热是否到时。单独的计时标志让起始毫秒数为0时也能正常计算。温度无效时立即关闭；若距上次接受的采样时刻达到500ms，本次仍无可用温度，则记录传感器故障。首次尚无采样时，从初始化时刻计算。

默认 `MC02_HEATER_ENABLED=0`，输出始终为0，仍检查采样和故障。启热配置的 PWM 比较值最多500，约占每周期的5%，还按 VIN 与47Ω将允许值降到估算功率0.30W对应的范围。软件回归只检查这些计算和选择，VIN精度、Q9实际关断与电阻温升仍需按既有物理验收安排检查。

#### 11.4.1 几个关闭和恢复接口怎样配合（MC02-0120）

[imu_heater.h](../../modules/imu/imu_heater.h) 集中说明用法，[imu_heater.c](../../modules/imu/imu_heater.c) 在各次返回前解释为何保持关闭：

| 调用 | 对后续更新的影响 |
|---|---|
| `IMUHeaterForceOff()` | 清零输出、PID积分和两次输出，结束连续加热计时；后续 `Update()` 仍可按条件恢复 |
| `IMUHeaterUpdate(sample, force_off)` | `force_off` 非0时保持本次关闭，也阻止清故障；后续需用 `Update(..., 0)` 撤回该请求 |
| `IMUHeaterBeginLongOperation()` | 登记标定或 Flash 操作并关闭输出，两类可同时登记，同类不能重复开始 |
| `IMUHeaterEndLongOperation()` | 成功后等待序号更新、采样时间不早于结束时刻的数据；失败记录会持续禁止加热，不能由清故障或重复初始化解除 |
| 重复 `IMUHeaterInit()` | 只执行 `ForceOff()`，保留目标、故障和操作记录 |

`Update()` 接受-20～80°C的温度，两端均允许。重复序号只沿用已保存的数据和原时间，传入另一个温度或较新的时间也不能替换它；新序号的采样时间不能更早。`GetStatus()` 读取已保存的状态，不重新检查时间；其中温度可能是旧值，应结合 `sensor_valid` 使用。

首次初始化把目标设为40°C。`SetTarget()` 接收摄氏温度，小于30按30、大于45按45，NaN/Inf 时保留原目标。设置目标不会清故障或立即改变输出。输入电压低于10V时暂时关闭，恢复后可重新检查；高于30V会记录故障，恢复电压后仍需清除检查。

已有 [故障恢复回归](../../tests/host/imu_heater_fault_recovery_test.c) 在启热、禁热两种主机配置下检查恢复、温度及采样时限、连续加热计时和耗时操作；[采样使用回归](../../tests/host/imu_heater_sample_test.c) 检查旧数据和供电状态。注释整理同时比较启热、禁热两种 ARM GCC 处理结果，不连接硬件。

### 11.5 Windows 路径传给 OpenOCD 时要用正斜杠

OpenOCD 的 `-c` 参数交给 Tcl 解释。把 `D:\RoboMasterRelated\...\firmware.elf` 直接拼进 Tcl 命令时，反斜杠会被当作转义符处理，OpenOCD 最终可能尝试打开 `D:RoboMasterRelated...firmware.elf` 这样的错误路径。Windows 主机上应先取得绝对路径，再把分隔符转换为 `/`，例如 `D:/RoboMasterRelated/.../firmware.elf`，并用日志确认 OpenOCD 打开的文件名。

要区分主机命令错误与已经改写芯片：`Programming Started` 只表示进入编程命令，不证明 Flash 已擦除或写入。若随后立即出现 `couldn't open`，且日志没有目标扇区擦除、写入和 verify 结果，就应停止并保留日志；不能把命令退出或“没有整片擦除命令”当成写入成功。MC02-0039 本次先保存 1MiB Flash 和参数区备份，OpenOCD 因反斜杠路径打不开 ELF，未进入目标 Flash 擦写；随后只复位运行已有固件，没有重试烧录。备份文件哈希与原始日志见 [MC02-0039 票据](../workflow/tickets/MC02-0039.md)。

用户随后明确授权重新尝试。把 ELF 绝对路径转换成正斜杠后，OpenOCD 完成写入并报告 `Verified OK`。日志还显示，由于 Flash 写入对齐，工具把扇区擦除范围扩展到 `0x0803FFFF`；因此要检查实际擦除范围，而不只看 ELF 段的末地址。本次参数区从 `0x080C0000` 开始，烧录前后完整回读并逐字节一致。之后只读快照与 60 秒 COM14 被动采集均通过；细节和原始证据见 MC02-0039 票据。该结果只覆盖固件启动、BMI088 采样、通信帧和禁热状态，不能代替 VIN 精度、PB1 电平、温升或实际加热验收。

### 11.6 关掉 PWM 后，还要确认谁在驱动引脚（MC02-0041）

PB1 的输出涉及三类状态：GPIO 输出锁存 `ODR`、引脚模式 `MODER` 和 TIM3 的通道配置。`CCR4=0`、`CC4E=0`、`CEN=0` 表示定时器没有开启该 PWM 输出；它们不说明 PB1 一定由 GPIO 主动拉低。若 `MODER` 仍选复用模式，写 GPIO 的 ODR 也不能把输出控制权切回 GPIO。禁热配置的明确目标是：PB1 为推挽 GPIO，输出锁存为低，定时器通道和计数器都关闭。

本轮问题出在初始化顺序。此前的安全入口已经配置 GPIO 低输出，但后续 `HAL_TIM_MspPostInit()` 又按 CubeMX 生成代码把 PB1 配为 AF2/TIM3，覆盖了前面的设置。因此不能只检查关断函数是否正确，还要沿启动调用链检查它后面有没有重新配置同一引脚的函数。

修复位于 [Core/Src/tim.c](../../Core/Src/tim.c) 的 TIM3 用户代码区域：禁热时先启用 GPIOB 时钟，再写 PB1 低锁存，最后配置推挽输出并返回。先写低再切换模式，是为了避免输出模式生效的一刻使用历史高锁存值。返回会跳过后面的复用配置；放在 CubeMX 用户保护区域，便于以后重新生成工程时保留该规则。重复初始化也必须遵循同一顺序，不能依赖“启动时已经做过”。启热配置仍走原 AF2 路径，但本轮只在主机模拟中覆盖它。

主机测试直接调用生产 `HAL_TIM_MspPostInit()`，把起始锁存设为高，验证低写入先于 GPIO 模式配置，再重复一遍。修复前，裸板禁热和整机禁热两种测试都失败；修复后通过。另一组测试直接调用生产 `MotorControlTask()`：裸板仍消费 CAN、UART、VCP 队列，但电机输出函数的调用数为零。接收队列消费者属于通信运行所需逻辑，不能随执行器控制一起删掉。

配置隔离要在三个层面交叉核对：CMake 拒绝裸板启热，ELF 检查执行器入口没有被链接，板上运行态只读检查实际寄存器。两种优化等级都检查 ELF，可避免只验证一种链接结果。新建 Release 构建目录还暴露了 DWT 测试桩缺少变量声明；补齐硬件替身的接口比依赖旧构建缓存更可靠。

这些结果可以证明软件配置和数字寄存器状态，不能证明 PB1 引脚实测电压、开关管关断能力、VIN 精度或温升。主机及板上证据集中在 [MC02-0041 票据](../workflow/tickets/MC02-0041.md)，后续物理测量仍在 LCD-09；本节没有把阅读文档记作已掌握。

本轮实板五次快照中，GPIOB `MODER=0xa95feaa6`、`OTYPER=0`、`ODR=0x1c00`。判断 PB1 时只提取它的两位模式和对应输出位：`(MODER >> 2) & 3 = 1`，表示 GPIO 输出；`ODR & 2 = 0`，表示 PB1 锁存低。整个 ODR 非零是其他引脚的状态，不能因此判定 PB1 为高。TIM3 `CR1=0x80` 也不等于计数器运行：`CEN` 是 bit0，该位为零；bit7 的 ARPE 仍保留初始化配置，CCER 和 CCR4 均为零。

通信验收同样需要观察变化：1000 个禁止控制的全零指令使 RX 从 0 增至 1000，发送期间接收时间更新，停止后整个接收帧和时间归零，CRC 错误保持 0。只看“mode=0”无法证明旧数据被清除，因为发送的中性指令本身 mode 就是 0；所以额外读取了全部 29 字节，其中原本非零的 SP 头与 CRC 也必须归零。60.306 秒收到 12,060 个 CRC 正确状态帧，四元数全部有限。软件与寄存器观测没有出现复位或启热；用户报告主输入电流由约 0.09A 升至 0.115A，原因仍需供电与负载测量，不能把软件回归通过当作电流变化的解释。

后续用户确认电流已回落至约 0.09A 并稳定，C.V 正常亮、LCD 正常刷新、电机摘要全部为 0，补齐了本轮人工验收。记录电流时应保留“升高—回落—稳定”的顺序：单次 0.115A 读数不能被写成持续升高，后来回落也不能反推此前变化的原因。主机脚本能够校验通信和寄存器，LCD 实际显示与电源面板观察则需要人补充；任务关闭依据是两部分证据满足本轮条件，并不把尚未测量的引脚电平、VIN 精度或温升一并判定通过。

## 12. 初始化失败为什么进入失能诊断（R25-10）

系统初始化在 RTOS 调度器启动前执行。此时若某个 CAN/UART/PWM 注册器返回失败，继续创建后续控制模块会把“前一项缺资源”伪装成多处异常；在失败处无限循环则既没有诊断进展，也可能卡在中断关闭状态。R25-10 的规则是：注册失败返回 `NULL`，调用方逐层传播；`RobotInit()` 记录阶段、模块和资源，恢复进入时的 `PRIMASK`，然后保持 SAFE/FAULT，拒绝 READY、使能和标定。

诊断记录只保留首次失败的阶段、模块、原因和资源编号，后续失败仍会增加报告次数。这个次数包含重复报告，不能直接当作失败任务的数量。任务创建逐项检查并记录具体任务编号。`init_diagnostic_snapshot.heartbeat` 增加说明诊断代码仍在运行，控制系统是否就绪还要看启动结果和 RobotSafety 状态。

看门狗分成两个阶段：`BSPInit()` 先设置 4 秒启动窗口，RTOS 任务都创建成功后才缩到运行期的 200ms。若任务创建或启动失败，主循环不启动机器人任务，而是重复执行输出关断、更新诊断心跳并喂 IWDG，等人工读取记录和处理。任务开始后发生 INS 算法或蜂鸣器初始化失败，则锁存 `ROBOT_FAULT_INIT_FAILURE`；失败任务只做受限诊断，其他已运行任务继续经过 RobotSafety 和任务监控，普通手势不能清除此故障。

这条路径会等待人工处理，因此不会靠看门狗自动反复重启。完整复位后，启动程序才会重新清零普通 RAM 中的诊断记录；所以应先通过只读 `--init` 查询保存记录，再决定复位。运行记录和主机故障测试没有证明物理关断引脚或负载状态，裸板验收仍需检查 BMI088、SP 通信、禁热及输出隔离。

### 12.1 读懂启动诊断的记录和计数（MC02-0109）

第二批注释整理对应检查清单015、016。先看 [init_diagnostic.h](../../application/init_diagnostic.h) 的阶段、原因和结构体，再沿 [init_diagnostic.c](../../application/init_diagnostic.c) 的判断阅读各入口，注意下面几个用法。

- `InitDiagnosticBegin()` 和 `InitDiagnosticSetStage()` 只更新阶段。已经记录失败时，两者都保留首次失败的阶段；再次调用 Begin 也不会清除标志或计数。
- `InitDiagnosticReportFailure()` 第一次调用时保存四项失败信息，以后的调用只增加 `failure_count`。任务创建失败使用 `InitDiagnosticResource_e` 找到具体任务，其他资源编号由报告失败的代码指定。报告接口只记录，调用方还要负责停止控制等后续处理。
- `failure_count` 到 `UINT32_MAX` 后保持不变，避免重新变成 0；`heartbeat` 每次调用加 1，超过 `UINT32_MAX` 后会回到 0。两者的单位都是“次”，心跳没有固定的毫秒含义，失败后的循环也会继续更新它。
- `InitDiagnosticGetSnapshot()` 将完整记录复制到调用方的结构体，传入 `NULL` 时直接返回。复制前暂时关闭普通中断，防止读到一半时被改写；完成后恢复原来的 `PRIMASK`，调用前已经关闭中断时仍保持关闭。
- `InitDiagnosticMarkReady()` 在启动协调者完成核心步骤并放行周期任务后调用，只把诊断阶段改为 READY；实际是否允许控制由 RobotSafety 处理。已有失败时，它也不会覆盖失败阶段。

本批只补注释，不改变字段类型、编号、调用顺序或判断。现有 [init_diagnostic_test.c](../../tests/host/init_diagnostic_test.c) 连续报告两次不同失败，再调用 MarkReady 和 Heartbeat，检查首次失败保留、报告次数为 2、心跳次数为 1，以及读取后中断状态恢复。比较记录和验证日志保存在本地 `build/mc02-0109/`，验证结果随本批交付记录在 TODO 中。

### 12.2 长操作结束时还要检查什么（MC02-0123）

[task_monitor.h](../../modules/task_monitor/task_monitor.h) 为五个任务分别设置 5、5、20、30、30 ms 的允许间隔，
超出才报告失败；标定和 Flash 长操作使用另外的计时，达到 15000、8000 ms 就失败。
这两种比较里的等号位置不同，阅读接口时要留意。

标定只允许 INS 暂时不更新运行记录；Flash 擦写会让整个内核暂停，按时结束后给全部任务重新计时。
若在标定过程中保存参数，结束 Flash 还会检查外层标定是否用完总共 15 秒，不能靠内层操作延长总时间。
操作期间已经发现的任务故障会保留，结束操作不能顺带清掉。只有全部正常才继续喂看门狗。
`TaskMonitorAllAlive()` 读取上次检查结果，实时检查发生在周期调用的 `TaskMonitorTick()`。

因此不能把接口前提写成已经由启动流程保证；这项接入问题归现有 MC02-0054 处理，本轮只改注释。

### 12.4 专用UART发送任务也要更新运行记录（MC02-0061）

UART发送、超时停止和业务完成通知现在由单独任务处理，正常约1ms推进一次；允许间隔30ms，边界允许，超过后沿现有任务失败路径关闭输出并停止喂看门狗。其他任务持续更新不能替代UART任务。UI约115ms的发帧节奏不影响监控，因为UART任务每轮都会更新记录，即使没有报文也继续运行。

停止HAL／DMA在任务中执行，不放在临界区；停止失败会隔离该串口并保留其内部数组。任务监控能发现发送任务长时间不运行，不能证明DMA已经物理停止。新增任务创建失败会报告启动资源错误，接收对象保留，发送不接受提交。[任务入口测试](../../tests/host/uart_tx_worker_test.c)覆盖创建失败后重试、重复初始化和有限轮次执行；[监控回归](../../tests/host/task_monitor_shutdown_test.c)检查UART停更30／31ms边界，结果见[本轮记录](../workflow/tickets/MC02-0061.md)。

### 12.5 任务进度与总期限（MC02-0069）

`TaskMonitorInitConfigured()` 在调度器启动前复制固定任务表。每项指定周期或事件模式、核心或辅助角色、名义周期、总期限和首次运行宽限。启动宽限从调度器首次被任务监控观察到时开始，所以启动前的模块注册耗时不会吃掉宽限；调度器开始运行后不能再次初始化，避免清除已记录的核心故障。

任务用 `TaskMonitorBeginWork()` 开始一轮工作，用 `TaskMonitorReportProgress()` 记录阶段，用 `TaskMonitorSetWaiting()` 记录等待原因，结束时调用 `TaskMonitorCompleteWork()`。进度和等待只更新记录，不重置 `BeginWork()` 保存的总期限；一个循环即使不停报告新阶段，卡在同一轮里超过期限仍会故障。周期任务在工作期间按总期限检查，完成后按完成时刻检查下一轮是否及时；事件任务没有待处理事件时可以长期处于等待，不因空闲误报。

核心任务超过启动、工作或周期期限后，任务监控先锁存状态并关闭输出，再报告状态；Daemon 不再喂 IWDG，硬件看门狗随后复位。一个核心故障锁存后，其余核心任务也不能开始新的工作。现在任务期限故障会先写入恢复记录，重启时消耗有限额度；连续第4次故障启动锁定控制。辅助任务故障只调用配置的降级回调并暴露依赖位，不改变核心健康。当前机器人活动配置中的五项仍全为核心任务，辅助降级由主机配置测试覆盖。

任务进度、来源在线和数据新鲜度各自记录。健康快照里的通信状态不能代替任务是否完成本轮；任务定期运行也不能证明它收到的新传感器数据有效。只读 `TaskMonitorGetProgressState()` 返回开始、进度、等待与完成时间及计数，不推进任务、不续期；依赖位通过复制接口读取。现有有限标定／Flash 窗口继续独立计时，窗口结束还会重新检查核心任务。主机回归验证固定期限、事件空闲、tick 回绕、启动宽限、辅助降级和故障关断顺序；没有在板上注入任务故障，也不把 IWDG 的实际复位时序当成本轮已测结果。详见[MC02-0069任务记录](../workflow/tickets/MC02-0069.md)。

### 12.6 复位额度和何时禁止重新使能（MC02-0067／0069）

核心任务停滞先由任务监控锁存故障、关闭输出并停止继续喂 IWDG。异常入口另记录 CPU 异常、断言、栈溢出或致命处理器故障。下次启动读取恢复记录和 RCC 原复位标志：有待处理故障、IWDG／WWDG 复位或非 POR 的 BOR 都消耗一次恢复额度；单独的软件复位或 NRST 不消耗额度，除非前一运行已先写入故障标记。当前五个核心监控任务是 INS、MOTOR、ROBOT、DAEMON 和 UART_TX。

软件选择了最多 **3 次故障恢复启动**：第一次故障复位后额度变为1，仍可经过原有启动检查；连续第4次故障复位将记录锁定，机器人保持 `ROBOT_FAULT`，使能、标定和急停解除入口都不能清掉锁定位。RC掉线、IMU暂时无效、CAN BusOff、电机离线和辅助任务降级继续由各自安全状态处理，不单独触发自动复位。启动期初始化失败仍走原诊断等待，不作为可反复重启的恢复策略。

额度只在 `RobotSafety` 为 READY、全部核心任务健康且没有待处理故障／人工急停时连续观测 **30秒**后清零；计时使用无符号毫秒差，允许计数回绕。恢复期通过 `TaskMonitorAllCoreHealthyNow()` 按当前 HAL tick 重新核对每项核心任务期限；`TaskMonitorAllAlive()` 只是最近一次监控周期留下的健康快照，不能单独作为清额度依据。第四次故障后只能由真实冷上电重新开始恢复周期；普通软件或引脚复位不会解锁。记录放在 `.crash_record` 的 NOLOAD AXI SRAM，不写 Flash，因而不保证断电留存；H723 冷 POR 时会重新初始化该记录，人工急停也按 B5 规则不跨断电保留。这是当前 RAM 方案的限制，不能描述成掉电持久锁。

PX4 对未提交的 HardFault 维护重启计数，并提供提交或清计数操作；ArduPilot 在检测到 crash dump 时默认阻止解锁，要求先处理或明确确认。它们都把重复崩溃和重新使能分开处理，但项目没有规定通用的“三次”或“30秒”数字。本工程选择的数值属于本项目策略，仍需结合真实关断边界、看门狗窗口与整机验收确认。H723 的 AXI SRAM ECC 每个数据字为64位；记录写入采用对齐完整字提交，主机模型验证布局和 CRC，不能替代芯片复位后实测。[MC02-0067 记录](../workflow/tickets/MC02-0067.md) 保存了分类、参数和剩余边界。

### 为什么复位次数和30秒不是行业常数（MC02-0067）

参考项目按故障类型选择动作。本段核对了 PX4 v1.14／v1.14.3、ArduPilot Copter-4.6.0、ESP-IDF v5.5 和 Zephyr v4.2.0：PX4可把失联或电机异常映射到保持、返航、降落或解除使能；ArduPilot Rover检测到持续崩溃后切入Hold，并可按配置解除使能；存在崩溃记录时默认阻止解锁，但高级参数允许明确忽略。ESP-IDF把CPU异常、看门狗、欠压、栈溢出和断言列为致命错误，并允许配置重启或停机；Zephyr把任务进度检查与硬件看门狗后备分开。它们说明“局部故障如何失能”“CPU不能继续运行时如何复位”“何时重新允许输出”应分开设计，未给MC02提供统一次数或时间值；具体来源链接见[复位策略研究记录](../workflow/tickets/MC02-0067-reset-policy-research.md)。

systemd用时间窗和启动次数限制重复启动，达到上限后停止自动重启，并让管理员显式解除。它说明自动恢复需要有停止点；主机系统具备更多存储和维护入口，规则不能直接当作MCU安全锁定方案。MC02当前采用三次恢复、第4次锁定，并在READY、核心任务健康、无故障和无人为急停时连续30秒后清额度。这是本工程的软件取舍：保留几次短暂故障后的可用性，同时限制短时间内反复启动。30秒按RobotTask约5ms的观察节奏反复检查，但不能覆盖间隔更长才出现的故障。

当前锁定保存在NOLOAD AXI SRAM，冷POR会开始新周期，因此掉电会清除额度和锁定。普通软件复位、NRST、诊断清理和急停解除不能清除锁定位。若产品要求故障原因确认前即使断电也不能重新使能，必须另行设计跨断电保存方式；现有RAM记录不能提供此保证。完整来源和MC02每条计数路径见[复位策略研究记录](../workflow/tickets/MC02-0067-reset-policy-research.md)与[MC02-0067票据](../workflow/tickets/MC02-0067.md)。

## 启动前等待为什么需要两个上限

早期外设等待不能只依赖系统毫秒时钟：时钟或定时中断本身出故障时，该时钟可能停止。`PlatformStartupWait` 同时使用固定的周期计数期限和最大检查次数；计数回绕使用无符号差值处理，计数不再前进时仍可因次数用尽退出。条件检查和计数读取都必须有界返回，调用方还要按实际时钟与允许的启动耗时选择参数，不能把检查次数直接当成已经测得的时间。

看门狗更新寄存器时已使用这个组件：DWT 前进时按周期数检查期限，DWT 停止时按最大检查次数退出；条件函数执行所用的时间也算进期限。次数上限只是防止无限循环，不能当成板上已实测的毫秒数。看门狗配置失败会传给启动流程，运行窗口未确认时协调者保持任务未放行。

H723 主时钟启动现在使用固定的总周期和查询次数上限。VOS 就绪有独立等待期限；HAL 内部的电源、振荡器和时钟切换等待在总期限用尽时收到临时超时值。这个值不写回 HAL 原始计数；即使 HAL 随后返回成功，协调流程仍会拒绝到期结果。切换后还须确认原始 HAL tick 确实前进，不能把临时值当成正常时基。

期限按复位后 64 MHz 和切换后 480 MHz 估算，检查次数提供计数器停止时的兜底，不等于已实测的等待时间。失败时先关断输出，记录 HAL、电源、VOS、振荡器、切换或总期限对应的原因，再按已有恢复额度决定是否请求软件复位。复位前清除已读取的硬件复位标志，避免旧的上电标志在下一次启动时误清恢复次数。主机替身不能证明硬件电压、时钟与复位时序，仍由裸板验收确认。受控电源在 GPIO 配置输出前先置为关闭，车型配置决定是否及何时开启；GPIO 输出锁存读回不能证明实际电压。

主时钟完成后，ADC、SPI、PWM、UART、CAN 的早期准备和 ADC 采样启动共用一个外设阶段固定期限。当前按 480 MHz 估算为 3 秒，另设查询次数上限；切换到下一个外设不会重新开始计时。HAL 等待超过期限时，只有启动线程的受保护调用看到临时超时值，中断和日志仍读取真实毫秒计数。外设总期限失败在 BSP 阶段单独记录，并使用独立的复位原因。`DWT_Init()` 保留硬件周期数，软件累计时间从调用时刻重新计算，避免破坏已开始的期限。这个 3 秒配置和实际中断、复位行为仍需 MC02-0128 裸板验证。

这个保护能让查询 `HAL_GetTick()` 的超时循环退出，也会在外设调用返回后检查总期限。原 HAL ADC 校准使用固定次数轮询，不查询 `HAL_GetTick()`；本工程的单端偏移校准改为在硬件等待中直接检查同一个期限。期限耗尽后不再启动采样，启动流程立即关断并按恢复额度复位。主机替身能验证软件分支，不能证明 ADC 实际校准时长或复位时序。

致命错误入口也先关断输出，再记录故障并检查恢复额度。还有额度时请求复位；已锁定或复位调用意外返回时，程序留在关断循环中，并重载可能跨复位继续运行的独立看门狗，以避免因看门狗继续计数而反复复位。这个寄存器行为与实际复位次数仍需 MC02-0128 在裸板上验证。

### 调度器启动与周期任务放行

启动任务创建完成后，恢复调度器可能立即切换到新任务。因此 LCD 初始化、裁判界面初始化、守护任务的启动诊断、独立事件回调和 HT 电机任务都要先等待统一放行。`TaskMonitorRuntimeReleased()` 只读取监控状态，不刷新期限，也不授予电机运行许可。监控尚未初始化、调度器未运行或协调者尚未放行时，它返回未放行。

调度器已运行，只说明可以调度任务；启动协调者可能仍在初始化设备，控制任务尚未创建。整车启动先准备基础 BSP 并推迟任务监控，再由默认任务初始化业务模块和 INS、创建任务、确认看门狗运行窗口并放行。放行前不以周期任务身份记录协调者的等待，也不由周期监控喂狗；放行时记录统一起点，再计算各任务的首次运行宽限。启动标定仍受自身固定期限限制，有效样本在允许的间隔内报告进度；超期会关断并阻止放行。默认任务栈改为固定分配，避免占用创建其他任务的 FreeRTOS 堆；实际栈余量仍需裸板验证。

`RobotInit()` 不再在整个初始化期间关闭中断。CAN 和 UART 在配置硬件前准备实例，只在发布队列、实例地址和登记数量时短暂关闭中断，并恢复调用前状态。CAN 工作区还没建立时，早到的中断直接退出；工作区全部写好后才发布可用状态。主机模型验证了发布后立即到达的 CAN 接收帧，以及两种调用前中断状态；实际中断时序仍需裸板验证。

系统时钟就绪后，启动流程先建立 DWT 周期计数和 4000 ms 看门狗窗口，再初始化 GPIO、DMA 和所需外设。看门狗配置失败会进入故障处理；成功后也不会在 `BSPInit()` 中重新启动，以免抹去外设阶段已经消耗的时间。只有外设和 ADC 阶段在固定总期限内完成，才按这一实际进度喂狗。窗口时长基于 LSI 标称频率估算，实际裕量仍需在裸板上验证。

启动看门狗配置失败时，直接关断输出，并以独立原因写入跨系统复位恢复记录；下一次启动可以区分它与普通看门狗复位。原有记录长度、版本和原因编号不变，断电后的记录保留仍取决于该 RAM 的实际供电条件。
