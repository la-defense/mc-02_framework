# 07 看门狗与复位系统入门（写给零基础）

> 本篇是"每次任务后回顾技术栈"的成果之一：本次排查 `-O2` 启动故障时，**看门狗与复位系统**是绕不开的核心，
> 而《06 如何定位只在特定条件下出现的故障》只讲了"怎么查"（方法论），本篇讲"它到底是什么、怎么用对"（原理与实践）。
> 两篇互补：**06 讲排查流程，07 讲看门狗/复位本身**。

## 0. 一句话总结

**看门狗是一个独立计时的"死人开关"**：程序必须周期性地告诉它"我还活着"，否则它就复位整个系统。
它救的是"程序跑飞/死锁"这种情况；但用错会把系统变成**永远起不来**——本篇把 IWDG/WWDG、复位原因寄存器、
启动期设计、以及本工程踩过的坑一次讲清。

---

## 1. 为什么需要看门狗

嵌入式设备无人值守：程序可能因为以下原因"卡住"：

- 死循环（逻辑写错、等一个永远不来的标志）；
- 死锁（任务互相等锁）；
- 跑飞（数组越界/野指针破坏了返回地址或数据）；
- 硬件异常（总线卡死、外设不再响应）。

这时软件自己已经救不了自己了。看门狗是**独立于 CPU 的硬件计时器**：只要软件没有在超时时间内"喂狗"，
它就直接把 MCU 复位，让系统重新开始。**它是最后一道防线。**

---

## 2. STM32 上和"复位"有关的几个东西

| 名称 | 时钟源 | 能不能关 | 特点 |
|---|---|---|---|
| **IWDG**（独立看门狗） | LSI（≈32kHz，内部低速、精度差但独立） | **一旦启动就不能关** | 最常用、最可靠；CPU 停了它还在跑 |
| **WWDG**（窗口看门狗） | APB 时钟 | 复位后关闭 | 要求"在时间窗口内喂"，太早也会复位；用于严格时序监控 |
| **RCC_RSR**（复位原因寄存器） | —— | —— | 记录"上一次为什么复位"，排查必备 |

STM32 的复位来源包括：上电/掉电复位（POR/PDR）、欠压复位（BOR）、外部引脚复位（NRST）、
**看门狗复位（IWDG1/WWDG1）**、软件复位（`NVIC_SystemReset()`）、低功耗复位。

## 3. IWDG 深入（本工程用的就是它）

### 3.1 超时怎么算

```
超时 = (RLR + 1) × 预分频系数 / f_LSI
```

- `PR`（预分频）：可设 /4、/8、/16、/32、/64、/128、/256；
- `RLR`（重装载值）：12 位，0~4095；
- `f_LSI ≈ 32kHz`（**不精确**，所以超时只能当"数量级"，别拿它当精确计时）。

例：本项目运行期 200ms → 需要 `(RLR+1) × 分频 / 32000 = 0.2s`。
实际读寄存器验算的例子（本项目实测）：

```
IWDG->PR = 6（÷256）, IWDG->RLR = 2500
→ (2500+1) × 256 / 32000 ≈ 20.0s      ← 启动期长超时
```

**技巧**：排查时不要猜配置，直接读 `IWDG->PR/RLR` 反推超时（这就是《06》里"读寄存器"的具体应用）。

### 3.2 配置流程（必须按顺序）

当前实现先向 `KR` 写 `0xCCCC` 启动 IWDG1，让看门狗时钟工作，再执行下面的配置：

1. 等待上一次寄存器更新结束。
2. 向 `KR` 写 `0x5555` 允许修改配置，写入分频 `PR` 和重载值 `RLR`。
3. 再等待新配置更新，向 `KR` 写 `0xAAAA` 重载计数。

两次等待分别计时，每次按 CPU 频率估算 20ms。程序使用 DWT 的 `CYCCNT`，不依赖由中断更新的 HAL tick；因此须先初始化 DWT 并保证它在计数。当前代码遇到等待超时会尝试输出错误日志，随后继续执行配置或重载命令，没有向调用方返回失败。

### 读懂看门狗接口和等待循环（MC02-0116）

第九批注释整理对应检查清单060、061，接口见 [bsp_watchdog.h](../../bsp/watchdog/bsp_watchdog.h)，实现见 [bsp_watchdog.c](../../bsp/watchdog/bsp_watchdog.c)。阅读时注意软件保存的信息与寄存器操作各自表示什么。

- `BSP_WatchdogInit()` 保存请求时限、启动或重新配置看门狗，再重载计数。时限单位为 ms，按 LSI 为 32kHz 估算。传 0 时内部按 1ms 换算，软件仍保存 0；接口没有完整的参数范围检查，当前工程使用 200、4000 和 8000ms。
- `BSP_WatchdogSetTimeout()` 在已初始化时写硬件并重载计数；未初始化时只保存请求值，之后的初始化仍由 `BSP_WatchdogInit()` 自己的实参决定。`BSP_WatchdogGetTimeout()` 返回保存的请求值，初始为 200ms，没有读取硬件确认实际时限。
- `BSP_WatchdogFeed()` 在本次启动完成初始化后才写喂狗命令。`BSP_WatchdogIsRunning()` 也只返回这个软件初始化标志；等待超时后代码仍会设置它，不能据此确认寄存器更新成功。
- `BSP_WatchdogLogResetReason()` 先读出硬件复位标志，逐项打印，保存发现过的 IWDG1 信息，再清除硬件标志。应在日志初始化后、其他代码清除标志前调用。`BSP_WatchdogWasIwdgReset()` 在尚未读取时也返回 0；一旦记录为 1，本次启动中再次读取不会将它清零。

现有 [watchdog_debug_safety_test.c](../../tests/host/watchdog_debug_safety_test.c) 检查初始化没有设置调试冻结位，并在 HAL tick 停止、DWT 仍前进时，让更新标志一直保持忙，核对写前和写后都能退出等待、报告错误后继续重载计数。本批只改注释，比较结果和验证日志保存在本地 `build/mc02-0116/`，验证结果记录在 TODO 中；未连接硬件。

### 3.3 三个致命特性（本次故障的两条根因都在这里）

1. **启动后不能关闭**：只要没断电，IWDG 一直在计时；
2. **普通复位不会停止它**：软件复位、NRST 引脚复位之后，IWDG **仍然按原来的配置继续计时** → 于是出现
   "一次看门狗复位 → 复位后启动还没做完又被它打断 → 永远起不来"的**死亡螺旋**；
3. **LSI 精度差**：别用它做毫秒级精确判断（本项目只拿它做"死机兜底"）。

### 3.4 喂狗

```c
IWDG->KR = 0xAAAA;      /* 把计数器重装载 → 相当于"我还在正常前进" */
```

**喂狗的语义非常重要**：喂狗应当代表"系统在正常前进"，而不是"我还没死"。
本工程的做法是：**由 daemon 任务里的 TaskMonitor 统一喂狗**，且只有
`INS / Motor / Robot / Daemon` 四个关键任务都被标记为"活着"时才喂（见 `TaskMonitorTick`）。
这样任何关键任务卡死都会在 200ms 内触发复位，而不是被"某处随手喂一口"掩盖掉。

## 4. WWDG 深入（窗口看门狗，本工程未启用）

WWDG 与 IWDG 最大的区别是"**窗口**"：

- 计数器从初值递减到 `0x3F` 就复位；
- 但如果在计数器还**很高**（窗口之外）时喂狗，也会复位；
- 也就是说：喂狗既要"别太晚"，也要"别太早"。

它适合监控"必须在确定时间内完成"的流程（例如通信握手）。本项目在
`stm32h7xx_hal_conf.h` 里把 `HAL_WWDG_MODULE_ENABLED` 注释掉了，即**没有使用**；
`bsp_watchdog.c` 仍然保留了打印 WWDG 复位原因的代码，方便将来排查。

## 5. 复位原因寄存器（RCC_RSR）：必读、必清

```c
uint32_t rsr = RCC->RSR;
if (rsr & RCC_RSR_IWDG1RSTF)  /* 看门狗复位 */
if (rsr & RCC_RSR_PORRSTF)    /* 上电/掉电 */
if (rsr & RCC_RSR_PINRSTF)    /* NRST 引脚（下载器复位、复位按键） */
if (rsr & RCC_RSR_BORRSTF)    /* 欠压 */
if (rsr & RCC_RSR_SFTRSTF)    /* 软件复位 */
...
RCC->RSR |= RCC_RSR_RMVF;     /* ⚠️ 必须清除, 否则标志会"粘住" */
```

**为什么要清**：这些标志是**累积**的，如果不在启动时清掉，你会看到"每次启动都同时报 IWDG 和 NRST"，
从而误判复位来源。本工程在 `BSP_WatchdogLogResetReason()` 末尾已经加了清除。

**排查时的用法**：

1. 打印/记录复位原因到日志（本项目会打 `[watchdog] reset reason: ...`）；
2. 看到一个"周期性的 IWDG 复位"→ 说明系统在稳定地卡死，而不是偶发跑飞；
3. 看到 POR/PDR → 说明是供电问题（比如电机启动导致的电压跌落）。

## 6. 启动期 × 看门狗：本工程最有价值的一课

### 6.1 冲突从哪来

- 运行期看门狗 = **200ms**（要求所有任务都健康）；
- 启动后最耗时的一步 = **BMI088 在线标定**：6000 次采样，正常约数秒；最多三轮，DWT 期限约 12s，任务监控总窗口为 15s；
- 而 IWDG 一旦启动、复位也不停 → 于是：

```
第 1 次运行: 某处卡死 → 看门狗复位
第 2 次启动: IWDG 仍按 200ms 计时, 而启动要 3~15s → 又被复位
第 3 次启动: 同上 ... → "永远起不来"
```

现象上它看起来像"换了优化等级就起不来"，实际上**是看门狗把排查结论带偏了**。

### 6.2 正确做法（本项目已实现）

```c
void BSPInit(void) {
    DWT_Init(480);
    BSP_WatchdogInit(4000);   /* ① 启动期先给一个"够长"的窗口 */
    ...
}

/* ② 任务创建完成后切回短超时；运行期只由健康监控统一喂 */
BSP_WatchdogInit(200);        /* RobotInit() 末尾 */
```

标定发生在 RTOS 的 INS 任务中。标定入口先关闭并锁定加热器，再向 `TaskMonitor` 申请最多 15s 的 INS 期限；daemon、motor、robot 等其他任务仍要按时报告健康。标定循环会让出 CPU，不会直接调用 `BSP_WatchdogFeed()`。超时或其他任务故障时，监控停止喂狗，IWDG 负责复位。

长操作窗口里一旦观察到其他任务超时，故障会一直锁存到复位。任务后来恢复并再次调用 `TaskMonitorFeed()`，只能更新它的心跳时间，不能撤销这次故障；长操作结束仍会失败，监控也不会恢复喂狗。这样可以避免一次短暂失活被后续心跳“洗掉”，从而错误地恢复加热。

设计原则总结成一句话：

> **短期限用于发现故障；长操作只能获得有限豁免，不能自行喂狗把故障盖住。**

### 6.3 调试时的注意

原先 `BSP_WatchdogInit()` 会设置 `DBGMCU_APB4FZ1_DBG_IWDG1`，让 IWDG 在 CPU halt 时冻结。MC02-0034 已移除这项固件设置；现在 halt 时 IWDG 仍计数，但它到期前 CPU 不会执行软件关断，PWM 也可能保持原输出。连接调试器本身不等于停核。**不要把 IWDG 复位当成 PB1 已经低电平的物理证明。** 裸板 `bench_safe` 构建从启动阶段禁用加热；受控台架上的停核／探针故障电平仍未验收。

## 7. 常见误区（都是血泪）

| 误区 | 后果 | 正确做法 |
|---|---|---|
| 把喂狗放在定时器中断里 | 任务卡死但中断照跑 → 看门狗形同虚设 | 由"能代表系统健康"的任务喂（本工程：TaskMonitor） |
| 喂狗周期贴着超时 | LSI 精度差 + 任务抖动 → 偶发复位 | 留 2~5 倍余量 |
| 启动期忘了喂 | 启动长 → 死亡螺旋 | 启动期长窗口 + 长步骤按进度喂 |
| 不清 `RCC_RSR` | 复位原因误判 | 打印后立即 `RMVF` |
| 用 LSI 做精确计时 | 误差大 | 精确计时用 DWT/TIM |
| 只靠 IWDG 而不做任务监控 | 卡死一个任务却不复位，或反过来频繁复位 | IWDG + 任务级健康检查组合 |
| 断电靠"复位"清 IWDG | IWDG 不会被普通复位清掉 | 记住：只有掉电才清 |

## 8. 一套可复用的排查动作（看门狗相关问题）

1. 上电后先读/打印 `RCC_RSR`，判断上次复位来源，然后清除；
2. 读 `IWDG->PR/RLR` 反推当前超时，确认和设计一致；
3. 用"两次读数比较"区分卡死/复位（见《06》第 5 节）；
4. 若怀疑看门狗是干扰项：**把长耗时循环改成逐轮喂狗**再测——若仍然复位，就说明复位源不是看门狗；
5. 排查完把复位原因打印保留在启动日志里（这是长期资产）。

## 9. 提交参数到内部 Flash 时，看门狗怎么办（2026-09-22 新增）

这是本工程最典型的一次"看门狗和长耗时操作打架"，值得单独记下来。

### 9.1 冲突是怎么产生的

- 运行期 IWDG = **200ms**，由 `TaskMonitorTick()` 在 daemon 任务里喂；
- 把参数写进内部 Flash 需要**先擦一整个 128KB 扇区**，H7 单 bank 下实测
  擦 1 个扇区 ≈ **0.83s**、擦 2 个 ≈ **1.66s**；
- 单 bank 擦写期间 **CPU 取指被硬件暂停** → 所有任务一起停 → 没人喂狗。

结论：**200ms 的看门狗必然先超时复位**，而且复位后重新启动、重新提交，形成复位循环。

### 9.2 本工程的做法：先验证健康，再建立限时保护

`bsp/param/bsp_param.c` 的 `ParamCommit()` / `ParamReset()`：

`ParamCommit()` 和 `ParamReset()` 先调用 `RobotInit()` 注册的保护回调。回调先锁定加热，再由 `TaskMonitorBeginLongOperation(INS, FLASH)` 确认所有任务当前健康。获准后参数层保存原 IWDG 超时、切到最多 8s 并喂一次，然后执行擦写和回读。返回后恢复原超时，由任务监控继续决定是否喂狗；Flash 成功且窗口未超时，才清理任务时间戳，为恢复调度留出期限。成功结束也不会立刻恢复加热，温控必须收到操作之后的新鲜 IMU 样本。

如果保护回调未注册、入口发现已有任务故障、Flash 失败或窗口超时，参数操作失败，加热器保持锁定。Flash 窗口结束后没有直接喂狗，所以任何已记录的任务故障仍会导致 IWDG 复位。

### 9.3 三个容易忽略的细节

1. **IWDG 的 `PR`/`RLR` 有更新等待位**（`PVU`/`RVU`）：写进去后硬件要几个 LSI 周期才能生效，
   期间写新值会被忽略。本工程 `IWDG_WaitForUpdateFlags()` 会等这两个位清零再写、
   写完再等一次，避免"改了超时其实没生效"。
2. **Flash 是全核停顿**：所以入口要先确认任务健康，并只允许通过带 8s 上限的保护回调；任务时间戳只在成功返回后重置。
3. **不要在中断里提交**：ISR 里擦 1.7s Flash 会阻塞整个系统，
   而且 IWDG 的放长/恢复也需要任务上下文才安全。

### 9.4 更彻底的方案（本项目暂未采用，留作后续）

| 方案 | 代价 | 收益 |
|---|---|---|
| 后台"预擦"非活动区（SAFE 状态时提前擦好） | 需要状态机管理 | 真正提交时只需写入（~1ms），完全不碰看门狗 |
| 换外部 Flash / FRAM | 增加硬件 | 彻底避开"擦写停 CPU" |
| 用双 bank 的 H7（如 H743/H750 部分型号） | 换芯片 | 可以边执行边擦写另一个 bank |

## 11. 6S 上电时：停核、复位和断电是三件事（2026-10-04）

本节对应 [TB47S／6S 安全审查](../6S上电安全审查_2026-10-04.md)，源码基线 `0965d031ad60c5f1c1eeeac63c728dc44f7d4338`。具体任务状态见 [TODO](../../.Doc/TODO.md) 的 MC02-0034～0041、LCD-09 和 HIL-10；本节没有新增硬件测试或学习掌握记录。

### 11.1 为什么暂停程序还可能继续加热

CPU 的工作是读取 BMI088 温度、检查 VIN，再把输出写到 `TIM3->CCR4`。TIM3 是另一个硬件单元，会反复执行最后设置的 PWM；CPU 暂停并不会自动把 CCR4 写成 0。

例如 `IMUHeaterUpdate()` 刚写入一个非零占空比，随后调试器 halt：温控和五分钟软件超时都不再执行，TIM3 仍可能重复旧 PWM。现在 IWDG 不会因固件调试冻结位而停计数，但它只能在超时后触发复位，不能证明这段时间 PB1 已失能。**“我暂停了程序”不能推导为“加热已经关闭”。** 旧 `tools/probe_snapshot.py` 会 halt；运行态读取改用 [不停车快照工具](../../tools/probe_snapshot_live.py) 和 [OpenOCD 配置](../../tools/openocd_running_inspection.cfg)，但物理连接与探针错误行为尚未实测。

OpenOCD 官方的[运行态内存检查说明](https://openocd.org/doc/html/GDB-and-OpenOCD.html#using-gdb-as-a-non-intrusive-memory-inspector)要求目标支持 background memory access，并关闭默认的 GDB attach halt 行为。配置文件清空 attach/detach 事件；脚本使用 `--nx`、关闭 interrupt-on-connect，只对 ELF 全局 RAM 值发出 `printf` 读取，并对每个 GDB 子进程设硬超时。主机测试验证工具命令与分类逻辑，但不能代替 CMSIS-DAP 实测。

软件准备妥当后，在已烧录的运行态目标上分开启动 OpenOCD 服务和快照读取：

```powershell
openocd -f tools/openocd_running_inspection.cfg
python tools/probe_snapshot_live.py --elf build/bench-safe/Basic_Framework_MC02_bench_safe.elf --samples 5 --interval 1 --timeout 5
```

这里不执行 `halt`、`reset`、`resume` 或目标写入。若 GDB 连接失败或超过 5 秒，工具报告 `probe_io_error` 并退出；没有连接设备前，仅可验证脚本和命令构造，不能据主机测试宣称 CMSIS-DAP 不停车读取已实测。

仅冻结 TIM3 计数也不够：PWM1 的输出取决于当前计数和比较值，停在有效阶段可能保持高电平。要关闭加热，应确保输出实际失能，而不是只让某个时钟停止。ST 的 [RM0468](https://www.st.com/resource/en/reference_manual/dm00603761.pdf) 第 3231～3234 页分别定义 TIM3 和 IWDG 的调试冻结；主供下验证关断需受控供电，不能用无限流电池做停核实验。

### 11.2 为什么 5% 和 0.30W 仍有前提

PWM 占空比 `D` 是导通时间的比例。电阻平均功率近似为：

```text
P平均 ≈ (输入电压² / 等效电阻) × D
```

以 [官方原理图条件](../硬件定位/MC02-6S供电依据.md) 的 47Ω 为例，25.2V 全导通约 13.51W；要按 0.30W 限制，占空比需约 2.22%。当前代码按 VIN 计算这个限值，再受 5% 上限约束。

这依赖 VIN 新鲜且准确、电阻与图纸一致、Q9 受控及温度采样可信。ADC 缓存停更时，公式可能用错电压；SPI 失败但仍返回“成功”时，温控可能用错温度；Q9 损坏短路时，写 CCR4=0 也不能断开电流。因此软件限幅、看门狗和外部故障能量限制需要各自验证。

### 11.3 复位为什么也不能替代限流

看门狗复位主要解决程序不继续工作的情况，不能检测所有局部过热，更不能切断板外短路线。参数 Flash 操作会临时使用最多 8s 的窗口；标定只为 INS 任务申请最长 15s 的受限期限，daemon、motor、robot 等其他任务仍持续受监控。标定循环会让出 CPU，不直接喂狗。加热器在这些操作入口先关断并保持锁定，成功后也要等到操作完成后的新鲜 IMU 样本；监控期间发现的任务故障仍会锁存。软件关断和看门狗不能代替外部限流及实测。

USB 也可能继续给低压系统供电。停止上位机、复位 MCU 或只断开电池，分别改变不同部分，不能笼统称为“整套设备已经断电”。本次采用的交付边界是先审查和修复、在无加热能量的模拟中验证异常，再由受控供电核验实际电平和温升；电池上电单独验收。

### 11.4 加热故障为什么需要锁存和新样本恢复

故障锁存表示“曾经发生过危险条件”，不会因为温度后来下降就自动清除。当前加热控制在温度达到 **50°C** 时立即关断并锁存；恢复阈值是严格低于 **42°C**，两者之间的 8°C 是回差。若在 49.9°C 就自动恢复，采样噪声或温度回摆可能造成反复开关；手动清除要求维护者明确处理过原因。

IMUHeaterClearFault() 返回 1 表示安全检查通过，返回 0 表示拒绝。调用时先清零 PWM 和 PID 积分，再检查模块初始化、温度范围与有限性、IMU 快照年龄不超过 5ms、ADC 快照年龄不超过 20ms、换算配置有效，以及 VIN 位于 10–30V。过温、超时等已锁存故障还要求最新 IMU 样本的序号晚于故障发生时记录的序号；重复或回退序号不能作为恢复证据。序号用无符号差值判断前进，因此计数器从 UINT32_MAX 回到 1 时仍可正确识别新样本。

清除成功也只代表“解锁条件满足”，不代表立即重新加热。接口当次保持零输出，并记录恢复点；控制器必须再收到一份清除之后的新样本，才继续常规温控检查。标定／Flash 长操作期间禁止清除；操作失败锁定不会被清故障接口解除。当前没有面向 LCD、串口或遥控器的生产清除入口。

连续加热时间从**实际 PWM 非零**的时刻开始计，输出归零就结束这一段连续计时；达到 300000ms（5分钟）时锁存超时。起始 tick 单独用一个有效标志表示，因此 tick 为 0 也能正常计时；经过时间用无符号减法计算，可跨过 32 位 tick 回绕。温度无效或采样停止时，加热立即关闭，距最后有效温度达到 500ms 时锁存传感器故障。MC02_HEATER_ENABLED=OFF 构建仍运行这些采样与故障判断，但 PWM 永远保持零。

这套软件规则仍受既有占空比与功率限制：启热配置最多 5%，并按可信 VIN 将估算平均功率限制在 0.30W。它不能证明 VIN 测量精度、Q9 物理关断能力或加热电阻实际温升；这些需要受限供电和仪表另行验收。MC02-0039 的主机回归把生产温控和 PID 与模拟 PWM、时钟及 ADC 数据源联编，分别验证启热／禁热配置。

### 11.5 Windows 路径传给 OpenOCD 时要用正斜杠

OpenOCD 的 `-c` 参数交给 Tcl 解释。把 `D:\RoboMasterRelated\...\firmware.elf` 直接拼进 Tcl 命令时，反斜杠会被当作转义符处理，OpenOCD 最终可能尝试打开 `D:RoboMasterRelated...firmware.elf` 这样的错误路径。Windows 主机上应先取得绝对路径，再把分隔符转换为 `/`，例如 `D:/RoboMasterRelated/.../firmware.elf`，并用日志确认 OpenOCD 打开的文件名。

要区分主机命令错误与已经改写芯片：`Programming Started` 只表示进入编程命令，不证明 Flash 已擦除或写入。若随后立即出现 `couldn't open`，且日志没有目标扇区擦除、写入和 verify 结果，就应停止并保留日志；不能把命令退出或“没有整片擦除命令”当成写入成功。MC02-0039 本次先保存 1MiB Flash 和参数区备份，OpenOCD 因反斜杠路径打不开 ELF，未进入目标 Flash 擦写；随后只复位运行已有固件，没有重试烧录。备份文件哈希与原始日志见 [MC02-0039 票据](../../workflow/tickets/MC02-0039.md)。

用户随后明确授权重新尝试。把 ELF 绝对路径转换成正斜杠后，OpenOCD 完成写入并报告 `Verified OK`。日志还显示，由于 Flash 写入对齐，工具把扇区擦除范围扩展到 `0x0803FFFF`；因此要检查实际擦除范围，而不只看 ELF 段的末地址。本次参数区从 `0x080C0000` 开始，烧录前后完整回读并逐字节一致。之后只读快照与 60 秒 COM14 被动采集均通过；细节和原始证据见 MC02-0039 票据。该结果只覆盖固件启动、BMI088 采样、通信帧和禁热状态，不能代替 VIN 精度、PB1 电平、温升或实际加热验收。

### 11.6 关掉 PWM 后，还要确认谁在驱动引脚（MC02-0041）

PB1 的输出涉及三类状态：GPIO 输出锁存 `ODR`、引脚模式 `MODER` 和 TIM3 的通道配置。`CCR4=0`、`CC4E=0`、`CEN=0` 表示定时器没有开启该 PWM 输出；它们不说明 PB1 一定由 GPIO 主动拉低。若 `MODER` 仍选复用模式，写 GPIO 的 ODR 也不能把输出控制权切回 GPIO。禁热配置的明确目标是：PB1 为推挽 GPIO，输出锁存为低，定时器通道和计数器都关闭。

本轮问题出在初始化顺序。此前的安全入口已经配置 GPIO 低输出，但后续 `HAL_TIM_MspPostInit()` 又按 CubeMX 生成代码把 PB1 配为 AF2/TIM3，覆盖了前面的设置。因此不能只检查关断函数是否正确，还要沿启动调用链检查它后面有没有重新配置同一引脚的函数。

修复位于 [Core/Src/tim.c](../../Core/Src/tim.c) 的 TIM3 用户代码区域：禁热时先启用 GPIOB 时钟，再写 PB1 低锁存，最后配置推挽输出并返回。先写低再切换模式，是为了避免输出模式生效的一刻使用历史高锁存值。返回会跳过后面的复用配置；放在 CubeMX 用户保护区域，便于以后重新生成工程时保留该规则。重复初始化也必须遵循同一顺序，不能依赖“启动时已经做过”。启热配置仍走原 AF2 路径，但本轮只在主机模拟中覆盖它。

主机测试直接调用生产 `HAL_TIM_MspPostInit()`，把起始锁存设为高，验证低写入先于 GPIO 模式配置，再重复一遍。修复前，裸板禁热和整机禁热两种测试都失败；修复后通过。另一组测试直接调用生产 `MotorControlTask()`：裸板仍消费 CAN、UART、VCP 队列，但电机输出函数的调用数为零。接收队列消费者属于通信运行所需逻辑，不能随执行器控制一起删掉。

配置隔离要在三个层面交叉核对：CMake 拒绝裸板启热，ELF 检查执行器入口没有被链接，板上运行态只读检查实际寄存器。两种优化等级都检查 ELF，可避免只验证一种链接结果。新建 Release 构建目录还暴露了 DWT 测试桩缺少变量声明；补齐硬件替身的接口比依赖旧构建缓存更可靠。

这些结果可以证明软件配置和数字寄存器状态，不能证明 PB1 引脚实测电压、开关管关断能力、VIN 精度或温升。主机及板上证据集中在 [MC02-0041 票据](../workflow/tickets/MC02-0041.md)，后续物理测量仍在 LCD-09；本节没有把阅读文档记作已掌握。

本轮实板五次快照中，GPIOB `MODER=0xa95feaa6`、`OTYPER=0`、`ODR=0x1c00`。判断 PB1 时只提取它的两位模式和对应输出位：`(MODER >> 2) & 3 = 1`，表示 GPIO 输出；`ODR & 2 = 0`，表示 PB1 锁存低。整个 ODR 非零是其他引脚的状态，不能因此判定 PB1 为高。TIM3 `CR1=0x80` 也不等于计数器运行：`CEN` 是 bit0，该位为零；bit7 的 ARPE 仍保留初始化配置，CCER 和 CCR4 均为零。

通信验收同样需要观察变化：1000 个禁止控制的全零指令使 RX 从 0 增至 1000，发送期间接收时间更新，停止后整个接收帧和时间归零，CRC 错误保持 0。只看“mode=0”无法证明旧数据被清除，因为发送的中性指令本身 mode 就是 0；所以额外读取了全部 29 字节，其中原本非零的 SP 头与 CRC 也必须归零。60.306 秒收到 12,060 个 CRC 正确状态帧，四元数全部有限。软件与寄存器观测没有出现复位或启热；用户报告主输入电流由约 0.09A 升至 0.115A，原因仍需供电与负载测量，不能把软件回归通过当作电流变化的解释。

后续用户确认电流已回落至约 0.09A 并稳定，C.V 正常亮、LCD 正常刷新、电机摘要全部为 0，补齐了本轮人工验收。记录电流时应保留“升高—回落—稳定”的顺序：单次 0.115A 读数不能被写成持续升高，后来回落也不能反推此前变化的原因。主机脚本能够校验通信和寄存器，LCD 实际显示与电源面板观察则需要人补充；任务关闭依据是两部分证据满足本轮条件，并不把尚未测量的引脚电平、VIN 精度或温升一并判定通过。

## 12. 初始化失败为什么进入失能诊断（R25-10）

系统初始化在 RTOS 调度器启动前执行。此时若某个 CAN/UART/PWM 注册器返回失败，继续创建后续控制模块会把“前一项缺资源”伪装成多处异常；在失败处无限循环则既没有诊断进展，也可能卡在中断关闭状态。R25-10 的规则是：注册失败返回 `NULL`，调用方逐层传播；`RobotInit()` 记录阶段、模块和资源，恢复进入时的 `PRIMASK`，然后保持 SAFE/FAULT，拒绝 READY、使能和标定。

诊断记录只保留首次失败的阶段、模块、原因和资源编号，后续失败仍会增加报告次数。这个次数包含重复报告，不能直接当作失败任务的数量。任务创建逐项检查并记录具体任务编号。`init_diagnostic_snapshot.heartbeat` 增加说明诊断代码仍在运行，控制系统是否就绪还要看启动结果和 RobotSafety 状态。

看门狗分成两个阶段：`BSPInit()` 先设置 4 秒启动窗口，RTOS 任务都创建成功后才缩到运行期的 200ms。若任务创建或启动失败，主循环不启动机器人任务，而是重复执行输出关断、更新诊断心跳并喂 IWDG，等人工读取记录和处理。任务开始后发生 INS 算法或蜂鸣器初始化失败，则锁存 `ROBOT_FAULT_INIT_FAILURE`；失败任务只做受限诊断，其他已运行任务继续经过 RobotSafety 和任务监控，普通手势不能清除此故障。

这条路径会等待人工处理，因此不会靠看门狗自动反复重启。完整复位后，启动程序才会重新清零普通 RAM 中的诊断记录；所以应先通过只读 `--init` 查询保存记录，再决定复位。运行记录和主机故障测试没有证明物理关断引脚或负载状态，裸板验收仍需检查 BMI088、SP 通信、禁热及输出隔离。

### 12.1 读懂启动诊断的记录和计数（MC02-0109）

第二批注释整理对应检查清单015、016。先看 [init_diagnostic.h](../../application/init_diagnostic.h) 的阶段、原因和结构体，再沿 [init_diagnostic.c](../../application/init_diagnostic.c) 的判断阅读各入口，注意下面几个用法。

- `InitDiagnosticBegin()` 和 `InitDiagnosticSetStage()` 只更新阶段。已经记录失败时，两者都保留首次失败的阶段；再次调用 Begin 也不会清除标志或计数。
- `InitDiagnosticReportFailure()` 第一次调用时保存四项失败信息，以后的调用只增加 `failure_count`。任务创建失败使用 `InitDiagnosticResource_e` 找到具体任务，其他资源编号由报告失败的代码指定。报告接口只记录，调用方还要负责停止控制等后续处理。
- `failure_count` 到 `UINT32_MAX` 后保持不变，避免重新变成 0；`heartbeat` 每次调用加 1，超过 `UINT32_MAX` 后会回到 0。两者的单位都是“次”，心跳没有固定的毫秒含义，失败后的循环也会继续更新它。
- `InitDiagnosticGetSnapshot()` 将完整记录复制到调用方的结构体，传入 `NULL` 时直接返回。复制前暂时关闭普通中断，防止读到一半时被改写；完成后恢复原来的 `PRIMASK`，调用前已经关闭中断时仍保持关闭。
- `InitDiagnosticMarkReady()` 当前在 INS 初始化成功后调用，只把诊断阶段改为 READY；实际是否允许控制由 RobotSafety 处理。已有失败时，它也不会覆盖失败阶段。

本批只补注释，不改变字段类型、编号、调用顺序或判断。现有 [init_diagnostic_test.c](../../tests/host/init_diagnostic_test.c) 连续报告两次不同失败，再调用 MarkReady 和 Heartbeat，检查首次失败保留、报告次数为 2、心跳次数为 1，以及读取后中断状态恢复。比较记录和验证日志保存在本地 `build/mc02-0109/`，验证结果随本批交付记录在 TODO 中。
