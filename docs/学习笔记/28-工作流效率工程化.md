# 工作流效率工程化：让验证证据和反馈回路留在仓库里

本文对应 **MC02-0139、MC02-0140、MC02-0141**，并记录用 **MC02-0001** 检验这套流程的过程。规则入口仍是 [issue-tracker.md](../agents/issue-tracker.md)；这里解释为什么改、改完怎样用。

## 0. 一句话总结

先让证据能被别人复核，再让重复命令变少、变快；流程优化不能只省一次敲命令的时间，还要减少“结果只存在本机”和“同一份清单改三处”的浪费。

## 1. 证据为什么要离开 `build/`

`build/` 被 Git 忽略，适合放编译产物和原始日志，不适合放**结论**。以前很多 TODO 条目写“验证日志见 `build/mc02-0122/`”，清理构建目录或换一台机器后，这个链接就打不开了。

新的约定：

- 结论、命令、通过数、失败原因和未覆盖范围写进 `docs/workflow/tickets/<ID>-evidence/README.md`；
- 原始日志、ELF、map、ZIP 继续留在 `build/` 或 `/tmp`；
- TODO 只保留一句结论和票据链接。

`check_todo.py` 会对未完成条目里的 `build/...` 引用给提醒。它不阻止交付，因为调试期间引用原始日志是合理的；提醒的作用是让人补一份可提交的摘要。

## 2. 文档链接检查：先找得到，再谈可复核

文档里的相对链接是最容易腐烂的资产：文件改名、测试删除、票据目录调整，正文却还指向旧路径。以前只有 `check_exercises.py` 检查课程链接，其余靠人工。

[check_docs_links.py](../../tools/workflow/check_docs_links.py) 做四件事：

1. 只扫根说明、`.Doc/` 和 `docs/` 下的 Markdown，避免把第三方技能和构建目录算进来；
2. 跳过外部网址、页内锚点、围栏代码和行内代码；
3. 把 `build/`、仓库外路径和清单里的独立仓库记为提醒，目录缺失记为错误；
4. 用 `PathCache` 按目录缓存文件名，避免为每条链接调用一次 `resolve()`。

第 4 点不是提前优化：在本仓库的 WSL `/mnt/d` 工作区上，150 余个文档、2000 余条链接逐条 `resolve()` 约 10 秒；改成目录缓存和文本路径比较后约 0.9 秒。原因很直接：`resolve()` 会为路径的每一段查询文件系统，而 `os.listdir()` 一个目录一次就能判断该目录下有哪些名字。

`docs_links_allowlist.json` 记录两类允许缺失的路径：`tools/referee_sim/` 是独立仓库，`.Doc/资料/` 和 `资料/` 是体积大且有版权的厂商资料。清单只允许“提醒”，不允许悄悄忽略错误。

## 3. TODO 从“格式检查”变成“分诊入口”

原来的 `check_todo.py` 只检查未完成项的编号、分类、状态和 `验收：`。[扩展后](../../tools/workflow/check_todo.py) 多了三件事：

- 已完成项也参与编号查重。历史里同一个编号出现在两个条目时，现在能发现；
- 未完成项正文超过 1200 字时提醒。验收条件可以写长，但成段的验证记录更适合放票据；
- 未完成项只引用 `build/` 时提醒补证据摘要；
- `--summary` 输出未完成数、状态、分类和按章节的分布，`--json` 供其他脚本读取。

任务状态仍只从 `.Doc/TODO.md` 读取；摘要由检查器现算，票据和学习笔记只引用任务编号。

## 4. 一份预设清单，三个入口共用

十种官方固件预设原先在 CI 的构建循环、归档循环、profile 检查和文档里各写一遍。新增预设时，漏掉任何一处都不会立刻报错。

现在 [presets.py](../../tools/workflow/presets.py) 保存：

- 预设名、profile、板卡角色、构建类型；
- ELF 产物名（`bench_safe`／`robot`／`chassis`／`gimbal`／`rcdiag`）；
- `check_firmware_profile.py` 需要的参数；
- GitHub Actions 的 `include` 矩阵。

`presets.py --check-cmake` 会解析 `CMakePresets.json`，逐个核对 profile、角色和构建类型。CMake 仍是预设定义的来源，Python 文件只补“要验证什么、产物叫什么”。

## 5. `verify.py`：本地只记一个入口

[verify.py](../../tools/workflow/verify.py) 把常用检查拆成六个阶段：

| 阶段 | 做什么 | 典型耗时 |
|---|---|---|
| `todo` | TODO 契约和分诊摘要 | 0.1 秒 |
| `docs` | 文档相对链接 | 约 1 秒 |
| `tools` | `tests/tools` 的 Python 回归 | 约 10 秒 |
| `host` | 主机 Debug／Release 构建和 CTest | 数分钟 |
| `firmware` | 十种 ARM 预设构建和源码隔离 | 较长 |
| `archive` | 为已构建预设生成 ZIP | 取决于构建 |

常用组合：

```sh
python3 tools/workflow/verify.py --fast       # 改文档、脚本后
python3 tools/workflow/verify.py --host       # 改主机测试或纯 C 逻辑后
python3 tools/workflow/verify.py --firmware --presets bench-debug,robot-single-debug
python3 tools/workflow/verify.py --all --build-root ~/mc02-build
```

在 Windows 上直接运行会转交 WSL，不需要手写 `wsl.exe --cd ...`。`--build-root` 可以指到 WSL 的 ext4 目录；源码继续放在 `D:` 方便编辑，构建不再反复走 `/mnt/d`。`--dry-run` 只打印命令，适合先确认工具链和路径。

默认构建根仍是 `build/wsl`，没有强行改到家目录：现有任务、归档路径和文档都指向这个位置，改默认值会把一次效率改进变成一次路径迁移。

## 6. ccache 是“找到才用”

[cmake/mc02_ccache.cmake](../../cmake/mc02_ccache.cmake) 只在 `find_program(ccache)` 成功时设置 `CMAKE_C_COMPILER_LAUNCHER`。没装 ccache 时构建命令和原来完全一样，不会出现“本地能过、CI 因为找不到 ccache 而失败”。

本机 WSL 没有安装 ccache（`sudo` 需要密码），因此只验证了未安装时的配置和构建不受影响；缓存命中率和实际节省时间还没有数据。CI 安装了 ccache 并缓存 `.ccache`，第一次运行只能建立缓存，收益要从第二次开始看。

## 7. CI 先做低风险收敛

[c-cpp.yml](../../.github/workflows/c-cpp.yml) 这一轮加的是：

- `concurrency`：同一分支的新提交取消旧运行；
- `actions/cache` 缓存 `.ccache`，并在 apt 里安装 ccache；
- TODO 摘要、文档链接和预设清单检查；
- 原有十种固件构建、非法配置拒绝、源码隔离和归档步骤保持不变。

没有把十种预设改成矩阵，也没有改归档结构。原因是这些改动无法在本地完整模拟，先保留可回退的最小步骤；矩阵化留给能实际观察 Actions 运行的一轮。

## 8. 用 MC02-0001 检验：一条真实任务的路径

选中的 TODO 是 **MC02-0001**：给 BSP I²C 增加 10 位地址支持。它是纯软件、可用主机测试验收、不需要连接 10 位从机。

原来的路径大致是：读 `bsp_iic`、查 HAL 地址约定、改结构体、补测试、跑全部主机测试、再跑 ARM 构建、最后手写 TODO 和票据。新流程把可复用部分压缩成：

```sh
python3 tools/workflow/verify.py --fast
python3 tools/workflow/verify.py --host
python3 tools/workflow/verify.py --firmware --presets bench-debug
```

实际仍然需要读代码和设计测试，这部分没有被工具替代。省下来的是：不用记 `cmake -S tests/host` 的参数、不用手写 `--build-dir` 和产物名、不用在 CI、脚本和文档之间对照预设清单，也不会把证据只留在 `/tmp`。

以下实测来自 2026-10-28 的源分支，只作为历史数据保存；当前整合后的结果记录在第 11 节。

源分支实测：

| 阶段 | 结果 |
|---|---|
| `verify.py --fast` | 11.5 秒（TODO 0.1、文档 1.0、工具 10.4） |
| 主机回归 | Debug／Release 各 421 个 CTest 通过 |
| `bench-debug` 固件 | 161 步编译链接，43.7 秒，源码隔离检查 PASS |
| 归档 | ZIP 生成 28.4 秒，SHA-256 已记录 |
| 文档链接 | 2032 条，缺失 0；检查从约 10 秒降到约 0.86 秒 |

I²C 的实现细节见[第 03 篇 6.4 节](./03-非阻塞通信与CAN收发技术细节.md#64-10-位地址与-7-位地址不能只看数值mc02-0001)。

## 9. 这次没做的事

- **TODO 分文件**：主工作树当时有未提交的 MC02-0084 修改，重写 `.Doc/TODO.md` 会在合并时覆盖这些条目。先交付检查器和摘要，等那批修改提交后再迁移已完成项。

## 11. 2026-11-14 整合复验

本轮把外置 WSL 构建目录作为验证条件。主机回归暴露了格式诊断检查器假设编译数据库里的每个 C 源都位于仓库内；实际外置构建会把公开头检查源码生成在构建目录。检查器现在单独计数 `public-header-*.c` 生成文件，并拒绝其他意外的仓库外 C 源。这样保留源码清单审计，也能使用 WSL ext4 构建目录。

整合后的具体通过数、耗时和仍未覆盖的硬件条件，以[工作流票据](../workflow/tickets/WORKFLOW-20261028.md#整合后本机验证)为准；这里不沿用源分支数字冒充本轮结果。


## 主线整合时发现的预设冲突

命名预设存在，不等于它当前能生成固件。哨兵的机械参数和三轴实现尚未确认，生产预设必须在 CMake 配置阶段拒绝；把它放入要求成功的 CI 构建循环会使后续检查和归档无法执行。

现在 `OFFICIAL` 保留十种命名配置供一致性核对，`BUILDABLE` 只包含四种可生成的裸板配置。默认本地验证、CI 构建和归档使用后者。六种生产预设由 `check_production_rejection.py` 单独配置，必须同时满足返回失败和出现核心配置未确认的具体原因；找不到工具链等错误不能算通过。实物条件补齐后，需要同时更新成功构建清单与预期拒绝检查。

历史任务的回归数字迁入对应 evidence 文档，以保留版本与限制。合并前审查还发现 CAN 协议复杂语句和哨兵长参数表的注释欠缺，登记为 MC02-0143；这项说明补充不改变生产配置仍未确认的事实。
