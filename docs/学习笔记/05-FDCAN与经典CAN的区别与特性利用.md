# 05 FDCAN 与经典 CAN 的区别，以及怎么把 FDCAN 的特性用起来（写给零基础）

## 0. 先厘清三个容易混在一起的名词

| 名词 | 是什么 | 类比 |
|---|---|---|
| **CAN** | 一种**总线协议**（物理层差分信号 + 仲裁 + 错误处理 + 帧格式），ISO 11898 标准 | "语言" |
| **经典 CAN（CAN 2.0 / Classic CAN）** | 协议的经典版本：**数据最多 8 字节**、最高 1Mbps | "只会说短句" |
| **CAN FD（CAN with Flexible Data-rate）** | 协议的升级版：**数据最多 64 字节** + **数据段可以更快**（双比特率） | "短句照旧，但长句能说得又快又长" |
| **FDCAN** | STM32 芯片里**实现 CAN FD 的外设模块**（Bosch M_CAN IP 的授权实现）；H723 里有 3 个 | "嘴巴"（bxCAN 是 STM32 老芯片里只支持经典 CAN 的嘴巴） |

所以"FDCAN 和普通 CAN 总线的区别"要分两层看：

1. **外设层**：FDCAN 比老的 bxCAN 多了消息 RAM、可配置的 FIFO/队列、更多滤镜、时间戳、错误状态寄存器等；
2. **协议层**：FDCAN 既支持**经典 CAN 帧**（本项目现在用的就是这种），也支持 **CAN FD 帧**（长数据 + 双比特率）。

**重要**：FDCAN 外设 ≠ 一定在跑 CAN FD。可以把 FDCAN 配成纯经典 CAN 模式（我们就是），
此时它与普通 CAN 总线完全兼容、行为一致，只是"外设能力"更强。

## 1. 经典 CAN 的规格（我们现在的实际状态）

| 项目 | 经典 CAN |
|---|---|
| 数据长度 | **0~8 字节**（一帧最多 8 字节） |
| 速率 | 最高 **1 Mbps**（我们跑 1 Mbps） |
| 比特率 | 整帧**同一速率**（仲裁段与数据段相同） |
| 帧格式 | 标准帧（11 位 ID）/ 扩展帧（29 位 ID） |
| CRC | 15 位 |
| 关键机制 | 位填充、ACK、错误计数（TEC/REC）、错误主动/被动/BusOff |
| 一帧到底能带多少有效数据 | 8 字节数据，但整帧约 110~135 bit（含开销与位填充） |

由此推出一条很实用的结论：

> **1Mbps 下，一帧 8 字节实际只有约 60% 的"有效载荷"，其余都是帧头/CRC/ACK/位填充开销。**

我们的电机反馈就是这种：每帧 8 字节 × 1kHz × 每条总线 5 个电机 ≈ 5k 帧/s，把总线推到 60%~100%。

## 2. FDCAN（CAN FD）多出来的能力

### 2.1 数据段：最多 64 字节

CAN FD 的帧格式在"控制域"里用 FDF 位区分经典帧与 FD 帧，数据长度用 4 位（0~15）**非线性编码**：

| DLC 编码 | 实际字节数 |
|---|---|
| 0~8 | 0~8（与经典一致） |
| 9 | 12 |
| 10 | 16 |
| 11 | 20 |
| 12 | 24 |
| 13 | 32 |
| 14 | 48 |
| 15 | **64** |

意义：**同样数量的数据，帧数可以大幅变少**。例如 64 字节：

| 方式 | 帧数 | 每帧 overhead |
|---|---|---|
| 经典 CAN（8 字节/帧） | 8 帧 | 8 倍帧头/CRC/仲裁/中断 |
| CAN FD（64 字节/帧） | **1 帧** | 1 倍 |

对 CPU 来说，收益不只是带宽：**每帧至少要进一次中断**。帧数降 8 倍 = 中断次数降 8 倍 = CPU 占用和抖动一起降。

### 2.2 双比特率（BRS：Bit Rate Switch）

CAN FD 允许一帧里**两段不同的速率**：

- **仲裁段**（帧头、ID）：仍用较慢的速率，保证仲裁的物理距离/拓扑余量；
- **数据段**（真正搬运数据）：可以用更高速率（BRS 位=1 时切换），可达 5 Mbps（取决于芯片、收发器与线束）。

为什么这么设计：仲裁要在整条总线上"同时收敛电平"，速率越高可用的线长越短；而数据段只有 1 个发送方，可以快。

> 注意：跑 CAN FD 需要**支持 FD 的收发器**（例如 TJA1044/TJA1051 这类）和**支持 FD 的调试工具**；
> 我们现在的 MC-02 用的就是经典 CAN（`FDFormat = FDCAN_CLASSIC_CAN`、`BitRateSwitch = FDCAN_BRS_OFF`）。

### 2.3 消息 RAM 与可配置的收发结构（FDCAN 外设层）

老 bxCAN：2 个接收 FIFO（各 3 级）、每组 3 个发送邮箱、14 个滤镜（CAN1/CAN2 各一半）。
FDCAN：

- 一块**消息 RAM**（H7 的 3 个 FDCAN 共享这段 RAM），里面划分出：滤镜、Rx FIFO0/1、Rx Buffer、Tx Buffer、**Tx FIFO 或 Tx Queue**、Tx Event FIFO；
- 每个区域的大小、深度、元素大小**都可在 CubeMX 里配置**（本项目：`RxFifo0ElmtsNbr=4`、`TxFifoQueueElmtsNbr=16`、`StdFiltersNbr=14`）；
- 发送缓冲有两种组织方式：**FIFO（先进先出）** 与 **Queue（按 ID 优先级）**；接收有 FIFO / Buffer / Queue 三种。

**我们能利用的点**：
- 发送深度从 4 提到 16，突发时少丢帧（本项目已做）；
- 接收 FIFO 从 4 提到 8~16，降低"来不及取走就溢出（MESSAGE_LOST）"的概率（本项目待办）；
- 滤镜数量按需分配：给"必须收"的 ID 精确滤镜，其余一律 REJECT（本项目已用全局滤镜 REJECT + 精确 ID 滤镜）。

### 2.4 时间戳与 Tx Event FIFO

- 接收帧可以带 **16 位时间戳**（来自内部时间基准），用来算"这帧是什么时候到的"；
- **Tx Event FIFO** 记录每一帧**真正发出去**的时间戳（而不是"交给硬件"的时间）。

**能利用的点**：
- 做**总线时延/抖动统计**（例如：控制指令发出到对方接收的时间）；
- 给上位机（NUC）的数据打时间基准 —— 这正好是"协议 v2 需要时间戳"的低成本方案之一（我们目前还没用）。

### 2.5 更强的错误与健康管理

FDCAN 提供完整的寄存器：

- `PSR`（协议状态）：BusOff、Error Passive、Warning、当前活动、最后错误码；
- `ECR`（错误计数）：TEC / REC；
- 协议异常处理（ProtocolException）、自动重传开关（AutoRetransmission）、收发器延迟补偿（TDC）、时钟校准（CDR）。

**能利用的点**：把 TEC/REC/BusOff 做成"总线健康仪表"（本项目已实现：10Hz 健康检查 + BusOff 自动恢复 + 计数）。

### 2.6 多实例

H723 有 3 个 FDCAN，可把负载分摊到多条总线（本项目底盘在 CAN1、云台 GM6020 在 CAN3 等）。
这也是"总线负载过高"时最直接的手段：**把设备摊到不同总线**，而不是硬压帧率。

## 3. 一张表看清差异

| 维度 | 经典 CAN（bxCAN 时代） | FDCAN 外设 + CAN FD |
|---|---|---|
| 单帧数据 | ≤ 8 字节 | ≤ **64 字节** |
| 比特率 | 单一速率，≤ 1 Mbps | 仲裁段 ≤1 Mbps，**数据段可切换更快**（BRS） |
| 每帧开销占比 | 高（8 字节时约 40%） | 低（64 字节时约 10%） |
| 接收结构 | 2 个 FIFO × 3 级 | 消息 RAM 里自由配置的 FIFO/Buffer/Queue |
| 发送结构 | 3 个邮箱 | Tx FIFO / Tx Queue，深度可配（本项目 16） |
| 滤镜 | 14 个（分给 CAN1/CAN2） | 数量可配（消息 RAM 里分配） |
| 时间戳 | 无 | **有**（接收时间戳 + Tx Event FIFO） |
| 错误管理 | 基础（ESR 等） | PSR/ECR/TDC/CDR，协议异常处理可选 |
| 与老设备兼容 | — | FD 帧老控制器无法正确解析；**同一总线建议统一跑经典或统一跑 FD** |
| 调试工具要求 | 普通 CAN 分析仪 | 必须支持 CAN FD 才能看懂 FD 帧 |

## 4. 我们该怎么"充分利用"FDCAN？（结合本工程的清单）

### 4.1 首先明确现在的定位

| 项目 | 当前实现 | 说明 |
|---|---|---|
| 帧格式 | `FDCAN_CLASSIC_CAN` | 与电调/裁判/视觉的既有设备兼容 |
| 比特率 | 1 Mbps（整帧同速） | 电机总线都用这个 |
| 数据长度 | 8 字节 | |
| 发送 | Tx FIFO（深度 16）+ 非阻塞丢帧计数 | 已完成 CPU 优化 |
| 接收 | RxFIFO0/1（各 4 级）+ 精确 ID 滤镜 + O(1) 派发 | 已完成 |
| 健康管理 | TEC/REC 读取 + 10Hz BusOff 自动恢复 | 已完成 |
| 时间戳 | **未使用** | 待补 |
| CAN FD 长帧 | **未使用** | 需要两端设备都支持 |

### 4.2 优先做（零硬件成本，收益明确）

1. **把大包数据改走 FD 长帧 + 高速数据段**（前提：对端也支持 FD）
   - 目标场景：与 NUC 的协议 v2（带时间戳四元数、导航帧、裁判完整转发）；
   - 收益：帧数从 N 帧降到 1 帧，中断/CPU/抖动一起降；
   - 注意：要确认 NUC 侧接口（USB-CAN-FD 适配器）与线束支持；总线两端必须都是 FD 设备。
2. **接收 FIFO 加深**（4 → 8/16）
   - 5 个电机 × 1kHz = 每秒 5000 帧，一旦 ISR 被抢占久一点就会溢出丢帧；
   - 这也是我们"接车后要复核 MESSAGE_LOST"的待办。
3. **用 Timeout/时间戳做诊断**
   - 给接收帧打时间戳 → 统计"反馈周期抖动"，找出偶发的总线拥塞；
   - Tx Event FIFO 记录实际发送时刻 → 判断"是软件没发，还是总线发不出去"。
4. **把总线健康写进仪表盘**（已部分完成）
   - TEC/REC、BusOff 次数、恢复次数、丢帧计数都能在 LCD/RTT 上看到。
5. **分摊总线**
   - 每条总线 5 个 1kHz 反馈设备已经接近极限（见《02》第 7 节）；
   - 有余量就把设备挪到空闲总线（我们 CAN3 目前只挂云台）。

### 4.3 需要硬件支持才能做

- **收发器换成支持 FD 的型号**、线束/终端按更高速率设计；
- **调试工具换成支持 CAN FD 的分析仪**（否则抓到 FD 帧也解不开，或者直接报错）；
- **同一总线不要混跑**：FD 帧对经典节点是"错误帧"，会把总线搅乱。

### 4.4 明确不要做的（常见误区）

| 误区 | 事实 |
|---|---|
| "FDCAN = 5Mbps，直接提速就行" | 提速要收发器、线束、对端设备全都支持；只有仲裁段保持 1Mbps 时拓扑才最宽容 |
| "把电机总线也换成 FD 就能提速 8 倍" | 电机（DJI 电调）说的是经典 CAN，换不了；反馈帧率由电调决定，我们改不了 |
| "数据段快就一定好" | 高速率对线长、终端、地线更敏感；采样点/延迟补偿（TDC）也要正确配置 |
| "时间戳没成本" | 用的是同一个消息 RAM/寄存器组，配置错了会导致帧丢失或时间戳漂移 |

## 5. 用 FDCAN 自测（本项目即将做的"内部回环"）

FDCAN 内置两种自测模式，能在**没有第二个节点**的情况下验证收发链路：

| 模式 | 行为 | 用途 |
|---|---|---|
| **内部回环（Internal Loopback）** | 发送的帧在芯片内部被自己接收，**不驱动总线** | 验证"软件发送 → 硬件收发 → 中断 → 解析"整条链路；**总线上挂着别的设备也安全** |
| 外部回环（External Loopback） | 帧真的发到总线上，同时内部接收 | 额外验证收发器/线束（但会影响总线，慎用） |

关键点：

- 回环模式下节点把自己当作接收方，**不需要外部 ACK**，所以不会像空总线那样错误计数狂涨、进 BusOff；
- 自测应该覆盖：发送是否被接受（`tx_ok`）、接收中断是否触发、ID/DLC/数据是否一致、滤镜是否正确匹配；
- 自测期间要**临时切模式并重新初始化**：`HAL_FDCAN_Stop()` → 改 `Init.Mode` → `HAL_FDCAN_Init()` → 重配全局滤镜/启动/开中断；
  **重新初始化会清掉消息 RAM 里的滤镜**，所以测试结束后必须把已注册实例的滤镜重新加回去（本项目在 `CANRunLoopbackSelfTest()` 里做了这件事）。

本项目的实现与实测结果见 `docs/代码审查报告_MC-02.md` 的 CAN 章节；自测结果保存在
`can_selftest_tx_ok / rx_ok / rx_bad / tx_fail / pass_mask` 这些变量里，可用 Live Watch 或 OpenOCD 读取。

## 6. 术语速查

| 术语 | 一句话 |
|---|---|
| Classic CAN | 经典 CAN：≤8 字节、单速率、≤1Mbps |
| CAN FD | 升级版：≤64 字节 + 数据段可提速 |
| FDCAN | STM32 里实现 CAN FD 的外设（也兼容经典 CAN） |
| BRS | Bit Rate Switch，数据段切换高速率 |
| DLC | 数据长度码（FD 里是 0~15 的非线性编码） |
| Message RAM | FDCAN 专用存储区，放滤镜与收发缓冲 |
| Tx FIFO / Queue | 发送缓冲：先进先出 / 按 ID 优先级 |
| Tx Event FIFO | 记录已发送帧（含时间戳）的日志区 |
| TDC | 收发器延迟补偿（高速率下必要） |
| PSR / ECR | 协议状态寄存器 / 错误计数寄存器（TEC、REC） |
| Internal Loopback | 内部回环自测：自己发自己收，不驱动总线 |
