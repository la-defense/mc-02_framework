# 17 LCD 刷新的性能账：为什么"少画"比"画得快"更有效（写给零基础）

> 本篇回答的问题：
> 1. 刷屏到底花多少时间？怎么从 SPI 频率算出"一帧能画多少像素"？
> 2. 为什么"每帧耗时 58ms"和"CPU 占用 15.3%"是两个完全不同的数？
> 3. 提 SPI 频率和"少画一点"，哪个收益更大？上限分别是多少？
> 4. "内容没变就不重绘"听起来简单，坑在哪？
> 5. 帧缓冲、局部刷新、脏矩形这些词是什么意思，本工程为什么不用？
>
> 对应代码：`modules/lcd/lcd_ui.c` 的值区缓存、`Core/Src/spi.c` 的分频。
> 本次实测：`lcdtask` 占用 **15.3% → 1.0%**，IDLE 余量 **52.2% → 66.2%**。

---

## 1. 先算一笔账：刷一次屏要多久

LCD 用的是 SPI，每个像素 16 位（RGB565，2 字节）。所以：

```
SPI 实际字节速率 = SPI 时钟 / 8
一帧耗时 ≈ 一帧总字节数 / SPI 字节速率
```

本工程 SPI1 = **15MHz**（PLL1Q 120MHz ÷ 8）时：

```
字节速率 = 15MHz / 8 = 1.875 MB/s
```

再看一帧要画多少东西（每页 9 行值区）：

| 内容 | 像素数 | 字节数 | @1.875MB/s |
|---|---|---|---|
| 一行值区的清屏（172×16） | 2752 | 5504 | 2.94 ms |
| 一行文本（约 10 字符 × 16×8） | 1280 | 2560 | 1.37 ms |
| **9 行合计** | — | **约 72.6 KB** | **约 39 ms** |

**结论很直白**：15MHz 下画满一页要几十毫秒，而刷新周期只有 200ms（5Hz），
也就是说 **CPU 有相当大一块时间是在"重复画同样的东西"**。

---

## 2. 墙钟时间 ≠ CPU 占用（很容易搞混的一点）

本工程的探针里有这么两个数：

```
lcd_upd  = 58397 (us, last)      ← 上一次刷新的"墙钟"耗时
lcdtask  = 153 (千分比)          ← LCD 任务的实际 CPU 占用 = 15.3%
```

**它们为什么差这么多？**

- `lcd_upd` 测的是"从开始刷到刷完，墙上时钟走了多久"；
- LCD 任务是**低优先级**任务，刷新过程中会被 INS(1kHz)、motor、robot、daemon 抢占；
- 被抢占的时间**也算进墙钟**，但**不算 CPU 占用**。

所以：

> **想知道"省了多少 CPU"，看 `[cpu]` 的占用率；想知道"用户按键后多久屏幕上才变"，看墙钟。**
>
> 优化前 15.3% 意味着 LCD 每秒要吃掉 153ms 的 CPU —— 这才是真正要压下去的数字。

---

## 3. "画得快"与"画得少"：两条路的收益上限完全不同

优化无非两个方向：

| 思路 | 做法 | 理论上限 |
|---|---|---|
| **画得快** | 提高 SPI 频率 | 最多减半（15→30MHz） |
| **画得少** | 内容没变就不画 | 上限取决于"实际变化的内容占比"，本工程是 **88.6% 不用画** |

本工程两条都做了，但**收益主要来自第二条**：

| | 改造前 | 只提频率（理论） | 只少画（理论） | **两条都做（实测）** |
|---|---|---|---|---|
| 每帧要传的字节 | ~72.6KB | ~72.6KB | ~8KB | ~8KB |
| 传输耗时 @15MHz | 39ms | 19.5ms(@30M) | 4.3ms | 2.2ms(@30M) |
| lcdtask 占用 | 15.3% | ~7.7% | ~1.7% | **1.0%** |

> **一般规律**：当"要画的内容大部分其实没变"时，**减少绘制量永远比提升总线速度更值**，
> 因为减少的是"乘数"（次数），而提频只是把"被乘数"砍一半。
> 而且提频有物理上限（信号完整性、排线质量），少画没有。

## 4. "内容没变就别画"的坑在哪

实现只有一句话：**记住上次画了什么，一样就跳过**。但有几个必须想清楚的点：

### ① 要比较"最终画出去的文本"，不是原始输入

```c
draw_value_ascii(row, buf);   /* buf 里可能是被截断过的内容 */
```

如果拿原始字符串比较，可能出现"入参每次都不同、但显示出来一模一样"的情况，
那就白白重绘了。本工程的做法是：**先把超长文本按可用宽度截断/降字号，
拿截断后的结果去比较**。

### ② 不同类型的内容，比较方式不同

| 内容类型 | 怎么比 |
|---|---|
| ASCII 文本 | 字符串比较（`strcmp`） |
| 中文标签（如"在线"/"离线"） | **比指针**——它们本来就是同一个常量数组，内容相同就是同一个指针 |
| 浮点数值 | 比"数值 + 小数位数"（本工程不用 `%f`，没法先格式化成字符串） |

### ③ 最关键：缓存必须在"整页被重画"时失效

这是最容易出 bug 的地方。想一想这个时序：

```
① 翻页 → DrawStatic() 把整页清空重画(值区是空的)
② UpdateValues() 被调用 → 发现"这一行内容没变" → 跳过 ✗
③ 结果: 这一页的值区永远是空的
```

**根因**：屏幕被清空了，但缓存里还记着"上次画过什么"，两边状态不一致了。

本工程的解法是：**只要发生整页重画，就清空整张缓存**：

```c
void LCD_UI_DrawStatic(uint8_t page)
{
    LCD_UI_InvalidateValueCache();   /* 必须先失效! */
    ...
}
```

选 `LCD_UI_DrawStatic()` 作为唯一的失效点，是因为所有"整页重画"的路径
（初始化、热插拔恢复、翻页、冻结切换、标定提示消失）**都经过它**，
一处生效、不会漏。

> **通用经验**：给任何缓存/增量更新机制设计时，先问清楚"**谁会让它失效**"，
> 并且尽量让失效点收敛到一处。

## 5. 更"高级"的做法：帧缓冲、局部刷新、脏矩形

LCD 刷新还有几种常见思路，本工程**没有**采用，但值得知道：

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **全屏帧缓冲** | 在 RAM 里维护一整屏的像素，改完再整屏推 | 逻辑最简单、绝不会有残影 | 280×240×2 = **134KB**，本工程 RAM 根本放不下 |
| **局部刷新**（本工程用的） | 只更新发生变化的矩形区域 | 省 RAM、省带宽 | 要自己维护"哪里变了"，漏了就是残影 |
| **脏矩形 / 区域合并** | 记录所有变化区域，合并成几个大矩形一次推 | 比逐行推更省（减少窗口设置次数） | 实现复杂，收益在小区域场景下有限 |
| **提高分频** | 直接让 SPI 更快 | 一行代码 | 有信号完整性上限 |

本工程选"局部刷新 + 行级缓存"，是**RAM 与复杂度的折中**：
每个值区行只有 48 字节文本缓存（4 页 × 9 行 ≈ 1.7KB），而不是 134KB 的帧缓冲。

**为什么不做"只清变化部分的宽度"**：理论上还能再省一点（旧文本 40px、新文本 20px，
只清 40px 就够），但重绘次数已经降了一个数量级，
这点开销不显著，反而引入"残留宽度算错就出残影"的新风险 —— **不值得**。

### 5.1 一个真实案例：按键时"黑屏然后重刷"

优化上线后用户反馈：**按键时偶发黑屏再重刷**。查下来是个很典型的"重画范围画大了"：

```c
void LCD_UI_DrawStatic(uint8_t page)
{
    LCD_BufFill(0, 0, LCD_W - 1u, LCD_H - 1u, BLACK);   /* ← 整屏刷黑 */
    ...画标题、画标签...
}
```

而**翻页、冻结/恢复、长按重初始化**三条按键路径都经过它，于是每次按键都是
"整屏黑 → 重画标题和标签 → 再逐行画值"。这一瞬间只有几毫秒，人眼有时看得见、
有时看不见，所以表现为"偶发"（实际上每次都会发生）。

**改法就是"按影响面决定重画范围"**：

| 按键 | 实际影响的内容 | 应该重画的范围 |
|---|---|---|
| 上/下（翻页） | 标题 + 9 行标签 + 9 行值 | 标题栏（覆盖）+ 标签列（清）+ 值区（逐行清画） |
| 中键短按（冻结/恢复） | 只有标题栏右上角那个"冻结"标记 | **只重画标题栏** |
| 中键长按（重初始化） | 屏幕内容未知（模组刚重新初始化） | **整屏清**（这一处必须保留） |

三个关键点：

1. **能"覆盖"就不用"清"**：标题栏底色本来就会被重画，不必先整屏清一次；
2. **清的范围要盖住"旧内容可能占的最大范围"**：标签列清到 `COL_VALUE_X` 为止，
   是为了盖住"上一页标签比这一页长"的情况，否则会留残影；
3. **有些场合必须整屏清**：模组刚上电/重新初始化时屏幕内容完全未知，
   这时"少画"反而会留下不认识的东西 —— 所以要区分"内容已知的翻页"和"内容未知的初始化"。

改完之后：翻页是逐块替换（看不到黑屏），冻结/恢复完全不闪，
而长按重初始化仍然整屏重画（那本来就该闪一下）。

> **一句话**：**重画范围要按"这次操作实际改变了什么"来定**。
> 画少了会留残影，画多了会闪 —— 两边都是 bug，只是表现不同。

## 7. 速查表

| 问题 | 答案 |
|---|---|
| 刷一屏要多久 | 总字节数 ÷ (SPI时钟/8)。15MHz 下画满一页约 39ms |
| 墙钟 58ms 和 CPU 15.3% 为什么不一样 | 墙钟含被高优先级任务抢占的时间；CPU 占用才是实际消耗 |
| 提频和少画哪个值 | 少画。提频最多减半，少画的上限取决于"实际变化比例"（本工程 88.6%） |
| 比较什么来判断"变了" | 比较**最终画出去的**内容，不是原始入参 |
| 缓存什么时候必须失效 | **整页被重画/清空时**（翻页、恢复、冻结切换…） |
| 缓存失效点怎么选 | 收敛到一处（本工程是 `LCD_UI_DrawStatic`），所有整页重画都经过它 |
| 为什么不用全屏帧缓冲 | 280×240×2 = 134KB，RAM 放不下 |
| 为什么不做脏矩形合并 | 实现复杂，在"行级缓存"已经把重绘降到 1 行/帧后收益有限 |

## 8. 有界 LCD 绘图与刷新结果（MC02-0097）

当前 LCD 只保留界面实际使用的初始化、清屏、矩形、ASCII、中文字形和数值接口；旧逐点、线段、圆、图片及另一套汉字入口已从活动 API 移除。主要入口集中在 [lcd.h](../../modules/lcd/lcd.h)、[lcd_buf.h](../../modules/lcd/lcd_buf.h) 和 [lcd_ui.h](../../modules/lcd/lcd_ui.h)，实现分别位于 `lcd.c`、`lcd_buf.c` 和 `lcd_ui.c`。

面板默认横屏，绘图区为 **252×212** 像素，坐标从左上角开始。矩形的末端像素也会绘制；越界或起点大于终点时，整块请求拒绝，不自动裁剪。绘图共用一条最多280像素的静态行缓冲：先生成一行 RGB565 像素，再同步发送并复用缓冲，因此只允许 LCD 显示任务串行调用。

ASCII 接口接收明确的字节长度，长度不含字符串结束符；合法范围是 `0x20～0x7E`，字号为12或16像素。中文字形接口接收字形枚举和数量，不找结束标记，也不解码 UTF-8；每个编号须小于 `LCD_CN_COUNT`。输入数组须在调用期间可读。入口先检查整段文字和完整区域，发现坏字符时不会先画出合法前缀。空文本成功且不发送。

整数显示覆盖完整 `int32_t` 范围。浮点显示只接受有限值和0～3位小数，按最近值舍入、恰好半数远离零；缩放后的值须能用 `int32_t` 表示。独立格式化函数先写局部候选文本，容量或数值不合要求时不改调用者输出。界面行文字会按剩余像素缩短并附加 `~`；不能安全显示的动态数值改成 `--`，单位仍保留。

`LCD_Init()`会复位面板并发送现有初始化寄存器，420ms面板等待计入1000ms顶层预算，但不会单独点亮背光。完整界面初始化或恢复要完成清屏、静态内容和值区绘制后才确认缓存并打开背光。单次 HAL 发送最多等待2ms；清屏／静态页使用250ms，周期数值刷新使用20ms，嵌套绘图共用最外层期限。阻塞期间使用 HAL tick lease；这些期限受任务调度影响，是协作检查值，不是严格截止时间或 WCET。

SPI 错误或期限到达会抬高片选、关背光、使界面和行缓存失效，并记录失败状态。后续刷新不再发送；显示任务继续采按键和只读诊断。长按中键或稳定检测到重新接入后才请求一次恢复，若不能确认 SPI 已停止则保持隔离。SPI 传输返回成功只说明 MCU 完成本次发送，不能证明面板已收到或显示。

验证把生产 `lcd.c`、`lcd_buf.c`、`lcd_ui.c` 和裁判行实现链接到 WSL 主机测试，只替换 HAL、时钟和硬件数据。固定像素、RGB565 字节、全部95个可打印 ASCII、中文字形、数值边界、缓存确认、发送失败、关背光及恢复都由主机测试覆盖；Debug／Release 全量测试和 LCD 的 ASan／UBSan／浮点转换检查通过。具名 LCD 诊断只允许 `bench_safe/single` 禁热配置，四张测试画面各展示15秒，随后返回普通页面。实物画面、按键操作和恢复仍须按本票据完成裸板验收。

本轮不调整页面／冻结状态所有权、故障页面或 ADC 在位判断算法；这些仍由 LCD-14、MC02-0098 和 LCD-15 跟踪。

### 8.1 行绘制、按键和页面怎样配合（MC02-0123）

`lcd_buf.h` 的绘制入口共用一行数组：先把这一行所有字符的像素排好，再同步发送，随后复用数组画下一行。ASCII 字库按行读取、低位对应左侧像素；界面中文表按列读取，每列两个字节、低位对应上方像素，两个读取公式不能混用。中文标签使用枚举数组和显式数量，不再依赖数组结束标记。

### 8.2 OLED 的页缓冲和坐标（MC02-0123）

[oled.h](../../modules/oled/oled.h) 把128×64屏幕的缓冲区按128列、8页保存，每页对应8行像素。`OLED_draw_point()` 使用像素坐标 x=0～127、y=0～63；`OLED_set_pos()` 的第二个参数却是页号0～7。字符接口使用行0～4、列0～20，每个字符占6×12像素，读代码时不要把这三套坐标混在一起。

绘图入口只改 RAM 缓冲区，调用 `OLED_refresh_gram()` 后才按8页、每页128列发送整屏。水平线、竖线和斜线分别沿对应方向循环写入像素。`oled_write_byte()` 没有返回 I2C 状态，因此绘图调用方也无法从返回值知道面板是否接受了数据。

### 8.3 OLED 边界检查（MISC-06）

现在 OLED 绘图入口在访问字模或显存前检查坐标和字符。像素使用有符号8位坐标，负数会被拒绝；线段两个端点均须在屏幕内，算法逐点包含端点，并把端点排序后计算，所以反向输入画出的像素一致。传入屏外端点时整条线不画，也不尝试裁剪。

`OLED_show_string()`只读屏幕剩余格数范围内的文字：抵达第4行末后停止，也不会因计数回绕而从头继续。函数先检查本次可见文字，再开始绘制；非法字符不会留下半段新文字。传入的字符串必须保证在结束标记前可读；若恰好填满剩余屏幕格，也允许调用者只提供这些可读字符，不要求函数继续寻找结束标记。

`OLED_printf()`将最多21个可见字符和一个结束标记放入栈上的22字节数组。`vsnprintf`会报告原本需要的长度，但接口仍为`void`，按既有约定只显示当前行可容纳的前缀；空格式、格式化失败或可见前缀含非法字符时保留显存原值。这个长度限制只覆盖本行，不会清理未被覆盖的旧字格。

验证使用生产绘图入口，测试替身只记录I2C整屏发送数据；固定像素和字形结果、屏幕边缘、非法输入、长字符串及格式化失败均在WSL主机侧检查。它证明软件显存内容与访问范围，不证明OLED实物收到或显示了这些字节。

### 8.4 诊断失败后仍要允许按键恢复（MC02-0097）

四页诊断进入 `FAILED` 后，测试序列已经终止，但 LCD 任务仍须处理普通按键和页面刷新。旧判断把 `FAILED` 也当作“诊断正在占用界面”，导致按键松开事件被忽略；即使在位恢复重新画出普通页，界面也会像卡住一样。现在只有 `RUNNING` 状态占用界面；`FAILED` 保留为诊断结果，但不再挡住中键恢复和普通页面操作。主机回归直接检查诊断状态的界面占用结果，并在旧判断下稳定失败三次。

累计 `spi_errors` 表示此前至少发生过一次发送或期限错误，不会因恢复而清零。恢复后是否继续有 SPI 活动要看后续计数是否增加，并结合用户目视确认；MCU 报告发送完成本身仍不能证明面板显示正确。

### 8.5 绘图接口怎样避免依赖芯片头（MC02-0086）

`lcd.h` 只公开面板尺寸、颜色、状态和初始化入口；STM32 片选、复位、数据选择和背光引脚定义由面板硬件实现持有。绘图缓冲使用框架短时探针，MC-02 后端继续按原来的 DWT 周期差换算微秒；界面的通信数据年龄也沿用原有毫秒时钟。这样绘图和数据类型可以独立编译，当前 SPI 初始化、发送期限和错误处理仍由原有面板实现负责。

主机回归检查边界、字体、超时、SPI 失败和界面恢复，ARM 禁热固件构建检查绘图对象的头依赖与实际链接。这些检查不证明显示屏实际收到数据或测得刷新时间。

### 8.6 LCD 任务怎样隔离 FreeRTOS 统计与时间接口（MC02-0086）

LCD 任务现通过 `PlatformTimeNowMs()` 读取毫秒时钟，通过 `PlatformTaskDelayMs()` 保持原来的50ms按键采样、200ms数值刷新和100ms初始化失败等待；耗时仍使用 `PlatformProbeStart()`／`PlatformProbeElapsedUs()`，所以时钟来源、回绕和采样周期保持原样。LCD 文件不再包含 `main.h`、`task.h`、`cmsis_os.h` 或 `bsp_dwt.h`。

任务统计结构由 `platform_task_stats.h` 定义，含11字节任务名、累计运行计数、优先级和历史最小剩余栈字数。FreeRTOS 后端只捕获最多12条原生记录，并在需要时逐条转成框架结构；LCD 不再为适配额外保存第二份完整任务数组。捕获期间如任务数量改变，总任务数取捕获前、捕获后和实际记录数中的最大值；空任务名输出为空字符串，过长名字只复制前11字节。

运行统计由调试工具通过奇偶 `generation` 识别是否正在写入。任务以 C11 顺序一致内存栅栏包住发布边界；当前 Cortex-M7 编译器把它生成为 `dmb ish`，与原有 `__DMB()` 的板级行为相符。FreeRTOS 统计暂不可用时恢复旧版本号，不发布旧数组作为新样本；单条记录读取意外失败时保持奇数版本号，表示当前数组没有完成发布。

标定状态、请求和确认声明已拆入不含 SPI、GPIO、HAL 类型的 `bmi088_calibration.h`，BMI088 硬件配置仍留在原驱动头。Debug 主机全量536/536通过，任务统计适配器专项通过 ASan；禁热 H723 裁判诊断固件实际链接并通过编译数据库、头依赖及源码清单检查。该同配置 ELF 为 FLASH 249836 B、RAM 122720 B，较上一条记录增加72 B和32 B；反汇编确认 `dmb ish`。这没有测试 LCD 实物显示、SPI传输、按键电气读数，也没有测量真实任务统计耗时。
