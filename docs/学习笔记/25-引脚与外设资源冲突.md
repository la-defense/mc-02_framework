# 引脚与外设资源冲突

本篇用 MC02 的 PA5 说明：一个 MCU 引脚在同一时刻只能接收一种配置。它可以作为 ADC 输入，也可以连接外设复用功能；后一次配置会替换前一次配置。

## PA5 为什么会失去按键采样

[`Core/Src/adc.c`](../../Core/Src/adc.c) 把 ADC1 通道19接到 PA5，`BSP_ADCInit()` 启动按键和电源的循环采样。原来的 [WS2812 初始化](../../bsp/ws2812/ws2812.c) 把 PA5 配为 SPI6 的 SCK，同时把 PA7 配为 MOSI。若这两个初始化都运行，PA5 就不再是 ADC 模拟输入，按键采样会失效。

当前 `BSPInit()` 会启动 ADC 采样，LED 初始化接口暂时没有生产调用点。这个调用现状不能保证以后接入 LED 时不会发生冲突，所以仍要修正初始化请求。

## 只把灯的数据线接到 PA7

WS2812 只读取单根数据线上的编码序列。SPI6 在芯片内部仍使用移位时钟产生 MOSI 数据，但程序不必把 SCK 输出到 GPIO。`WS2812_SPI6_Init()` 现在只将 PA7 配为 SPI6 MOSI；PA5 保持 ADC1 的模拟输入配置。

这次改动没有重映射 ADC 通道，也没有改变 SPI 字节编码、颜色顺序和复位低电平发送规则。真实灯珠的高低电平时间仍需用板上测量确认。

## 怎样验证引脚请求

主机测试直接链接生产 `ws2812.c`，用 HAL 替身记录 `HAL_GPIO_Init()` 收到的引脚掩码。测试要求初始化只请求 PA7，且重复初始化不会再次配置 SPI。它先在旧实现上失败，再在修复后通过。

WSL Debug 和 Release 主机回归各 419 项通过；bench_safe、rcdiag、robot single/chassis/gimbal 的 Debug 与 RelWithDebInfo 共10种 ARM 固件均构建成功。测试代码见[主机回归](../../tests/host/ws2812_pin_ownership_test.c)，完整证据见[BSPMISC-06任务记录](../workflow/tickets/BSPMISC-06.md)。源码层面的测试能检查驱动请求的引脚，不能证明板上 MOSI 波形、LED 亮度或 ADC 电气采样质量。

## 仍需单独验证的内容

本轮没有电流受控的主输入，因此没有给板上电，也没有测量 LED 波形。SPI 位宽、频率和 WS2812 的 T0H/T1H 时序仍由 MC02-0025 跟踪；构建中还观察到 `modules/alarm/led.c` 对 `malloc()` 和 `abs()` 缺少显式标准库声明，留在 MC02-0051 的可选驱动审查中。

## 车型编号与板级 CAN 绑定（MC02-0086）

[platform_resources.h](../../bsp/board/platform_resources.h) 给车型提供不含芯片句柄的 CAN 编号，[board_can_stm32.c](../../bsp/board/board_can_stm32.c) 决定 MC-02 上编号与 FDCAN1／2／3 的对应关系。双板桥接启动时先查询绑定；编号没有绑定就拒绝启动，避免静默使用另一条总线。底盘板仍选总线 2，云台板仍选总线 1，板间帧 ID 不改变。

板级表只能说明软件声明了哪个控制器，不能说明外设初始化成功、线上设备存在或总线能够通信。两种桥接角色已在主机测试验证映射、非法编号和既有通信逻辑；当前禁热固件不编译桥接，双板实物通信仍未验证。

车型的 DJI、LK、HT、DM 电机配置也只保存逻辑总线和 ID；驱动注册前通过板级绑定取得现有 CAN 注册参数。转换失败不改旧输出，并在申请电机资源前拒绝未绑定总线。核心底盘配置也会拒绝无效编号；对应的 PID、电机组帧和故障回归在主机通过。驱动的实际收发接口及超级电容等其他 CAN 使用方仍待迁移，完整资源能力检查见 [MC02-0086 记录](../workflow/tickets/MC02-0086.md)。

遥控配置同样使用逻辑 UART 编号：哨兵选择编号 5，[board_uart_stm32.c](../../bsp/board/board_uart_stm32.c) 将它绑定到 UART5。板级表也列出当前工程初始化的其余串口，但句柄存在不代表连接的设备在线。未绑定编号会在遥控来源注册和 DMA 启动前被拒绝，模块启动计划根据该功能的核心或辅助属性处理失败。主机回归检查所有编号映射、非法编号、遥控失联和并发读取；实际串口收发平台接口仍需继续迁移。

裁判接收也从车型读取逻辑串口，哨兵选择编号 1；[裁判初始化](../../modules/referee/rm_referee.c) 先向板级表查询句柄，再注册守护实例和 DMA。编号未绑定时返回参数错误，随后仍可使用有效配置初始化。公开头不再包含芯片串口类型，[主机测试](../../tests/host/referee_snapshot_test.c) 使用自行绑定的测试句柄验证拒绝路径及后续接收；实际板级编号映射沿用遥控测试对生产板级表的检查。禁热裁判诊断固件可完成 ARM 构建，未进行板上通信验证。

[上位机通信](../../modules/master_machine/master_process.c) 的 UART 模式也从车型读取逻辑编号，哨兵配置保留串口 9。启用 UART 时，编号未绑定会在注册话题和来源监控前返回失败；USB 模式不读取该绑定，因此可以使用无效 UART 编号启动。主机测试分别覆盖 UART 的非法编号与恢复、USB 不依赖 UART，以及原有协议收发；这不能代替设备实际通信验证。

## CAN 队列如何从逻辑总线找到硬件（MC02-0086）

[platform_can.h](../../bsp/can/platform_can.h) 让调用者用逻辑总线提交可中断帧组、查询或取消请求，并为指定总线提供一次发送推进机会。[H723 适配器](../../bsp/board/platform_can_stm32.c) 先通过板级表找到控制器，再调用原来的队列；编号未绑定时返回失败，保留调用者原有请求编号。帧数据、优先级和结果类型放在不依赖芯片头的 [can_tx.h](../../bsp/can/can_tx.h)，旧字段名和数值保持兼容。

生产 CAN 队列的主机测试检查未绑定总线、原始截止时间和取消结果。双板桥接的额外发送推进已改用逻辑总线；接收注册及其他发送调用仍在原接口上，不能据此认为整个 CAN 链路已经完成解耦。

板间对时模块现在也通过逻辑总线提交帧、查询完成情况和取消超期请求。它保存发送 ID 与一个不解引用的端点标识；接入当前接收链路时，链路还会核对标识、ID 和板级总线，避免对时帧发往错误控制器。主机测试覆盖不同总线、错误 ID 和缺少端点时的拒绝；对时模块可在没有芯片或 RTOS 头路径的情况下编译。现有接收链路本身仍需平台适配。

话题分片层使用相同的逻辑发送接口；接收时由链路提供只读帧和最初的入队时间，分片层不再读取 CAN 硬件对象。链路通过平台注册逻辑总线；未绑定时在注册回调前拒绝。队列满或期限失效时不推进消息序号，未完成的旧请求仍按原规则取消或等待。主机回归覆盖错误总线、超长帧、分片和过期恢复。

逻辑 CAN 接口还提供接收端点：调用者在启动阶段提供长期保存的端点和回调，平台在接收任务中交付只读帧副本与原始入队时间。启动回退不能与接收任务并发；底层注销会先撤销查找表和排队帧中的旧实例引用，再释放实例，其他端点的排队帧不受影响。主机测试检查了同一 ID 重注册不会收到旧帧。

双板话题链路现在通过该接口注册接收，端点初始化后固定在链路对象中，不能移动或复制。链路、分片和消息桥接只使用框架头；平台负责将实际 CAN 帧复制后派发。启动失败回退、旧命令失效和原始接收时间都有主机回归；实物双板通信仍待验证。

构建时，板间话题、对时和时间映射只有被原车型源码清单选中才进入独立框架目标；没有选择的功能不会因拆分目标而加入固件。独立目标不继承芯片和 RTOS 头路径，构建检查还核对实际头文件依赖及最终链接对象。主机独立目标和 ARM 编译器语法检查覆盖了这组文件；当前机器人配置尚未满足构建条件，因此不能将其当作完整双板固件验证。

裁判图形编码中的发送完成状态也通过任务临界区接口保护：回调写入与查询复制仍分别在同一保护范围内，具体任务锁由平台实现。裁判 UI 被车型选中时进入相同的独立框架目标；主机测试覆盖绘图、发送预算与串口完成事件，ARM 独立语法检查未引入芯片或 RTOS 头。当前禁热裁判诊断配置没有选择图形 UI，不能代表含 UI 的机器人固件已链接验证。

裁判接收模块的状态发布、读取与发送额度保护改用同一任务临界区接口，毫秒计数改由平台提供。接收、离线和发送回调由任务派发，原来的嵌套保护及 32 位回绕计算保持不变。并发读取测试使用互斥锁模型；Debug、Release 和地址／未定义行为消毒器均通过相应检查。串口注册仍使用板级句柄，后续需要继续隔离，不能据此认为接收模块已脱离硬件。

现在裁判解析器通过 [platform_uart.h](../../bsp/usart/platform_uart.h) 传入逻辑 UART 编号，不再取得 STM32 句柄。平台后端解析板级绑定，沿用原来的 DMA 注册、只读接收块、发送队列和回调：注册失败时原有隔离规则仍由底层执行，不能假设 DMA 借用的缓冲已经释放。裁判解析器在不提供芯片及 RTOS 头路径的目标中编译，并已进入禁热裁判诊断固件的框架目标；其他 UART 用户仍待迁移。

遥控解析器也使用逻辑 UART 接口注册和重启接收；掉线时仍先撤销输入并请求急停，再请求重启。接收与发送适配分别编译，让只接收的模块不必链接发送入口。遥控代码进入不带芯片和 RTOS 头路径的框架目标，遥控诊断固件的编译、链接与头依赖检查通过；上位机通信等其他用户还需继续迁移。

上位机通信的 UART 模式也经逻辑串口注册、重启接收和提交发送；USB 模式不查询 UART 绑定。两种模式的任务临界区和毫秒计数通过框架接口取得，保留 SP／V2 原协议、来源时间和掉线处理。主机测试分别覆盖 UART 流和发送、USB 下 V2 消息及校验失败；上位机模块仍包含整车公共定义等依赖，不能把这一步当作整个业务层已独立编译。

传输方式选择已从整车定义中抽到 [vision_transport_select.h](../../modules/master_machine/vision_transport_select.h)：未显式选择仍默认 USB，同时选择 USB 和 UART 会报错。上位机处理文件不再包含整车定义，SP／V2 与 USB／UART 四种组合均通过无芯片和 RTOS 头路径的主机编译；实际 USB 和 UART 禁热固件也分别验证了链接及依赖。V2 使用的整车话题只放行编号声明头，并不开放整个业务目录。

姿态任务不再直接填写 SPI 句柄和片选，而是通过 [ins_sensor_port.h](../../modules/imu/ins_sensor_port.h) 获取完整样本；[MC-02 板级适配](../../bsp/board/ins_sensor_mc02.c) 保留 BMI088 的 SPI2、片选、周期采样和启动标定设置。主机测试用不同的片选替身检查两路绑定，并覆盖注册失败、无效样本及 EKF／Fusion 结果。

车型现在显式指定逻辑 IMU 编号。模块启动检查会确认当前板卡存在对应绑定，实际传感器注册仍在 INS 任务中执行；没有选择或选择未绑定编号不会访问 SPI，也不能产生有效姿态。目前 MC-02 只绑定板载 BMI088，其他 IMU 仍需实现并验证对应的板级适配。

板载 IMU 的资源绑定进一步拆为逻辑 SPI2、陀螺片选和加速度计片选：[SPI 映射](../../bsp/board/board_spi_stm32.c) 与 [GPIO 映射](../../bsp/board/board_gpio_stm32.c) 负责返回 MCU 句柄和引脚，姿态业务不接触这些类型。启动检查只确认这三项有绑定；任何一项缺失都拒绝注册 IMU。主机故障注入分别覆盖三项缺失，绑定存在并不证明 SPI 电气连接或传感器可用，也不替代整板引脚冲突检查。

短时探针也通过 [platform_probe.h](../../bsp/dwt/platform_probe.h) 使用原有 DWT 后端；统计对象字段和原有周期回绕计算保持一致。调用适配函数会带来额外开销，目前没有实板耗时数据，不能据此判断实时裕量。姿态任务已在无芯片和 RTOS 头路径的目标中编译；其实际构建只放行样本数据和探针公共头，不放行 DWT 寄存器头。
