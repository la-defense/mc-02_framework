## 1. 什么是"异常"

在 Cortex-M 里，**异常（Exception）** 是个统称，包含两类东西：

1. **中断**：外设来事件（CAN 收到帧、串口收到字节、定时器到点）；
2. **故障（Fault）**：CPU 自己发现"这条指令没法执行"（访问了不存在的地址、
   执行了非法指令、栈指针坏了……）。

两者的处理方式一样：**CPU 停下当前的事，按向量表跳到一段固定的代码去处理**。

本工程用到的那几个"故障"入口：

| 异常 | 什么时候进 |
|---|---|
| `HardFault` | 兜底：其它故障没被单独使能时，全部升级到这里 |
| `MemManage` | 内存保护单元（MPU）拦截，或取指/访存违规 |
| `BusFault` | 访问了总线上不存在的地址（比如没接外设的 FMC 区） |
| `UsageFault` | 指令用法错误（未定义指令、非对齐访问且禁止、除零等） |
| `NMI` | 不可屏蔽中断（外部硬件引脚或看门狗等） |

**关键点**：默认情况下 `MemManage/BusFault/UsageFault` 是**没被单独使能**的，
它们会"升级"成 `HardFault`。所以你经常看到一堆不同原因最后都进同一个 `HardFault`。

## 2. 硬件自动帮你压栈的 8 个字

异常发生时，**硬件会自动把现场保存到栈上**（不需要你写一行代码），顺序固定：

```
[SP+0x00] R0        [SP+0x10] R12
[SP+0x04] R1        [SP+0x14] LR      ← 出错时的返回地址
[SP+0x08] R2        [SP+0x18] PC      ← 出错的那条指令的地址  ★
[SP+0x0C] R3        [SP+0x1C] xPSR
```

**`PC` 就是"崩在哪"的答案**：把它喂给 `addr2line`，就能定位到源文件和行号：

```bash
arm-none-eabi-addr2line -f -e build/Basic_Framework_MC02.elf 0x08014DA0
```

在本工程的实际验证里，这一招直接定位到了出错的函数：

```
[crash] type=HARDFAULT pc=0x08014DA0 lr=0x08014D91 sp=0x24003CB0
[crash] 任务 'selftest' 栈溢出
```

### 用哪个栈？看 `EXC_RETURN`

Cortex-M 有两个栈指针：**MSP**（主栈，中断/启动用）和 **PSP**（进程栈，RTOS 任务用）。
异常帧压在**出错那一刻正在用的那个栈**上。

那怎么知道是哪个？看进入异常时硬件塞进 `LR` 的那个特殊值（叫 `EXC_RETURN`）：

- `bit2 = 0` → 用的是 **MSP**
- `bit2 = 1` → 用的是 **PSP**

所以取帧的标准写法（本工程就是这么写的）：

```asm
    tst lr, #4          ; 测 EXC_RETURN 的 bit2
    ite eq
    mrseq r0, msp       ; bit2=0 → 帧在 MSP 上
    mrsne r0, psp       ; bit2=1 → 帧在 PSP 上
    mov r2, lr          ; 保存 EXC_RETURN，用 bit4 判断基本帧/浮点扩展帧
    movs r1, #<类型>
    mov r4, r0          ; 跨低层关断函数保存 3 个参数
    mov r5, r1
    mov r6, r2
    bl BSP_SafetyLatchOutputsOff
    mov r0, r4
    mov r1, r5
    mov r2, r6
    b CrashLogHandlerC  ; 关断后才进入 C 记录现场
```

## 3. 为什么 handler 必须是 `naked`

这是本工程实现时最容易踩的一个坑。

普通 C 函数在**进入时会先执行"序言"**：`push {r7, lr}` 之类的指令，
**把 `SP` 往下挪**。

如果 handler 是普通函数，那么序言跑完之后 `mrs r0, msp` 拿到的
**已经不是异常帧的起始地址**了（中间隔了函数自己压的那几个寄存器），
读出来的"R0/R1/PC"全部错位。

解决办法就是 `__attribute__((naked))`：

```c
__attribute__((naked)) void HardFault_Handler(void)
{
    CRASH_HANDLER_BODY(CRASH_TYPE_HARDFAULT);   /* 里面只有 __asm，没有 C 代码 */
}
```

`naked` 告诉编译器"不要生成序言和收尾"，函数体里只能放汇编。
这样 `mrs` 拿到的就是硬件压的那个帧。

> 代价：这段代码不能被 CubeMX 重新生成覆盖掉，生成后需要手工恢复。

### 有浮点时，核心帧会后移

如果出错时代码用过 FPU，硬件会在栈的较低地址处额外保留 18 个字
（S0~S15、FPSCR 和保留字），总帧长是 26 个字（104 字节）。因此 R0 并不在
`SP+0`，而是在 `SP+0x48`。`EXC_RETURN` 的 bit4 为 0 表示浮点扩展帧；bit4 为 1
表示基本帧。Arm 的 Cortex-M7 指南还规定异常帧起始地址 8 字节对齐。

本工程在读取前检查 `EXC_RETURN`、栈地址是否位于允许的 RAM 内，以及整个寄存器区域是否
超出该段 RAM 的末尾。同时检查 CFSR 中保存、恢复寄存器或保存浮点数据时的错误。
任何一项失败，就跳过寄存器和栈上数据的读取。对应生产逻辑在
[`bsp_crash_frame.c`](../../bsp/crash/bsp_crash_frame.c)，主机边界测试在
[`bsp_crash_frame_test.c`](../../tests/host/bsp_crash_frame_test.c)。

### 读取前检查地址和长度（MC02-0111）

第四批注释整理对应检查清单033、034。先看 [bsp_crash_frame.h](../../bsp/crash/bsp_crash_frame.h) 的参数和输出，再对照实现中的 RAM 地址、返回标记和长度检查。这个模块只计算地址与数量，实际读取由 `bsp_crash.c` 完成。

- `CrashLogFrameResolve()` 要求原始栈地址是 8 的倍数，检查 8 项基本寄存器数据能否完整放在同一段 RAM 内。`EXC_RETURN` 的 bit4 为 0 时，还要把前面的 18 项浮点相关区域计入长度。确认范围后，`core_frame_address` 才指向 R0，供调用方读取后面的 8 项寄存器数据。
- `view` 为 `NULL` 时直接返回 0。非空时先将两个输出字段清零，后续任一检查失败都保持为 0，避免调用方继续使用上次的地址。
- `CrashLogReadableStackWords()` 只计算还能复制多少个 `uint32_t`，每项 4 字节，最多 32 项；它要求地址是 4 的倍数，不检查 `EXC_RETURN` 或 CFSR。`snapshot_words` 从原始栈起点计数，用于保存栈上数据；包含浮点区域时，计数起点仍在 R0 前面。
- 允许范围来自实现中写出的 DTCMRAM、RAM、RAM_D2、RAM_D3 地址，需要与 [STM32H723VGTx_FLASH.ld](../../STM32H723VGTx_FLASH.ld) 一起核对。地址恰好等于某段末尾时，剩余长度为 0；计算数量会返回 0，寄存器区域检查也不能通过。

现有回归覆盖基本寄存器区域、包含浮点区域的地址偏移、靠近 RAM 末尾时的可复制数量、地址不符合要求、不认识的返回标记和六个相关错误位。本批只改注释，比较结果和验证日志保存在本地 `build/mc02-0111/`，验证结果记录在 TODO 中。

## 4. 故障状态寄存器：CFSR / HFSR / BFAR / MMFAR / DFSR

硬件压栈告诉你"在哪崩"，这几个寄存器告诉你"为什么崩"：

| 寄存器 | 地址 | 里面有什么 |
|---|---|---|
| **CFSR** | `0xE000ED28` | 三类具体状态拼在一起：低 8 位 MMFSR、中间 8 位 BFSR、高 16 位 UFSR |
| **HFSR** | `0xE000ED2C` | bit30 = `FORCED`（表示这个 HardFault 是从别的故障升级来的） |
| **BFAR** | `0xE000ED38` | 出错时访问的**地址**（仅当 CFSR 的 `BFARVALID` 置位才有意义） |
| **MMFAR** | `0xE000ED34` | 同上，给 MemManage 用 |
| **DFSR** | `0xE000E048` | 调试状态（`HALTED` 表示"CPU 其实是被调试器停住的"，不是真故障） |

本工程实际抓到的两次典型：

```
# 一次"非对齐访问"
CFSR = 0x01000000   → UFSR 的 bit8 = UNALIGNED
HFSR = 0x40000000   → FORCED

# 一次"访问不存在的地址"(写 FMC 区)
CFSR = 0x00000400   → BFSR 的 bit10 = IMPRECISERR(写操作通常是缓冲的, 所以"不精确")
HFSR = 0x40000000   → FORCED
```

**怎么读 CFSR 的位**：把值按 32 位十六进制看，
第 8~15 位是 BusFault、第 16~31 位是 UsageFault。
比如 `0x00008200` = BFSR 的 bit1(`PRECISERR`) + bit7(`BFARVALID`)。

> 注意：**这些寄存器在复位后会被清零**，所以必须在 handler 里读、写进 RAM。

## 5. `.noinit`：为什么普通变量一复位就没了

普通全局/静态变量分两类：

- 有初值的（`.data` 段）：启动时从 Flash 拷到 RAM；
- 没有初值的（`.bss` 段）：启动时**被清零**。

启动代码（`startup_stm32h723xx.s`）里的 `FillZerobss` 就是干第二件事的，
它按链接脚本给的 `_sbss` 和 `_ebss` 两个符号，把这段 RAM 全部写成 0：

```asm
    ldr r2, =_sbss
    ldr r4, =_ebss
FillZerobss:
    str r3, [r2]        ; r3 = 0
    adds r2, r2, #4
LoopFillZerobss:
    cmp r2, r4
    bcc FillZerobss
```

**所以想让一段 RAM"跨复位保留"，就要让它落在这段范围之外**：

```ld
  .noinit (NOLOAD) :        /* NOLOAD = 不占 Flash 空间, 也不参与启动初始化 */
  {
    *(.noinit)
    *(.noinit*)
  } >RAM
```

```c
__attribute__((section(".noinit"))) static CrashLog_t g_crash_log;
```

这样：

- **系统复位（看门狗 / 软件复位 / NRST）后内容保留** —— 因为 SRAM 不掉电；
- **掉电后丢失** —— 这是本工程有意接受的取舍（为了不在 handler 里写 Flash）。

## 6. 为什么先关输出，再记录现场

记录故障前，先让已知输出停止。

异常可能发生在 HAL、时钟、RTOS 或日志尚未可用时，也可能来自坏栈或总线错误。
所以入口分两步：

1. `BSP_SafetyLatchOutputsOff()` 先关闭普通中断，依次将 PB1、PC13/14/15 设为低电平输出，
   再清零 TIM3 的比较值、关闭通道 4 并停止计数。它不调用 HAL、tick、RTOS 或日志。
2. 再校验异常帧地址和 CFSR 状态，记录可安全读取的现场，然后请求系统复位。

如果记录现场时又发生异常，异常入口会在进入 C 代码前再次关闭已知输出。随后 `CrashLogGuardEnter()` 发现已经开始记录，就立即请求复位，避免覆盖第一次已经写下的数据。通过该检查的 C 异常记录入口直接继续保存现场，不再重复写关断寄存器。

关断后，记录路径不使用 HAL、FreeRTOS 或日志，并限制栈读取范围：

```
关中断并关输出 → 读取 SCB 状态 → 验证栈帧 → 写 .noinit → NVIC_SystemReset()
```

如果整个调度器停摆，守护任务无法执行软件关断；IWDG 会先触发复位。重启后，`main()` 的首个用户初始化步骤调用 `BSP_SafetyStartupLatchOutputsOff()`，在 HAL 和模块初始化前再次关断已知输出，并恢复调用前的 PRIMASK。复位向量到 `main()` 之间的引脚状态仍未实测。

已知 GPIO/TIM/RCC 寄存器写入只是软件关断请求。主机寄存器测试不能证明板上引脚
电压、外接电源通道或负载响应；这些仍需仪表及外部限能条件验收。

### 关闭输出的两个入口和执行顺序（MC02-0114）

第七批注释整理对应检查清单051、052，接口见 [bsp_safety.h](../../bsp/safety/bsp_safety.h)，实现见 [bsp_safety.c](../../bsp/safety/bsp_safety.c)。

`BSP_SafetyLatchOutputsOff()` 返回后保持普通中断关闭，供异常、错误和任务故障入口使用。`BSP_SafetyStartupLatchOutputsOff()` 先保存 `PRIMASK`，执行同一组关闭步骤，再恢复原值。这样启动流程可以继续运行；调用前已经关闭普通中断时，调用后仍保持关闭。两个入口采用不同的中断状态处理方式，引脚和定时器都保持这次设置。

公共步骤先开启 GPIOB、GPIOC 和 TIM3 时钟，并读回时钟寄存器，再访问相应外设。设置 PB1 时，先把它的 GPIO 输出值写为 0，再改为普通输出，引脚用途切换后就使用预先写好的低电平。PC13/14/15 也按同样顺序处理。最后关闭 TIM3_CH4 和 TIM3 计数，停下原来的 PWM 来源。这些函数只设置当前寄存器，后续代码仍可重新配置输出。

现有 [bsp_safety_test.c](../../tests/host/bsp_safety_test.c) 记录关键寄存器的写入顺序，检查先设置低输出值再切换用途、TIM3 停止，以及启动入口恢复两种原中断状态。[fatal_error_entry_test.c](../../tests/host/fatal_error_entry_test.c) 检查 `Error_Handler()` 调用同一套关闭逻辑。本批只改注释，比较结果和验证日志保存在本地 `build/mc02-0114/`，验证结果记录在 TODO 中；未连接硬件。

### Error_Handler 为什么关断后等待（MC02-0115）

第八批注释整理对应检查清单053，实现见 [bsp_safety_error.c](../../bsp/safety/bsp_safety_error.c)。外设初始化等流程报告错误后，`Error_Handler()` 先关闭普通中断，再调用直接操作寄存器的输出关闭入口。这时模块初始化可能尚未完成，处理过程不依赖 HAL、任务调度或日志。

### 再次进入记录时为什么直接复位（MC02-0112）

第五批注释整理对应检查清单035、036，接口见 [bsp_crash_guard.h](../../bsp/crash/bsp_crash_guard.h)，实现见 [bsp_crash_guard.c](../../bsp/crash/bsp_crash_guard.c)。

`bsp_crash.c` 的各入口共用 `g_crash_handler_active`。这个普通全局变量在启动时清零；第一次调用将它设为 1 并返回，调用方随后写入现场数据。记录期间一直保留为 1，后续异常再次进入时便会请求复位，跳过再次写入。标志随下次启动重新清零，保存在 `.noinit` 中的现场数据则按原流程留给下次启动读取。

传入 `NULL` 时无法检查标志，也会直接请求复位。这个函数只检查标志、设置标志和请求复位，输出关断、寄存器读取和现场保存由其他代码完成。`NVIC_SystemReset()` 正常不会返回；后面的空循环是在它意外返回时停住程序，避免继续执行记录流程。

现有 [crash_guard_test.c](../../tests/host/crash_guard_test.c) 检查首次调用后标志为 1 且没有复位，再次调用时请求复位且标志保持不变；测试用主机函数代替实际复位。本批只改注释，比较结果和验证日志保存在本地 `build/mc02-0112/`，验证结果记录在 TODO 中。

### 最后写 magic 后，读取时还要检查什么（MC02-0113）

```c
    // 已写入头部、寄存器和允许读取的栈上数据
    g_crash_log.progress = 4u;
    // 再计算并保存 task_name 到结构体末尾的 CRC
    g_crash_log.magic = CRASH_LOG_MAGIC_OK;
    // 等待固定次数，给最后的内存写入留出时间
    NVIC_SystemReset();
```

第六批注释整理对应检查清单031、032，接口见 [bsp_crash.h](../../bsp/crash/bsp_crash.h)，实现见 [bsp_crash.c](../../bsp/crash/bsp_crash.c)。`magic` 表示写入状态。读取时接受 OK；BUSY 且 `progress` 为 4 也会继续检查。之后还要核对记录长度、版本、编译编号和 CRC，全部通过才作为可用记录。BUSY 记录未通过检查时，启动日志只报告已保存的进度。

`fw_id` 由 `bsp_crash.c` 的编译日期、时间和配置名生成。其他文件单独改动而它没有重新编译时，编号未必改变。CRC 只覆盖 `task_name` 到结构体末尾，前面的次数、类型和附加参数不在 CRC 计算范围内。查询成功后，还要看 `frame_status` 才能知道异常寄存器数据是否读到。

`CrashLogGetLast()` 传入 `NULL` 或记录未通过检查时返回 0，不改写调用方原有内容；成功时复制整份记录并返回 1。`CrashLogClear()` 只将 `magic` 清零，其他字段保留，后续查询会忽略这份记录；下一次写记录时，旧标志不再是 OK/BUSY，次数便从 1 开始。

本批复用地址检查和重复进入的主机回归，它们没有直接运行整份记录的保存和查询流程。另行比较两份文件的非注释代码及当前禁热配置的编译器处理结果；比较时给两份源码使用相同的日期和时间，避免 `__DATE__`、`__TIME__` 随检查时间改变。默认关闭的故障自测不启用。比较结果及验证日志保存在本地 `build/mc02-0113/`，验证结果记录在 TODO 中。

## 7. 断言与栈溢出也是"崩溃"

除了硬件故障，还有两种"自己把自己弄死"的情况：

### `configASSERT`

FreeRTOS 的断言原来长这样：

```c
#define configASSERT( x ) if ((x) == 0) { taskDISABLE_INTERRUPTS(); for( ;; ); }
```

关中断 + 死循环 —— 板子就那么停着，啥也看不出来。现在改成：

```c
#define configASSERT( x ) if ((x) == 0) { CrashLogAssertFail(__FILE__, (uint32_t)__LINE__); }
```

这样记录里会带上**文件名和行号**，实测输出：

```
[crash] assert: D:/.../bsp/crash/bsp_crash.c:258
```

### 任务栈溢出

FreeRTOS 有个开关 `configCHECK_FOR_STACK_OVERFLOW = 2`：
创建任务时把栈填成固定图案（本工程是 `0xA5`），任务切换时检查栈末尾
那 16 字节的图案还在不在。被踩了就是溢出，于是调用：

```c
void vApplicationStackOverflowHook(TaskHandle_t xTask, char *pcTaskName)
{
    CrashLogStackOverflow(pcTaskName);
}
```

任务名来自 FreeRTOS 任务内存中的字符数组，复位后那段内存可能被重新使用。
当前实现直接复制最多 15 个字符并补 `\0`，不可打印字符替换为 `.`；传入 `NULL` 时保存空串。
这样下次启动读取的是记录里的任务名，无需再访问原来的字符数组。

> 栈上保存的数据里若能看到成片的 `A5A5A5A5`，通常是尚未使用的栈空间。
> 从 A5 的位置可以反推这个任务最多用过多深的栈。

## 8. 没有调试器时怎么查（本工程的日常流程）

1. 板子重启后先看日志：有没有 `==== 上次运行崩溃现场 ====`；
2. 记下 `type` 和 `pc`；
3. 用 `addr2line` 把 `pc` 翻成源码行；
4. 看 `CFSR/HFSR/BFAR` 判断是哪类故障；
5. 如果是断言/栈溢出，日志里直接给了文件名行号或任务名；
6. 还定位不了，就用栈快照手工回溯（见 `docs/学习笔记/06`）——
   从 `sp` 往后扫，形如 `0x08xxxxxx`（Flash 地址）的值就是各级返回地址。

## 9. 速查表

| 问题 | 答案 |
|---|---|
| 崩在哪一行？ | 异常帧里的 `PC`，喂给 `addr2line` |
| 为什么崩？ | `CFSR`（具体类型）+ `HFSR`（是否升级）+ `BFAR`（出错地址） |
| 用哪个栈的帧？ | `EXC_RETURN` 的 bit2：0=MSP，1=PSP |
| 为什么 handler 要裸写汇编？ | 普通函数的序言会动 `SP`，读到的帧就错位了 |
| 复位后现场还在吗？ | 放在 `.noinit` 段才在（普通 `.bss` 变量会被启动清零） |
| 掉电后还在吗？ | 不在（要持久化就得写 Flash，但 handler 里写 Flash 很危险） |
| handler 里能打日志吗？ | 不要。只做"读寄存器→写 RAM→复位"，日志留给下次启动 |
| 断言失败也能记录吗？ | 能，把 `configASSERT` 改成调用记录函数即可（带文件+行号） |
| 栈溢出怎么发现？ | `configCHECK_FOR_STACK_OVERFLOW=2` + `vApplicationStackOverflowHook` |
