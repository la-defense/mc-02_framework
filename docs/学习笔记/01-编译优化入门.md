# 01 编译优化入门（写给 MC-02 工程）

## 0. 一句话版本

**同一份代码，换一个编译参数，速度可以差 1.5~3 倍。** 本工程原来整体用 `-Og`（Debug 专用等级）编译，这是目前 CPU 占用的最大"隐形"来源；正确做法是另建一套 `-O2 -g` 的性能构建，**绝对不要用 `-Ofast`**（它会让我们的 NaN 安全检查失效）。

## 1. 为什么会有这篇文档

- 实测背景：`IDLE` 只剩 5.9%，`motortask 48.2%`、`instask 35.7%`、`lcdtask 8.9%`；
- 排查时发现：`CMAKE_BUILD_TYPE=Debug` → 整机 135 个目标全部是 `-Og -g`；
- 浮点/矩阵密集代码（我们的四元数 EKF、PID、坐标变换）在 `-Og` 下开销是 `-O2` 的 1.5~3 倍是常态 —— 这部分开销是"白送"的，先把它拿回来。

## 2. 优化等级到底在优化什么

"优化等级"决定编译器**愿意为性能改写你多少代码**。它不改变 C 语言规定的语义（除 `-Ofast` 和未定义行为），只是换一种等价但更快的翻译方式。

| 等级 | 大致做了什么 | 典型用途 | 代价 |
|---|---|---|---|
| `-O0` | 基本不优化：每条语句对应几段机器码，变量都放栈上 | 需要逐行跟踪时 | 最慢，代码最大 |
| `-Og` | 为调试设计的**轻度**优化，刻意不做跨语句重排、不做内联 | 日常开发调试（**本工程现状**） | 比 `-O2` 慢很多 |
| `-O1` | 删死代码、简单内联、寄存器分配 | 折中 | 一般 |
| `-O2` | 发布级：函数内联、循环优化、公共子表达式消除、指令调度、部分向量化 | **推荐（性能构建用这档）** | 单步/看局部变量变难 |
| `-O3` | 在 `-O2` 上更激进：更多内联、循环展开、向量化 | 数字信号处理 | 代码变大，个别代码反而变慢 |
| `-Os` | 以体积为目标（关掉会显著增大代码的优化） | Flash 紧张时 | 速度略降 |
| `-Ofast` | `-O3` + `-ffast-math` 等一组"**改变浮点语义**"的开关 | 不在乎 IEEE 语义的纯数值计算 | **安全性风险，本工程禁用** |

速度从哪来（以 `-O2` 为例）：

- **内联**：省掉函数调用的入栈/出栈/跳转；
- **寄存器分配**：把循环里的变量放进 CPU 寄存器，不再每次读写栈内存；
- **循环优化**：把循环不变量提到循环外、消除多余下标计算；
- **CSE（公共子表达式消除）**：同一个算式只算一次；
- **指令调度**：把相互不依赖的指令交错排列，填满流水线；
- **（部分）向量化**：一次算多个数（Cortex-M7 有单精度 SIMD）。

> 直觉理解：`a*b + c` 在 `-Og` 下可能是"从栈取 a、取 b、乘法、存回栈、取 c、加法、存回栈"，在 `-O2` 下就是寄存器里的两条指令。

## 3. `-ffast-math` 会破坏什么（本工程最需要注意的一条）

`-Ofast` = `-O3` 加上这一组开关：

`-fno-math-errno`、`-ffinite-math-only`、`-fno-signed-zeros`、`-fno-trapping-math`、`-funsafe-math-optimizations`、`-fno-rounding-math`、`-fno-cx-limited-range` 等。

它们带来的语义变化：

1. **假设不存在 NaN / Inf**（`-ffinite-math-only`）：于是 `isfinite(x)`、`x != x`、`isnan(x)` 这类判断会被当作"永远为真/永远为假"直接优化掉；
2. **允许重排浮点运算**（`-funsafe-math-optimizations`）：`(a+b)+c` 可以被改写成 `a+(b+c)`，结果与按源码顺序计算**不再逐位一致**；
3. **忽略有符号零 / 极小值**：`-0.0` 与 `0.0` 视为相同，denormal（非规格化数）可能被当作 0；
4. 允许把 `x/y` 变成 `x * (1/y)` 之类，误差放大。

本工程里**直接依赖这些语义**的地方（都做过安全加固）：

- `application/cmd/robot_cmd.c`、`modules/algorithm/controller.c`：PID 的 `isfinite` 校验、死区/除零保护；
- `modules/algorithm/QuaternionEKF.c`：`invSqrt(0)` 兜底、加速度范数兜底；
- `modules/imu/ins_task.c`：`imu_valid` 判据（决定是否把姿态发给视觉、是否报 IMU 失效）；
- `modules/imu/imu_heater.c`：温度的有限性与范围检查（起火事故后加的硬保护）；
- `modules/lcd/lcd_ui.c`：姿态/温度的 `isfinite`/范围判断。

**结论：本工程永远不用 `-Ofast`/`-ffast-math`。** 需要提速就用 `-O2` + 代码级优化。

## 4. 那为什么工程模板里 Release 档是 `-Ofast`？

因为 STM32 的 CubeMX/模板工程默认如此（很多裸机 DSP 工程确实这么用），但**带安全判据的控制工程不该这么用**。本工程的处理：

- 把 `Release` / `RelWithDebInfo` 两档的 `-Ofast` 改为 `-O2`（`RelWithDebInfo` 再加 `-g`），避免以后有人一切换就静默丢掉安全检查；
- 日常 Debug 档保持 `-Og -g` 不动。

## 5. Debug 构建为什么慢（`-Og` 的代价）

`-Og` 的设计目标是"单步执行时与源码一一对应"，于是：

- 变量**必须**留在栈上（否则调试器看不到"当前值"）→ 每次读写都是内存访问；
- 不做（或少做）内联 → 每个小函数都是真实调用；
- 不做指令重排 → 流水线经常空等；
- 不做跨语句的化简 → 重复计算照做。

这对"跑得对不对"没影响，对"跑得多快"影响很大。

## 6. 本工程的两套构建（约定）

| 构建目录 | 类型 | 参数 | 用途 |
|---|---|---|---|
| `build/` | Debug | `-Og -g -gdwarf-2` | 日常开发：单步、看局部变量、Live Watch |
| `build-perf/` | RelWithDebInfo（改成 `-O2 -g`） | 性能构建 | 测性能、上车前验证 |

用法示例（PowerShell）：

```powershell
# 配置性能构建（只做一次）
cmake -S . -B build-perf -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo

# 编译
cmake --build build-perf -j 12

# 产物：build-perf/Basic_Framework_MC02_bench_safe.elf（由配置的固件 profile 决定名称）
```

**Live Watch 在 `-O2` 下还能用吗？**

- 全局变量：基本都能看（地址固定、一般是真实的内存读写）；
- 局部变量：可能被优化进寄存器甚至完全消失 → 重要调试量要声明 `volatile`（本工程里 `lcd_*`、`can_*` 这些探针变量都加了）；
- 单步跟踪：会跳行/合并行，属于正常现象。

## 7. 怎么自己验证优化是否生效

1. **看当前优化参数**
   ```powershell
   Select-String -Path build\build.ninja -Pattern '-O[0-9sg]' | Select-Object -First 3
   ```
2. **看体积**
   编译结尾会打印 `FLASH: xx%`，两套构建对比即可。
3. **看关键安全判据有没有被优化掉**（改完优化参数后必做一次）
   ```powershell
   arm-none-eabi-objdump -d build-perf\Basic_Framework_MC02.elf | Select-String -Pattern '<pid_calculate>|<PIDCalculate>' -Context 0,40
   ```
   在反汇编里应仍能看到比较/分支（NaN 判定），而不是被折叠成常量。
4. **看速度**
   读 RTT 的 `[cpu]` 汇总行（每 5s 一条），或 Live Watch 里的 `lcd_stats_*` / `can_*` 探针变量，比较改造前后同工况的数字。
5. **看数值一致性**
   两种构建下姿态 `Yaw/Pitch/Roll`、PID 输出应在浮点末位量级内一致；若出现明显差异，优先怀疑未定义行为（越界、未初始化、`volatile` 缺失）。

## 8. 常见误区

| 误区 | 事实 |
|---|---|
| "优化会改变程序逻辑" | 不会（除非 UB、`-ffast-math`、或依赖 `volatile` 缺失的时序）；`-O2` 只是更快 |
| "Debug 就一定慢、Release 就一定快" | 慢/快只看实际参数。我们这次就是 Debug(`-Og`)，与"Debug 标签"无关 |
| "加 `volatile` 能提高性能" | 恰恰相反：`volatile` 禁止优化，热路径滥用只会更慢。它只用于"必须真的读写内存"的场景（寄存器、跨中断共享变量） |
| "优化能掩盖时序 bug" | 优化只压缩执行时间，竞态/优先级反转依然存在 |
| "先跑通再优化" | 本项目顺序是：先测量定位 → 再低风险优化 → 最后才动结构 |

## 10. 已配置构建如何发现新增源码（MC02-0032）

CMake 配置阶段会展开 `file(GLOB...)`，并把当时找到的源码写进 Ninja 构建文件。之后单独运行 `cmake --build`，默认不会重新读取所有 `CMakeLists.txt`。如果此时新增 `.c` 文件，构建可能显示成功，却仍然没有编译新模块。

`CONFIGURE_DEPENDS` 会让生成器在构建时检查对应 glob 的结果；新增、删除或移动文件后，CMake 会重新配置并更新编译和链接清单。本工程把它加在基础源码 glob、业务源码递归 glob，以及递归收集头文件目录的 glob 上。头文件目录也会改变编译器的 `-I` 搜索路径。

MC02-0032 的隔离回归先配置并完整构建一次，再逐项改变源码树；每次只对原构建目录执行 `cmake --build`，并将 `compile_commands.json` 与新建构建目录的源码清单对比。测试还检查被删除的对象不再出现在 Ninja 链接命令中，以及 `_template.c` 仍被排除。Windows 与 WSL 的结果均为通过，阶段日志保存在各自的 `build/mc02-0032/` 回归目录。

glob 检查会在已有构建上增加少量目录扫描开销，且 CMake 文档提示不同生成器的支持可能不同。本工程的 CI 和本次验收使用 Ninja；若改用其他生成器，应先运行同一组回归再采用。

## 11. 为什么 Release 回归不能依赖 `assert`（R25-13、MC02-0053）

标准 C 的 `assert(expr)` 在定义 `NDEBUG` 时会被预处理器移除。Release 常定义 `NDEBUG`，所以不仅比较条件消失，放在断言里的函数调用也会一起消失。例如 `assert(PubPushMessage(...) == 1)` 在 Release 不会发布消息；测试仍可能以退出码 0 结束，看起来通过，却没有执行要验证的行为。

本工程主机测试统一用 `tests/host/test_check.h` 的 `TEST_CHECK(expr)`。它在 Debug、Release 都计算条件，失败时打印文件、行号和表达式并以非零退出。正向和负向控制用例分别确认通过与故意失败；负向用例由 CTest 包装，只有检查确实拒绝故意错误才算通过。具有副作用的生产接口先赋值到局部变量，再单独检查返回值，避免把“做事”和“判结果”藏进宏。

优化构建也会改变测试替身观察到的分配形式：例如编译器可以把生产代码的 `malloc()+memset()` 合并成 `calloc()`。若故障注入只拦截 `malloc`，Release 下就没有真正制造分配失败。本次给资源回归同时拦截两种入口，并在 Debug／Release 都确认失败路径。

构建告警也可能指出真实的可移植性问题。本工程将 EKF 的快速反平方根位型操作从 `float*` 与 `long*` 强制转换改为 32 位整数和 `memcpy`，避免严格别名违规，并避免在 64 位主机读取 8 字节 `long` 越过 4 字节 `float`。公开行为测试通过四元数 EKF 更新检查加速度模长；测试不直接调用私有的 `invSqrt()`。LCD 字模括号修正前后用字节转储逐字节核对，确认仅修复初始化层级而未改变字模内容。

复核 R25-10、R25-11 时，原始 Release 测试数保留为历史记录，但其中 `assert` 检查并不能证明相关行为曾执行。修复后重新运行当前全部主机 CTest：Debug 与 Release 均为 102/102。这个结果证明本次覆盖到的测试检查有效，不替代未接入的硬件或可选驱动验证。
