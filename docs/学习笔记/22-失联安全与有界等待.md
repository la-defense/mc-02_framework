# 失联安全与有界等待

本篇记录两条实际联调中发现的边界：固件不能把上一周期的开火命令留在静态状态里；相机和网络等待要有期限，超时后控制循环才能及时撤销。

## 接收、派发和撤销是三个时间（BSPUART-03U1）

假设UART在0ms通知数据，任务到50ms才派发。该数据此时已经50ms旧；若把派发时刻写成来源时刻，就会凭空多给它50ms。新接收块直接交付原RxEvent通知时间，0也合法，协议不能用派发或查询时刻替换。

| 检查对象 | 从哪个时刻计算 | 允许边界 |
|---|---|---|
| 队列块、裁判/SP残帧 | 原通知，组帧取首个组成块 | 不超过50ms |
| 遥控器在线 | 最近合法独立18字节块原通知 | 不超过100ms |
| 键鼠心跳 | 最近向前变化心跳所在块原通知 | 不超过150ms |
| 裁判在线 | 最近合法已支持命令的首块通知 | 不超过300ms |
| SP命令 | 最近合法帧的首块通知 | 不超过50ms |

DaemonReload仍负责原有周期计数，但不能延长上述来源期限。遥控查询发现来源超时后清输入、撤销许可并请求急停；诊断的offline_tick、pc_expire_tick等另记录真正发现或撤销的时刻。跨毫秒回绕时使用无符号差计算短时间间隔。

DR16没有供自动寻找边界使用的帧头及CRC。因此只接受单个18字节块，两个9字节块不能自动拼接；错误长度或字段不刷新上一合法输入。键鼠仍要求两帧完全松开、心跳向前变化才恢复。无线帧持续到达而键鼠心跳不变时，无线可继续在线，键鼠会独立到期。

离线任务通过标记请求重建，接收任务自己修改残帧数组，避免两个任务同时移动字节。查询只检查数据期限，不产生新数据或刷新来源时间。[遥控回归](../../tests/host/remote_control_test.c)和[流式接收回归](../../tests/host/uart_stream_test.c)覆盖0ms、50/51ms、100/101ms、300/301ms及回绕；键鼠150/151ms沿用既有生产测试。未连接开发板，电平、执行器动作和真实调度耗时不在本轮验收内。

## 输入失效时要生成完整的新命令

`shoot_cmd_send` 是跨控制周期复用的静态结构。旧实现只在视觉数据有效时改写它；视觉回调失联时函数直接返回，上一帧 mode 2 的 `SHOOT_ON` 和 `LOAD_BURSTFIRE` 就会保留下来。跳过一次更新不等于撤销旧状态。

现在 `VisionControlBuildShootCommand` 每次都生成一份完整的视觉发射策略：mode 1 保留预热但停止装填；mode 2 允许 burstfire；无效输入生成中立命令。这里 `shoot_mode` 是发射电机组的总使能，mode 1 可保持它开启来预热摩擦轮；是否装填/击发由 `load_mode` 控制，所以 mode 1 必须是 `LOAD_STOP`。`RobotCMDTask` 再由 `VisionControlSelectShootCommand` 决定当前命令来源：有效视觉优先；视觉 mode 0、过期或断连时，若遥控器或键鼠仍是当前输入，就保留本周期刚算出的手动命令；没有有效控制源时才撤销为中立。这样“视觉命令无效”不会误删仍有效的手动请求，也不会让无控制源时的上一条命令残留。

手动遥控器在摩擦轮或装填被请求时打开发射总使能；键鼠在 E 选择单发/三发/连发或 F 打开摩擦轮时也使用同一规则，键鼠连发射频固定为 8 发/秒，不继承上一帧视觉射频。拨轮阈值和 E/F 映射被提取为纯函数，固件与主机测试共用，避免测试只验证手工构造的示例命令。主机回归覆盖拨轮边界、键鼠模式、视觉 10→手动 8 发/秒恢复、视觉优先、mode 0、过期、断连和无控制源中立输出，不需要 STM32 或执行器。它验证命令生成和选择逻辑；遥控器帧合法性、机械限位和真实电机响应仍由其他待办负责。完整任务进度见 [R25-06](../../.Doc/TODO.md)。

## 通信有效与控制有效是两道检查（R25-02）

CRC 正确说明接收到的字节通过协议校验；它不能证明目标角度在云台机械范围内。接收计数增长、在线和时间戳更新仍保留为通信证据，控制层另检查模式、50ms 内的新鲜度、六个数值有限，以及明确配置的机械范围。这样诊断时能区分“没有收到帧”和“收到帧但不能接管”。

`VisionControlLimits_s` 中的角度范围用度表示，SP 通信中传来的角度用弧度表示，程序先换算单位，再给 pitch 加上补偿角度。以电脑测试为例：上下转动的输入相当于 25°，补偿 5°，最后得到 30°。设置的范围是 [-20°,30°]，30° 刚好等于上限，可以使用；输入相当于 30° 时，加完补偿得到 35°，就不能使用这份视觉目标。检查角度范围时要用加完补偿的结果。这组数字只是测试数据，正式配置的 `VISION_LIMITS_CONFIGURED` 默认是 0，表示角度设置还没准备好。yaw 还需要明确选好转动方式：可以连续转动，或只能在指定范围内转动。

`VisionControlInput_s` 只保存指向角度设置的地址，设置内容仍放在原来的位置。因此，调用函数时这份设置必须还在，也不能被其他代码改写。正式代码把设置放在一直存在的只读变量里，并在每次计算前固定当前时间和本次视觉数据，让云台和发射使用相同的内容。`VisionControlBuildGimbalCommand()` 会先清零输出，全部检查通过后再填入算好的结果。这样某一步失败时，输出里就不会残留上一次的目标。

视觉失效后，要清的不只有发射位。旧目标角度、角速度和角加速度都存放在跨周期结构中；直接返回会继续保留它们。当前任务每周期先清除前馈，切回手动时用本周期收到的有限姿态反馈作为起点，再应用遥控杆或鼠标增量。例如上一视觉目标是 14.32°、板子当前实际朝向为 12°，遥控要求加 0.2°，新手动目标应为 12.2°，不会继承旧目标 14.32°。交接时拿不到反馈就发布中立，并等待新反馈；正常连续手动则保持目标增量累积。

手动接续还要求遥控链路在线且选择了有效模式。没有来源时清零目标与前馈、停云台输出并关闭发射；SAFE/CALIB/FAULT/ESTOP 在发布前再次覆盖选择结果。有效手动命令仍可发射，故“视觉退出”在此表示撤销视觉控制，而不是新增全局发射锁存规则。

本轮回归直接运行生产 `RobotCMDTask()`、RobotSafety 与消息队列，通过订阅实际发布的命令验证行为；默认未配置与模拟有效配置各构建一个主机目标。裸板构建不链接整机控制任务，裸板烧录成功不能证明视觉接管决策已经在板上运行，更不能证明真实云台或发射机构已失能。软件与裸板记录见 [R25-02 票据](../workflow/tickets/R25-02.md)，真实机械范围和输出失能继续由 TODO 跟踪。

## 从函数注释判断失效后的输出（MC02-0105）

注释应让学生看清函数接收什么、返回什么，以及失败后输出如何处理。样例见 [vision_control.h](../../modules/master_machine/vision_control.h) 和 [vision_control.c](../../modules/master_machine/vision_control.c)，任务入口为 [MC02-0105](../../.Doc/TODO.md)。

文件头交代用途。函数声明用 `@brief` 说明功能，`@param` 说明输入和输出，`@return` 解释返回值，`@note` 补充容易误用的条件。单位和字段含义集中说明，简单换算、四档循环等容易读懂的内容无需再举例。

源文件在重要的选择处用 `//` 单行注释解释原因或结果：哪些输入会让函数返回失败，视觉不能用时怎样选择手动命令，`switch` 的各档分别做什么。先清零是为了避免失败后沿用旧目标，补偿角度后再检查范围，换算后还要检查数字是否过大。参数和返回值的完整说明仍放在头文件。

注释紧挨着对应的判断，学生可以沿着代码阅读。`load_cycle % 4u` 取出四档中的一档，`switch` 注明单发、三发、连续供弹和停止；F 键次数的奇偶决定摩擦轮开关。这里说明选择结果即可，无需列举按键次数的例子。普通赋值不必逐行加注释。

本模块有几处容易看错：

| 代码 | 需要保留的说明 |
|---|---|
| `max_age_ms` | 可设为 0～50 ms，等于时长仍允许；为 0 时只接受同一毫秒的数据 |
| `VisionControlBuildShootCommand()` | mode 1 请求摩擦轮转动、停止供弹；mode 2 再请求以 10 发/秒连续供弹 |
| `VisionControlSelectShootCommand()` | 返回 0 也可能已选中手动命令；手动命令由外部检查后原样复制 |
| `manual_command` 与 `command` | 输入和输出必须分开存放，避免清零输出时把手动输入也清掉 |

中文写法参考 [Humanizer-zh](https://github.com/op7418/Humanizer-zh/blob/main/SKILL.md)，直接说明条件、动作和结果，删掉重复说明。精简时仍要保留会影响用法的内容，包括空指针、时间要求和输入输出分开存放。

样例提交 `9bbb1ab` 只改注释，函数参数、类型、常量和计算步骤保持原样。修改前后除注释以外的代码相同，GCC 去掉注释、展开头文件后的内容也相同。已有的[角度范围与单位换算测试](../../tests/host/vision_limits_test.c)、[视觉与手动发射测试](../../tests/host/vision_protocol_test.c)、[命令切换测试](../../tests/host/robot_cmd_task_test.c)及相关集成测试在 WSL Debug／Release 下各 13/13 通过，bench_safe／robot Debug 禁热固件编译通过。电脑测试与编译检查涉及软件行为，实际电机和发射机构的表现仍需要单独验证；样例改写未连接硬件。

### 先检查注释，再决定修改范围（MC02-0107）

[业务文件注释清单](../workflow/maps/comment-style-audit-20261016.md)逐份记录了 application、bsp、modules 中的源码与头文件。清单提供文件位置、已经找到的问题和建议修改范围，供用户选择；任务记录见 [MC02-0107](../../.Doc/TODO.md)。检查清单不代表已获准修改其中的源码。

检查注释时，先找对应的声明、实现和调用处。以 [CANTransmit 的接口说明](../../bsp/can/bsp_can.h#L166)为例，文字仍在提醒等待超时，但[实现](../../bsp/can/bsp_can.c#L675)已经忽略 timeout，发送空间不足就返回失败。只把旧句子润色得更顺，会继续误导调用者；需要先确认函数现在怎样处理，再写清返回结果和使用条件。

返回值也要看实际代码。[PubPushMessage 的注释](../../modules/message_center/message_center.h#L83)写成功推送给几个订阅者，而[当前实现](../../modules/message_center/message_center.c#L179)调用 PubPushMessageAt，成功时固定返回1。函数声明里的 uint8_t 只告诉我们返回值的类型，不能替代“1和0各表示什么”的说明。修改这类注释前，应核对所有返回位置；如果发现功能也需要调整，另行讨论，避免在整理注释时顺带改变程序。

函数体重点看会改变后续动作的地方：数据过期后为什么清零，失败后为什么保留旧值，循环在找什么、何时停止。已有说明足够清楚的部分保持简短；没有分支的普通赋值不用补一排解释。字库只需说明字符与数据的对应方式，空文件先确认用途，不能给它写出尚未实现的接口保证。

Git 记录能帮助区分原有内容、移入内容和后续修改，但提交者姓名不能证明具体代码由人工还是 AI 编写。因此清单保留提交依据，并明确来源尚不能确认的位置。核对清单时还要与实际跟踪文件逐一对上，避免漏文件、重复计算，或把一对 .h/.c 合并后少算一份。本轮只改文档，验证文件覆盖、代码位置、链接和源码未变即可；获准补注释后，再按实际修改选择检查方式。

## 把一次裸板回归拆成可核对的证据（R25-02）

2026-10-09 烧录软件提交 `59f6b4d` 的 bench_safe Debug 禁热固件，写入 verify 成功，参数区前后 262144 字节逐字节一致。60.189 秒收到 12036 帧有效状态，恰好发送并接收 1000 帧中性指令；停发 200ms 后全部旧帧与接收时间清零，CRC 计数不增长。IMU 序号持续增加，四元数有限，PB1/TIM3 与闲置电源输出保持规定的寄存器隔离状态。

这些结果分别回答“写进去的是哪份程序”“参数有没有被覆盖”“协议是否解析”“超时是否撤销”和“输出配置是否隔离”。裸板没有链接整机接管入口，不能用这里的 RX 增长证明云台已经正确采用机械限位；生产控制决策由主机回归验证，真实参数与输出由台架验证。完整 SHA、哈希、加载区间和统计见 [R25-02 票据](../workflow/tickets/R25-02.md)。

人工检查又发现 LCD 启动黑屏、按键恢复后偶发乱码。即使采集脚本的自动检查全绿，显示验收仍然失败。故障拆为 [MC02-0046](../workflow/tickets/MC02-0046.md) 保留，R25-02 不关闭。报告中的 `passed=true` 必须说明覆盖哪些检查；一个布尔值不能自动覆盖用户的实物观察。用户报告电流曾约 0.11A，随后回落至约 0.09A、CV 亮；没有测量支路，不能从“加热 duty=0”推导所有电流变化都来自 LCD。

## 完整帧、合法输入和在线租约（R25-03）

遥控接收分成三个判断：是否收齐本次帧、字段是否合理、最近一次合法输入是否仍在有效期限内。这三者不能用“UART 中断发生了”代替。旧回调先喂 daemon，再从 DMA 缓冲解析；收到 17 字节时，第 18 字节可能来自上一帧，非法摇杆又被归零后继续接受。结果是噪声也能延长在线状态。

现在生产[UART派发](../../bsp/usart/bsp_usart.c)先把中断数据复制到队列；回调参数`block->data`只在本次回调期间提供该队列项的只读地址。不能保存这个指针用于下一周期：回调结束后队列项可能被复用。DMA数组属于下一次接收，解析时不应依赖它保持不变。超出容量的事件丢弃并计数，不把异常长度改成“完整帧”。零长度事件不派发；遥控回调拒绝1～17字节。

[遥控解析](../../modules/remote/remote_control.c) 要求恰好 18 字节；先解码到局部候选，检查五个现有通道原始值在 364～1684、两个开关为 1/2/3、鼠标按键为 0/1，全部成功后才发布输入、更新按键边沿并给 daemon 续期。非法帧不会制造一次按键按下或松开，也不会改变最近合法帧时间。键位与拨轮仍按工程现有映射，版本核对留在 MSG-05。

[DJI 用户手册](https://cdn-hz.robomaster.com/tem/09f88aafe7ae51516874829340553427.pdf) 的 DBUS 帧表没有独立 CRC 字段。因此这里做的是长度和字段检查；不能称为 CRC 校验，也不能声称所有噪声都可识别。如果错误字节碰巧满足合法字段范围，软件不能仅凭这些检查知道它来自噪声。

daemon 的注册宽限期只是给模块启动留时间，并不证明已经收到遥控输入。`RemoteControlIsOnline()` 增加“已收到合法帧”门槛。合法帧到来后，daemon 形成约 100ms 的在线租约：非法帧不续约，期限结束清空输入并锁存急停。主机测试以 10ms 调用 daemon，下降沿回调最迟在第 11 次调用执行；实际时延还受任务调度影响，需要实测最后合法帧到离线事件的差值，验收上限为 150ms。

## 在线恢复不等于允许输出（R25-03）

断链后重新收到合法帧可以恢复在线，却不能自动解除急停。两个开关居中保持一秒才尝试 `EstopClear()`；现有任务故障仍可阻止清除。共享 [安全手势](../../modules/remote/remote_safety.c) 为每个组合保存 `active` 和开始时间：tick=0 是合法时间，不再兼作“尚未开始”的标记；无符号 `now-start` 可以处理一次计数回绕。离线时取消所有正在累计的保持时间。

新增的 [裸板诊断](../../modules/remote/remote_bench.c) 每周期明确禁止使能，并使用同一个手势实现。居中恢复后只能返回 SAFE；双开关向下保持一秒也不能 READY。诊断名称和构建指纹含 `rcdiag_bench_safe`，避免误当整机产物。它仍消费接收队列，但 ELF 不得包含执行器初始化或控制入口。这个隔离检查能证明哪些代码被链接，不能代替输出电平测量。

本轮测试直接联编 UART、遥控、daemon、RobotSafety 和命令任务，只替换 HAL、时钟和消息输入边界。既检查短帧、非法字段、旧尾部和 DMA 改写，也订阅实际发布的云台、底盘及发射命令，验证离线或非 READY 时为中立。实机只被动接收 SP 状态帧，不通过遥控诊断驱动任何执行器。测试与接收机记录见 [R25-03 票据](../workflow/tickets/R25-03.md)。

## 枚举成功为什么还不能烧录（R25-03 实测教训）

2026-10-10 软件提交 `0951f81` 已通过回归，现场也能看到调试器 COM9 和板载 COM14。但备份的 OpenOCD 日志在识别 CMSIS-DAP 后报 `CMD_INFO failed`：USB 设备枚举、调试协议握手、SWD 访问芯片、Flash 读写是不同层次。一个串口名不能证明后面三步成功。

本次失败发生在 `init`，还没有到目标连接和 `dump_image`，所以没有备份，也没有执行烧录。正确记录应写“连接失败，停止本轮”，不能把“已构建”和“已烧录”合为一句。原始命令与完整日志保留在 [R25-03 票据](../workflow/tickets/R25-03.md) 指定的位置。等待人工重新连接调试器后再发起新的验证，不从这条日志推断芯片或 DR16 损坏。

只读快照也要匹配 ELF 的数据宽度。本次离线解析发现 `robot_state` 在 ARM ELF 中大小为 1 字节，固定 `--rc` 字段按字节读取；若错按 32 位读取，既违反对齐规则，也可能把相邻状态读进来。应修正字段类型与读宽，保持地址白名单和 running 检查，不放宽工具约束绕过错误。

## 分清启动宽限期与真实断链时延（R25-03）

用户要求继续后，同一固件的备份、烧录 verify 与参数逐字节保留均成功。DT7 关闭时，板上合法帧计数为零、在线为零、急停锁存；这才是“启动时没有输入”的证据。前次 CMD_INFO 失败没有复现，只能说本次连接成功，不能宣称探针偶发问题已找到根因。

启动快照还记录 `offline_tick=1004、offline_last_valid_tick=0`。它对应 daemon 初始宽限期到期，此前没有合法帧，所以 1004ms 不能拿来验收“最后合法输入到断链清零”的速度。接收机实测应先建立合法接收，再关闭发射机，查看新增离线事件及其保留的最后合法帧时间。人工回复可能晚几秒，事件时间戳仍能提供板上记录的差值；逐字段 SWD 快照本身并不是瞬时原子快照。

## 受控拨杆动作如何证明急停恢复（R25-03）

本次最初计划用“重新开机后仍急停”作证据，但实物两拨杆都在中间。板上收到 3/3，按 [共享安全手势](../../modules/remote/remote_safety.c) 保持一秒后清除急停，正好执行了人工恢复条件。它不能证明“重连自动解锁”，也不能拿来通过“重连仍锁存”这一检查。原采集报告的失败断言必须保留，然后修正动作前提重新采集。

新的对照先让左下、右中，板上核对为 2/3，再关闭/开启发射机。三个事实分别检查：在线恢复说明合法帧续约；`estop_latched=1` 说明断链造成的锁存没有自动解除；`enable_requested=0` 和非 READY 状态说明诊断仍禁止控制。随后双居中一秒只返回 SAFE，再双下保持一秒也仍 SAFE。这比只看一次“在线=1”的截图更能验证恢复过程。不能把三档拨杆与摇杆混为同一个输入。

三轮记录的离线延迟为 105、109、101ms，按板上 `offline_tick-offline_last_valid_tick` 计算，事件号从 2 到 4，每次都是新的事件。第 1 轮受控重连连续观察 60.422 秒，合法计数增加 4302、各快照急停保持。结束时的被动 SP 采集共有 202088 个有效状态帧，CRC 错误为零。注意这里的 CRC 属于 SP 状态帧，DR16 的长度/字段校验没有因此变成 CRC 校验。

[裸板诊断任务](../../modules/remote/remote_bench.c) 把 `allow_enable` 固定为 0，并每周期关闭使能请求；ELF 隔离检查还排除了执行器入口。板上寄存器观测与主机非法帧测试互相补充：前者检查真实接收、断链及手势，后者能安全注入短帧和非法字段。它们不验证实际电平和波形，也不证明整机执行器失能已通过。全部阶段、固件 SHA 与原始日志哈希见 [R25-03 票据](../workflow/tickets/R25-03.md)。本文记录调试依据，不据此新增个人“已掌握”的学习记录。

## 故障位必须参与控制判定（R25-05）

原实现将电机离线、CAN BusOff 和倾斜写入 `fault_flags`，但 READY 只看几个布尔输入。因此，日志中有故障不代表输出已经失能。生产回归先让系统 READY，再调用 `RobotFaultReport(ROBOT_FAULT_MOTOR_OFFLINE)`，复现状态仍 READY；修复后同一接口转为 FAULT，实际发布的云台、底盘和发射命令全部中立。

故障字是位集合，不能把它当单一错误编号。电机离线与 BusOff 同时存在时，清除电机离线只能移除那个位，BusOff 仍阻止控制。所有待处理位都阻止 READY；直接报告遥控离线也会锁存急停，直接报告任务超时也取消使能请求，避免布尔输入与故障字不一致时放行。实现见 [RobotSafety](../../modules/safety/robot_safety.c)，生产测试见 [状态与恢复](../../tests/host/robot_safety_test.c) 和 [命令发布](../../tests/host/robot_cmd_task_test.c)。

### 自动恢复与人工恢复是设计选择

本项目按用户选择，MOTOR_OFFLINE、CAN_BUSOFF、TILT 进入 FAULT 时保留使能请求；所有阻断条件消失后可以自动回到 READY。保留的是“希望使能”的请求，故障期间输出仍关闭。若期间人工取消使能、开始标定、任务超时或急停，则旧请求被撤销，恢复健康后仍需重新申请。

自动恢复会重新使用当前输入。测试先产生带速度/加速度前馈的视觉命令，报告故障并检查前馈全部清零，再改变当前姿态和手动输入、撤销视觉、清除故障；恢复命令必须从新姿态起算。只比较状态名，无法证明旧目标没有残留。

### CALIB 不允许执行器工作

CALIB 表示静置 IMU 标定。它允许在这三类 FAULT 下进行，因为标定本身不要求电机转动；标定请求会取消使能，所有非 READY 命令继续失能。任务超时和 ESTOP 的优先级更高，不能用 CALIB 绕过。标定结束也不恢复旧使能。

本轮区分了两件需要分别验证的事：RobotSafety 如何处理**已收到**的故障，以及真实硬件如何产生故障。前者用生产接口注入验证；后者仍由 R25-04、MC02-0047、MC02-0048 跟踪。裸板上的 `fault_flags` 只读快照只能证明当时报告了哪些位，不证明未报告的硬件一定健康。证据与验收边界见 [R25-05 票据](../workflow/tickets/R25-05.md)。

### 故障字快照与裸板证据如何对应（R25-05 实测）

新固件在 DT7 关闭时读到故障字 `1`，对应 `RC_OFFLINE`，在线为零且状态 ESTOP。人工双开关居中开启后，故障字变为零，急停解除但状态只到 SAFE。随后双下保持观察 60.176 秒，合法遥控帧增加 4285，开始/中段/结束快照的使能请求均为零、状态均 SAFE。这同时检查了新故障判定没有破坏既有人工恢复和裸板禁止使能。

全会话被动收到 52527 个 SP 状态帧，CRC 错误为零、四元数有限；没有发送控制帧。参数区回读与烧录前逐字节一致，IMU 有效递增、加热与输出寄存器隔离正常。全会话计数包含人工操作等待期间；60 秒窗口单独为 12032 个状态帧，不能混用两者作为同一窗口的频率依据。

本次板上实际观察到的故障位只有遥控离线。其余故障的控制规则由主机联编生产代码验证，不在板上写内存伪造故障，更没有连接电机进行失能试验。板上 `fault_flags=0` 只表示“当前没有上报的故障”，并不证明未接入的 CAN 和倾斜检测已经工作。报告保存准确软件 SHA、ELF 哈希与原始读取响应，见 [R25-05 票据](../workflow/tickets/R25-05.md)；这些实测记录不代表学习者已展示掌握。

## 接管期间的手动输入也要保持最新（R25-06）

“视觉优先”只决定本周期发布哪份命令，不应冻结手动输入。假设拨轮原先回中，视觉正在 mode 2 连发；期间把拨轮拉到连发区，视觉撤销时应选择当前手动 8/s，而不是进入视觉前的停止命令。键鼠同理：接管期间 E 的边沿计数变为 2，F 变为 1，撤销后应使用当前三发档与摩擦轮状态。边沿计数是从未按下到按下的次数，持续按住不能每帧累计；固件计数为 8 位，会回绕。

新增 [生产任务回归](../../tests/host/robot_cmd_task_test.c) 通过真实消息中心订阅最终发射命令，先激活视觉、改变被覆盖的手动源，再撤销检查结果。只测试 `VisionControlSelectShootCommand()` 的返回值无法证明命令任务确实每周期调用它、也无法证明最终安全门禁没有遗漏。本轮新场景直接通过，说明已有实现符合这些规则；增加证据不需要制造一次无必要的生产改动。mode 2→1 是“停止装填、保留摩擦轮”，无来源/非 READY 则完全关闭，二者输出不同。

50ms 年龄仍允许，51ms 撤销；使用无符号时间差验证跨 tick 回绕。六个视觉字段每个都可能出现 NaN/Inf，测试分别注入，确保非法前馈不能保留视觉发射。机械范围只在主机模拟中配置；生产缺参数仍拒绝接管。完整范围与日志见 [R25-06 票据](../workflow/tickets/R25-06.md)，主机测试不能代替真实发射台架。

## 两段键鼠协议与两种断链（MC02-0049）

电脑键鼠经 USB 到 DT7，再无线到 DR16，最后经 DBUS 到 MC-02。每一段都有自己的帧格式；板上 18 字节解析布局不能直接用作电脑发送格式，SP 状态帧 CRC 正确也不能证明键鼠传输正确。独立工具必须先查证电脑协议，再用全松开、单键、鼠标及按钮动作核对板上字段。官方客户端静态代码能提供来源依据，但设备固件适用性和实物映射仍需实测。

新 [`--rc-input` 观测接口](../../tools/probe_snapshot_live.py) 只读固定字段：键位低/高字节合成位图，鼠标 `ff ff` 合成 -1，`00 80` 合成 -32768。位图无符号，鼠标有符号，同样的两个字节不能都按正数解释。工具保留原字节，也不把两个运行态读取伪称原子快照；保持动作后反复读取更适合核对。E/F 边沿对应当前固件索引，不对尚未验证的物理键位暗中补偿。

电脑窗口失焦应发送全松开并暂停；断开电脑 USB 后，DR16 可能仍持续输出合法无线帧，此时“遥控在线”不保证键鼠已经释放。必须分别测试正常退出和物理拔 USB，发生残留就关闭 DT7，让现有遥控超时清空输入。串口写失败时只能记录释放失败，不能据此宣称下位机已清零。协议门槛与工具验收见 [MC02-0049 票据](../workflow/tickets/MC02-0049.md)。

### 校验“帧能收到”之后，还要校验键位含义

本轮从官方 Client 5.0.2.37 程序集取得电脑发送格式，有限动作实测确认 A 发 `0x0004`、D 发 `0x0008`；MC-02 收到的原始位图正确，但头文件把 bit2 命名为 `d`、bit3 命名为 `a`。链路工作正常不等于应用动作方向正确。生产解析回归直接给 A 的固定向量并检查 `.a`，先失败，再交换宏和位域，两者必须一起改；只改宏会让边沿数组和具名字段继续冲突。代码见 [remote_control.h](../../modules/remote/remote_control.h)，MSG-05 仍跟踪完整协议单位核对。

电脑帧的 CRC16 多项式也采用 `0x8408`，但初值为 `0x1862`、没有末尾异或；SP 的 X25 有不同初值/异或。因此不能仅看到“CRC16”就共享现有函数。独立 [编码器](../../tools/dt7_input.py) 与官方重建字节向量逐一比较，随后九组板上动作均符合期望；来源/版本/哈希记录在[协议调查](../workflow/tickets/MC02-0049-协议调查.md)。静态来源与板上成功是两份证据。

工具的回放和窗口都维护“当前按住的键/按钮”，不发送“每周期按下一次”的事件。鼠标不同：位移是增量，成功发送后才清零；写失败保留诊断数据并停止，不能继续累计/重连发送。窗口失焦发送全松开且停止周期发送，重新获得焦点也不会自行恢复，需要点击开始。33ms 周期迟到时只发送一份最新状态，不连续补发旧包。`release-write-completed` 只表示串口写完，是否清零还要用板上快照确认。

### 分清回归证据的范围（R25-06）

第一轮裸板全会话收到 68684 个状态帧；双下保持的 60.274 秒窗口单独收到 12054 帧，合法遥控帧增加 4289，均 SAFE/使能零。期间电脑端只有九个有限向量和各自松开共 18 次写入；COM14 始终被动接收。两类流量的端口、格式、计数不同，应分别报告，不能用 SP CRC 为电脑键鼠帧背书。

既有生产发射实现的新切换场景通过，补测试而未改策略；A/D 解析回归则真正失败并产生最小修复。两种交付都提供了证据，但不能都称为“修复了一个新故障”。裸板没有运行真实发射模块，最终输出行为仍要台架验收；写出这些说明也不记录学习者已掌握。

### 监听端口不等于目标状态已经可读（MC02-0049）

第二轮烧录前的临时预检，看见 OpenOCD 开始监听 Telnet 就立即查询目标，返回 `unknown`；之前成功的 HIL 在建立服务后还等待一秒。这是值得对照的时序差异，但现有日志没有保留该次完整 Telnet 状态行，只记录程序解析后的异常。不能把推测写成“已修复”或据此判定板子损坏。

保护的实际作用是：`unknown` 不被当作 `running`，第一个 RAM 读取之前就停止，更没有继续备份/烧录。修正下一轮采集脚本，既保留已验证的建立间隔，也记录请求、完整响应及时间；失败仍停止，不用停核绕开检查。软件提交 `bb7c727` 与板上旧固件 `5c64ed0` 必须分开记录。完整失败和下一轮安排见 [MC02-0049 票据](../workflow/tickets/MC02-0049.md)，真实回放和窗口功能尚未通过实机验收。

### 采集程序失败和目标程序失败要分开（MC02-0049）

重新开始烧录时，完整日志确认 SWD 已读取运行态和 RAM/寄存器，但临时脚本末尾报 `KeyError: imu_heater_duty`。它复用了一个会检查禁热隔离的采集函数，却只给它遥控字段，忘记包含 IMU 的占空比字段。这里失败的是采集方的字段契约；不能写成“芯片不运行”或用停核去绕过。先在本机检查字段集合，再进行新的只读预检，两份完整快照通过后才备份/烧录。两次日志都保留；之前 unknown 的具体原因仍不能由这次成功倒推。

烧录成功、Flash verify 成功和参数保存是三个独立判断。本次部署 `bb7c727` 后，用读回的整个 256KiB 参数区与备份逐字节比较，确认相同；`program verify` 本身只核对 ELF 加载区域，不能证明未加载的参数区没有改变。全片备份的哈希与参数区哈希不同，也不能拿来互相比较。范围和哈希见 [MC02-0049 票据](../workflow/tickets/MC02-0049.md)。

### 短暂事件可能发生在两次观测之间

18 秒真实回放中，220 次板上观测捕获了 W/E/F/A/D、两按钮和 E/F 各一个边沿，退出后全部释放；鼠标位移只在一个发送周期内存在，随后发送零。逐字段 SWD 读取需要时间，两个字节也不是原子读取，因此没有采到非零位移，不能判定鼠标失败，更不能判定鼠标已验收。工具日志中的发送字节只证明电脑写出过该增量，不证明这一次下位机观察到了它。

持续来回移动可提供更多观测机会；若需要精确核对一个短事件，则需保持事件或改进有限观测方式，并记录这个变化。验收应分别看“程序没有报错”“期望字段确实出现”“退出确实清零”，避免一个通用 `passed` 布尔值掩盖尚未取证的子项。本轮这些观测都保持 SAFE/使能零，未驱动真实执行器。

### Z 的数字解释与无线透传证据（MC02-0049）

DBUS 第 10/11 字节组成鼠标 Z，`00 80` 按有符号数解释为 -32768，按原始位模式解释为 0x8000。未来的自定义心跳需要保留位模式，不能把负号当成非法序号。第一阶段用 32 位诊断字段零扩展保存这两个字节，既保留 32768 的原始模式，又在只读工具中展示 -32768；没有把控制结构加上滚轮动作。只有完整合法帧会更新该字段；短帧或非法按钮不能制造新的诊断证据。

主机测试通过生产 UART 队列接收，再改写 DMA 原缓冲，确认仍解析已入队的字节；补齐字段后，旧实现会在 Z=1 时失败，最小修复后通过。电脑端六个固定帧用官方 DLL 提取的 CRC 表独立重建，再与编码器逐字节比较。这些测试证明解析和编码，实机是否保存 Z、是否复用旧值，仍须有限对照；在透传通过前，连续工具保持 Z=0。详见 [remote_control.c](../../modules/remote/remote_control.c)、[编码器](../../tools/dt7_input.py) 与 [MC02-0049 票据](../workflow/tickets/MC02-0049.md)。

用户选择了仅撤销键鼠来源的保护方案：遥控在线与电脑输入有效性将分别判断，失效时清掉键鼠和边沿，其他有效来源继续由既有策略选择。恢复需两份递增、全松开的心跳；这可避免一根线重新插回后旧 W 或 E/F 档位重新生效。此机制属于本项目约定，当前阶段尚未实现，也不记录学习者已掌握。

### 首帧前超时和真实断链的时间不能混用

Z 观测版本烧录后，DT7 保持关闭，`accepted_frames=0` 且 `last_valid_tick=0`，首帧前 daemon 回调在 tick 1003 记录离线。这证明启动没有被误当在线，不能把 1003ms 写成“关机后离线延迟”：根本没有发生最后一个合法无线帧到发射机关机的对照。真实断链必须在已收到合法帧后，比较对应的最后合法帧与离线事件时间。

本轮用户居中开启后只返回 SAFE，使能仍为零；启动及居中窗口分别收到 648/649 个有效 SP 状态帧，IMU 与输出隔离正常。这里证明的是已部署固件的基础运行。即使原始 Z 字段目前读到零，也可能因为电脑尚未发送，因此既不能证明非零 Z 会透传，也不能证明不支持透传。要回答这个问题，必须在限定拨杆模式下发送有来源的六组 Z 对照，再读 DBUS 解析出的原始位模式。准确 SHA、ELF 哈希、Flash 备份和窗口原始日志见 [MC02-0049 票据](../workflow/tickets/MC02-0049.md)。

### 已在线与急停已解除是两个状态

同一轮等待期间，遥控超时计数从 1 增为 2，新的最后合法帧至离线为 110ms；随后读取到 `online=1`、`fault_flags=0`，但 `estop_latched=1`、状态仍为 ESTOP。这些值并不矛盾：新的合法帧恢复了在线，锁存急停需要另一个人工恢复条件。居中清除曾经通过，不代表后续阶段无需再次确认；相隔十多分钟的两次快照尤其不能被当成连续安全证明。

Z 透传对照要求 SAFE，此阶段检查失败时，没有发送任何 Z 包，也没有用复位抹掉急停。保留原始时间和离线事件，再请操作者居中保持进行新一轮检查，可以区分“前置条件未满足”和“Z 透传失败”。前者尚未测试 Z，不能把任务阻断原因写成“不支持 Z”。现有字段只证明发生过遥控超时，尚不足以断言是用户关闭遥控器还是无线/接收路径中断。证据见 [MC02-0049 票据](../workflow/tickets/MC02-0049.md)。

### 一个字段会自动清零，不代表整份输入会清零

新一轮 Z 对照实际通过：0/1/256/0x7fff/0x8000/0xffff 各两次原始位模式一致；停止电脑发送一秒后，DBUS 的 Z 已变为零，合法遥控帧仍在增加。先前维持 W 再拔 USB 却留下 W=1。接收端每个字段的语义可以不同，不能用 Z 的清零替 W、按钮或 E/F 边沿作验收。

本项目让 Z 承载递增心跳，属于新的约定。Z=0 可作为立即撤销证据；即使 Z 没有清零，重复心跳也不能续期。两项条件一起覆盖“字段自动清零”和“冻结旧值”两类现象。真实透传通过只允许开始实现这层保护，仍需验证持续 33ms 心跳、150ms 边界、全松开恢复及三轮真实 USB 断开。完整原始记录见 [MC02-0049 票据](../workflow/tickets/MC02-0049.md)，未测试的断连子项继续保留。

### 心跳前进、租约到期与新操作

新的 [授权输入接口](../../modules/remote/remote_control.h) 返回遥控在线和 `pc_valid` 两个状态。遥控仍在线时，电脑键鼠可以因心跳停更而失效；控制任务可继续选择有效遥控或视觉，不把一条输入来源的撤销升级为新的全局急停。没有可用来源才发布中立命令，RobotSafety 的失能优先级继续覆盖最后输出。

16 位序号不能用普通 `new > old` 比较：65535 后跳零回到 1，应当前进。代码把差值转换为 `uint16_t`，1−65535 得 2；倒退的 1−2 得 65535，属于后半圈而拒绝。差值 0 是重复，32768 及以上也拒绝。这是序号在一个有限环上的约定；时间年龄另用 32 位无符号 tick 差，150ms 允许、151ms 撤销，两种回绕都由生产解析回归覆盖。

到期判断同时放在接收与每周期快照接口中。只在串口回调检查会漏掉“完全没有新帧”的情况；生产命令任务回归曾在这一情景下读到旧云台命令，改为每周期取得快照后中立。快照提交与读取均用短临界区，拷贝完恢复原 PRIMASK，不在临界区内发送日志或访问串口。时钟也在临界区内取得，避免先读旧 tick、再取得更晚的样本而误算巨大年龄。外部逐字段 SWD 诊断仍可能跨不同更新，不能与这个控制接口的原子拷贝混为一谈。

撤销时不只清 W 和鼠标，还清 E/F 等边沿历史，否则恢复后可能把旧摩擦轮/装填档位继续使用。恢复必须先两份递增的全松开心跳，再接受新操作。窗口在握手期间见到的按键/按钮只记为“需先释放”，不排队发送；握手结束后系统重复按下事件仍不能使旧 W 生效，需松开再按。回放则先握手再从动作时间零点开始，整体仍限于 180 秒；原版 Z=0 客户端默认不能获得键鼠授权。这些是本项目约定，不称为 DJI 官方心跳协议。

本轮主机 Debug/Release 各 87 项、工具 37 项及六种禁热构建通过。生产模块联合测试证明有效视觉在 PC 失效后仍能接管，撤销视觉且没有来源时前馈和发射清零；模拟参数只属于测试。真实断连的撤销时间要看 `pc_last_advance_tick` 与 `pc_revoke_tick`，并结合撤销原因和原始键位；不能用电脑收到用户回复的时间代替 MCU 到期时间。软件候选 `5d0e696` 已随后上板，完整验证与红绿记录见 [MC02-0049 票据](../workflow/tickets/MC02-0049.md)。

### 部署版本、启动安全与故障保护验收分开记录

本次烧录的 ELF 哈希为 `d018185b101c6b28308b264994d6d2e7532a0ff51c3c9724a5de6f8f338fdc3a`；旧 Z 观测 ELF 继续保留。预检用旧 ELF 解析地址，烧录后的观测改用新 ELF：即使字段名不变，链接后的 RAM 地址也可能改变。仅把 Git HEAD 写进报告却读取旧地址，会把别的变量误当作租约状态。

### 2026-10-10：首次断开 USB 暴露了租约覆盖的范围

真实窗口的失焦保护有了板上证据：按住 W 切出窗口后释放，暂停区间的 670 份快照都为零；重新聚焦没有自动发送，显式开始后才能继续。程序正常退出也清零。随后专门维持 W 并拔 DT7 USB，工具在 WriteFile 报错后停止，却在约 0.384 秒后的板上快照中仍读到 W=1、遥控在线。由此只能确认存在残留，未继续等待测量它的最长持续时间。

本工程 daemon 的约 100ms 租约由完整合法 DBUS 帧续期。电脑断开时，DT7 到 DR16 的无线链路仍在，接收端无法仅凭合法 DBUS 帧判断电脑输入是否过期；工具也无法通过已经断开的 USB 发出全松开。关闭 DT7 后，无线输入停止，实测 101ms 内离线清零并锁存急停。新的电脑输入租约若要解决此问题，就必须把电脑端的新鲜度传递到真正采用输入的接收端；单纯增加 Python 清理代码不能覆盖物理链路已断开的情况。这是租约实现前的失败记录，后续修复实测见下一节，历史证据保留。

本轮裸板全会话有 99693 个 CRC 正确、四元数有限的 SP 状态帧，禁热及寄存器隔离正常；这证明固件运行与状态通信正常，也为发现残留提供了安全测试环境。它不能把 USB 断连子项变为通过。记录中同时保留“烧录回归通过”和“键鼠工具断连验收未通过”，最终板上已离线、输入为零、急停锁存。证据见 [MC02-0049 票据](../workflow/tickets/MC02-0049.md)。

### 2026-10-11：原始输入残留，授权输入已经撤销

租约固件 `5d0e696` 的三轮真实 USB 断开，原始 W/E/F 位图都保持 641，Z 分别冻结为 1024/549/614；但 `pc_authorized` 和控制输入已为零，E/F 边沿也为零，无线仍在线且处于 SAFE。这两份数据分别回答“器件最后发了什么”和“现在允许控制用什么”。诊断应保留原始证据，命令任务必须只使用授权快照，不能因为诊断位图仍有 W 就重新应用它。

撤销时间按 MCU 的 `pc_revoke_tick - pc_last_advance_tick` 计算，三轮为 **154、151、153ms**。150ms 时仍允许，下一次 5ms 命令周期在超过期限时撤销，因此裸板上测到的值在 151–155ms 之间。只读采样本身约百毫秒一次，电脑日志看到清零的时间会更晚；不能拿收到人工回复或最后一份 SWD 快照的时间替代 MCU 的期限。在冻结后的稳定快照中核对 tick、原因和无线在线，才排除了“无线掉线清零”这个不同机制。

工具重连时显式发送全松开/Z=0，再发送全松开/Z=1、2，之后才发送新的 W/E/F。两次重新开工具前边沿都为零，新 E/F 各产生 1 次；旧边沿没有自动恢复。失焦暂停的 253 份稳定观测全零，重新聚焦按 W 没有恢复发送，第二次显式开始才接受新的 E。这是恢复动作的证据，不能把单张 `online=1` 截图当成恢复验收。

### 控制消息快照的 50ms 有效期（R25-11）

输入源“在线”和控制消息“新鲜”是两个条件。一个发布者停止更新后，消息中心仍保留最后一份字节；如果任务只读缓存，旧目标就会持续驱动电机。R25-11 为消息快照附加 `valid`、更新序号和毫秒时间戳，控制接口统一使用 50ms 有效期：年龄恰为 50ms 时仍可用，超过 50ms 后下一次任务周期必须撤销控制。`valid` 与时间戳分开，因此 tick 为零的首帧也能是有效帧；年龄用无符号减法，覆盖计数器回绕。

队列时间必须来自**接收入队时**。如果队列里的老帧在解析时才盖上当前时间，它会被误当成新数据。CAN、UART 和 USB VCP 现在携带入队 tick 派发；UART/VCP 的只读帧只在解析回调期间有效。视觉协议只在长度/帧尾/CRC 都通过后提交数据和接收时间，读路径与发送路径都会检查并清除过期状态。过期的排队事件会丢弃，不重新续期。

`SubGetSnapshot()` 和 `CANCommGetSnapshot()` 在短临界区内把数据与元数据一起复制。它们不消费保留值，也不因读取而续期；同一数值的新发布仍会增加序号并刷新时间。控制应用已经迁移到底盘、云台、发射与命令任务的快照接口。失联时任务把参考值清零并停止执行器；云台姿态反馈过期时，手动接续起点也会清除，恢复后必须从新鲜姿态重新建立。

单发和三连发还要防止通信恢复时重放旧边沿：启动或命令超时后，发射任务要求先收到新鲜的 `LOAD_STOP`，之后才重新接受单发/三连发触发。连续控制则可在新鲜命令到达且 RobotSafety 允许时重新计算。50ms 规则撤销控制，不自行建立全局急停。生产快照、CANComm、队列分发、控制任务及空反馈初始化回归共 99 项 Debug/Release 全过；工具 40 项通过。实际执行器失能行为仍需受控台架确认，主机测试不等于实物测量。代码与完整验证见 [R25-11](../workflow/tickets/R25-11.md)；空的 `shoot_feed` 反馈话题导致 `RobotCMDInit()` 失败的修复见 [MC02-0052](../workflow/tickets/MC02-0052.md)。

E/F 计数在撤销时有意清零，正常退出后的“末值减初值”会等于零，但中途确实各发生一次按下。回归应核对事件窗口和撤销后的零状态；用旧的末值差分验收，会把正确的清理误判为没有收到按键。同理，18 秒回放只有一个短鼠标事件被只读采样捕获，持续实时移动才补足正负 X/Y 的出现证据，仍不据此宣布位移精度。

USB 拔除后，工具三轮都记录写失败且没有继续成功写入，释放仅记为未确认；板上清零由租约完成。最后关闭 DT7，106ms 内无线离线并锁存急停。两段 HIL 合计 300746 个 SP 状态帧 CRC 正确、四元数有限，禁热及输出寄存器隔离正常。MC02-0049 的当前软硬件链路验收已完成，真实执行器接续仍归 R25-06；完整原始日志与离线核验见 [票据](../workflow/tickets/MC02-0049.md)。这些记录不代表学习者已掌握，也不代替供电轨或波形测量。

Git blob 与工作副本也要分清：Windows 工作副本可能是 CRLF，仓库用 `.gitattributes` 将 Python 内容规范为 LF，字节哈希会不同。比较发布代码时用同一种表示，并核对 Git 提交 SHA；本次另外比较了不含说明字符串的 AST，以确认运行逻辑没有改变。详细来源和上传证据见 [MC02-0050](../workflow/tickets/MC02-0050.md)，独立仓库自带 `docs/design.md` 教学与 `docs/firmware-integration.md` 对接说明。

## 为相机和连接等待设定期限

联调主循环必须能在相机停止送帧时继续运行，发送中立控制并响应退出信号。`CameraBase::read_for` 现在是纯虚接口；每个启用的后端都必须实现带期限的读取，不能再默认调用可能永久阻塞的 `read()`。MindVision 通过 `ThreadSafeQueue::pop_for` 等待队列数据，HikRobot 已使用同一限时队列模式。

Windows MVS 桥的 TCP 客户端在连接阶段切换到非阻塞模式，用 `poll` 等待可写，再读取 `SO_ERROR` 确认连接结果。所有已解析地址共用两秒期限，避免 IPv6 和 IPv4 轮流等待各自的系统超时。DNS 解析在这个期限之外；桥接脚本使用 WSL 可达的数值地址，避免依赖慢速主机名解析。

当前 CTest 用本地关闭端口验证连接被拒绝时构造函数快速失败。它没有模拟 SYN 静默丢弃，所以 [VIS25-0015](https://github.com/la-defense/sp_vision_25/blob/85c27907725b58929505de69f05a6235cf217386/TODO.md) 仍未完成。相机超时到中立帧的完整路径也还需要主机故障注入或硬件记录，见 [VIS25-0005](https://github.com/la-defense/sp_vision_25/blob/85c27907725b58929505de69f05a6235cf217386/TODO.md)。

## 收尾发送也属于发送

视觉 HIL 在循环结束时发送一次中立帧；异常退出时，RAII 清理对象也可能发送中立帧。两条路径都使用相同的计数发送函数。正常退出先完成发送并更新摘要计数，再关闭清理对象，避免摘要输出后又悄悄重试一帧。

### 应用停止时为什么还要清参考值（MC02-0123）

发射命令中断后设置 `require_load_stop`，新消息若仍为单发或三发，先改成停止供弹，

## 底盘跟随和四轮限速（R25-07）

底盘跟随率先暴露了 C 语言整数函数的类型问题。`abs()` 接收 `int`，把 `0.5f` 传进去时会先转换为整数 `0`，所以旧表达式算出的角速度是零。浮点数应使用 `fabsf()`：`-1.5f × 0.5f × fabsf(0.5f) = -0.375 deg/s`，角度为 `-0.5°` 时结果方向相反。测试要选小于 1° 的分数角，整数角测试发现不了这个错误。

这条链路里有几种“速度”，单位不能混用：平移输入 `vx/vy` 是 `mm/s`；底盘偏转角 `offset_angle` 是 `deg`；底盘角速度 `wz` 是 `deg/s`；轮子线速度换成电机轴角速度后仍是 `deg/s`，但表示电机转子轴。转换先由轮子线速度除以轮半径得到 `rad/s`，再乘 `180/π` 转为 `deg/s`，最后乘减速比得到电机轴转速。接口和变量名应带上这些单位，避免把 `mm/s` 直接交给电机速度环。

麦轮计算会产生四个电机参考值。程序先找四轮中绝对值最大的转速；超过电机轴上限时，计算共同倍率 `k = 最大允许转速 / 当前最大转速`，再把四轮和输出的 `wz` 都乘以 `k`。这样整体动作变慢，四轮之间仍保持原来的比例和正负方向。float 不能精确保存所有小数，乘法后轮速可能略超上限；程序会把共同倍率调到下一个更小的 float 数，再一起计算，最多计算4次。全部检查通过后才写入输出；四次都没通过时保留零输出。

真实底盘限值没有测定前，配置标志为未就绪、默认限值为零。计算接口会拒绝所有运动并返回零输出；`ChassisTask()` 停止四个电机并清除旧参考值。安全输出不能靠“目前还没有写入限值”推断为零，必须在缺配置分支明确失能。测试里的几何、角速度和转速上限只是模拟数据，不能复制为正式机器人配置。

本轮生产计算测试覆盖分数角、正反方向、旋转、平移和混合运动、单位换算、限幅比例、NaN/Inf、非法几何及极值溢出；任务测试通过实际消息中心检查参考值写入、使能顺序和失效清零。WSL Debug/Release 各 90/90，六种禁热固件和 ELF 隔离检查通过。代码在[底盘计算](../../application/chassis/chassis_motion.c)与[底盘任务](../../application/chassis/chassis.c)，完整证据见 [R25-07 票据](../workflow/tickets/R25-07.md)。真实轮型、尺寸、限值和台架轮速核对留给 APP-10。

## 裁判在线不等于每组数据都新鲜（MC02-0094）

裁判串口整体在线只看最近一条合法命令，300ms用于链路诊断。某一条命令有自己独立的接收时间和期限：10Hz组默认300ms，3Hz组1000ms，1Hz组3000ms，小地图最近内容3000ms。其他命令即使不断到达，也不能替停止更新的那一组续期。

`RefereeGetSnapshot()`一次复制所有命令和元信息。读者按每项的 `state` 判断能否把数值当作当前数据：`UNSEEN`表示从未收过，`FRESH`表示仍在期限内，`EXPIRED`表示只保留旧数值供诊断。比赛结果、伤害、射击及交互帧是最近事件记录；其状态只说明何时最后收到，不表示事件仍能执行。0x0303在一次点击后会被裁判系统重复发送，重复包可刷新最近记录，但接收层不生成新的点击事件或动作。

快照来源时间取组成帧的首个UART块通知时刻，0毫秒是合法值。该时间表示本机接收事件，不是裁判服务器的生成时刻，也不是客户端用户操作时刻。跨块超过50ms、队列连续性中断、长度不符、CRC失败或有效字段为NaN/Inf时，解析器不替旧数据刷新期限。

LCD从同一份副本逐组显示；未接收或过期的项目显示`--`。组合值必须检查其每个依赖组。0x0202的前8字节是保留字段，不能把其中的浮点位形当成“实际功率”；最近弹速也应标为射击记录而不是当前持续状态。裁判UI另行绑定状态并在每次发送前检查0x0201身份的新鲜度，UI失败不会关闭接收。

验证入口是[生产快照测试](../../tests/host/referee_snapshot_test.c)、[UI测试](../../tests/host/referee_ui_test.c)和[LCD逐组显示测试](../../tests/host/lcd_referee_rows_test.c)。详情、官方PDF页码及边界见[MC02-0094任务记录](../workflow/tickets/MC02-0094.md)。本机测试不证明裁判实际串口、客户端显示或真实链路延迟。

## 来源期限与状态事件由所属任务处理（MC02-0071）

来源监控使用 HAL 毫秒时钟保存接收时间，不再把 Daemon 被调用了几次当成超时依据。`DaemonReportAt()` 接收组成数据的原始 RxEvent 时间；即使接收队列延迟派发，也不会把旧数据伪装成刚到达。0毫秒是有效时刻，比较使用无符号时差，因此一次 `uint32_t` 回绕仍能判断短时间间隔。时间恰好等于期限时仍有效，超过才过期。

通信在线和数据有效是两件事。协议帧通过 CRC、长度等检查后可以刷新通信时间；某个关键字段未通过语义检查时，可报告通信在线、数据无效。数据期限单独计算，其他帧或状态查询都不能替它续期。首帧宽限期间显示等待首帧，宽限结束后才转为离线。

`DaemonTask()` 只检测状态变化并放入每来源固定队列，不直接执行电机、遥控或通信恢复。每个来源可选保序 FIFO、同来源计数合并或最新状态合并，容量和事件期限单独配置；队列溢出、事件过期和处理次数都能通过复制状态查询。MotorTask 与 RobotCMDTask 只消费分配给自己的事件。独立模式使用固定的1ms任务轮询，每轮最多处理8条；任务创建失败可读取状态并重试。回调应短小，设备恢复步骤由来源模块负责。

来源在启动阶段串行注册。监控或事件消费开始后不允许注销实例，避免队列处理期间释放仍在使用的对象。实现和测试见 [daemon.c](../../modules/daemon/daemon.c)、[daemon_event_task.c](../../modules/daemon/daemon_event_task.c) 与[生产测试](../../tests/host/daemon_source_monitor_test.c)。WSL Debug／Release 各413/413、专项 ASan／UBSan 11/11，六种禁热 ARM 固件、ELF 隔离和 CMake 增量检查通过。板子保持 USB-only，因此这些结果证明软件接口和构建行为，不代表真实通信或设备恢复已经实测。完整证据见 [MC02-0071](../workflow/tickets/MC02-0071.md)。

## safety 快照驱动的灯声告警（MC02-0084）

告警输出属于诊断辅助，不拥有安全状态。`RobotAlarmTask()` 每轮从 `RobotSafetyGetSnapshot()` 取得同一时刻的运行状态、故障位和急停锁存，再由纯策略模块选择最高优先级事件。存在多个故障时只持续表达优先级最高的一项；最高项清除后，下一项在下一轮自动接替。没有故障时才显示车型配置的 STOP／INIT／SAFE／CALIB／READY 等状态图案。

告警节奏使用 HAL 毫秒计时，时间差按无符号减法计算，因此支持计数从 `UINT32_MAX` 回绕到0。灯效可使用常亮、闪烁、呼吸和有上限的分段；蜂鸣器段单独循环，但与灯光共用本次告警的起点。新事件会撤销静音并从新起点计算，避免上一事件的音符或节奏延续。

静音请求有两个检查：车型位图必须允许当前故障等级，时长必须在1毫秒到车型上限之间。请求只排队给 Daemon 处理；若故障在处理前已经变化，旧请求会被拒绝。静音到期后恢复同一告警的声音，不清除故障，不改变灯光或运行许可。`RobotAlarmGetState()` 仅复制最近事件、通道可用性、失败计数和静音结果，不推进节奏。

LED／蜂鸣器初始化失败、输出忙或运行错误只记入辅助通道状态。WS2812 当前仍通过阻塞 SPI 发送，HAL 超时参数为2毫秒；发送前申请时基保护，时基不可用时不进入发送。调度会影响实际耗时；告警模式在 Daemon 任务中按时间推进，异步传输仍未完成，也不能据此证明灯珠物理波形。WSL 测试核对策略、驱动编码和失败隔离，ARM 构建核对固件接入；MC02-0025 仍负责实际单灯波形验收。详细证据见 [MC02-0084 票据](../workflow/tickets/MC02-0084.md) 和 [蜂鸣器模块说明](../../modules/alarm/buzzer.md)。
