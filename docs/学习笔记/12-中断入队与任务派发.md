# 12 中断入队 + 任务派发：CAN 接收链路是怎么改的（写给零基础）

> 本篇回答的问题：
> 1. "中断上下文"和"任务上下文"到底差在哪？为什么有些事不能在中断里做？
> 2. 接收数据时，为什么不能"只把最新一帧丢给任务去处理"？
> 3. 环形队列（SPSC）怎么写才安全？`head`/`tail` 各归谁管？为什么要内存屏障？
> 4. 没有示波器、没有真实电机，怎么验证这条链路是对的？
>
> 对应代码：`bsp/can/bsp_can.c` 的 `CANRxQueuePush()` / `CANProcessRx()`、
> `modules/motor/DJImotor/dji_motor.c` 的注入自测、`motor_task.c` 的消费点。

---

## 1. 为什么要把事情从中断里搬出来

中断服务函数（ISR）是**插队执行的代码**：它一跑，被它打断的那个任务就停在那里，
而所有优先级不高于它的中断也都得等着（同优先级不能互相抢占）。

所以 ISR 里有两条铁律：

| 铁律 | 原因 |
|---|---|
| **要短** | ISR 占用的时间会直接推迟其它中断的响应（中断延迟） |
| **不能阻塞** | ISR 里不能等锁、不能等 DMA、不能睡（没有"任务"可以让出） |

那"短"是多短？对 1kHz 的控制系统来说，**几微秒**是合理的量级。
一旦某个 ISR 动辄几十微秒、还每秒进一万次，它就会悄悄吃掉 10%~30% 的 CPU，
并且让别的中断抖动。

**本工程改造前**，CAN 接收中断里做的事包括：查表找实例、把数据拷进实例缓冲、
然后**直接调用模块回调做解析**——对 DJI 电机来说就是：喂守护进程、取 dt、
解析四个字段、跑两路浮点低通滤波、再做多圈角度累加。

这一串加起来每个帧几微秒，而 12 个电机在 1kHz 反馈下是**每秒 1.2 万帧**。

## 2. 关键约束：有些状态"必须逐帧按顺序"处理

改造最容易想到的做法是：**中断里只把数据存一份，任务来了拿最新的算**。

但这在本工程行不通，因为解码里有**跨帧状态**：

```c
    /* 低通滤波: 新值依赖上一帧的值 */
    measure->speed_aps = (1 - k) * measure->speed_aps + k * new_raw;

    /* 多圈累加: 新角度依赖上一帧的角度 */
    if (measure->ecd - measure->last_ecd > 4096)
        measure->total_round--;
    else if (measure->ecd - measure->last_ecd < -4096)
        measure->total_round++;
    measure->total_angle = measure->total_round * 360 + ecd * 360 / 8192;
```

如果任务只处理"最新一帧"，那么两帧之间的那几帧就**从来没被处理过**：

- 滤波少更新几次——影响小；
- **多圈累加跳过了几帧**——如果跳过的角度超过半圈（4096/8192 对应 180°），
  `total_round` 就会**算错**，而且错一次之后就永远偏一圈。

所以结论是：**要么在中断里逐帧处理，要么用一个能保住顺序的队列。**

本工程选了后者。

## 3. 环形队列（SPSC）怎么写才安全

"SPSC" = Single Producer, Single Consumer（单生产者、单消费者）。
这是并发里最简单、也最好写对的一种模型：

```
   中断(生产者)                     任务(消费者)
        |                                |
        v                                v
  写 rxq[head] → 推进 head        读 rxq[tail] → 推进 tail
```

两条规则保证它不需要加锁：

1. **`head` 只有生产者写、消费者只读；`tail` 只有消费者写、生产者只读**；
2. **先写数据，再发布索引**（否则消费者可能看到"索引更新了但数据还没写完"）。

第二条就是**内存屏障**的作用：

```c
    /* 生产者: 先把数据写进槽位 */
    it->instance = ins;
    it->len = len;
    memcpy(it->data, data, len);

    __DMB();                 /* 保证上面的写, 在下面这句之前对别的核/总线可见 */
    bus->rxq_head = next;    /* 发布: 消费者看到 head 变了, 数据一定已经就绪 */
```

消费者反过来——**先把数据取完，再推进 `tail`**：

```c
    CANRxItem_t *it = &bus->rxq[bus->rxq_tail];
    ... 取出 instance/len/data 并处理 ...
    __DMB();
    bus->rxq_tail = (bus->rxq_tail + 1) % DEPTH;   /* 这时生产者才能复用这个槽 */
```

**判空/判满**（长度为 N 的环，浪费一个槽位是常规做法）：

```
空: head == tail
满: (head + 1) % N == tail
```

### 队列满的时候丢谁？

两种语义：

| 策略 | 含义 | 适合场景 |
|---|---|---|
| **丢新帧** | 队列里保留的是"较旧但顺序完整"的帧 | 本工程选它：实现最简单、无竞争；队列满本身就说明消费不及时 |
| 覆盖最旧 | 保证消费者总能拿到最新数据 | 控制类数据；但生产者要动 `tail`，和消费者抢 |

本工程选了**丢新帧 + 计数**（`rxq_drop`）。理由：32 帧 ≈ 32ms 的缓冲，
真出现满说明任务已经被阻塞了 32ms，这时候丢哪个都一样，重要的是**计数告警**而不是
"更聪明地丢"。

### 队列深度怎么估

```
深度 ≈ 平均消费间隔内到达的帧数 × 安全系数
     = (任务周期 1ms × 12 个电机 × 1kHz) × 2~3
     ≈ 12 × 2.5 ≈ 30  → 取 32
```

再加上一个**历史峰值观测**（`rxq_peak`），实测峰值只有 8/32，说明深度足够。
（这个观测很重要：改成"接车后 5 个电机分摊到 CAN3"之类的配置时，可以立刻看出够不够。）

## 4. 消费者放在哪：两个细节决定成败

### 4.1 必须在"算控制之前"消费

```c
void MotorControlTask(void)
{
    CANProcessRx();      /* 先把本周期到达的帧全部解析完 */
    DJIMotorControl();   /* 再用最新值算 PID */
}
```

顺序反过来的话，本周期到达的反馈要等下一周期才被解析 —— 白白多 1ms 延迟。
按上面这个顺序，**端到端延迟和"在中断里直接解析"完全相同**，但 ISR 短了、
数据竞争也没了。

### 4.2 只能有一个消费者

SPSC 的前提就是"单消费者"。一旦有两个任务都调用 `CANProcessRx()`：

- 两个任务同时读同一个 `tail` → 同一帧被处理两次；
- 或者各自推进 `tail` → 中间的帧被跳过。

本工程实际就遇到这个坑：**启动期的自测跑在 daemon 任务里**，
而那时 motor 任务已经在跑了。解决办法是用一个原子的 test-and-set 挡住第二个调用者：

```c
    static volatile uint8_t processing = 0;
    uint32_t primask = __get_PRIMASK();
    __disable_irq();
    if (processing) { __set_PRIMASK(primask); return; }   /* 别人正在处理, 本轮跳过 */
    processing = 1u;
    __set_PRIMASK(primask);
    ... 处理 ...
    processing = 0u;
```

被挡下的那一方**直接返回是安全的**：队列里的帧不会丢，另一个消费者会把它们处理掉。

> 注意这里为什么要关中断：`if (processing) ... processing = 1;` 这两步必须原子，
> 否则两个任务可能都读到 0 然后都进入临界区。

## 5. 没有电机怎么验证？——回环 + 假帧注入

这条链路一旦写错（比如队列下标算错、滤镜没配好），在没有电机的台面上是**看不出来**的。
所以本工程做了一个"自己给自己发假数据"的自测：

FDCAN 有一种 **内部回环模式（Internal Loopback）**：发出去的帧不出芯片，
但会像正常接收一样经过"滤镜匹配 → 写入 RX FIFO → 触发接收中断"。

于是可以：

1. 把总线切到内部回环；
2. 注册一个**只发不收**的临时实例，它的 `tx_id` 设成**目标电机的 `rx_id`**（比如 `0x201`）；
3. 往 `tx_buff` 里按 DJI 反馈格式填伪造数据（ECD、转速、电流、温度），发出去；
4. 环回来的帧命中目标电机的滤镜 → 走它**正常的那条解码路径**；
5. 消费队列后检查 `measure` 里的值对不对。

这样连"多圈累加"都能验证：连续发几帧让 ECD 跨过 `8191→0` 边界，
检查 `total_round` 是不是正确地 ±1。

**实测踩的坑**（很值得记）：切换总线模式用的 `CANForceMode()` 内部会调
`HAL_FDCAN_Init()`，而它会**重新配置整块消息 RAM，把各实例之前注册的接收滤镜全清掉**。
所以切完回环必须补一次"重装滤镜"，否则注入的帧根本没人接——现象是
"发送成功、但一帧都收不到"。

## 6. 顺带改掉的两个小问题

1. **ISR 里的日志**：接收中断原本会在 FIFO 溢出时调限速日志（要写 RTT，
   是几十微秒级的操作）。现在中断里**只累加计数**，打印挪到 10Hz 的任务里做。
   原则：**中断里只做"记账"，不做"输出"。**
2. **发送前的饱和**：`set = (int16_t)pid_ref;` 这种直接强转，在 `pid_ref` 超出
   `int16` 量程时会**回绕**成反方向的大值（例如 30000 → -25536）。
   必须先 `LIMIT` 到有效量程（DJI 电流指令是 ±16384）再截断，并计数告警。

## 7. 速查表

| 问题 | 判断/做法 |
|---|---|
| ISR 里能不能做浮点运算/滤波？ | 能，但要想清楚"每秒多少次 × 每次多少微秒"；超过几个微秒就该搬走 |
| ISR 里能不能写日志？ | 不能（写 RTT 是长耗时操作）；改成计数 + 任务里打印 |
| 能不能"只把最新一帧给任务"？ | 有跨帧状态（滤波、积分、多圈）时**不行**，会丢顺序 |
| 环形队列深度怎么定？ | 任务周期内到达帧数 × 2~3，并加"历史峰值"观测来复核 |
| 队列满丢谁？ | 简单可靠选"丢新帧 + 计数"；要保最新才考虑覆盖最旧 |
| 消费者放哪？ | 放在"用数据之前"，且**全工程只有一个** |
| 有多个消费者怎么办？ | 用原子 test-and-set 互斥，被挡方直接返回（不是丢数据） |
| 没硬件怎么验证接收链路？ | FDCAN 内部回环 + 注入假帧，走正常滤镜和回调 |
