## 0. 先看结论：日志实现的演进

| 场景 | LOG-02 时的修补（历史） | 当前 MC02-0066 |
|---|---|---|
| 生产者接口 | 固定格式串的`LOGINFO`等可变参数宏 | 固定目录的`BSP_LOG_EVENT_*`类型化提交 |

## 1. 一条日志的完整链路（六段）

你在代码里写的其实只是一行宏调用：

```c
LOGINFO("[dji_motor] motor id=%lu online", (unsigned long)id);
```

它到出现在你屏幕上，要经过六段：

```
 ① 宏展开（编译期）
    LOGINFO(...) → LOG_PROTO("I:", 绿色, "...", ...)
    → do { ... snprintf(...); SEGGER_RTT_WriteString(...); } while (0)
        ↓
 ② 格式化（CPU 干活）
    snprintf 把格式串 + 参数拼成一串字符："  \x1B[1;32mI:[dji_motor] motor id=3 online\r\n\x1B[0m"
      ↑ 这一段由 newlib 的 snprintf 完成，结果放在"栈上的缓冲区"里
        ↓
 ③ 写 RTT 上行环形缓冲（还是 CPU 干活，但只做内存拷贝）
    SEGGER_RTT_WriteString() → 把上面那串字符 memcpy 进 RAM 里的 1KB 环形缓冲
      ↑ 到这里，目标板的工作就结束了：它把日志"写在内存里"，然后该干嘛干嘛
        ↓
 ④ 调试器经 SWD 读内存（硬件搬运）
    DAPLink/J-Link 每隔几毫秒在后台读一次 RTT 控制块，把缓冲里的新数据搬走
      ↑ 这一步不占 CPU：用的是调试器的读写内存通道（SWD），不是 CPU 指令
        ↓
 ⑤ 上位机（OpenOCD 原生 RTT 服务 / 只接收客户端）
    把读到的字节流转成"日志行"，可选做颜色解码、时间戳、存文件
        ↓
 ⑥ 显示
    VSCode 任务“RTT receive only (OpenOCD native)”输出 / 可选原始日志文件
```

**为什么说"不占串口、不占引脚"**：从 ③ 开始，数据走的是
「RAM → SWD 调试口（本来就要接的那两根线）→ 电脑」，全程没有 UART TX 引脚参与，
也不需要在板子上再留一路串口。代价是**必须连着调试器**（见 2.4）。

## 2. SEGGER RTT 是什么

### 2.1 原理：RAM 环形缓冲 + 控制块

RTT = **Real Time Transfer**，SEGGER 给"目标板往电脑打日志"设计的一套机制。它的全部秘密就是
**一块放在 RAM 里的缓冲区**：

```
目标板 RAM 里：
 ┌─────────────────────────── _SEGGER_RTT（控制块，有固定签名 "SEGGER RTT"） ─┐
 │ 上行缓冲 0: 地址=0x2400xxxx  大小=1024  WrOff=374  RdOff=374  Flags=...  │
 │ 上行缓冲 1: ... (未使用)                                                  │
 └──────────────────────────────────────────────────────────────────────────┘
                   ↑ 目标板只往这里写（memcpy），电脑只从这里读
```

- 目标板侧（我们）：`SEGGER_RTT_WriteString()` → `memcpy` 到 `WrOff` 后面 → 推进 `WrOff`。
  **只动内存**，不发中断、不查外设状态、不等待。
- 电脑侧（调试器）：周期性（几十 µs ~ 几 ms）通过 SWD 读 `RdOff`/`WrOff`，
  把两者之间的新数据搬走，然后回写 `RdOff`。
- 两边各动一个游标，互不阻塞 —— 这就是它比"串口 printf 阻塞在波特率上"快得多的原因。

本工程的实际配置（`Middlewares/Third_Party/SEGGER/Config/SEGGER_RTT_Conf.h`）：

| 配置 | 值 | 含义 |
|---|---|---|
| `BUFFER_SIZE_UP` | 1024 | 上行（板子→电脑）缓冲 1KB |
| `BUFFER_SIZE_DOWN` | 16 | 下行（电脑→板子）缓冲，本工程不用 |
| `SEGGER_RTT_MODE_DEFAULT` | `NO_BLOCK_SKIP` | 缓冲满时**直接丢弃新数据**，绝不阻塞 |
| `SEGGER_RTT_LOCK()` | `BASEPRI = 0x20` | 写缓冲期间**关中断**（见 2.3） |

`NO_BLOCK_SKIP` 很关键：日志是"尽力而为"的东西，**绝不能因为它把控制任务拖住**。
缓冲满了就丢 —— 这也是为什么热路径日志要限速（每秒上千条会把 1KB 缓冲刷爆，
连占用率汇总行都会被挤掉，这个坑本工程踩过）。

### 2.2 三个必记的代价

1. **必须连着调试器**：RTT 靠调试器搬运，拔了调试器日志就没人读了（数据在缓冲里绕圈然后被丢）。
2. **内容在 RAM，复位即丢**：所以崩溃现场要"存到 `.noinit` 或 Flash"才能跨复位（见《13》）。
3. **它和"串口日志"是两条路**：本工程的 VCP（USB 虚拟串口）是给视觉/上位机通信用业务的，
   不要把日志塞进去抢带宽。

### 2.3 一次 `WriteString` 是"原子"的（这条决定了本轮的写法）

`SEGGER_RTT_Write()` 的第一件事是 `SEGGER_RTT_LOCK()`：把 `BASEPRI` 抬到 `0x20`，
于是**所有优先级数字 ≥ 0x20 的中断都被挡住**——包括 SysTick 和 PendSV，
也就是**连任务切换都被挡住**。等这次 `memcpy` 进缓冲结束，`SEGGER_RTT_UNLOCK()` 再放开。

所以：

- **一次 `SEGGER_RTT_WriteString()` 写出去的内容是连续的**，不会被别的任务插队；
- 但如果一条日志分**两次** `WriteString`（例如"正文一次、换行一次"），
  两次之间就可能被其它任务的一条日志插进来 → 屏幕上看到两行日志**互相穿插**。

这就是本轮把「正文 + `\r\n` + 复位色码」拼在**同一个缓冲区**里、只调用一次
`SEGGER_RTT_WriteString()` 的原因（见第 5、6 节）。

### 2.4 和"串口 printf"对比

| | 串口 printf | SEGGER RTT |
|---|---|---|
| 占用硬件 | 一个 UART + 一个引脚 | 不占（借调试口 SWD） |
| 目标板开销 | 要等波特率（115200bps 下 1 字节约 87µs，一行 80 字节 ≈ 7ms！） | 一次 `memcpy`，几微秒 |
| 是否需要中断/DMA | 裸写会阻塞；想不阻塞就得配 DMA + 队列 | 不需要，`memcpy` 完就返回 |
| 前提 | 只要有线就行 | **必须连着调试器** |
| 掉电/复位 | 数据已经从引脚出去了 | RAM 里的内容丢失 |

> 那为什么还要给上位机留 VCP？因为业务数据（视觉帧、裁判帧）要求"真的一条链路 + 不用调试器"。
> 日志是给人看的，业务数据是给程序用的 —— 两者要求不同，所以分成两条路。

## 3. newlib 是什么，它在我们工程里干了什么（重点）

### 3.1 一句话定义

**newlib 是面向嵌入式（裸机）的 C 标准库实现**，GCC 的 `arm-none-eabi-` 工具链默认带的就是它。
你写的 `#include <stdio.h>`、`printf`、`snprintf`、`memcpy`、`memset`、`malloc`、`sinf`……
这些函数的**代码实体**都在 newlib 里。

那 glibc（Linux 的 C 库）为什么不能用？

| | glibc | newlib |
|---|---|---|
| 面向 | 有操作系统的桌面/服务器 | **没有操作系统的裸机** |
| 体积 | 几 MB | 几十~几百 KB，可裁剪（nano 版更小） |
| 依赖 | 大量 Linux 系统调用（`open`/`write`/`mmap`…） | 只依赖**你自己实现**的十几个小函数 |

### 3.2 根本矛盾：`printf` 要"文件"，`malloc` 要"操作系统"

标准 C 规定 `printf` 是"往 `stdout` 这个**文件**写"，
`malloc` 是"向**系统**申请内存"。可裸机上：既没有文件系统，也没有操作系统。

newlib 的解法叫 **"库只实现算法，底层留成弱符号桩（stub）"**：

- newlib 把 `printf` 的**格式解析、数字转字符串**这些真正的算法都实现了；
- 但它需要"把字节送出去"的那一步，只**声明**成一个外部函数 `_write(...)`（弱符号）；
- 谁来提供 `_write`？**你的工程**。

于是就有了工程里这两个文件：

| 文件 | 里面实现的东西 | 作用 |
|---|---|---|
| `Core/Src/syscalls.c` | `_write` / `_read` / `_close` / `_lseek` / `_fstat` / `_isatty` / `_sbrk` / `_kill` … | **系统调用桩**：`_write` 决定"printf 的字节往哪去"，`_isatty` 决定"是不是终端"，等等 |
| `Core/Src/sysmem.c` | `_sbrk()` | **堆的增长函数**：`malloc` 每次要内存都调用它，它负责把"堆指针"往上推 |

```c
/* Core/Src/sysmem.c 的核心：把堆指针往高地址推一点，交给 malloc 用 */
void *_sbrk(ptrdiff_t incr) {
    void *prev = _end;      /* 堆的起点（链接脚本给的符号） */
    ...
    _end += incr;
    return prev;
}
```

所以"能不能用 `printf` 打日志"取决于 **你在 `_write` 里写了什么**：

- 写成"往 UART 发" → 日志走串口；
- 写成"什么都不做，返回长度" → `printf` 正常返回但没输出；
- 本工程：日志**根本不走 newlib 的 `stdio` 输出通道**，而是自己 `snprintf` 到缓冲区，
  再交给 SEGGER RTT —— 也就是说，`_write` 在这里并不是日志的必经之路。
  （它仍然要存在，否则链接器会因为找不到 `_write` 而报错。）

### 3.3 newlib 和 newlib-nano：为什么要那个"瘦身版"

CMake 里链接参数是 `-specs=nano.specs`。`nano.specs` 是一个**告诉 GCC 换一套库**的配置文件，
它的实际内容（`.../arm-none-eabi/lib/nano.specs`）是：

```
%rename link                nano_link
%rename link_gcc_c_sequence                nano_link_gcc_c_sequence
%rename cpp_unique_options  nano_cpp_unique_options

*cpp_unique_options:
-isystem =/include/newlib-nano %(nano_cpp_unique_options)   ← 头文件也换成 nano 那套

*nano_libc:
-lc_nano                                                     ← 库由 -lc 变成 -lc_nano

*link_gcc_c_sequence:
%(nano_link_gcc_c_sequence) --start-group %G %(nano_libc) %(nano_libgloss) --end-group

*link:
%(nano_link) %:replace-outfile(-lc -lc_nano) %:replace-outfile(-lg -lg_nano) ...
```

翻译成人话：**`-specs=nano.specs` 的效果就是"凡是要链接 libc/libg 的地方，都换成 `libc_nano.a` / `libg_nano.a`，
顺便把头文件搜索路径也切到 `newlib-nano`"**。nano 版把格式化、`scanf`、locale 等实现换成更小的版本，
代价是功能少一点（最关键的就是：**浮点格式化默认没链进来**，见 3.4）。

本工程还踩过一个相关的坑，写在 CMakeLists 注释里：

> **不要加 `-lnosys` / `-specs=nosys.specs`**：
> `syscalls.c` 与 `sysmem.c` 已经实现了 `_exit`/`_sbrk` 等，再链 `libnosys.a` 会
> 产生 **multiple definition（重复定义）** 链接错误。
>
> `libnosys` 就是"别人帮你写好的、什么都不做的空桩库"。我们既然自己写了桩，就不需要它。

### 3.4 `-u _printf_float`：为什么加了它，`%f` 才真的能用

newlib-nano 把浮点格式化单独编译成一个目标文件（`libc_a-nano-vfprintf_float.o`），
里面是 `_printf_float()`。而 `snprintf` 的实现（`_svfprintf_r`）对它只是**弱引用**：

```armasm
; 反汇编 libc_nano.a(libc_a-nano-svfprintf.o) 里的 _svfprintf_r（节选）
1b4:  bl  _printf_float        ; ← 弱引用
```

如果没有任何东西引用 `_printf_float`，归档文件（`.a`）里那个成员**就不会被拉进最终镜像**，
于是链接器把这个调用**直接改写成一条空指令**。本工程改造前的最终 ELF 里就是这样：

```armasm
; 反汇编 build/Basic_Framework_MC02.elf 里 _svfprintf_r 的同一处（节选）
80216a8:  nop.w                ; ← bl _printf_float 被换成了 NOP
80216ac:  adds r2, r0, #1
80216ae:  bne.n 8021660        ; 继续循环（r0 是 _reent 指针, 非 0 → 当"成功"处理）
```

也就是说，**不加 `-u _printf_float` 时，`%f` 既不打印、也不消费参数**
（真正的 `va_arg(double)` 在 `_printf_float` 内部，而它根本没被链进来）。
这与 SEGGER 精简 printf 的行为一模一样 —— 所以单靠"换成 `snprintf`"并不能解决 `%f` 错位问题。

`_printf_float()` 里确实做了参数消费（反汇编 `libc_a-nano-vfprintf_float.o`）：

```armasm
24:  ldr.w r3, [r8]       ; r8 = va_list 指针
30:  adds  r3, #7
32:  bic.w r3, r3, #7     ; 8 字节对齐
36:  vldmia r3!, {d0}     ; 取出 double
4a:  str.w r3, [r8]       ; 推进 va_list —— 参数被消费掉了
```

所以在 CMake 里显式加上：

```cmake
-u _printf_float
```

`-u symbol` 是链接器的意思"**把这个符号当作未定义引用，强制从库里拉进来**"。
加上之后，`%f/%e/%g` 才是"正常消费 + 正常打印"。

**实测代价**（同一份代码、Debug/-Og，只差这一个开关）：

| | 不加 `-u _printf_float` | 加（本工程默认） |
|---|---|---|
| FLASH | 162624 B | **172816 B**（+10192 B ≈ 10KB） |
| RAM | 105912 B | 106328 B（+416 B） |

10KB Flash 换"`%f` 从"会错位"变成"能用"，在 768KB Flash 里只占 1.3%，很划算。
嫌大可以在 CMake 里 `-DENABLE_PRINTF_FLOAT=OFF` 关掉 —— 但那样又回到"日志里绝对不能写 `%f`"。

### 3.5 本工程到底用了多少 newlib（统计）

（只统计 `bsp/ modules/ application/ Core/Src` 下的源码，`\b名字(` 出现次数）

| 函数 | 次数 | 用在哪 |

## 4. 格式化与 printf：为什么要"先格式化再输出"

### 4.1 可变参数的"盲取"机制

`printf` 家族是**可变参数函数**：调用者把参数一股脑放好（前 4 个在 `r0~r3`，
其余在栈上），函数**并不知道**你传了什么、传了几个 —— 它只能**按格式串的指示去取**。
`va_arg(args, T)` 的语义是"把下一个参数按类型 `T` 取出来，游标往后挪 `sizeof(T)`"。

铁律：**谁取参数，谁就必须认识这个格式符**。
（详细版：`%f` 会先被提升成 `double`、占 2 个 32 位槽，见《10-可变参数与格式串安全》。）

### 4.2 `snprintf` 为什么不会错位

`snprintf` 是**标准 C 库函数**，它认识全部标准格式符。只要格式符本身合法，
它就一定**按标准规则消费参数**（`%d` 取 `int`、`%s` 取 `char*`、`%f` 取 `double`）。

于是"参数错位"这件事被压缩成了一个**非常小的面**：

> 只有"格式符本身写得不标准（比如 `%q`）"或"**库没实现这个格式符**（本工程的 `%f` 曾属于这种）"
> 才可能出问题。

而本轮做的三件事把这个面彻底堵上：

1. **用户格式串后面不再有任何格式符** —— 我们自己的 `%s`（复位色码）改成格式化之后用 `memcpy` 拼上去。
   这一条才是 `LOG-01` 那类崩溃的结构性根因：**错不在 `%f`，错在"我们自己追加了一个 `%s`"**。
2. **`-u _printf_float`** —— `%f` 从"库不支持"变成"库支持"，参数会被正常消费。
3. **编译期检查** —— `snprintf` 的格式串是标准函数的标准参数，宏展开后它又是一个**字符串字面量**，
   所以 GCC 的 `-Wall` 里的 `-Wformat` **真的会检查每个日志调用点**。

### 4.3 第 3 条的实战价值：这一轮直接查出 3 个真 bug

改造前是 `SEGGER_RTT_printf(...)` —— GCC 不认识这个函数，**完全不做格式检查**，
所以下面这些错误在工程里躺了很久：

| 位置 | 原来写的 | 问题 | 现在 |
|---|---|---|---|
| `modules/can_comm/can_comm.c:77` | `LOGWARNING("...rx[%d]...", &comm->can_ins->rx_id)` | 把**指针**当 `%d` 打印，日志里永远是个像随机数的地址 | `%lu` + 真值 |

## 5. 缓冲为什么要放在栈上

### 5.1 为什么"必须有缓冲"

`snprintf` 是"生成字符串"的函数：它**必须先有一个地方把字写完**，再让调用者整体使用。
所以日志宏无论如何都要有一块 `char buf[N]`。

### 5.2 三种放法的取舍

| 放法 | 好处 | 坏处 | 本工程 |
|---|---|---|---|
| **栈上**（局部变量） | 每个调用点天然独立；**不需要任何锁**；用完自动回收 | 占栈空间（N 字节 × 调用链深度） | ✅ 采用 |
| 全局静态 + 关中断 | 省栈 | 多任务/中断同时打日志会互相覆盖，必须关中断几十微秒 —— 对 1kHz 控制任务不可接受 | ✗ |
| 全局静态 + 环形队列 | 不丢日志 | 要管理队列、要锁、更复杂 | ✗（日志不需要这么强的保证） |

关键判断：日志是**低频、可丢**的东西，**不值得为它引入锁**。

### 5.3 `do { } while (0)` 的两个作用

```c
#define LOG_PROTO(type, color, format, ...)   \
        do {                                  \
            char _log_buf[LOG_BUF_SIZE];      \
            ...                               \
        } while (0)
```

1. **能当"一条语句"用**：写 `if (x) LOGINFO(...); else ...` 时不会因为宏里有分号而语法错乱；
2. **作用域独立**：`_log_buf` 是块内变量 —— 同一个函数里写 10 条日志，
   编译器会让它们**复用同一块栈空间**（同一时刻只有一条日志活着），不会叠加成 10×256 字节。

### 5.4 代价：任务栈要留够余量

缓冲区大小按"本工程最长的一行"定：**256 字节**（最长的 `[seg]` 行最坏约 230 字节；
再给 `"\r\n" + 复位色码` 留 8 字节 → 正文可用 248）。

于是**每个日志调用点会临时占 256 字节栈**。原来 daemon 任务的栈只有 128 words（=512 字节），
而它恰恰是打日志最多的任务（限速告警、CAN/串口统计），所以这一轮把它加到了 **256 words（1024 字节）**，
代价是多占 512 字节 FreeRTOS 堆。

> 想自己核对：`configCHECK_FOR_STACK_OVERFLOW = 2` 已经打开，
> 一旦哪个任务被顶爆，`vApplicationStackOverflowHook()` 会把任务名记进崩溃现场（见《13》）。

## 6. 这次改了什么（逐条对照代码）

### 6.1 日志宏：`bsp/log/bsp_log.h`

```c
#define LOG_BUF_SIZE 256u /* 整行日志缓冲(放在栈上) */
#define LOG_BODY_TAIL 8u  /* 给结尾的 "\r\n" + 复位色码预留的位置 */

_Static_assert(sizeof("\r\n" RTT_CTRL_RESET) <= LOG_BODY_TAIL,
               "LOG_BODY_TAIL 放不下结尾的换行+复位色码");

#define LOG_PROTO(type, color, format, ...)                             \
        do {                                                            \
            char _log_buf[LOG_BUF_SIZE];                                \
            int _log_n = snprintf(_log_buf,                             \
                                  LOG_BUF_SIZE - LOG_BODY_TAIL,         \
                                  "  %s%s" format,                      \
                                  color, type, ##__VA_ARGS__);          \
            if (_log_n < 0)                                             \
                _log_n = 0;                                             \
            else if ((unsigned)_log_n > LOG_BUF_SIZE - LOG_BODY_TAIL - 1u) \
                _log_n = LOG_BUF_SIZE - LOG_BODY_TAIL - 1u;             \
            memcpy(_log_buf + _log_n, "\r\n" RTT_CTRL_RESET,            \
                   sizeof("\r\n" RTT_CTRL_RESET));                      \
            SEGGER_RTT_WriteString(BUFFER_INDEX, _log_buf);             \
        } while (0)
```

逐点解释：

- `snprintf` 只负责"颜色 + 等级 + 用户正文"，**结尾不再有格式符**；
- `_log_n` 是 `snprintf` 的返回值 = "本来想写多少个字符"。**被截断时它会大于缓冲容量**，
  所以这里要夹一次，否则 `memcpy` 会写到缓冲区外面（越界）——这是本宏唯一需要小心的细节；
- `memcpy(_log_buf + _log_n, "\r\n" RTT_CTRL_RESET, ...)` 把换行 + `\x1B[0m` 拼在正文后面，
  **整体一次 `SEGGER_RTT_WriteString` 写出去**（原子，不会被别的任务插队）；
- `_Static_assert` 保证预留量真的够（编译期就能发现 RTT 色码变长）。

### 6.2 `PrintLog()`：同一套机制

`bsp/log/bsp_log.c` 里的 `PrintLog()`（当前无调用点）也从 `SEGGER_RTT_vprintf()` 改成
`vsnprintf()` + `SEGGER_RTT_WriteString()`，保持"工程里只有一种格式化方式"。

### 6.3 兜底仍然保留

`SEGGER_RTT_printf.c` 的 `default:` 分支里那段"遇到 `f/F/e/E/g/G/a/A` 就
`va_arg(double)` 把它消费掉"的兜底**继续保留** —— 现在没有人从这条路径走日志了，
但它保护"将来有人直接调用 `SEGGER_RTT_printf()`"的情况，无害。

### 6.4 可开关的自测：`LOG_TEST`

```c
#ifndef LOG_TEST
#define LOG_TEST 0        /* 置 1 = daemon 任务启动时打一组混合格式日志做自测 */
#endif
```

打开（`-DLOG_TEST=1`）后，daemon任务启动时输出五条样例和一条结束说明，其中第3条是
`%f` + `%s`**：

```c

```

本机测试检查混排结果中的 `tail_s=OK`。LOG-04将第5条改为合法的百分号和零位小数样例，原来的故意超长常量移至编译失败测试；动态长文字另用主机测试覆盖。自测默认不编进固件，开启后也须通过严格格式检查。本机接受文字不证明查看器已显示，不用于认定板上耗时。

## 8. 一句话回忆

**日志 = 栈上 `snprintf` 格式化（newlib 负责按标准消费参数） → 一次 `SEGGER_RTT_WriteString`
写进 RAM 环形缓冲 → 调试器经 SWD 搬走 → 上位机显示。**
它不占串口、不占引脚、也几乎不占 CPU —— 代价是"必须连着调试器、复位即丢"。

## 9. 初始化时的内存不是“要了就有”（R25-10）

`malloc()` 返回的是“申请结果”，不是无条件有效的地址。堆不足时它会返回 `NULL`。所以这种写法有两个操作，第二个不能先于检查：

```c
void *p = malloc(size);
if (p == NULL)
    return 0u;
memset(p, 0, size);
```

如果直接 `memset(p, ...)`，失败分支就会把 `NULL` 当作可写地址。类似地，`zmalloc(0)` 没有可清零的对象；本工程把零长度请求明确拒绝，并且只在分配成功后清零。

### 9.1 本工程有两套堆，释放必须配对

- C 库的 `malloc/free` 使用 newlib 的堆；`Core/Src/sysmem.c` 里的 `_sbrk()` 负责扩展它。
- 通过 FreeRTOS `pvPortMalloc/vPortFree` 分配的对象属于 RTOS 堆，由所选 `heap_*.c` 实现管理。
- `modules/algorithm/kalman_filter.h` 根据 CMSIS-RTOS 头是否已包含来选择 `user_malloc/user_free`。本次 Kalman 矩阵按该配对释放；`zmalloc()` 当前仍走 C 库 `malloc/free`。

两套分配器的地址可能都在 RAM，但这不意味着可以交叉释放：`free(pvPortMalloc(...))` 和 `vPortFree(malloc(...))` 都是错误的。排查 RAM 紧张时，也要先问清楚失败的是哪套分配器。

### 9.2 多次申请要像事务一样提交

Kalman 初始化需要很多数据数组和 CMSIS 矩阵。若中间第 12 次申请失败，前 11 块必须全部释放，同时不能把半初始化的对象交给姿态任务。本次生产实现先构造局部 `prepared` 对象，逐项检查分配和矩阵初始化后置条件，全部成功才复制到正式实例；失败走统一释放路径。零个控制维度时不申请零字节数组。

模块注册也遵循同一个顺序：先验证参数和容量、准备私有实例、分配依赖资源并检查 HAL 启动结果，最后才把实例放进全局注册表。因而失败应返回 `NULL`，不能先占索引，再发现 DMA/滤镜/PWM 启动失败。

### 9.3 启动失败时保存首个原因

连续初始化模块时，最先失败的资源通常最接近根因。R25-10 增加固定内存的 `init_diagnostic_snapshot`：保存失败阶段、模块、原因、资源编号、失败次数和诊断心跳；首个失败字段保持不变。访问快照只在短临界区内复制，恢复原来的 `PRIMASK`，不依赖日志、堆分配或 HAL tick。

故障注入测试会让主机测试实际使用的分配入口逐次失败，检查没有空指针访问、已分配资源全部释放、正式实例保持原样。Release 测试也很重要：优化器可能把 `malloc+memset` 合并成 `calloc`，所以测试必须同时拦截实际出现的分配入口。

诊断快照和 `--init` 只读工具用于回答“哪个阶段、哪个模块、哪个资源先失败”。工具从匹配 ELF 离线解析固定 RAM 白名单地址，在线只读取字节/字；它不能代替板上启动失败注入，也不能通过一次成功启动证明所有内存分配都会成功。

### 9.4 成功启动时看任务监控心跳

初始化诊断快照里的 `heartbeat` 只在**启动失败后的失能诊断循环**增加。正常启动后它保持 0 是预期值，不能据此判断任务停摆。正常运行要读取任务监控自己的字段：`monitor_initialized` 应为 1，`monitor_tick_count` 应继续增加，每个受监控任务的 `alive` 应为 1、`fault_logged` 为 0，`last_feed_ms` 应随时间前进。

R25-10 裸板回归用匹配当前 ELF 的只读符号快照，在约 1 秒间隔读取两次：监控计数从 39805 增至 39913，四个任务均保持存活且无故障，各自的最后喂送时间也前进。60 秒期间系统 tick、BMI088 样本序号持续增加，IWDG 复位标志未置位。这几项共同说明调度和监控链路在这段观察期持续工作；其中任一单独读数都不能证明所有注册失败分支正确，更不能证明物理输出已关断。

运行态读取必须使用不停车快照：离线 GDB 只解析 ELF 符号地址，OpenOCD 侧检查目标仍为 running 后按固定 RAM 白名单读字/字节，读取期间不执行 halt、reset 或写入。记录时同时保存 ELF SHA、原始串口字节、快照和时间；它们让板上结论可追溯，但不能取代主机故障注入，也不能把一次成功启动说成“所有失败注入都通过”。R25-10 的备份哈希、烧录范围、串口统计和用户观察见[验收票据](../workflow/tickets/R25-10.md)。

### 日志返回长度和限速计数怎样读（MC02-0123）

[bsp_log.h](../../bsp/log/bsp_log.h) 的 `PrintLog()` 返回完整格式化所需的字节数，
长于本地数组时只输出前面能放下的部分，返回值仍可能超过实际输出长度；负值时不输出。
`Float2Str()` 不是打印浮点数的必要步骤。BSPMISC-08 已将旧入口替换为有容量和返回状态的固定三位小数转换，具体用法见第10节；日志宏仍可直接使用 `%f`。

限速对象从零初始化，当前时间达到 `period_ms` 才允许首次报告；未满间隔时也会增加 `total`。
允许报告时保存的 `dropped` 实际是这一段的调用次数，包含本次，并非精确的省略条数。
传入空计数对象则始终允许报告；这些命名不能替代对计算式的核对。

### 9.5 零长度消息也是初始化错误

消息中心要求话题负载长度大于零。旧的 `Shoot_Upload_Data_s` 是空结构，C 编译器对空结构的处理属于扩展；在本构建中它的 `sizeof` 为零，`SubRegister("shoot_feed", 0)` 会明确返回 `NULL`。`RobotCMDInit()` 把这个未使用的订阅者当作必需资源检查，因此整机应用初始化失败。给它塞入一个没有语义的占位字节，只会掩盖接口问题。

MC02-0052 删除了 `shoot_feed` 的空发布/订阅和状态变量，保留真实的 `shoot_cmd` 控制话题。生产回归实际调用 `RobotCMDInit()` 与 `ShootInit()`，验证二者成功；如果以后要增加发射反馈，应先定义有实际用途的非空结构，再验证两端注册兼容。对应代码在 [`robot_cmd.c`](../../application/cmd/robot_cmd.c) 和 [`shoot.c`](../../application/shoot/shoot.c)，验收记录见 [MC02-0052](../workflow/tickets/MC02-0052.md)。

## 10. 把浮点数写成三位小数文字（BSPMISC-08）

旧的 `Float2Str()` 分别取整数和小数，再用 `%d.%d` 拼接。这样 `1.002f` 的小数部分可能只写成 `2`，输出不再代表原来的值；小数部分也没有完整的舍入和进位。它还没有数组容量参数，调用者无法要求函数在空间不足时停止写入。

现在的[公开头文件](../../bsp/log/float_to_string.h)要求调用方提供数组和容量，并检查状态。类型化日志直接保存`float`字段，处理任务再转成文字；`Float2Str()`仍供其他必须得到固定三位小数文字的接口使用：

```c
char text[FLOAT2STR_BUFFER_SIZE];
Float2StrStatus_t status = Float2Str(text, sizeof(text), value);
if (status == FLOAT2STR_OK) {
    /* 把text交给需要固定三位小数的显示或存储接口。 */
}
```

函数先在自己的小数组中准备整条结果，确认调用者的空间能同时放下文字和结尾0，再一次复制过去。失败时原数组没有变化，所以调用方必须检查本次状态，才能分清它保存的是旧文字还是新结果。

### 10.1 舍入、补0和整数进位一起完成

[实现](../../bsp/log/float_to_string.c)先把实际输入转为 `double` 并乘1000，再按最近整数、半数远离0的规则舍入，用 `int64_t` 保存千分数。整数部分由除1000得到，小数部分由余数得到。因此 `9.9996f` 会写成 `10.000`，不用单独猜测小数是否需要进位。小数总是写三位，正负零及舍入后为零的结果只写 `0.000`。

| 传入值 | 输出 |
|---|---|
| `1.2f` | `1.200` |
| `1.0625f` | `1.063` |
| `-1.0625f` | `-1.063` |
| `9.9996f` | `10.000` |
| `-0.0004f` | `0.000` |

输入 `float` 已经保存好的数值才是计算对象。`1.0005f` 实际略小于十进制的1.0005，因此三位小数结果为 `1.000`。测试使用能精确保存的 `0.0625f` 检查半数，再用 `nextafterf()` 取得它两侧紧邻的 float，分别检查两边会选择什么结果。

### 10.2 范围要在强制转整数前检查

输入和舍入结果都限定在 `[-2147483648,2147483647]`。比较使用 `double`：如果先把上界2147483647存成 float，它会变成2147483648，反而可能放过越界值。千倍结果仍放在 `int64_t` 中，避免把整个值放大1000后硬塞进32位整数。

最长文字为 `-2147483648.000`，共15字节，再加结尾0需要16字节。调用方可以提供更小数组，但只有完整结果能放下才成功。少一个字节也不写半条文字。这里的容量宏只说明文字空间，不扩大允许的数值范围。

### 10.3 本机怎样证明结果和写入范围

[C回归](../../tests/host/float_to_string_test.c)检查固定答案、半数两侧、补0、进位、正负零和数值上下界，并在输出数组前后放入哨兵；空参数、NaN／Inf、越界和容量不足时比较整个数组，确认原字节未变。两个数组还会交错使用，WSL用真实线程同时运行，检查没有共享临时数据。

[Python参考](../../tests/host/float_to_string_reference.py)把相同的binary32位形交给C入口，再用 `Decimal.from_float()` 得到输入的精确十进制值，以独立的十进制算法生成三位小数答案。固定种子及边界集合共有27035个向量，覆盖正常、极小、半数两侧和超范围位形；Release也执行全部检查。

实现只依赖标准C，不申请内存，也不访问HAL、RTOS或RTT。当前没有生产调用方，固件链接器可移除未使用函数；本机直接链接生产实现验证转换。验证不包含调试器实际显示或板上耗时，证据见 [BSPMISC-08记录](../workflow/tickets/BSPMISC-08.md)。

## 11. 编译格式诊断的历史（LOG-04）

LOG-04曾为`PrintLog()`、`UICharDraw()`和`OLED_printf()`增加格式属性，并为自有C源码启用选定格式告警。随后MC02-0066删除了工程日志的可变参数入口；当前`bsp_log.h`只有固定目录事件封装，不接受格式串，日志核心也不调用`printf`家族。裁判UI和OLED仍保留自己的文字接口，相关格式检查与OLED容量修复状态见[LOG-04记录](../workflow/tickets/LOG-04.md)和[MISC-06对应说明](17-LCD刷新的性能账.md)。

LOG-04的ARM／WSL长度诊断、MinGW覆盖限制和标准库格式接口负例仍是历史工具链证据，不能当作类型化事件日志的运行时保证。

## 12. 类型化事件怎样进入 RTT（MC02-0066）

生产日志路径不再先拼一条`printf`格式串。每个事件在[固定目录](../../bsp/log/bsp_log_events.def)中声明编号、模块来源、严重程度、类别、说明和字段类型。调用点用`BSP_LOG_EVENT_0`到`BSP_LOG_EVENT_8`提交固定字段；字段类型和个数由目录生成的专用封装检查。浮点和整数在提交时仍是数值，文字显式带长度。

提交接口把文字复制进固定记录，不保存调用者指针。每条事件最多96字节，单个文字字段最多48字节；超长文字保留前缀并计数。提交从启动代码和普通任务调用，ISR返回上下文错误。提交不分配内存、不调用格式化函数，也不等待输出。

32条待处理记录中，普通事件最多占24条，给关键事件留下空间。每个来源默认设为`STATUS`，所以故障和状态变化可以排队，普通事件先被过滤；运行等级可以独立调整，并受构建上限限制。普通事件限速为每秒20条、突发8条。队列满时普通事件拒绝，关键事件可挤出最早的普通待发项；没有普通项可挤出时仍写入关键RAM历史并返回“仅保留”。首次关键故障另存一份，最近16条关键记录循环覆盖；查询只复制记录，不消费历史。

日志任务使用静态1024字栈，每5ms推进一次，每轮最多处理2条，并优先关键记录。RTT后端先检查整条记录可否写入环形缓冲；空间不足就跳过这一条，增加失败计数，不截断、不补发，也不进入等待。启动失败循环只能在调度器运行前调用相同处理入口，每轮最多处理1条。NMI和HardFault继续使用独立崩溃记录路径。

标准输入输出不作为诊断旁路：正长度`_write()`和`fputc()`返回失败，`_read()`返回不支持。USART10接收来源等级命令，也接受MC02-0065的按需健康快照请求；它不镜像日志事件或周期推送状态，日志仍通过RTT输出。构建选项`MC02_LOG_COMPILED_MAX_LEVEL`取`FAULT`、`STATUS`或`VERBOSE`，默认上限为`VERBOSE`，运行命令不能越过上限；重启后各来源恢复默认`STATUS`。诊断串口使用`D3 6C`帧头、版本、命令、序号、长度、负载和`CRC16_MODBUS_A5`，分帧使用固定缓冲并先验CRC。日志只保存在本次启动的RAM中，断电或复位后不承诺保留。DCache开启时RTT后端停用，关键记录仍留在RAM。

### 12.1 编译上限与运行等级（MC02-0004）

“编译上限”限制本次固件允许设置的最高日志类别；“运行等级”逐来源决定新事件是否进入队列。两者分开后，可以在正式构建中保留故障和状态信息，同时临时提高一个来源的详细度。设置`FAULT`时状态事件依然保存在RAM历史，只是不排队输出。格式化仍只发生在日志任务中，过滤事件不会进入渲染流程。

诊断串口服务等级`SET`／`GET`命令和`GET_HEALTH`按需查询。健康请求无负载，命令号为`0x03`；回复沿用请求序号，健康体版本1固定118字节，加状态和schema后总负载120字节，完整帧128字节。健康体按小端字段逐项编码，不复制C结构体内存；尚未发布时返回“未就绪”，温度无效用`0x8000`表示，未知复位额度带单独known位。应答提交到现有UART复制队列；命令帧CRC错误、等级超过构建上限、发送队列拒绝和串口隔离都能从只读状态看到。日志正文不会复制到USART10，也不会定期推送健康数据。当前USART10使用工程已有921600、8N1配置；本轮没有验证实物TTL波形。

[生产测试](../../tests/host/log_test.c)使用真实日志核心，替换时钟、临界区、任务和输出端口；它检查固定字段、文本复制、队列挤出／仅保留、重复合并、首次故障与16条历史、序号和时钟回绕、线程并发、任务失败重试、输出失败、诊断命令分片、CRC、满长健康回复和编译上限。[健康快照测试](../../tests/host/vehicle_health_test.c)检查四种角色、50ms更新、交错读取、118字节编码、无效温度和未就绪应答。标准IO有单独的[行为测试](../../tests/host/log_stdio_test.c)。WSL测试和ARM构建能验证软件状态转换及链接布局，不证明RTT查看器显示、串口波形、板上格式化耗时、实际栈水位或链路吞吐。细节见[MC02-0066记录](../workflow/tickets/MC02-0066.md)、[MC02-0004记录](../workflow/tickets/MC02-0004.md)和[MC02-0065记录](../workflow/tickets/MC02-0065.md)。

## MC02-0100：日志接收与 RAM 观测分开

RTT 日志继续走 RTT 环形缓冲，但现在由 OpenOCD 原生 RTT 服务提供通道，接收客户端只调用 socket 接收，不发送下行数据，也不直接读写或消费 RTT 控制块。`.vscode/tasks.json` 中的“RTT receive only (OpenOCD native)”任务使用匹配 ELF 中 `_SEGGER_RTT` 符号定位控制块。

任务、DWT、CAN、LCD 性能数据不再通过旧探针或日志文本拼装，而由 `probe_snapshot_live.py --performance` 从运行中 RAM 的固定记录读取。它在业务字段前先核对 Build ID 和身份布局，并将每次原始读取写入 JSONL。RTT 日志和观测快照是两条独立证据路径。
