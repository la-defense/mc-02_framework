# SP 固定帧与 CRC 校验

本文记录 MC-02 与 `sp_vision_25` 的固定帧约定，以及如何用纯主机测试守住两端的协议边界。

## 本次接收改造（BSPUART-03U1）

UART视觉保存29字节候选，裁判保存128字节候选。找到头后逐步积累，长度或CRC不对就移走一个字节继续寻找；完整帧消费一次，后面的帧继续处理。每个保留字节同时保存所在块的原时间，坏候选里包含的新帧头也不会因重新寻找而获得新时间。来源时间取组成帧的首个接收块通知值，毫秒0合法。

组帧从首块起超过50ms就放弃，等于50ms仍允许。丢块、错误或显式重启会打断连续性，不能将旧帧头和新尾段拼起来。普通DMA重装保持连续性。BSPUART-03U1阶段曾保留裁判命令前缀兼容；MC02-0094已改为本工程21条命令严格匹配固定长度，未知、短帧、额外尾部或CRC失败都不发布、不续期。128字节只服务当前接收范围，不宣称覆盖官方全部大帧。

默认USB链路未改变，`VISION_USE_UART`可在编译时选择；同时定义两种传输会报错。UART流式接收与USB无状态扫描分别回归，SP线格式仍是29/43字节。

[端到端测试](../../tests/host/uart_stream_test.c)经过真实BSP队列、生产解析及CRC，覆盖所有分割位置、逐字节、多帧、噪声、CRC失败、来源时限及重启。固定裁判帧为`A5 01 00 00 68 02 00 05 03 97`，长度10字节；尾CRC用反射后`binascii.crc_hqx`另行核对。[详细证据](../workflow/tickets/BSPUART-03U1.md)记录软件验证范围，没有硬件或吞吐保证。

## 1. 两个方向，两种长度

| 方向 | 结构 | 长度 | 典型内容 |
|---|---|---:|---|
| MC-02 → Vision | `Vision_Send_s` / `GimbalToVision` | 43 字节 | 模式、姿态四元数、云台角度与弹速/计数 |
| Vision → MC-02 | `Vision_Recv_s` / `VisionToGimbal` | 29 字节 | 控制模式与 yaw/pitch 位置、速度、加速度 |

帧头为两个字节 `SP`。双方结构加上 packed 属性和 `static_assert` 能检查大小，但字段顺序、浮点表示、大小端和 CRC 覆盖范围仍必须由双方共同遵守。

## 2. 从字节流里找帧

UART/USB回调拿到的是字节区间，不保证从帧头开始。两者都只在完整且CRC正确后发布，但接收片段的保存方式不同。USB继续使用无状态扫描器`VisionProtocolFindCommandFrame()`，片段短于一帧直接拒绝，找到首个完整帧返回。UART在BSPUART-03U1中增加独立29字节候选，保存跨块半帧，同块内多个完整帧按顺序各处理一次。坏CRC不续期。

无状态扫描器不依赖HAL，可以由主机GCC直接测试；其行为仍是：

```text
长度不足 → 拒绝
完整但没有 SP → 继续扫描
SP + CRC 不匹配 → 计错误，继续扫描
找到有效帧 → 返回帧；只由调用方发布并刷新在线状态
```

## 3. CRC 不是认证

CRC 可以发现覆盖范围内常见的意外传输损坏，但不能证明发送者是谁，也不防止恶意构造。这个工程的线格式要求完整保留当前 CRC 算法、初值、反射方向、覆盖长度和两个 CRC 字节的顺序；“都叫 CRC16”不代表结果相同。

MC-02 和视觉代码的当前实现使用同一位运算表述，主机测试将 `123456789` 的结果固定为 `0x6f91`。这是仓库实际协议实现的回归向量；更换 CRC 库前先核对 MCU 端算法和已抓取的真实帧。

CRC16 数值在协议帧尾按低字节、再高字节排列。读回时也按相反步骤组合为 16 位数值。测试应同时验证已知向量、完整合法帧、帧头错误、载荷翻转、短帧，以及坏帧后紧跟合法帧的重同步行为。

## 5. 找到帧以后怎样使用（MC02-0123）

[crc.h](../../modules/algorithm/crc.h) 提供计算入口，[vision_protocol.h](../../modules/master_machine/vision_protocol.h) 提供检查帧和找帧入口：
计算入口的长度不含待追加的 CRC，检查入口的长度包含末尾两字节。
找帧入口逐字节前移，头或 CRC 不对就继续，找到第一份完整正确帧立即返回。
失败时命令输出不改写，错误计数则先清零；调用方不能把上一份输出当成本次找到的帧。

[master_process.h](../../modules/master_machine/master_process.h)在采用数据前按原接收通知时刻检查50ms时限，
读取和发送时也会检查旧命令是否到时。角度使用 rad，角速度使用 rad/s，进入电机控制前另做换算。
CRC 正确只说明字节检查通过，模式、数字、机械角度和当前是否允许控制仍由后续代码检查。

同目录的 [seasky_protocol.h](../../modules/master_machine/seasky_protocol.h) 保留另一种 A5 帧头格式，
不能和 SP 帧混用。它没有接收长度或输出容量参数，调用方须先保证整帧及空间足够，
帧头长度至少包含两字节标志；校验失败返回 0，标志和数据输出保持原值。

## 6. 裁判系统 CRC 和图形发送（MC02-0123）

[crc.h](../../modules/algorithm/crc.h) 提供统一的计算接口，裁判接收和 UI 组包直接检查返回状态。计算长度不含预留的校验字段：CRC-8 写末尾1字节，CRC-16 按低字节、高字节写末尾2字节。计算函数只交付数值，写帧和比较字段由调用方完成；裁判 CRC-8 必须选择 `CRC8_REFEREE`，不能换成同为8位的 CAN／A5 算法。

[referee_UI.h](../../modules/referee/referee_UI.h) 的 `UIGraphRefresh()` 只支持1、2、5或7个图形；REF-04已改成数组、实际容量和发送数量，删除旧可变参数入口。函数整批检查后，根据数量选择命令并显式编码字节、追加CRC。[RefereeSend()](../../modules/referee/rm_referee.h)经MC02-0061改为复制入UART队列；返回接受只表示已入队，发送任务另外通知本机完成或失败。115ms节奏由UI状态机检查，不再在发送入口等待。具体边界见[本篇REF-04说明](#12-ui的30字节容量与本机接受ref-04)。

## 7. 同样的位数，五套参数（MC02-0079）

完整算法需要同时说明多项式、初值、输入／输出位方向和最后异或值。项目只提供五种固定选择，配置和查表均在只读区；调用者不能改写配置或在首次调用时生成共享表。

| 选择 | 多项式正常表示 | 初值 | 输入／输出反射 | 最后异或 | `123456789` |
|---|---|---|---|---|---|
| `CRC8_CAN_A5` | `0x31` | `0` | 否／否 | `0` | `0xA2` |
| `CRC8_REFEREE` | `0x31` | `0xFF` | 是／是 | `0` | `0x0B` |
| `CRC16_MODBUS_A5` | `0x8005` | `0xFFFF` | 是／是 | `0` | `0x4B37` |
| `CRC16_SP_REFEREE` | `0x1021` | `0xFFFF` | 是／是 | `0` | `0x6F91` |
| `CRC32_IEEE` | `0x04C11DB7` | `0xFFFFFFFF` | 是／是 | `0xFFFFFFFF` | `0xCBF43926` |

正常表示省略最高位；从低位处理的实现分别使用反射后的多项式，例如 SP 的 `0x8408`。当前 SP 结束时没有取反，因此文档不再把它称为 CRC16/X25。此次保留原字节结果，不要求视觉端升级。

## 8. 先检查状态，再使用数值

新接口把失败原因与 CRC 数值分开。有效 CRC 可以正好为0，不能用 `if (crc)` 判断计算是否成功。

```c
uint32_t result;
CRCStatus_t status = CRCCompute(CRC16_SP_REFEREE, bytes, byte_count, &result);
if (status != CRC_OK)
    return; // 没有本次结果，不提交报文。
frame_tail_low = (uint8_t)result;
frame_tail_high = (uint8_t)(result >> 8u);
```

长度以字节计，调用者负责真实容量。长度为0允许空数据地址；空输出地址、非法算法和未初始化上下文都会失败，原输出保持不变。保留旧输出便于调用者决定如何处理，不能把它当成本周期计算成功。

CAN、SP 和裁判接收计算失败时不发布字段、不刷新有效时间；发送失败时不提交帧。参数保存先算 CRC，再擦除目标区；读取计算失败则不接受记录。A5 组包改为返回状态，失败把输出长度置0，数组中可能已有部分内容，不得发送。A5 原有接收长度和容量检查限制仍由调用者承担。

## 9. 分段接收和异常入口

分段计算先将 `CRCContext_t` 置零，再调用 `CRCInit()`；每段使用 `CRCUpdate()`，最后用 `CRCFinal()` 读取结果。Final 不清除历史数据，可重复读取，也可继续 Update。它保存的是尚未进行最后异或的余数，不能随意把已经输出的 CRC32 当成下一段初值。

每个上下文单独保存算法和余数，不同对象可交错或并发计算；同一对象仍须串行访问。失败不会改上下文或输出。普通模块不需要 HAL、RTOS、动态分配或硬件 CRC 外设。

[异常 CRC 入口](../../bsp/crash/bsp_crash_crc.h) 独立逐位处理固定记录中的32位字，每字先处理低字节。它不调用普通查表模块，不打印日志、不等待、不分配内存。读取长度来自当前固定结构，不能使用损坏记录声称的长度；未算出 CRC 时不写完成标记，继续原有复位路径。

CRC 算法兼容不代表任意旧固件的崩溃记录都会被当前固件接受：原有版本、长度和构建编号检查仍然保留。

## 12. UI的30字节容量与本机接受（REF-04）

### 文字区不是普通C字符串

裁判字符帧的文字区固定为30字节，恰好30字节时不包含NUL。先用31字节临时区调用`vsnprintf()`，它返回所需长度；返回负数表示格式化失败，超过30表示整条拒绝。只有检查通过才复制候选对象，因此失败保留原对象，文字尾部不会残留上一次长文本。长度按字节计，UTF-8汉字通常占多个字节，当前接口不转换编码。

```c
String_Data_t label;
UIStatus_t result = UICharDraw(&label, "txt", UI_Graph_ADD, 0,
                              UI_Color_White, 15, 2, 100, 200, "%s", "ready");
if (result == UI_OK)
    result = UICharRefresh(&id, &label, NULL);
```

`UI_OK`只表示本地构图成功。`UI_SUBMITTED`表示本机接受发送，仍未证明裁判客户端收到或显示；失败保留旧对象时，不得跳过本次状态检查直接发送。格式字符串及参数由程序提供并保证合法，不把任意外部字节作为格式字符串。

### 容量、范围和位段要在写入前检查

`UIGraphRefresh(&id, graphics, capacity, count, options)`检查1／2／5／7的合法数量和真实元素容量；调用者仍须提供实际可读数组。旧可变参数方式无法核对传入对象数量，现已删除。整批图形有一项错误就不提交，不会只发前半批。

构图入口检查坐标、图层、颜色、角度、字号和编码尺寸，再写入候选对象。x为0～1920、y为0～1080，不靠11位字段丢掉高位后得到另一个坐标；圆半径为10位、椭圆半轴为11位，不保证整幅图形完全在屏幕内。名称保留旧逆序规则，短名称其余字节清零。各类未使用字段清零，负整数用无符号位运算拆分。

2026协议中的浮点数是int32_t除以1000，传入24000表示24.000。旧`Graph_Digit`参数并不能选择显示小数位，对应无作用字段现在固定发0。功率显示先在double中检查有限性和转换范围，再转整数，避免NaN或大数先强制转换。

### DMA还在借用谁的内存

帧编码在局部数组完成，`RefereeSend()`提交后由UART队列独立保存；成功入队后原数组可以复用。每路4条、每条最多128字节，队列满立即拒绝。内部数组一直保存到TX停止并完成任务通知；停止失败则隔离并保留数组。115ms由UI状态机按上次实际启动时刻检查，函数内部不等待。

| 结果 | 调用方动作 |
|---|---|
| 构图错误／文字过长／格式化失败 | 不发送保留的旧对象，保留待刷新标记 |
| CRC失败／入队被拒绝 | 不推进序号，不清待刷新标记 |
| 成功入队 | 推进序号，255之后回到0；暂不清待刷新标记 |
| 对应版本本机传输完成 | 清该版本待刷新标记；已出现的新变化继续保留 |
| 入队后传输失败 | 序号不回退，停止本轮UI，保留待刷新内容，等待显式初始化 |
| UI初始化失败 | 停用后续UI刷新，裁判接收仍可用；再次初始化由显式调用触发 |

`UITask()`按115ms逻辑步长运行原演示，50步换档；1ms发送轮询不会加速演示，也不追赶积压步骤。`UIRefresh()`只推进已绑定状态。当前已有有界的初始化和增量分批发送；车型布局、真实数据绑定、自动恢复重绘、REF-03共享预算和客户端确认不在本轮。

### 用独立字节检查生产入口

[UI测试](../../tests/host/referee_ui_test.c)保留一份30字节完整图形帧，图形名、坐标、位段、头CRC及尾CRC都有独立核对值。它同时覆盖0／1／29／30／31字节和长文字、所有图形类型及边界、有符号整数极值、CRC两阶段失败、忙与启动错误、在途缓冲不变、序号回绕，以及初始化失败后接收仍正常。

正常路径使用真实格式化和CRC；只有选定失败被包装。Linux包装`vsnprintf`，MinGW包装对象实际引用的`__mingw_vsnprintf`，避免测试声称注入失败却未走到生产调用。所有检查在Release下执行，另有地址和未定义行为检查；完整结果和协议页码见[REF-04证据](../workflow/tickets/REF-04.md)。没有连接开发板，软件通过不能替代真实显示和串口时序验收。

## 13. 裁判数据按命令独立过期（MC02-0094）

裁判UART帧完整并通过CRC，只说明这一帧可以尝试解码。字段长度、取值和有限浮点也检查通过后，解析器才在短临界区内一起更新该命令的数据与接收元信息。读者一次复制全部命令得到一致副本；查询不会消费、刷新或延长任何来源时间。

0x0203机器人位置的详细表和示例结构是12字节，但协议总览写16字节；0x0303小地图字段表和示例是12字节，总览写15字节。本工程按详细字段表和示例锁定12字节，固定长度命令不接受额外尾部。0x0301也只接收当前业务需要的内容ID 0x0200和5字节内容，并验证本机身份、同队和接收目标；协议中其他交互内容不会被当作通用消息发布。

| 数据类别 | 命令 | 默认有效期限 | 查询状态 |
|---|---|---:|---|
| 10Hz周期数据 | 0x0201、0x0202、0x0208 | 300ms | 边界仍新鲜，超过后过期 |
| 3Hz周期数据 | 0x0003、0x0204、0x0209、0x020A | 1000ms | 每条命令单独计时 |
| 1Hz周期数据 | 0x0001、0x0101、0x0104、0x0105、0x0203、0x020B、0x020C、0x020D、0x020E | 3000ms | 其他命令更新不能续期 |
| 小地图最近内容 | 0x0303 | 3000ms | 裁判重复重发可更新最近内容，不生成新操作事件 |
| 最近事件记录 | 0x0002、0x0206、0x0207、0x0301 | 不承诺持续有效 | 保留记录、来源时间和年龄 |

组帧来源时间取首个UART块的原RxEvent时间，0合法。它不是服务器生成时间或用户点击时间。整体在线300ms只用于链路诊断；LCD与其他调用方应逐项检查数据状态，过期值只供诊断，不作为当前读数。

主机回归[referee_snapshot_test.c](../../tests/host/referee_snapshot_test.c)通过真实BSP队列、生产CRC和生产解析器逐命令检查长度与字段，另覆盖12字节矛盾、浮点拒收、保留字节、分块时间、独立期限、事件记录、回绕和线程并发读取。UI独立初始化，测试[referee_ui_test.c](../../tests/host/referee_ui_test.c)确认UI失败不关接收；LCD测试确认未接收或过期组显示`--`。页码、PDF指纹和本轮本机验证见[MC02-0094记录](../workflow/tickets/MC02-0094.md)。

## 14. UI的初始化请求和实际传输分开（MC02-0061／MC02-0095部分）

`UITaskInit()`只绑定长期对象，`MyUIInit()`只登记初始化请求并返回，不循环发帧或等待。`UIGetState()`只读当前阶段：未绑定、等待新鲜身份、初始化中、运行、等待显式初始化、错误停止。接收仍由独立的`RefereeInit()`完成，UI失败不撤销接收。

初始化保留原15帧顺序：清屏、五条准星线、五组固定标签与动态初值、功率标题、外框、功率数值及进度线。每次`UIRefresh()`最多提交一帧，上一帧本机传输完成后才推进步骤；第15帧完成后才进入运行。全流程最多持有一条UI报文，相邻实际启动至少115ms。即使发送任务延后启动，后面也不会密集追赶。

刷新将六个显示项分别编号。某项发送期间再次变化，就提高该项版本；旧完成通知只确认旧版本，不能清掉最新变化。队列满保留待刷新项和初始化步骤，下次再尝试入队。已启动后发生错误或超时，保留待刷新内容并停止本轮流程，必须显式调用`MyUIInit()`恢复。

入队时以及发送任务实际启动前，都检查`0x0201`本组新鲜度和机器人ID。身份过期或变化后停止，取消旧代尚未发送的报文；已发送的字节无法撤回。重新初始化会增加流程代号，旧代完成通知只负责释放旧请求，不允许推进新流程。身份重新变新鲜本身不会自动恢复UI。

低层绘图发送的末参数为`UITxOptions_t *`：可提供长期context、完成回调、启动检查和事务编号输出。传NULL会记录到`UIGetLastTxEvent()`，适合只诊断最近一次结果；需要逐条对应结果时必须提供自己的回调。回调由UART发送任务调用，禁止等待。编号输出只在提交期间写入，context则保存至通知结束。两种用法都要先完成接收和发送任务初始化，也都不表示客户端显示成功。

[真实队列与UI联测](../../tests/host/uart_ui_integration_test.c)经过生产CRC、接收分帧、身份发布、组帧、复制队列和H723后端，检查完整初始化、115ms节奏、版本合并、拥塞、身份变化、旧代通知及显式恢复。寄存器和RTOS调度由主机模型代替；[本轮证据](../workflow/tickets/MC02-0061.md)只覆盖软件行为。
