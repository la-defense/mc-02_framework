# SP 固定帧与 CRC 校验

本文记录 MC-02 与 `sp_vision_25` 的固定帧约定，以及如何用纯主机测试守住两端的协议边界。

## 本次接收改造（BSPUART-03U1）

UART视觉保存29字节候选，裁判保存128字节候选。找到头后逐步积累，长度或CRC不对就移走一个字节继续寻找；完整帧消费一次，后面的帧继续处理。每个保留字节同时保存所在块的原时间，坏候选里包含的新帧头也不会因重新寻找而获得新时间。来源时间取组成帧的首个接收块通知值，毫秒0合法。

组帧从首块起超过50ms就放弃，等于50ms仍允许。丢块、错误或显式重启会打断连续性，不能将旧帧头和新尾段拼起来。普通DMA重装保持连续性。BSPUART-03U1阶段曾保留裁判命令前缀兼容；MC02-0094已改为本工程21条命令严格匹配固定长度，未知、短帧、额外尾部或CRC失败都不发布、不续期。128字节只服务当前接收范围，不宣称覆盖官方全部大帧。

默认USB链路未改变，`VISION_USE_UART`可在编译时选择；同时定义两种传输会报错。UART流式接收与USB无状态扫描分别回归，SP线格式仍是29/43字节。

[端到端测试](../../tests/host/uart_stream_test.c)经过真实BSP队列、生产解析及CRC，覆盖所有分割位置、逐字节、多帧、噪声、CRC失败、来源时限及重启。固定裁判帧为`A5 01 00 00 68 02 00 05 03 97`，长度10字节；尾CRC用反射后`binascii.crc_hqx`另行核对。[详细证据](../workflow/tickets/BSPUART-03U1.md)记录软件验证范围，没有硬件或吞吐保证。

## 1. 两个方向，两种长度

| 方向 | 结构 | 长度 | 典型内容 |
|---|---|---:|---|
| MC-02 → Vision | `Vision_Send_s` / `GimbalToVision` | 43 字节 | 模式、姿态四元数、云台角度与弹速/计数 |
| Vision → MC-02 | `Vision_Recv_s` / `VisionToGimbal` | 29 字节 | 控制模式与 yaw/pitch 位置、速度、加速度 |

帧头为两个字节 `SP`。双方结构加上 packed 属性和 `static_assert` 能检查大小，但字段顺序、浮点表示、大小端和 CRC 覆盖范围仍必须由双方共同遵守。

## 2. 从字节流里找帧

UART/USB回调拿到的是字节区间，不保证从帧头开始。两者都只在完整且CRC正确后发布，但接收片段的保存方式不同。USB继续使用无状态扫描器`VisionProtocolFindCommandFrame()`，片段短于一帧直接拒绝，找到首个完整帧返回。UART在BSPUART-03U1中增加独立29字节候选，保存跨块半帧，同块内多个完整帧按顺序各处理一次。坏CRC不续期。

无状态扫描器不依赖HAL，可以由主机GCC直接测试；其行为仍是：

```text
长度不足 → 拒绝
完整但没有 SP → 继续扫描
SP + CRC 不匹配 → 计错误，继续扫描
找到有效帧 → 返回帧；只由调用方发布并刷新在线状态
```

## 3. CRC 不是认证

CRC 可以发现覆盖范围内常见的意外传输损坏，但不能证明发送者是谁，也不防止恶意构造。这个工程的线格式要求完整保留当前 CRC 算法、初值、反射方向、覆盖长度和两个 CRC 字节的顺序；“都叫 CRC16”不代表结果相同。

MC-02 和视觉代码的当前实现使用同一位运算表述，主机测试将 `123456789` 的结果固定为 `0x6f91`。这是仓库实际协议实现的回归向量；更换 CRC 库前先核对 MCU 端算法和已抓取的真实帧。

CRC16 数值在协议帧尾按低字节、再高字节排列。读回时也按相反步骤组合为 16 位数值。测试应同时验证已知向量、完整合法帧、帧头错误、载荷翻转、短帧，以及坏帧后紧跟合法帧的重同步行为。

## 5. 找到帧以后怎样使用（MC02-0123）

[crc.h](../../modules/algorithm/crc.h) 提供计算入口，[vision_protocol.h](../../modules/master_machine/vision_protocol.h) 提供检查帧和找帧入口：
计算入口的长度不含待追加的 CRC，检查入口的长度包含末尾两字节。
找帧入口逐字节前移，头或 CRC 不对就继续，找到第一份完整正确帧立即返回。
失败时命令输出不改写，错误计数则先清零；调用方不能把上一份输出当成本次找到的帧。

[master_process.h](../../modules/master_machine/master_process.h)在采用数据前按原接收通知时刻检查50ms时限，
读取和发送时也会检查旧命令是否到时。角度使用 rad，角速度使用 rad/s，进入电机控制前另做换算。
CRC 正确只说明字节检查通过，模式、数字、机械角度和当前是否允许控制仍由后续代码检查。

历史 A5 编解码源码和原协议说明已移至[归档入口](../history/seasky/README.md)，与当前 SP 视觉链路分开保存。它没有接收长度或输出容量参数，调用方须先保证整帧及空间足够；帧头长度至少包含两字节标志。校验失败返回 0，标志和数据输出保持原值。此接口只供阅读历史资料和兼容回归，不是当前固件接口。

固件 CMake 只从 `bsp/`、`modules/` 和 `application/` 收集自有 C 文件，因此迁入 `docs/history/` 的 A5 源码不会参与固件编译。主机历史测试仍显式编译归档源码，锁定旧帧字节；“测试编译过”不表示它进入固件 ELF。

## 6. 裁判系统 CRC 和图形发送（MC02-0123）

[crc.h](../../modules/algorithm/crc.h) 提供统一的计算接口，裁判接收和 UI 组包直接检查返回状态。计算长度不含预留的校验字段：CRC-8 写末尾1字节，CRC-16 按低字节、高字节写末尾2字节。计算函数只交付数值，写帧和比较字段由调用方完成；裁判 CRC-8 必须选择 `CRC8_REFEREE`，不能换成同为8位的 CAN／A5 算法。

[referee_UI.h](../../modules/referee/referee_UI.h) 的 `UIGraphRefresh()` 只支持1、2、5或7个图形；REF-04已改成数组、实际容量和发送数量，删除旧可变参数入口。函数整批检查后，根据数量选择命令并显式编码字节、追加CRC。[RefereeSend()](../../modules/referee/rm_referee.h)经MC02-0061改为复制入UART队列；返回接受只表示已入队，发送任务另外通知本机完成或失败。115ms节奏由UI状态机检查，不再在发送入口等待。具体边界见[本篇REF-04说明](#12-ui的30字节容量与本机接受ref-04)。

## 7. 同样的位数，五套参数（MC02-0079）

完整算法需要同时说明多项式、初值、输入／输出位方向和最后异或值。项目只提供五种固定选择，配置和查表均在只读区；调用者不能改写配置或在首次调用时生成共享表。

| 选择 | 多项式正常表示 | 初值 | 输入／输出反射 | 最后异或 | `123456789` |
|---|---|---|---|---|---|
| `CRC8_CAN_A5` | `0x31` | `0` | 否／否 | `0` | `0xA2` |
| `CRC8_REFEREE` | `0x31` | `0xFF` | 是／是 | `0` | `0x0B` |
| `CRC16_MODBUS_A5` | `0x8005` | `0xFFFF` | 是／是 | `0` | `0x4B37` |
| `CRC16_SP_REFEREE` | `0x1021` | `0xFFFF` | 是／是 | `0` | `0x6F91` |
| `CRC32_IEEE` | `0x04C11DB7` | `0xFFFFFFFF` | 是／是 | `0xFFFFFFFF` | `0xCBF43926` |

正常表示省略最高位；从低位处理的实现分别使用反射后的多项式，例如 SP 的 `0x8408`。当前 SP 结束时没有取反，因此文档不再把它称为 CRC16/X25。此次保留原字节结果，不要求视觉端升级。

## 8. 先检查状态，再使用数值

新接口把失败原因与 CRC 数值分开。有效 CRC 可以正好为0，不能用 `if (crc)` 判断计算是否成功。

```c
uint32_t result;
CRCStatus_t status = CRCCompute(CRC16_SP_REFEREE, bytes, byte_count, &result);
if (status != CRC_OK)
    return; // 没有本次结果，不提交报文。
frame_tail_low = (uint8_t)result;
frame_tail_high = (uint8_t)(result >> 8u);
```

长度以字节计，调用者负责真实容量。长度为0允许空数据地址；空输出地址、非法算法和未初始化上下文都会失败，原输出保持不变。保留旧输出便于调用者决定如何处理，不能把它当成本周期计算成功。

CAN、SP 和裁判接收计算失败时不发布字段、不刷新有效时间；发送失败时不提交帧。参数保存先算 CRC，再擦除目标区；读取计算失败则不接受记录。归档 A5 组包接口返回状态，失败把输出长度置0，数组中可能已有部分内容，不得发送。A5 原有接收长度和容量检查限制仍由调用者承担。

## 9. 分段接收和异常入口

分段计算先将 `CRCContext_t` 置零，再调用 `CRCInit()`；每段使用 `CRCUpdate()`，最后用 `CRCFinal()` 读取结果。Final 不清除历史数据，可重复读取，也可继续 Update。它保存的是尚未进行最后异或的余数，不能随意把已经输出的 CRC32 当成下一段初值。

每个上下文单独保存算法和余数，不同对象可交错或并发计算；同一对象仍须串行访问。失败不会改上下文或输出。普通模块不需要 HAL、RTOS、动态分配或硬件 CRC 外设。

[异常 CRC 入口](../../bsp/crash/bsp_crash_crc.h) 独立逐位处理固定记录中的32位字，每字先处理低字节。它不调用普通查表模块，不打印日志、不等待、不分配内存。读取长度来自当前固定结构，不能使用损坏记录声称的长度；未算出 CRC 时不写完成标记，继续原有复位路径。

CRC 算法兼容不代表任意旧固件的崩溃记录都会被当前固件接受：原有版本、长度和构建编号检查仍然保留。

## 12. UI的30字节容量与本机接受（REF-04）

### 文字区不是普通C字符串

裁判字符帧的文字区固定为30字节，恰好30字节时不包含NUL。先用31字节临时区调用`vsnprintf()`，它返回所需长度；返回负数表示格式化失败，超过30表示整条拒绝。只有检查通过才复制候选对象，因此失败保留原对象，文字尾部不会残留上一次长文本。长度按字节计，UTF-8汉字通常占多个字节，当前接口不转换编码。

```c
String_Data_t label;
UIStatus_t result = UICharDraw(&label, "txt", UI_Graph_ADD, 0,
                              UI_Color_White, 15, 2, 100, 200, "%s", "ready");
if (result == UI_OK)
    result = UICharRefresh(&id, &label, NULL);
```

`UI_OK`只表示本地构图成功。`UI_SUBMITTED`表示本机接受发送，仍未证明裁判客户端收到或显示；失败保留旧对象时，不得跳过本次状态检查直接发送。格式字符串及参数由程序提供并保证合法，不把任意外部字节作为格式字符串。

### 容量、范围和位段要在写入前检查

`UIGraphRefresh(&id, graphics, capacity, count, options)`检查1／2／5／7的合法数量和真实元素容量；调用者仍须提供实际可读数组。旧可变参数方式无法核对传入对象数量，现已删除。整批图形有一项错误就不提交，不会只发前半批。

构图入口检查坐标、图层、颜色、角度、字号和编码尺寸，再写入候选对象。x为0～1920、y为0～1080，不靠11位字段丢掉高位后得到另一个坐标；圆半径为10位、椭圆半轴为11位，不保证整幅图形完全在屏幕内。名称保留旧逆序规则，短名称其余字节清零。各类未使用字段清零，负整数用无符号位运算拆分。

2026协议中的浮点数是int32_t除以1000，传入24000表示24.000。旧`Graph_Digit`参数并不能选择显示小数位，对应无作用字段现在固定发0。功率显示先在double中检查有限性和转换范围，再转整数，避免NaN或大数先强制转换。

### DMA还在借用谁的内存

帧编码在局部数组完成，`RefereeSubmit()`检查身份、构造CRC并提交后由UART队列独立保存；成功入队后原数组可以复用。每路4条、每条最多128字节，队列满立即拒绝。内部数组一直保存到TX停止并完成任务通知；停止失败则隔离并保留数组。115ms由UI状态机按上次实际启动时刻检查，函数内部不等待。

| 结果 | 调用方动作 |
|---|---|
| 构图错误／文字过长／格式化失败 | 不发送保留的旧对象，保留待刷新标记 |
| CRC失败／入队被拒绝 | 不推进序号，不清待刷新标记 |
| 成功入队 | 推进序号，255之后回到0；暂不清待刷新标记 |
| 对应版本本机传输完成 | 清该版本待刷新标记；已出现的新变化继续保留 |
| 入队后传输失败 | 序号不回退，停止本轮UI，保留待刷新内容；身份失效后恢复会重绘，也可显式请求重绘 |
| UI配置无效 | `UITaskInit()`报告配置错误，不启用UI；裁判接收仍可用 |

`UITask()`每轮最多推进一帧；完成清除帧和所有配置字段后进入运行，运行中只发送有变化的字段。当前已由 MC02-0095 接入车型布局、真实裁判来源和身份恢复重绘；本机任务状态仍不代表裁判客户端确认显示。REF-03共享预算见第15节。

### 用独立字节检查生产入口

[UI测试](../../tests/host/referee_ui_test.c)保留一份30字节完整图形帧，图形名、坐标、位段、头CRC及尾CRC都有独立核对值。它同时覆盖0／1／29／30／31字节和长文字、所有图形类型及边界、有符号整数极值、CRC两阶段失败、忙与启动错误、在途缓冲不变、序号回绕，以及初始化失败后接收仍正常。

正常路径使用真实格式化和CRC；只有选定失败被包装。Linux包装`vsnprintf`，MinGW包装对象实际引用的`__mingw_vsnprintf`，避免测试声称注入失败却未走到生产调用。所有检查在Release下执行，另有地址和未定义行为检查；完整结果和协议页码见[REF-04证据](../workflow/tickets/REF-04.md)。没有连接开发板，软件通过不能替代真实显示和串口时序验收。

## 13. 裁判数据按命令独立过期（MC02-0094）

裁判UART帧完整并通过CRC，只说明这一帧可以尝试解码。字段长度、取值和有限浮点也检查通过后，解析器才在短临界区内一起更新该命令的数据与接收元信息。读者一次复制全部命令得到一致副本；查询不会消费、刷新或延长任何来源时间。

0x0203机器人位置的详细表和示例结构是12字节，但协议总览写16字节；0x0303小地图字段表和示例是12字节，总览写15字节。本工程按详细字段表和示例锁定12字节，固定长度命令不接受额外尾部。0x0301机器人交互支持内容ID 0x0200～0x02FF及0～112字节内容，并验证本机身份、同队和接收目标；其他子命令不作为机器人交互发布。

### 最近交互内容怎样读取（MC02-0022）

`RefereeGetInteraction()`一次复制内容、长度、双方编号和接收时间。新合法帧覆盖旧记录，因此它适合查看最近内容，不提供逐条队列或确认对端执行的能力。时间来自组成帧的第一个UART接收块，不能当作对端生成时间；读取不会续期，业务仍须检查数据年龄及当前许可。为控制内存，普通分组读取的交互项只保留前五字节预览，需要完整内容时使用专门接口；两次分别读取之间可能接收到新帧。

发送仍经共享队列：入队成功表示本机保存了副本，完成通知表示本机发送结束。独立固定字节同时进入生产CRC接收、生产发送和模拟器组帧检查，错误帧不能改变旧记录。测试未连接真实裁判链路，不能证明对端已经收到。细节见[任务记录](../workflow/tickets/MC02-0022.md)。

同队身份也不等于比赛规则允许该方向通信。现在初始化配置可分别列出本车允许发送和接收的同队编号：位0对应编号1，位8对应编号9，红蓝双方共用编号位，但不得跨队。未配置时机器人交互关闭，普通裁判接收和UI仍可使用。配置复制后固定，来源与目标须匹配新鲜本机身份；现场赛项、阶段的正式规则仍须由配置者核验，测试掩码不是官方允许表。整车配置入口仍在MC02-0054跟踪，当前生产初始化未配置交互。

### 各组数据的有效期限

| 数据类别 | 命令 | 默认有效期限 | 查询状态 |
|---|---|---:|---|
| 10Hz周期数据 | 0x0201、0x0202、0x0208 | 300ms | 边界仍新鲜，超过后过期 |
| 3Hz周期数据 | 0x0003、0x0204、0x0209、0x020A | 1000ms | 每条命令单独计时 |
| 1Hz周期数据 | 0x0001、0x0101、0x0104、0x0105、0x0203、0x020B、0x020C、0x020D、0x020E | 3000ms | 其他命令更新不能续期 |
| 小地图最近内容 | 0x0303 | 3000ms | 裁判重复重发可更新最近内容，不生成新操作事件 |
| 最近事件记录 | 0x0002、0x0206、0x0207、0x0301 | 不承诺持续有效 | 保留记录、来源时间和年龄 |

组帧来源时间取首个UART块的原RxEvent时间，0合法。它不是服务器生成时间或用户点击时间。整体在线300ms只用于链路诊断；LCD与其他调用方应逐项检查数据状态，过期值只供诊断，不作为当前读数。

主机回归[referee_snapshot_test.c](../../tests/host/referee_snapshot_test.c)通过真实BSP队列、生产CRC和生产解析器逐命令检查长度与字段，另覆盖12字节矛盾、浮点拒收、保留字节、分块时间、独立期限、事件记录、回绕和线程并发读取。UI独立初始化，测试[referee_ui_test.c](../../tests/host/referee_ui_test.c)确认UI失败不关接收；LCD测试确认未接收或过期组显示`--`。页码、PDF指纹和本轮本机验证见[MC02-0094记录](../workflow/tickets/MC02-0094.md)。

## 14. UI的初始化请求和实际传输分开（MC02-0061／MC02-0095部分）

`UITaskInit()`只绑定长期对象，`MyUIInit()`只登记初始化请求并返回，不循环发帧或等待。`UIGetState()`只读当前阶段：未绑定、等待新鲜身份、初始化中、运行、等待显式初始化、错误停止。接收仍由独立的`RefereeInit()`完成，UI失败不撤销接收。

初始化保留原15帧顺序：清屏、五条准星线、五组固定标签与动态初值、功率标题、外框、功率数值及进度线。每次`UIRefresh()`最多提交一帧，上一帧本机传输完成后才推进步骤；第15帧完成后才进入运行。全流程最多持有一条UI报文，相邻实际启动至少115ms。即使发送任务延后启动，后面也不会密集追赶。

刷新将六个显示项分别编号。某项发送期间再次变化，就提高该项版本；旧完成通知只确认旧版本，不能清掉最新变化。队列满保留待刷新项和初始化步骤，下次再尝试入队。已启动后发生错误或超时，保留待刷新内容并停止本轮流程，必须显式调用`MyUIInit()`恢复。

入队时以及发送任务实际启动前，都检查`0x0201`本组新鲜度和机器人ID。身份过期或变化后停止，取消旧代尚未发送的报文；已发送的字节无法撤回。重新初始化会增加流程代号，旧代完成通知只负责释放旧请求，不允许推进新流程。身份重新变新鲜本身不会自动恢复UI。

低层绘图发送的末参数为`UITxOptions_t *`：可提供长期context、完成回调、启动检查和事务编号输出。传NULL会记录到`UIGetLastTxEvent()`，适合只诊断最近一次结果；需要逐条对应结果时必须提供自己的回调。回调由UART发送任务调用，禁止等待。编号输出只在提交期间写入，context则保存至通知结束。两种用法都要先完成接收和发送任务初始化，也都不表示客户端显示成功。

[真实队列与UI联测](../../tests/host/uart_ui_integration_test.c)经过生产CRC、接收分帧、身份发布、组帧、复制队列和H723后端，检查完整初始化、115ms节奏、版本合并、拥塞、身份变化、旧代通知及显式恢复。寄存器和RTOS调度由主机模型代替；[本轮证据](../workflow/tickets/MC02-0061.md)只覆盖软件行为。


## 15. UI与机器人交互共用裁判发送额度（REF-03）

官方2026 V2.0.0 PDF第24～25页规定：`0x0301`所有子命令合计上限30Hz，完整帧最多127字节，交互内容最多112字节。旧代码的10Hz和113字节注释已修正。机器人目标的滚动1000ms完整帧字节额度为普通机器人3720、哨兵／雷达5120；身份表见PDF第80～81页。PDF指纹及页码口径见[任务记录](../workflow/tickets/REF-03.md)。

完整帧长度为`5字节头 + 2字节命令 + 6字节交互头 + 内容 + 2字节CRC`。新的[`RefereeTxRequest_t`](../../modules/referee/referee_tx.h)只收接收者、子内容ID、内容、总期限和长期回调上下文；发送者取新鲜`0x0201`。机器人交互只允许同队合法机器人与`0x0200～0x02FF`；UI仍只有六类既有子命令及准确长度。服务器自主决策等入口没有接入；机器人交互接收已由MC02-0022扩展为0～112字节。

UI不再自己生成头CRC、整帧CRC和序号，所有发送者都由共享入口完成。成功入队后序号递增，255之后回0；后来失败或取消不会回退。拒绝提交保持编号输出，不产生完成通知；入队成功后调用者可以复用源内容，但回调上下文要一直保存至最终通知结束。

```c
// done必须短小、不等待；context由调用方长期保存。
uint8_t payload[] = {1, 2, 3};
RefereeTxRequest_t request = {
    .receiver_id = 4u, .content_id = 0x0200u,
    .content = payload, .length = sizeof(payload), .timeout_ms = 100u,
    .complete = done, .context = context,
};
uint32_t id;
RefereeSendStatus_t status = RefereeSubmit(&request, &id);
// 仅ACCEPTED时id有效；此时只是已复制入队，尚未证明传输或接收。
```

共享调度保持严格FIFO。34ms间隔或目标字节额度不足时只暂缓队首，原100ms期限继续计时。UI最多持有一条未完成请求：尚未开始就超期，可以保留步骤／待刷新版本并提交最新内容；实际启动失败、启动后失败和隔离则进入错误停止。15帧初始化顺序、115ms实际启动间隔、30字节文字及旧完成不能清新变化的规则均保留。

身份在提交和实际启动前检查。变更身份不会清额度；已排队的旧身份被取消，UI恢复仍需显式初始化。共享完成观察不表示对端确认。`RefereeGetTxState()`给出队列容量、拒绝／完成／取消／过期／错误与限流原因，只供诊断。

裸板诊断开关`MC02_BENCH_REFEREE_DIAGNOSTICS`默认关闭，只允许独立bench_safe禁热配置。具名`Basic_Framework_MC02_refdiag_bench_safe.elf`等待首个新鲜身份后，先运行30秒满长交互，再运行45秒混合空操作UI与交互，随后停止产生测试流量；没有新增任务，也不请求READY。正常六种配置不含这个自动负载。测试内容不代表正式业务，不运行旧模拟器GUI／MQTT。

[`referee_budget_capture.py`](../../tools/referee_budget_capture.py)只通过专用裁判口提供机器人状态，保存原始二进制、逐帧CRC／序号和MCU完成记录。它要求已verify的准确ELF身份登记，读取期间MCU保持运行；记录丢失、错布局、串口残帧、预算超限或测试时长不足都不能报告通过。UART物理波形、其他发送者的额度、真实客户端显示仍不由此保证。[软件与硬件证据](../workflow/tickets/REF-03.md)分别注明实际完成范围。


### 裸板记录怎样互相核对（REF-03）

本轮最终固件先通过67.4秒被动观察，再采集30秒满长交互和45秒混合流量。PC完整收到2171帧，独立逐位CRC全部正确；MCU记录2174次提交，其中2171次完成、3次因身份取消。线上序号与请求编号对应，越过255八次；取消留下序号空缺是预期行为。

MCU最小启动间隔34ms，UI最小136ms，目标滚动窗口最大3683字节。115ms是UI的最小间隔，严格FIFO和其他流量可以让它等待更久，不能把115ms解释为固定刷新周期。限流等待计数按发送轮询累计，不等于丢帧数。结束时四条存储、活动标志和各条UART计时许可全部清零，没有错误或隔离。

原始文件仍在写入时，缓冲及文件系统元信息可能尚未刷新；进行中的文件大小不能单独证明线路没有数据。应在采集结束后，用CRC正确的完整帧与对应MCU完成记录核验。身份停更窗口与身份变更后的PC到达时间仅作粗略交叉观察，预算仍按MCU时刻计算。这些结果不表示真实裁判客户端已经显示，也不测量精确物理波形。

## 16. 固定SP帧旁边的版本化业务帧（MC02-0070／0089）

SP的29／43字节固定帧仍是默认兼容协议。构建选项`MC02_VISION_PROTOCOL=sp|v2`只选一种实现；V2目前限制在`robot/single`，其他车型没有经过验证的裁判与跨板许可快照，CMake会拒绝组合。V2没有上位机生产代码，本节的字节向量和主机回归用于固件侧核对，不代表现成上位机已支持。

V2帧按字节编码：`MC`、版本`2`、类型、负载长度LE16、序号LE16、来源时刻LE32、负载、CRC16_MODBUS_A5 LE16。帧头12字节，CRC 2字节；负载固定如下。

| 方向与类型 | 负载 | 含义 |
|---|---:|---|
| 上位机→MCU `0x01` | 25字节 | 模式＋偏航／俯仰角、角速度和角加速度；单位依次为rad、rad/s、rad/s²。模式0表示无目标，1表示使用瞄准数据，不含开火字段。 |
| 上位机→MCU `0x02` | 13字节 | 有效位＋本体坐标`vx/vy`与偏航角速度；x向前、y向左，平移m/s，转动rad/s。合法范围由解码器检查。 |
| MCU→上位机 `0x81` | 34字节 | 有效位、0=未就绪／1=READY、四元数(w,x,y,z)、偏航／俯仰角及角速度。角度为rad，角速度为rad/s。 |
| MCU→上位机 `0x82` | 36字节 | 裁判结构化摘要；机器人状态、功率热量和最近射击记录有独立有效位与原接收时刻。 |

导航转换为现有底盘接口时，m/s乘1000得到mm/s，rad/s乘180/π得到deg/s；转换及最终角速度范围不合法时采用零移动命令。自主移动还要求遥控器在线、左开关选择自主、PC输入有效、RobotSafety为READY、机器人状态和功率热量组新鲜且裁判底盘供电位有效。瞄准与导航各自过期：瞄准过期会停瞄准并禁用发射，仍可独立用新鲜导航移动；导航过期、许可丢失或整条USB业务链路离线会清除平移与转动命令。V2本身不提供视觉击发能力。

每种业务使用不同消息中心快照。瞄准50ms、导航100ms，恰好到期仍有效；消息头里的远端源时刻原样保留，当前没有对时就不拿它和本机计时相减。过期检查使用本机首次接收时刻。CRC错误、非法浮点或超龄帧不会发布话题，也不会刷新链路有效时间。

USB连接代号改变后，连接状态先转为离线；首份新连接的合法业务帧可使用任意序号。它会先清空两类旧快照，再只发布当前帧，因此只收到导航不会复用上个连接的瞄准，反之亦然。控制任务在链路离线时清除移动命令；恢复在线但没有新鲜命令时仍保持停止。新导航可独立恢复移动，新瞄准可独立恢复瞄准，对时不作为普通控制恢复的门槛。V2没有击发字段，瞄准恢复不会重放旧击发请求。

消息中心在启动期复制固定话题目录并检查编号、负载大小、端点关系、时钟域、容量及溢出策略。订阅者数据使用静态2048字节池，不在运行时申请内存；快照替换旧值，事件FIFO可拒绝最新项或覆盖最旧项。每条记录分别留来源时刻、首次接收时刻和发布时刻。读取快照不消费也不续期，事件读取按FIFO丢弃过期队头，不能越过它执行后续事件。当前V2协议不含操作事件，所以应用只注册连续状态快照；FIFO语义由独立主机测试验证，不能把裁判射击记录当成控制动作。

需要查看队列时，话题描述符的 `diagnostics_enabled` 决定它是否出现在只读目录。统计复制会一起返回允许关系、实际注册端点、各订阅者队列的合计深度／余量、最高积压和发布／覆盖／拒绝／过期次数；它不会取消息或清理过期数据。过期只在读取者发现并处理时计数，快照每个槽只记一次，FIFO项目在丢弃时计数。robot固件可通过USART10命令`0x04`按目录序号读取单项，仍使用`D3 6C`帧、CRC16_MODBUS_A5和现有发送队列，不发周期统计或日志文字。固定字节、队列以及生产解析器回归见[MC02-0012任务记录](../workflow/tickets/MC02-0012.md)。

板间时钟／CAN桥接仍由MC02-0092、0093跟踪。

[V2编解码测试](../../tests/host/vision_protocol_v2_test.c)使用独立核对的完整固定字节和CRC答案，覆盖四种负载、字段顺序、NaN/Inf、CRC错误、块切分、丢块、重连与组帧超时；[生产链路测试](../../tests/host/vision_v2_link_test.c)还验证错误CRC、CRC正确但含NaN的帧不续期、连接代号切换、任意序号恢复和旧分组清除；[控制任务测试](../../tests/host/robot_cmd_v2_test.c)验证50／100ms边界、离线停止、恢复在线仍不复用旧命令，以及新瞄准／导航分别恢复。SP的跨块接收和超时回归继续由[UART链路测试](../../tests/host/uart_stream_test.c)与[兼容测试](../../tests/host/crc_protocol_test.c)覆盖。WSL和ARM证据见[MC02-0009任务记录](../workflow/tickets/MC02-0009.md)及[V2协议任务记录](../workflow/tickets/MC02-0070-0089.md)。这些结果不验证真实上位机、USB物理时序或底盘实车表现。

## 18. 双协议诊断帧与 DT7 输入窗口（MC02-0101）

`tools/vision_sim.py` 必须显式给出 `--port`，协议用 `--protocol sp|v2` 选择；默认只发全零、mode 0 中立帧。mode 只接受0或1，拒绝SP的mode 2供弹请求。V2工具只构造 `AIM_COMMAND`，该负载没有开火字段。SP mode 1 会提交瞄准数据，固件控制层保持供弹停止，但其火控路径可能使能摩擦轮；不要把“禁火”误读成“所有执行器都不动作”。

命令行角度统一使用度：`--yaw-deg`、`--pitch-deg`、两个角速度和两个角加速度参数分别以度、度/秒、度/秒²输入。SP与V2在线上都使用弧度，编码前统一乘以 π/180；字段按小端float32写入。V2额外带16位序号和32位单调毫秒来源时刻，序号自然回绕。SP沿用其反射CRC，V2使用CRC16/MODBUS。两者固定向量都与独立生产测试向量核对。

串口必须由操作者明确指定；工具不猜端口、不扫描备用端口。默认20Hz、10秒，每次写入默认100ms超时，频率最多200Hz、单轮最多3600秒。串口占用／打开错误、超时、短写或其他写错误均报告后结束本轮，不重试或追赶积压帧。USB CDC可能忽略波特率，但写入仍受有限时限约束。工具和测试只在主机运行，不连接带执行器的机器人。

`tools/dt7_input.py` 保留已核对的 DJI 控制器 VID/PID/序列号、输入租约、启动时两帧全松开、暂停释放和发送失败即停止。实时窗口标题取显式选择的端口；180秒时长上限只限制离线回放文件，不限制 live 窗口。上述检查由[工具测试](../../tests/tools/test_vision_sim.py)和[DT7回归](../../tests/tools/test_dt7_input.py)覆盖，详见[任务记录](../workflow/tickets/MC02-0101.md)。它们不替代真实设备上的物理接口或运动验证。


## 17. V2 对时只建立局部时间映射（MC02-0090）

V2 构建由 MCU 主动发起对时探测：`0x83` 负载携带非零请求编号，帧头来源时刻记录 MCU 发出探测时的毫秒值 T1。PC 回应 `0x03` 时，在负载返回请求编号和 PC 收到探测的时刻 T2，并在回应帧头来源时刻写入 PC 发出回应的时刻 T3。MCU 解析完整回应帧时，用最后一个字节所属接收块的原始时间记录 T4。解析器仍保留首字节接收时间，业务期限继续使用原接收时间。

时间映射按四个时刻估计 `PC 时钟−MCU 时钟` 偏差：`((T2−T1)+(T3−T4))/2`；网络往返时间为 `(T4−T1)−(T3−T2)`。四个计数均按 32 位毫秒回绕计算，无法区分半周期、逆序、超过 100 ms 的交换或超过 50 ms 的往返样本会被拒绝，边界允许。连续三个合格样本后才报告同步，并使用最近三个偏差的中位数。新样本与当前偏差相差超过 50 ms 时重新收集三份样本。超过 2 秒没有有效样本后，同步状态失效；最后偏差仍可用于诊断，但不再允许转换。

链路每 500 ms 最多发起一个探测，同一时刻只保留一个请求；100 ms 响应期限到达后记超时，探测仍按 500 ms 节奏。请求编号回绕时跳过 0。USB 连接代号改变会清除旧映射；旧连接回应不参与恢复。`VisionGetTimeSyncSnapshot()` 复制偏差、样本年龄、最近往返时间和同步状态；`VisionMapRemoteTime()` 只在映射有效时执行转换，失败保留调用方输出。

映射是显式局部工具，不自动改写消息中心的远端来源时间，也不改变瞄准／导航按 MCU 接收时刻判断的新鲜度。旧 SP 格式没有来源时刻，SP 构建明确报告对时不可用，不虚构时间戳。主机生产链路测试覆盖固定字节、100 ms 与 50 ms 边界、请求超时、连接代号切换、三样本同步、2 秒失效和业务接收计数保持；这些结果不替代上位机实机互通或 USB 物理链路测量。

## 18. V2 发送 BMI088 原始加速度（MC02-0006／0007）

MC02-0006和MC02-0007共用V2 IMU状态帧`0x84`。17字节负载为有效标记、非零样本序号和三轴小端float32；帧头的`source_time_ms`保存BMI088样本建立时刻。无效帧将标记、序号、数值及源时刻全部置零。采样0毫秒仍合法，不能用`if (timestamp)`判断样本有没有更新。

三轴使用BMI088传感器x/y/z轴，单位m/s²并包含重力。INS在原始采样有效性检查后发布它，不要求EKF同时接受加速度量测，也不做安装方向修正。V2每50ms最多发一帧，姿态、裁判摘要和加速度轮流占用发送机会，所以加速度名义上约每150ms出现一次；被报告为有效的样本必须不超过5ms。过期、失效或话题记录消失时发送全零无效帧，避免远端误用旧值。接收方可以用样本序号检查重复／乱序，用源时间检查年龄；本轮没有迁移生产上位机。

SP仍是原来的29字节命令和43字节状态，未增加隐式字段。固定字节向量和生产INS—消息中心—V2路径分别由[协议测试](../../tests/host/vision_protocol_v2_test.c)和[链路测试](../../tests/host/vision_v2_link_test.c)覆盖。WSL Debug／Release和ARM的SP、V2 USB、V2 UART构建只证明软件兼容及编译链接，不证明传感器安装坐标、物理串口、上位机消费或实体加速度精度；具体证据见[任务记录](../workflow/tickets/MC02-0006-0007.md)。

## 19. 消息中心不增加裸指针读取（MC02-0013）

`MessagePublishAt()`把调用方数据复制到模块自己的话题槽，发布函数返回后，调用方可以复用栈上或临时缓冲。`MessageReadSnapshot()`再把最新且未过期的数据复制到读取者自己的对象。复制接口让生产者和读取者各自持有稳定数据，不要求调用者记住何时释放一份跨任务共享的指针。

只读视图仍要先把发布数据复制到消息中心拥有的存储。读取者取得视图时需要登记租约；发布者替换最新值时必须保留仍被读取者使用的旧槽。读取者要在同一个普通任务中串行取得和释放租约；未释放的视图会占住槽位。池满时发布必须返回容量错误并保留旧快照，不能改写读者仍在看的字节。多订阅者还需要独立引用计数和代号检查，防止重复或过期释放把新槽误认为旧槽。V2解码和INS等调用处会传入局部变量，消息中心仍需复制它们，原始指针不能直接留到后续任务读取。

本轮按九个生产话题逐项跑了WSL模型：每话题均为单发布者、单订阅者、容量1的最新快照；负载大小总和236字节。只读租约模型按每话题`订阅者数+2`个版本槽计，九个话题需要708字节负载区；另一个三订阅者租约压力样例使用40字节。这个估算没有计算引用计数、代号、时间信息和订阅者租约字段，也不是固件RAM增量测量。

当前单板`RobotCMDTask()`只读取云台反馈话题`0x0104`，负载为42字节。生产任务的5次测量每轮都复制42字节；100批、每批50000轮的WSL CPU时间均值分别为233、232、235、246、239 ns/轮，中位数235 ns。对`0x0104`单独反复读取时，生产复制读取的5次均值中位数为21 ns（范围19～23 ns）；候选`Acquire/Release`视图模型的中位数为32 ns（范围31～37 ns）。视图省去每次读取的42字节复制，但租约登记、引用计数和额外释放临界区使这份主机模型变慢约11 ns。这个模型没有实现生产模块全部校验与统计，数字只用于当前接口决策，不代表H723速度或物理运行收益。

当前话题负载很小，主机测量没有显示只读视图带来净耗时收益，还要额外管理版本池和租约失败。于是本轮不增加生产指针接口，保留`MessageReadSnapshot()`的复制语义。若后续H723性能记录确认某个大负载复制已成为瓶颈，应先针对那个话题测量，再单独设计有限租约和池满行为。完整边界、运行数据和主机限制见[MC02-0013评估记录](../workflow/tickets/MC02-0013.md)；可重跑模型见[视图评估测试](../../tests/host/message_center_pointer_eval_test.c)和[RobotCMD性能测试](../../tests/host/robot_cmd_perf_test.c)。

## 20. 裁判 UI 用车型配置和新鲜数据绘制（MC02-0095）

`RefereeUIConfig_t` 是车型长期保存的只读布局。每项字段包含唯一三字节图形名、ASCII标签、坐标、字号、线宽、颜色和数据来源；启动时检查字段数量、文本长度、坐标、协议枚举以及图形名重复。当前最多8项、单条文字最多30字节，帧启动间隔配置为115～1000ms。哨兵配置五项数据：比赛阶段和剩余时间、当前／最大血量、底盘功率上限、缓冲能量及17mm热量。

`UIRefresh()` 每轮复制一次裁判数据，随后只读取布局指定的命令组。对应命令过期或从未收到时绘制`--`，不把缓存的数值误当作当前数据。状态变化时缓存每项的数值和有效位；文字在准备发送时再格式化，这样就不需要在RAM中为每个字段长期保存完整文本。一次服务最多提交一帧：先删旧图，再每字段提交一帧；运行后只更新变化项。在途字段继续变化时用版本号保留新值，等旧帧结束后再发最新内容。

裁判机器人身份失效时，UI停止刷新并取消尚未启动的旧身份报文；再次收到有效身份或身份编号变化时，自动进行一次有限重绘。`MyUIInit()`可由上层显式请求重新绘制。UI与机器人交互消息共用REF-03队列和额度，实际发送还需通过启动身份检查。`UI_SUBMITTED`只表示本机队列接受，`UI_OK`表示本轮没有提交新报文；两者都不代表裁判客户端已显示。

软件回归由[裁判UI测试](../../tests/host/referee_ui_test.c)、[UI与UART队列联测](../../tests/host/uart_ui_integration_test.c)和[裁判发送预算测试](../../tests/host/referee_budget_test.c)覆盖。WSL Debug／Release全量CTest各486/486，ASan／UBSan专项31/31；哨兵UI开启固件在Debug及RelWithDebInfo下成功构建。链接报告主RAM仍接近128KiB上限：分别剩余256和296字节；不能把“链接成功”理解成后续无需检查静态RAM。没有实测真实串口波形或客户端屏幕显示，证据见[MC02-0095记录](../workflow/tickets/MC02-0095.md)。

## V2 编解码的编译边界（MC02-0086）

车型选择 V2 协议时，`vision_protocol_v2.c` 现在进入框架对象目标，只引用标准 C 和框架 CRC 接口。Windows ARM 编译与依赖检查没有发现厂商或 RTOS 头；Windows 主机在 `-O0` 和 `-O2` 下通过既有固定帧及流式拼帧测试，WSL Debug／Release 全量回归也覆盖该测试。尝试配置禁热 V2 固件时被现有构建门槛拒绝：当前 V2 仅允许 `robot/single`，因此完整 V2 固件链接仍待验证。
