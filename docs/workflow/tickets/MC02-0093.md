# MC02-0093：CAN 板间对时与桥接恢复计划

任务状态以 [TODO](../../../.Doc/TODO.md) 为准。本计划与 [MC02-0092](MC02-0092.md) 共用当前分支：双板桥接需要实际的时间映射才能安全交付命令，两个任务分别记录验收。

## 现状和目标

当前双板 `RobotCanBridgeInit()` 向接收桥接传入空时间映射，远端命令和反馈始终被拒绝；不能以能编译或替身映射通过当作实际可通信。两板先使用各自 HAL 毫秒计数，通过经典 CAN 交换时间，将远端来源时刻转换到本地，桥接继续按最早可能来源时刻检查有效期。目标是两端同时运行新版桥接与对时，失同步时撤销旧消息、禁止依赖它的控制，恢复后只接收新消息。

## 实施步骤

1. 复用现有 `TimeMapping` 的四时刻、三样本、32 位回绕和期限检查，补充板间传输；不改变 USB 对时已有语义。两个板各自主动发起探测，避免任何一侧只能发送不能判断自己的接收数据。
2. 复用已有桥接 CAN 接收 ID 和生产有界发送队列，以高半字节不同于话题分片的独立帧类型区分探测与响应。每帧最多 8 字节，携带类型、请求编号、一个毫秒时刻和软件 CRC8；一条响应由两个有序帧分别携带对端收、发时间，完整请求匹配后才交给时间映射。响应组数量、排队期限、单次处理量及重试均有界，不阻塞电机控制。
3. 记录探测提交时刻和中断入队的原始接收时刻；响应生成时读取发送提交时刻，排队和总线等待计入往返。默认限制往返与交换时长，连续取得三份有效样本后允许转换；给桥接返回包含量化、往返上限和声明的时钟频率误差的保守余量。误差上限依赖真实时钟误差及硬件时基连续性，必须说明并在实物验收时核对。
4. 丢帧、CRC错误、重复／错序／错误编号、旧响应、过期、回绕和时间跳变不得刷新同步。停止收到样本后按有效期限关闭映射，周期服务撤销已发布数据并丢弃半包；物理断线本身并非能够瞬间观察到的事件。检测到对端时钟向后跳转时清除旧来源序号，重新取得三份有效样本后接受新消息。限制同一方向同时在途的响应组，避免积压旧响应被复位后的新请求反复采用。
5. 先写双端生产协议及生产消息中心行为测试，覆盖两端不同起点、双向收发、错误帧、时钟回绕、超时、偏差变化、单板复位与恢复；再接入实际 CAN 回调和电机任务服务。核查话题与对时同时发送时队列、CAN 带宽和高优先级电机帧期限，测试包括积压及中断；不以模拟 HAL 的瞬时完成证明实物时序。
6. 使用 WSL Debug／Release、适用 ASan／UBSan 和双板／单板禁热 ARM 构建验证；复核每种角色的资源余量、源文件和 ELF 隔离。更新 CAN 使用说明、教学笔记和索引，说明真实总线、频率误差、重启和设备参数仍须裸板或实际硬件验证。完成工作区自查后按用户要求审查、更新两个 TODO 项并提交。

本计划不授权连接开发板、发送真实 CAN 帧或驱动执行器；物理波形与时钟精度不属于主机测试证据。

## 软件实现与验证

双方通过同一个板间CAN端点各自发起探测；`C1`探测、`C2`接收时刻、`C3`响应提交时刻各占一帧，序号16位、时刻32位小端，CRC8多项式`0x31`、初值0、无反射和异或。最多一组响应在途；拥塞时按200ms节奏重试。收到重复、错误序号、损坏CRC或逆序响应时不接受样本。异常处理使用源接收时间而非任务处理时刻。

主机测试覆盖两端不同时钟起点、固定线字节、CRC与序号错误、重复与乱序、32位回绕、队列拥塞、样本过期、时钟跳变和对端重启；桥接集成测试验证重启或映射不可用时撤销旧话题，重新对时后接受新来源。两种生产角色均通过实际初始化及状态副本测试；`production_can_time_sync`、`production_can_topic_bridge`、两个角色实例、发送预算和绝对期限共6项ASan／UBSan通过。WSL Debug／Release各480／480通过，十种ARM固件与角色隔离通过，内存和调度模型数据见[MC02-0092](MC02-0092.md)。

误差界依赖两板时基持续运行且相对频率误差不超过0.2%，没有实测时不能将其当成硬件保证。短暂断线由话题自身期限及同步样本期限发现，不保证断线瞬间获知；总线BusOff的恢复仍由既有任务处理。实体线上的仲裁、重试、时钟与任务负载，以及自动恢复行为均未连接硬件验证。
