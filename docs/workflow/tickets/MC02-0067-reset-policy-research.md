# MC02-0067：复位边界与恢复参数的资料核对

## 目的与范围

本记录核对整机自动复位应覆盖哪些故障、重复复位怎样停止，以及恢复额度多久清零。资料于2026-10-26查阅。外部项目用于比较处理方式，不替MC02确定可直接照搬的次数或时长，也不构成安全认证。

## MC02中可能触发故障复位的路径

以下内容按当前实现核对，是否在板上可靠失能仍由[MC02-0067主任务记录](./MC02-0067.md)中的硬件验收确认。

| 故障入口 | 当前行为 | 是否计入恢复额度 |
|---|---|---|
| INS、MOTOR、ROBOT、DAEMON、UART_TX等核心任务超过期限 | 任务监控写入核心任务故障原因并关闭已知输出；之后停止喂IWDG，由看门狗复位 | 是 |
| NMI、HardFault、MemManage、BusFault、UsageFault等CPU异常 | 保存崩溃现场、写入CPU异常原因并请求系统复位 | 是 |
| `assert`、FreeRTOS栈溢出钩子、致命`Error_Handler()` | 记录对应原因并进入现有复位／等待路径 | 是 |
| IWDG、WWDG复位 | 启动时读取RCC复位标志；WWDG标志按芯片头文件定义读取 | 是 |
| 非POR的BOR复位 | 启动时按RCC的BOR标志记为欠压复位；POR建立新运行周期 | 是，POR例外 |
| 普通软件复位或外部NRST，且之前没有写入故障原因 | 继续启动检查，但单独不消耗故障额度 | 否 |
| 遥控器／USB／裁判来源失联、传感器数据失效、CAN BusOff、电机离线、辅助任务失败 | 由各自来源状态、控制失能或依赖降级处理；这些输入或单项功能失效不能单独证明整机调度已损坏 | 否 |

任务监控故障和通信来源故障要分开看：例如CAN来源离线本身不触发整机重启；若负责控制的核心任务也超过自身期限，则由任务期限路径计数。启动配置阶段的`Error_Handler()`记录致命原因，但看门狗是否已启动、何时复位要按实际启动阶段另行验证。

## 外部项目的处理方式

| 来源 | 查到的做法 | 对MC02可参考之处 |
|---|---|---|
| [PX4安全与失效保护](https://docs.px4.io/main/en/config/safety) | 按故障提供警告、Hold、Return、Land、Disarm或Terminate等动作；遥控链路和电机异常会按模式及配置选择动作。 | 可恢复的来源问题优先采用针对来源的控制动作，不把所有失效都变成整机复位。该文档没有规定恢复重启次数或稳定时长。 |
| [ArduPilot Rover崩溃检查源码](https://github.com/ArduPilot/ardupilot/blob/master/Rover/crash_check.cpp) | 连续满足配置的崩溃条件后切入Hold，配置要求时解除电机使能。 | 机械或运动异常优先停止／保持车辆；不因一个普通运行状态异常统一重启。 |
| [ArduPilot崩溃记录上锁检查](https://github.com/ArduPilot/ardupilot/blob/master/libraries/AP_Arming/AP_Arming.cpp) | 有崩溃记录时默认产生解锁前错误；只有显式设置高级参数才跳过该检查，代码警告崩溃后的车辆可能不适合继续飞行。 | 把“程序重启成功”和“允许重新使能”分开；需检查或明确确认后才能解除。 |
| [ESP-IDF致命错误处理](https://docs.espressif.com/projects/esp-idf/en/latest/esp32/api-guides/fatal-errors.html) | 将CPU异常、看门狗、欠压、栈溢出、堆完整性错误和断言列为致命错误；可配置为保存寄存器后重启或停机。 | 致命错误类别应由目标平台明确列出，复位或停机是策略选择，不能从“可重启”推导“可重新使能”。 |
| [Zephyr任务看门狗](https://docs.zephyrproject.org/latest/services/task_wdt/index.html) | 多任务系统可以用多个看门狗通道分别检查线程；硬件看门狗可作为任务看门狗或调度器故障的后备。 | 核心任务进度应分别检查，硬件看门狗用于软件监控自身失效时的后备。该文档不提供跨启动重试次数。 |
| [systemd启动频率限制](https://www.freedesktop.org/software/systemd/man/260/systemd.unit.html) | 用时间窗和允许启动次数限制反复启动；达到上限后不再自动重启，管理员可以等待窗口或显式清理失败状态。 | 可参考“达到上限后停止自动循环”和“解除动作必须明确”。它运行在有管理员和更完整存储的主机上，不能照搬到MCU安全锁定。 |
| [ST STM32H723/733 RM0468](https://www.st.com/resource/en/reference_manual/dm00603761.pdf) | RCC复位状态寄存器提供POR、BOR、IWDG、WWDG、软件及引脚等复位来源标志。 | 启动代码应在既有清标志步骤前保存原始标志，并按硬件实际组合解释；软件标志不能替代断电、欠压和复位引脚实测。 |

资料的共同点是分类处理、限制故障重启循环，并将锁定与重新使能分开。不同项目的用途和硬件不同；没有来源能证明“3次”或“30秒”是通用标准。

## 对当前MC02参数的建议

当前实现最多允许三次合格故障复位；第4次故障启动进入锁定。恢复额度只在`RobotSafety`为READY、所有核心任务当前期限检查通过、没有待处理故障或人工急停时连续30秒后清零。`RobotTask()`约每5ms观察一次，任务健康按当前毫秒时间重新检查。

建议现阶段保留**3次＋30秒**作为明确的软件策略：三次允许少量瞬态故障恢复，第四次停止继续自动循环；30秒覆盖多个核心任务检查周期，并能较快释放一次已稳定恢复后的额度。此选择优先保留运行可用性，但不由外部项目数值背书。软件测试证明边界和状态转换，不证明实际任务调度、复位引脚或外部驱动安全。

达到第4次后保持故障锁定：普通诊断清理、软件复位、NRST、RobotSafety故障清理、标定、使能和急停解除均不能清锁。当前记录放在NOLOAD AXI SRAM，冷POR会重新建立运行周期并清除记录；因此这不是跨断电的持久锁。若将来要求“断电后仍需维护员确认故障原因才可解锁”，必须增加有独立故障语义的持久记录或硬件锁存，并单独评估异常路径写Flash的风险。

30秒清额度是连续条件：任何一项核心任务不健康、RobotSafety离开READY、出现待处理故障或人工急停，都会停止或重新开始计时。它仍可能放过间隔超过30秒才出现一次的低频问题；若日志或板测显示此类故障，优先增加滚动时间窗限制，再评估延长稳定期，而不是未经数据就拉长等待或放宽三次上限。

## 尚不能据此关闭MC02-0067

- 当前软件路径列出了故障原因，但没有证据证明所有车型的电机、舵机和加热输出在复位前、复位期间及启动前都处于安全电平。
- 板测尚未确认IWDG／WWDG实际窗口、BOR与POR标志组合、AXI SRAM ECC写入和复位保留。
- NOLOAD AXI SRAM会在断电时丢失；冷POR清额度不等价于维护人员已确认故障已排除。
- 因此三次和30秒可保留为待硬件验收的软件策略，MC02-0067继续开放。
