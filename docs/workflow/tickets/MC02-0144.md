# MC02-0144：受限调试固件的软件入口

任务状态和完整验收条件以 [TODO](../../../.Doc/TODO.md) 为准。此处记录构建边界与仍需接入的内容。

## 观察入口

`MC02_PROFILE=commissioning` 和 `MC02_COMMISSIONING_TARGET=observe` 生成独立命名的观察固件。它沿用裸板的禁热和不驱动执行器路径，但生成配置、健康接口与产物名称使用独立的调试身份。可选择已有的遥控观察功能；该功能不请求 READY。

观察固件不启用底盘、云台、发射、命令和电机控制，三路受控电源保持关闭。当前构建仍包含已有的视觉接收功能，但它不能取得运动授权。观察身份不表示允许实车通电或动作，现场条件另行确认。

本机可通过预设生成带遥控观察的 `commissioning/observe`，并检查构建身份和源码隔离。产物为 `Basic_Framework_MC02_commissioning_observe_rcdiag.elf`。

```sh
python3 tools/workflow/verify.py --fast --firmware --presets commission-observe-rcdiag-debug
```

预设从 `rcdiag-debug` 继承单板、Debug、禁热及遥控观察配置。`MC02_PROFILE=commissioning` 选择独立构建身份，`MC02_COMMISSIONING_TARGET=observe` 选择观察入口，`MC02_ENABLE_LCD=OFF` 关闭板载显示。校验检查三路受控电源的生成配置以及 ELF 中是否链接执行器入口。

## 受限底盘入口

`commissioning/chassis` 选择单板四轮底盘、独立底盘任务及 DJI 收发。遥控摇杆或有效键盘按车型映射产生本体坐标下的速度，人工明确使能后仍须等待新的来源数据。安全管理独立核对 IMU、轮组反馈、故障与时限。受限底盘不启动视觉和 USB 链路，云台、发射、加热及超级电容不参与构建。三路板控电源保持关闭，因此车型确认还需覆盖底盘独立供电条件。

四轮底盘共用车型配置中的 `dji_chassis_output_limit_raw`。运动固件在申请设备前检查该值和轮组配置，DJI 驱动在控制环和方向换算结束后限制报文中的最终值。这个字段使用电调原始命令单位。当前哨兵的几何、安装方向、输出上限、人工映射、供电和任务时限仍需结合实物确认。构建只接受车型源码中的确认声明，不能用命令行缓存覆盖。若声明通过而运行参数无效，启动仍然失能。

受限底盘要求配置有效的平移与转动变化率，单位分别为 m/s² 和 rad/s²。命令按上次成功发布以来的实测间隔逐步变化。上一个目标过期、间隔超限或发布失败时立即撤销当前输出许可。重新取得有效输入及许可后，首条命令从零速度开始。哨兵的实车变化率仍待确认。

整车命令任务在漏拍、超期或计时失败时先撤销运行许可，同时清除人工来源、底盘话题和速度变化基准，再报告时序故障。底盘命令的消费者无法继续读出尚未到期的旧目标。此前读出的目标或已经排队的旧帧仍须通过发送前的安全代际检查。[本机故障联测](MC02-0144-evidence/README.md#命令任务时序失败时撤销旧目标)

车型选择在受控电源开启和轮电机注册前检查人工映射、最长计算间隔和变化率。两种人工来源都须使用底盘本体坐标，最长间隔内的两个允许步长都须可计算。人工检查失败返回 `ROBOT_CONFIG_BAD_MANUAL_INPUT` 并清除活动车型。命令入口复用这项检查，然后再确认运行所需的话题期限。

车型预检还会对已分配的底盘轴试算。摇杆和拨轮使用车型允许范围及 DBUS 解码范围中的较小值，键盘使用实际按键幅值 1。按正式换算流程检查原始值到 SI 速度的乘法，并继续检查限幅后的 mm/s、deg/s。任一来源失败均报告 `ROBOT_CONFIG_BAD_MANUAL_INPUT`。

启动还会读取发布任务的名义周期。最大计算间隔、摇杆和键鼠映射期限以及协议允许的最长有效时间，都须覆盖该周期。否则启动诊断指出整车任务的时间配置不匹配，受限底盘保持失能。这个检查只排除无法跨过一个名义周期的配置。输入已使用的时间、任务抖动和通信延迟仍由运行期检查处理。

启动还会检查人工命令、底盘计算、电机计算和软件 CAN 发送的组合时限。已发布命令须能在话题期限内送到发送服务。若从合法人工输入已可读取开始算，整条路径还须落在摇杆、键鼠和协议的原有期限内。组合超限报告 `INIT_RESOURCE_TASK_CHASSIS_PIPELINE`，在启动设备前保持失能。实际接收排队、任务执行时间和 CAN 总线占用仍须实测。

相邻两次发布的名义最大间隔按发布任务的周期加执行预算计算。上一拍刚唤醒就发布、下一拍在预算末尾发布时，旧目标仍须在话题有效期和变化率最大计算间隔之内。配置无法覆盖这个间隔时，启动也会报告 `INIT_RESOURCE_TASK_CHASSIS_PIPELINE`。运行期继续检查原始来源是否过期及实际发布间隔。

纯底盘的 CAN 恢复复用真实轮组反馈和人工新输入检查，启用云台的车型仍需有效的云台应用反馈。哨兵的恢复稳定时长仍未确认，当前配置不启用自动恢复。`gimbal` 和 `both` 仍拒绝构建。

## 受限底盘构建提示

CMake 会列出[车型构建声明](../../../application/config/sentinel_robot/sentinel_build.cmake)中尚未满足的两组确认项。数据仍由[车型参数](../../../application/config/sentinel_robot/sentinel_config.c)提供。

| 确认项 | 需要核对的参数 |
|---|---|
| `MC02_VEHICLE_COMMISSIONING_CHASSIS_CONFIRMED` | 每轮位置、滚动方向和轮径，CAN 设备编号、安装方向和减速比，轮组速度及电调输出上限，底盘独立供电条件。 |
| `MC02_VEHICLE_MANUAL_INPUT_CONFIRMED` | 摇杆和键鼠映射、来源有效期和最大计算间隔，命令周期与底盘任务时序，平移和转动变化率。 |

两项都通过后，启动仍会校验数值和执行时限。单板受限底盘使用原有 IMU、裁判和遥控依赖，云台和发射保持关闭。

本机配置、源码和 ELF 检查见[验证记录](MC02-0144-evidence/README.md)。上板和上车观察、实物方向及停止表现属于另行确认的现场验收。

## USART10 只读运动反馈

`commissioning/chassis` 的诊断串口沿用 `D3 6C` 版本 1 帧，命令 `0x05` 的请求无负载，应答使用命令 `0x85` 并回显请求序号。应答负载固定为 38 字节。多字节整数及 binary32 浮点均按小端编码。其他配置未登记此命令时返回原有的单字节参数错误。[诊断帧头和 CRC](../../../bsp/log/bsp_log_diag.h)

序号为 `0x47` 的查询帧是 `D3 6C 01 05 47 00 A1 BC`。应答先校验帧长、序号及 CRC，再按下表读取负载。

| 负载位置 | 类型 | 内容 |
|---|---|---|
| 0 | u8 | 格式版本 1 |
| 1 | u8 | bit 0 表示速度有效，bit 1 表示里程计有效 |
| 2–5 | u32 | 速度所用的最早轮速接收时刻，ms |
| 6–17 | 3 × binary32 | 前向与左向速度（m/s）、绕上轴角速度（rad/s） |
| 18–25 | 2 × u32 | 位姿所用的最早轮速接收时刻（ms）、本地里程计段号 |
| 26–37 | 3 × binary32 | 相对段起点的前向与左向位移（m）、朝向（rad） |

缺测项的整组字段清零，须用有效位区分缺测和实际零值。当前哨兵的里程计配置为关闭，开启所需的反馈间隔仍待实测。每次请求读取一次，无周期推送。查询时继续检查原始样本期限和四轮反馈是否中断，返回值只表示查询当时的状态。段号变动后，两段位姿各用自己的原点。[线上编码](../../../application/chassis/chassis_motion_diag.c) · [底盘反馈接口](../../../application/chassis/chassis_feedback.h)
