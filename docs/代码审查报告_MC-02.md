# MC-02 代码审查报告与 Bug 修复 Todolist

> 审查日期：2026-08-07  
> 审查范围：`Core/`、`bsp/`、`modules/`、`application/`、`USB_DEVICE/` 全部自有代码，以及 Makefile / CMakeLists 构建配置  
> 审查方式：逐文件静态审查 + 模块间接口/中断/任务/外设交叉核对

## 0. 结论摘要

按源码分析，**该固件直接上电会因 `BuzzerTask()` 空指针崩溃而无法运行**（已核实为唯一真实 P0；原报告中的 SysTick 与 DWT 两项经交叉核实为误报，详见 CORE-01/CORE-02）：

1. **`BuzzerTask()` 遍历全空数组并解引用 NULL**（真实 P0，本次已修复）：`BuzzerRegister()` 从未被调用，daemon 任务第一次执行 `BuzzerTask()` 即 HardFault。
2. ~~**工程未定义 `SysTick_Handler`**~~（已核实为误报）：`FreeRTOSConfig.h` 将 `xPortSysTickHandler` 宏定义为 `SysTick_Handler`，`port.c` 编译产物即强符号 `SysTick_Handler`，链接 map 确认向量表正常指向它；HAL tick 由 TIM23 提供，无冲突。
3. ~~**DWT 时间基准配置错误**~~（已核实为误报）：HSE=24MHz，PLL M2/N40/P1 → SYSCLK=480MHz；`SYSCLKDivider=DIV1`，CPU 核时钟 480MHz；DWT CYCCNT 按 CPU 核时钟计数，`DWT_Init(480)` 正确（HCLK=240MHz 不是 DWT 计数时钟）。

除上述问题外，视觉链路（`VisionUpdateTx` 从未被调用、UART9 无中断）、电机控制（LK/HT/DM 多处拷贝粘贴错误）、底盘速度单位换算缺失等问题也直接影响整车功能，详见下文。

### 严重度定义

| 级别 | 含义 |
|---|---|
| P0 | 必然崩溃 / 无法启动 / 核心时序错误 |
| P1 | 功能失效、控制异常或大概率现场故障 |
| P2 | 边界条件、健壮性、潜在越界/数据竞争 |
| P3 | 建议优化、代码规范、死代码 |

## 1. Core / 系统层（main、FreeRTOS、中断、时钟）

### CORE-01 [P0] 缺少 `SysTick_Handler`，调度器启动后系统挂死

- 位置：`Core/Inc/FreeRTOSConfig.h:147`（`#define xPortSysTickHandler SysTick_Handler`），`startup_stm32h723xx.s:342`（弱别名到 `Default_Handler`），`Core/Src/stm32h7xx_it.c`（全文无 `SysTick_Handler`）
- 现象：`osKernelStart()` 后第一个 tick 进入 `Default_Handler` 的 `Infinite_Loop`，所有任务无法运行。
- 修复：在 `stm32h7xx_it.c` 添加：
  ```c
  void SysTick_Handler(void)
  {
      osSystickHandler();
  }
  ```
  注意 HAL 时间基准已由 TIM23 提供（`HAL_TIM_PeriodElapsedCallback` 中 `HAL_IncTick()`），不要再在 SysTick 里重复调用 `HAL_IncTick()`，否则 `HAL_GetTick()` 会加倍。

**核实结论（2026-08-07）：误报，无需修改。** `FreeRTOSConfig.h:147` 的宏会作用于 `port.c` 中 `xPortSysTickHandler` 的定义，编译链接产物为强符号 `SysTick_Handler`（`build/Basic_Framework_MC02.map:10266` 显示其来自 `build/port.o`），启动文件中的弱别名不会生效；HAL 时间基准已由 TIM23 提供，二者不冲突。注意：**不要**按上面原建议在 `stm32h7xx_it.c` 再添加 `SysTick_Handler`，否则会与 `port.o` 强符号重复定义导致链接失败；且 `cmsis_os.c` 的 `osSystickHandler()` 经宏展开会直接调用 `SysTick_Handler`，再加包装会产生无限递归。

### CORE-02 [P0] DWT 频率与实际 HCLK 不匹配

- 位置：`bsp/bsp_init.h:18`（`DWT_Init(480)`）；`Core/Src/main.c`（SYSCLK=500MHz，`AHBCLKDivider = RCC_HCLK_DIV2` → HCLK=250MHz）
- 现象：`DWT_GetDeltaT/GetTimeline*` 全部按 480MHz 计算，实际时间被压缩为 250/480≈52%。PID 积分/微分、电机离线计时、CAN 发送超时、EKF dt 全部失真。
- 修复：改为 `DWT_Init(SystemCoreClock / 1000000U)`（此时 `SystemCoreClock` 为 250MHz），或直接 `DWT_Init(250)`；同时更新 `bsp_dwt.h` 中“C板168MHz/A板180MHz”的注释。

**核实结论（2026-08-07）：误报，无需修改。** 本板 HSE=24MHz（`stm32h7xx_hal_conf.h:110`、`Basic_Framework_MC02.ioc:841`），PLL M2/N40/P1 → SYSCLK=480MHz；`SYSCLKDivider=RCC_SYSCLK_DIV1`（CDCPRE=DIV1）→ CPU 核时钟=480MHz；DWT CYCCNT 按 CPU 核时钟计数（STM32 官方社区确认），故 `DWT_Init(480)` 正确。HCLK=240MHz 是 AHB 总线时钟，不是 DWT 的计数时钟。原“500MHz / 250MHz / 偏小 1.92 倍”是按 25MHz 晶振推算的，不适用于本板；若硬件实际为 25MHz 晶振，应修 `HSE_VALUE` 而不是 `DWT_Init`。

### CORE-03 [P2] `BSPInit()` 定义在头文件中

- 位置：`bsp/bsp_init.h:13-22`
- 说明：非 `static`、非 `inline` 的函数定义放在头文件，一旦被多个 .c 包含会重复定义。目前仅 `robot.c` 包含，暂不报错，建议改为 `.c` 实现或 `static inline`。

### CORE-04 [P2] `main.c` 保留 2×32KB 未使用测试缓冲

- 位置：`Core/Src/main.c:47-49`（`W25Qxx_WriteBuffer/ReadBuffer`，各 32KB）
- 影响：占用 64KB RAM（H723VG 内部 RAM 紧张），且当前没有使用 OCTOSPI/W25Q 的代码调用它们。
- 修复：删除或改为小缓冲/条件编译。

### CORE-05 [P3] 运行时间统计回调为空实现

- 位置：`Core/Src/freertos.c:74-82`
- 说明：`configGENERATE_RUN_TIME_STATS=1` 但 `configureTimerForRunTimeStats/getRunTimeCounterValue` 是空实现，`vTaskGetRunTimeStats` 数据无意义。若不用统计功能可关闭宏。

### CORE-06 [P1] FDCAN 标称波特率约为 1.0417Mbps，不是 1Mbps

- 位置：`Core/Src/fdcan.c:48-51`（FDCAN1/2/3 均为 `NominalPrescaler=3, TSeg1=29, TSeg2=10`）
- 计算：FDCAN 内核时钟 = PLL1Q = 125MHz（PLLM=2、PLLN=40、PLLQ=4，VCO=500MHz）；位时间 = 3 × (1+29+10) = 120Tq → 125MHz/120 ≈ **1.0417MHz**，与 DJI/裁判等 1Mbps 总线偏差约 4.17%，超过 CAN 时钟容差，可能导致电机/裁判通信误码甚至无法同步。
- 修复：调整分频使位时间精确 1MHz，例如 `Prescaler=5, TSeg1+TSeg2=24`（125MHz/(5×25)=1MHz），或改 PLLQ 使内核时钟为 100MHz（如 PLLQ=5）后 `Prescaler=4, 25Tq`。修改后需用示波器/逻辑分析仪验证。

**核实结论（2026-08-07）：误报，无需修改。** 本板 HSE=24MHz，PLL1Q = 480/4 = **120MHz**（`fdcan.c:192` MspInit 中 `FdcanClockSelection = RCC_FDCANCLKSOURCE_PLL`），位时间 3×(1+29+10)=120Tq → 120MHz/120 = **1.000Mbps**，与 `.ioc` 中 `CalculateTimeQuantumNominal=25ns / CalculateBaudRateNominal=1000000` 一致。原“125MHz/1.0417Mbps”是按 25MHz 晶振推算的，不适用于本板。

### CORE-07 [P1] UART8/UART9 未使能 NVIC，且中断处理函数缺失

- 位置：`Core/Src/usart.c`（UART8/UART9 仅配置 DMA，无 `HAL_NVIC_EnableIRQ(UART8/9_IRQn)`）；`Core/Src/stm32h7xx_it.c`（无 `UART8_IRQHandler/UART9_IRQHandler`）
- 现象：UART9 用于视觉（`robot_cmd.c:58` `VisionInit(&huart9)`）。`HAL_UARTEx_ReceiveToIdle_DMA` 依赖 IDLE 中断，缺中断后只有 DMA 收满 128 字节才会触发回调，视觉数据只能“攒够一整个缓冲”才解析一次，且多帧只取第一帧，实时性和正确性都无法保证；错误/溢出后也无法恢复。
- 修复：在 `usart.c` MspInit 中为 UART8/9 添加 `HAL_NVIC_SetPriority/EnableIRQ`，并在 `stm32h7xx_it.c` 添加对应 IRQ Handler。

**修复记录（2026-08-07）：已修复。** `usart.c` UART8/UART9 MspInit 的 USER CODE 区新增 `HAL_NVIC_SetPriority(..., 5, 0)` + `HAL_NVIC_EnableIRQ(...)`（优先级与工程其他 UART 一致）；`stm32h7xx_it.c` 新增 `UART8_IRQHandler/UART9_IRQHandler`（调用 `HAL_UART_IRQHandler`）。上板验证（CMSIS-DAP + OpenOCD）：
  - 向量表：IRQ83(UART8)=`0x08001CC9`、IRQ155(UART9)=`0x08001CD9`，均指向新 handler；
  - NVIC：`ISER2=0x000C2070`（UART8 bit19）、`ISER4=0x98000000`（UART9 bit27）已置位；
  - UART9 `CR1=0x1D`（UE/TE/RE/IDLEIE），视觉 DMA+IDLE 接收已启动；
  - 系统正常运行（PC 在应用代码，无 HardFault）。

### CORE-08 [P1] I2C2 错误中断（ER）无处理函数

- 位置：`Core/Src/i2c.c:149`（只使能 `I2C2_EV_IRQn`）；`Core/Src/stm32h7xx_it.c`（无 `I2C2_ER_IRQHandler`）
- 影响：I2C 总线错误（NACK/仲裁丢失）时 HAL 无法进入错误回调，DMA/IT 传输可能永久卡住。
- 修复：使能 `I2C2_ER_IRQn` 并添加 `I2C2_ER_IRQHandler`。

**修复记录（2026-08-08）：已修复。** `i2c.c` MspInit USER CODE 区新增 `HAL_NVIC_SetPriority(I2C2_ER_IRQn, 5, 0)` + `HAL_NVIC_EnableIRQ(I2C2_ER_IRQn)`；`stm32h7xx_it.c` 新增 `I2C2_ER_IRQHandler`（调用 `HAL_I2C_ER_IRQHandler(&hi2c2)`）。上板验证：ISER1 bit2 置位、IRQ34 向量 `0x08001CD9` 指向新 handler，系统运行正常。

### CORE-09 [P1] BMI088/IST8310 的 EXTI 中断没有对应 IRQ Handler 和 NVIC 使能

- 位置：`Core/Src/gpio.c`（`ACC_INT_Pin=PE10`、`GYRO_INT_Pin=PE12` 配成 `GPIO_MODE_IT_RISING`）；`Core/Src/stm32h7xx_it.c`（无 `EXTI9_5_IRQHandler/EXTI15_10_IRQHandler`，也没有 `HAL_GPIO_EXTI_IRQHandler` 调用）
- 影响：即使启用 BMI088 新模块的触发模式，数据就绪中断也不会进入 `HAL_GPIO_EXTI_Callback`。
- 修复：按引脚使能 EXTI 并添加处理函数。

**修复记录（2026-08-08）：已修复（按 `bmi088.md` 为准）。** `ACC_INT_Pin/GYRO_INT_Pin`（PE10/PE12）由 `GPIO_MODE_IT_RISING` 改为 **`GPIO_MODE_IT_FALLING`**（文档示例 `EXTI_TRIGGER_FALLING`，与驱动 INT 低有效一致）；两个引脚都在 **EXTI15_10** 组，故在 `MX_GPIO_Init` 内使能 `EXTI15_10_IRQn`（优先级 5），`stm32h7xx_it.c` 新增 `EXTI15_10_IRQHandler`（调用 `HAL_GPIO_EXTI_IRQHandler(GPIO_PIN_10 | GPIO_PIN_12)`）。上板验证：ISER1 bit8 置位、IRQ40 向量 `0x08001CE9` 指向新 handler、FTSR1 bit10/12 置位（下降沿）、RTSR1 清零，系统运行正常。当前 block 模式无注册 GPIO 实例，回调为空操作；切 IT 模式后 `GPIORegister` 分发即可生效。注意 gpio.c 的 `USER CODE BEGIN 1/2` 均在函数体外，NVIC 使能需放在 `MX_GPIO_Init` 函数体内。

## 2. BSP-CAN

### BSPCAN-01 [P2] 过滤器数量检查应为 `>=`，且三个总线计数器互相牵连

- 位置：`bsp/can/bsp_can.c:39`
- 说明：`can1_filter_idx > hfdcan1.Init.StdFiltersNbr` 在 `idx == Nbr` 时仍放行，下一个 `HAL_FDCAN_ConfigFilter` 会越界写 Message RAM；同时任一总线计数越界都会误伤其他总线注册。
- 修复：改为各总线独立判断 `>=`。

### BSPCAN-02 [P2] CAN 接收回调在中断里执行模块回调，缺少与任务的数据同步

- 位置：`bsp/can/bsp_can.c:160-169`
- 说明：`can_module_callback` 在 FDCAN 中断里被调用，DJI 电机等模块会直接改写 `measure` 结构体；任务（`DJIMotorControl`）同时在读。32 位对齐读写大体原子，但 `total_round/total_angle` 这类多步更新仍可能被撕裂，历史“编码器跳动”问题与此相关。
- 建议：回调中仅拷贝到实例缓冲并 `osSignalSet` 唤醒解析任务；或对多字更新做临界区保护。

### BSPCAN-03 [P3] `CANTransmit` 依赖 DWT 超时，且 `busy_count` 为全局共享

- 位置：`bsp/can/bsp_can.c:207-231`
 - 说明：超时依赖 DWT 软件计时（CORE-02 已核实为误报，当前按 480MHz 计数正确）；`static uint32_t busy_count` 跨实例共享，日志计数无意义。建议超时改用硬件时间戳并去掉共享静态变量。

## 3. BSP-UART

### BSPUART-01 [P1] `USARTIsReady()` 恒返回“忙”

- 位置：`bsp/usart/bsp_usart.c:83-87`
  ```c
  if (_instance->usart_handle->gState | HAL_UART_STATE_BUSY_TX)
  ```
- 说明：位或结果恒非 0，函数永远返回 0。任何依赖它做 DMA/IT 连续发送的模块将永远不发。
- 修复：注意不能直接改“位与”——HAL 状态值中 `HAL_UART_STATE_READY=0x20`、`HAL_UART_STATE_BUSY_TX=0x21`，`0x20 & 0x21 = 0x20` 仍恒非 0。应改为状态相等判断：`(gState == HAL_UART_STATE_READY)`。
- 备注：当前全工程无调用方，修复后行为不变，仅修正 API 供后续连续发送使用。
- **修复记录（2026-08-08）：已修复（早期提交，待办补打勾）。** `USARTIsReady` 改为 `gState == HAL_UART_STATE_READY` 相等判断；当时无调用方，本次随 VISION-02 实际启用（`VisionSend` 忙时跳过）。

### BSPUART-02 [P1] 串口错误回调未先 Abort/清错误状态就重启 DMA 接收

- 位置：`bsp/usart/bsp_usart.c:127-135`
- 说明：HAL 出错后 `RxState` 仍为 `BUSY_RX`，直接 `HAL_UARTEx_ReceiveToIdle_DMA` 返回 `HAL_BUSY`，接收永久停摆（裁判、遥控、视觉断链后无法自恢复）。
- 修复：先 `HAL_UART_AbortReceive()`（或 `HAL_UART_Abort()`）再重启接收；`RefereeLostCallback/RCLostCallback/VisionOfflineCallback` 等离线恢复路径同样受益。

**修复记录（2026-08-07）：已修复（阻塞版）。** `HAL_UART_ErrorCallback` 中先 `HAL_UART_AbortReceive(huart)`（清错误标志、复位 `RxState`），再 `HAL_UARTEx_ReceiveToIdle_DMA` 重启；Abort 或重启失败均打日志（不做重试）。中断版 Abort 与重试机制已列入 P2 todolist 作为将来升级项。

### BSPUART-03 [P1] 模块回调拿不到“本次实际接收长度”

- 位置：`bsp/usart/bsp_usart.c:102-118`；`modules/master_machine/master_process.c:82`
- 说明：`HAL_UARTEx_RxEventCallback` 的 `Size` 被丢弃，模块回调无参数；`DecodeVision` 只能按 `recv_buff_size`（固定 128）整缓冲扫描，会把历史残留帧当新帧解析。
- 修复：给 `usart_module_callback` 增加长度参数（或把 `Size` 存到 `USARTInstance`），视觉/裁判等按实际长度解析。

**修复记录（2026-08-07）：已修复（方案 B）。** `USARTInstance` 新增 `last_recv_size`，`HAL_UARTEx_RxEventCallback` 回调前写入本次实际 `Size`；视觉 `DecodeVision` 改用 `vision_usart_instance->last_recv_size` 解析。回调签名升级（`void (*)(uint16_t size)`，让裁判/遥控等全部显式接收长度）作为将来升级项列入 P2 todolist。

### BSPUART-04 [P3] `recv_buff_size` 使用 uint8_t，缓冲上限 255

- 位置：`bsp/usart/bsp_usart.h:27`
- 说明：与 `USART_RXBUFF_LIMIT=256` 配合时若配置 256 会截断为 0。建议改为 `uint16_t` 并校验。

## 4. BSP-SPI

### BSPSPI-01 [P1] `SPIDeviceOnGoing` 只有索引 0 被初始化，SPI2 首次 `SPITransRecv` 死锁

- 位置：`bsp/spi/bsp_spi.c:8`

- 说明：C 初始化器只给 `[0]=1`，`[1]` 为 0；`SPITransRecv` 中 `while (!SPIDeviceOnGoing[1]) ;` 会永远等待。BMI088 新模块（`modules/BMI088/bmi088.c`）通过 SPI2 收发时必然卡死。
- 修复：`= {1, 1}` 或改用 `= { [0 ... SPI_DEVICE_CNT-1] = 1 }`。

**修复记录（2026-08-08）：已修复。** 改为 GCC 范围指定初始化 `{[0 ... SPI_DEVICE_CNT - 1] = 1}`，全部总线初始为空闲；自旋等待无超时问题另列 BSPSPI-04。

### BSPSPI-02 [P1] TX 完成回调缺失，DMA/IT 纯发送后片选不释放

- 位置：`bsp/spi/bsp_spi.c`（只重写了 `HAL_SPI_RxCpltCallback` 和 `HAL_SPI_TxRxCpltCallback`）

- 修复：实现 `HAL_SPI_TxCpltCallback`，复用与 RX 相同的 CS 释放逻辑。

**修复记录（2026-08-08）：已修复。** 新增 `HAL_SPI_TxCpltCallback`，直接复用 `HAL_SPI_RxCpltCallback` 的片选释放逻辑；与既有 `HAL_SPI_TxRxCpltCallback` 同构，无重复定义冲突。

### BSPSPI-03 [P2] `SPITransmit/SPIRecv` 不维护 `SPIDeviceOnGoing`，总线互斥不完整

- 位置：`bsp/spi/bsp_spi.c:36-92`
- 说明：仅 `SPITransRecv` 做等待/置位，另外两个接口不置忙标志，多从机共享总线时可能并发拉低 CS。
