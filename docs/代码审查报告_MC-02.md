# MC-02 代码审查报告与 Bug 修复 Todolist

> 审查日期：2026-08-07  
> 审查范围：`Core/`、`bsp/`、`modules/`、`application/`、`USB_DEVICE/` 全部自有代码，以及 Makefile / CMakeLists 构建配置  
> 审查方式：逐文件静态审查 + 模块间接口/中断/任务/外设交叉核对

## 0. 结论摘要

按源码分析，**该固件直接上电会因 `BuzzerTask()` 空指针崩溃而无法运行**（已核实为唯一真实 P0；原报告中的 SysTick 与 DWT 两项经交叉核实为误报，详见 CORE-01/CORE-02）：

1. **`BuzzerTask()` 遍历全空数组并解引用 NULL**（真实 P0，本次已修复）：`BuzzerRegister()` 从未被调用，daemon 任务第一次执行 `BuzzerTask()` 即 HardFault。
2. ~~**工程未定义 `SysTick_Handler`**~~（已核实为误报）：`FreeRTOSConfig.h` 将 `xPortSysTickHandler` 宏定义为 `SysTick_Handler`，`port.c` 编译产物即强符号 `SysTick_Handler`，链接 map 确认向量表正常指向它；HAL tick 由 TIM23 提供，无冲突。
3. ~~**DWT 时间基准配置错误**~~（已核实为误报）：HSE=24MHz，PLL M2/N40/P1 → SYSCLK=480MHz；`SYSCLKDivider=DIV1`，CPU 核时钟 480MHz；DWT CYCCNT 按 CPU 核时钟计数，`DWT_Init(480)` 正确（HCLK=240MHz 不是 DWT 计数时钟）。

除上述问题外，视觉链路（`VisionUpdateTx` 从未被调用、UART9 无中断）、电机控制（LK/HT/DM 多处拷贝粘贴错误）、底盘速度单位换算缺失等问题也直接影响整车功能，详见下文。

### 严重度定义

| 级别 | 含义 |
|---|---|
| P0 | 必然崩溃 / 无法启动 / 核心时序错误 |
| P1 | 功能失效、控制异常或大概率现场故障 |
| P2 | 边界条件、健壮性、潜在越界/数据竞争 |
| P3 | 建议优化、代码规范、死代码 |

## 1. Core / 系统层（main、FreeRTOS、中断、时钟）

### CORE-01 [P0] 缺少 `SysTick_Handler`，调度器启动后系统挂死

- 位置：`Core/Inc/FreeRTOSConfig.h:147`（`#define xPortSysTickHandler SysTick_Handler`），`startup_stm32h723xx.s:342`（弱别名到 `Default_Handler`），`Core/Src/stm32h7xx_it.c`（全文无 `SysTick_Handler`）
- 现象：`osKernelStart()` 后第一个 tick 进入 `Default_Handler` 的 `Infinite_Loop`，所有任务无法运行。
- 修复：在 `stm32h7xx_it.c` 添加：
  ```c
  void SysTick_Handler(void)
  {
      osSystickHandler();
  }
  ```
  注意 HAL 时间基准已由 TIM23 提供（`HAL_TIM_PeriodElapsedCallback` 中 `HAL_IncTick()`），不要再在 SysTick 里重复调用 `HAL_IncTick()`，否则 `HAL_GetTick()` 会加倍。

**核实结论（2026-08-07）：误报，无需修改。** `FreeRTOSConfig.h:147` 的宏会作用于 `port.c` 中 `xPortSysTickHandler` 的定义，编译链接产物为强符号 `SysTick_Handler`（`build/Basic_Framework_MC02.map:10266` 显示其来自 `build/port.o`），启动文件中的弱别名不会生效；HAL 时间基准已由 TIM23 提供，二者不冲突。注意：**不要**按上面原建议在 `stm32h7xx_it.c` 再添加 `SysTick_Handler`，否则会与 `port.o` 强符号重复定义导致链接失败；且 `cmsis_os.c` 的 `osSystickHandler()` 经宏展开会直接调用 `SysTick_Handler`，再加包装会产生无限递归。

### CORE-02 [P0] DWT 频率与实际 HCLK 不匹配

- 位置：`bsp/bsp_init.h:18`（`DWT_Init(480)`）；`Core/Src/main.c`（SYSCLK=500MHz，`AHBCLKDivider = RCC_HCLK_DIV2` → HCLK=250MHz）
- 现象：`DWT_GetDeltaT/GetTimeline*` 全部按 480MHz 计算，实际时间被压缩为 250/480≈52%。PID 积分/微分、电机离线计时、CAN 发送超时、EKF dt 全部失真。
- 修复：改为 `DWT_Init(SystemCoreClock / 1000000U)`（此时 `SystemCoreClock` 为 250MHz），或直接 `DWT_Init(250)`；同时更新 `bsp_dwt.h` 中“C板168MHz/A板180MHz”的注释。

**核实结论（2026-08-07）：误报，无需修改。** 本板 HSE=24MHz（`stm32h7xx_hal_conf.h:110`、`Basic_Framework_MC02.ioc:841`），PLL M2/N40/P1 → SYSCLK=480MHz；`SYSCLKDivider=RCC_SYSCLK_DIV1`（CDCPRE=DIV1）→ CPU 核时钟=480MHz；DWT CYCCNT 按 CPU 核时钟计数（STM32 官方社区确认），故 `DWT_Init(480)` 正确。HCLK=240MHz 是 AHB 总线时钟，不是 DWT 的计数时钟。原“500MHz / 250MHz / 偏小 1.92 倍”是按 25MHz 晶振推算的，不适用于本板；若硬件实际为 25MHz 晶振，应修 `HSE_VALUE` 而不是 `DWT_Init`。

### CORE-03 [P2] `BSPInit()` 定义在头文件中

- 位置：`bsp/bsp_init.h:13-22`
- 说明：非 `static`、非 `inline` 的函数定义放在头文件，一旦被多个 .c 包含会重复定义。目前仅 `robot.c` 包含，暂不报错，建议改为 `.c` 实现或 `static inline`。

### CORE-04 [P2] `main.c` 保留 2×32KB 未使用测试缓冲

- 位置：`Core/Src/main.c:47-49`（`W25Qxx_WriteBuffer/ReadBuffer`，各 32KB）
- 影响：占用 64KB RAM（H723VG 内部 RAM 紧张），且当前没有使用 OCTOSPI/W25Q 的代码调用它们。
- 修复：删除或改为小缓冲/条件编译。

### CORE-05 [P3] 运行时间统计回调为空实现

- 位置：`Core/Src/freertos.c:74-82`
- 说明：`configGENERATE_RUN_TIME_STATS=1` 但 `configureTimerForRunTimeStats/getRunTimeCounterValue` 是空实现，`vTaskGetRunTimeStats` 数据无意义。若不用统计功能可关闭宏。

### CORE-06 [P1] FDCAN 标称波特率约为 1.0417Mbps，不是 1Mbps

- 位置：`Core/Src/fdcan.c:48-51`（FDCAN1/2/3 均为 `NominalPrescaler=3, TSeg1=29, TSeg2=10`）
- 计算：FDCAN 内核时钟 = PLL1Q = 125MHz（PLLM=2、PLLN=40、PLLQ=4，VCO=500MHz）；位时间 = 3 × (1+29+10) = 120Tq → 125MHz/120 ≈ **1.0417MHz**，与 DJI/裁判等 1Mbps 总线偏差约 4.17%，超过 CAN 时钟容差，可能导致电机/裁判通信误码甚至无法同步。
- 修复：调整分频使位时间精确 1MHz，例如 `Prescaler=5, TSeg1+TSeg2=24`（125MHz/(5×25)=1MHz），或改 PLLQ 使内核时钟为 100MHz（如 PLLQ=5）后 `Prescaler=4, 25Tq`。修改后需用示波器/逻辑分析仪验证。

**核实结论（2026-08-07）：误报，无需修改。** 本板 HSE=24MHz，PLL1Q = 480/4 = **120MHz**（`fdcan.c:192` MspInit 中 `FdcanClockSelection = RCC_FDCANCLKSOURCE_PLL`），位时间 3×(1+29+10)=120Tq → 120MHz/120 = **1.000Mbps**，与 `.ioc` 中 `CalculateTimeQuantumNominal=25ns / CalculateBaudRateNominal=1000000` 一致。原“125MHz/1.0417Mbps”是按 25MHz 晶振推算的，不适用于本板。

### CORE-07 [P1] UART8/UART9 未使能 NVIC，且中断处理函数缺失

- 位置：`Core/Src/usart.c`（UART8/UART9 仅配置 DMA，无 `HAL_NVIC_EnableIRQ(UART8/9_IRQn)`）；`Core/Src/stm32h7xx_it.c`（无 `UART8_IRQHandler/UART9_IRQHandler`）
- 现象：UART9 用于视觉（`robot_cmd.c:58` `VisionInit(&huart9)`）。`HAL_UARTEx_ReceiveToIdle_DMA` 依赖 IDLE 中断，缺中断后只有 DMA 收满 128 字节才会触发回调，视觉数据只能“攒够一整个缓冲”才解析一次，且多帧只取第一帧，实时性和正确性都无法保证；错误/溢出后也无法恢复。
- 修复：在 `usart.c` MspInit 中为 UART8/9 添加 `HAL_NVIC_SetPriority/EnableIRQ`，并在 `stm32h7xx_it.c` 添加对应 IRQ Handler。

**修复记录（2026-08-07）：已修复。** `usart.c` UART8/UART9 MspInit 的 USER CODE 区新增 `HAL_NVIC_SetPriority(..., 5, 0)` + `HAL_NVIC_EnableIRQ(...)`（优先级与工程其他 UART 一致）；`stm32h7xx_it.c` 新增 `UART8_IRQHandler/UART9_IRQHandler`（调用 `HAL_UART_IRQHandler`）。上板验证（CMSIS-DAP + OpenOCD）：
  - 向量表：IRQ83(UART8)=`0x08001CC9`、IRQ155(UART9)=`0x08001CD9`，均指向新 handler；
  - NVIC：`ISER2=0x000C2070`（UART8 bit19）、`ISER4=0x98000000`（UART9 bit27）已置位；
  - UART9 `CR1=0x1D`（UE/TE/RE/IDLEIE），视觉 DMA+IDLE 接收已启动；
  - 系统正常运行（PC 在应用代码，无 HardFault）。

### CORE-08 [P1] I2C2 错误中断（ER）无处理函数

- 位置：`Core/Src/i2c.c:149`（只使能 `I2C2_EV_IRQn`）；`Core/Src/stm32h7xx_it.c`（无 `I2C2_ER_IRQHandler`）
- 影响：I2C 总线错误（NACK/仲裁丢失）时 HAL 无法进入错误回调，DMA/IT 传输可能永久卡住。
- 修复：使能 `I2C2_ER_IRQn` 并添加 `I2C2_ER_IRQHandler`。

**修复记录（2026-08-08）：已修复。** `i2c.c` MspInit USER CODE 区新增 `HAL_NVIC_SetPriority(I2C2_ER_IRQn, 5, 0)` + `HAL_NVIC_EnableIRQ(I2C2_ER_IRQn)`；`stm32h7xx_it.c` 新增 `I2C2_ER_IRQHandler`（调用 `HAL_I2C_ER_IRQHandler(&hi2c2)`）。上板验证：ISER1 bit2 置位、IRQ34 向量 `0x08001CD9` 指向新 handler，系统运行正常。

### CORE-09 [P1] BMI088/IST8310 的 EXTI 中断没有对应 IRQ Handler 和 NVIC 使能

- 位置：`Core/Src/gpio.c`（`ACC_INT_Pin=PE10`、`GYRO_INT_Pin=PE12` 配成 `GPIO_MODE_IT_RISING`）；`Core/Src/stm32h7xx_it.c`（无 `EXTI9_5_IRQHandler/EXTI15_10_IRQHandler`，也没有 `HAL_GPIO_EXTI_IRQHandler` 调用）
- 影响：即使启用 BMI088 新模块的触发模式，数据就绪中断也不会进入 `HAL_GPIO_EXTI_Callback`。
- 修复：按引脚使能 EXTI 并添加处理函数。

**修复记录（2026-08-08）：已修复（按 `bmi088.md` 为准）。** `ACC_INT_Pin/GYRO_INT_Pin`（PE10/PE12）由 `GPIO_MODE_IT_RISING` 改为 **`GPIO_MODE_IT_FALLING`**（文档示例 `EXTI_TRIGGER_FALLING`，与驱动 INT 低有效一致）；两个引脚都在 **EXTI15_10** 组，故在 `MX_GPIO_Init` 内使能 `EXTI15_10_IRQn`（优先级 5），`stm32h7xx_it.c` 新增 `EXTI15_10_IRQHandler`（调用 `HAL_GPIO_EXTI_IRQHandler(GPIO_PIN_10 | GPIO_PIN_12)`）。上板验证：ISER1 bit8 置位、IRQ40 向量 `0x08001CE9` 指向新 handler、FTSR1 bit10/12 置位（下降沿）、RTSR1 清零，系统运行正常。当前 block 模式无注册 GPIO 实例，回调为空操作；切 IT 模式后 `GPIORegister` 分发即可生效。注意 gpio.c 的 `USER CODE BEGIN 1/2` 均在函数体外，NVIC 使能需放在 `MX_GPIO_Init` 函数体内。

## 2. BSP-CAN

### BSPCAN-01 [P2] 过滤器数量检查应为 `>=`，且三个总线计数器互相牵连

- 位置：`bsp/can/bsp_can.c:39`
- 说明：`can1_filter_idx > hfdcan1.Init.StdFiltersNbr` 在 `idx == Nbr` 时仍放行，下一个 `HAL_FDCAN_ConfigFilter` 会越界写 Message RAM；同时任一总线计数越界都会误伤其他总线注册。
- 修复：改为各总线独立判断 `>=`。

### BSPCAN-02 [P2] CAN 接收回调在中断里执行模块回调，缺少与任务的数据同步

- 位置：`bsp/can/bsp_can.c:160-169`
- 说明：`can_module_callback` 在 FDCAN 中断里被调用，DJI 电机等模块会直接改写 `measure` 结构体；任务（`DJIMotorControl`）同时在读。32 位对齐读写大体原子，但 `total_round/total_angle` 这类多步更新仍可能被撕裂，历史“编码器跳动”问题与此相关。
- 建议：回调中仅拷贝到实例缓冲并 `osSignalSet` 唤醒解析任务；或对多字更新做临界区保护。

### BSPCAN-03 [P3] `CANTransmit` 依赖 DWT 超时，且 `busy_count` 为全局共享

- 位置：`bsp/can/bsp_can.c:207-231`
 - 说明：超时依赖 DWT 软件计时（CORE-02 已核实为误报，当前按 480MHz 计数正确）；`static uint32_t busy_count` 跨实例共享，日志计数无意义。建议超时改用硬件时间戳并去掉共享静态变量。

## 3. BSP-UART

### BSPUART-01 [P1] `USARTIsReady()` 恒返回“忙”

- 位置：`bsp/usart/bsp_usart.c:83-87`
  ```c
  if (_instance->usart_handle->gState | HAL_UART_STATE_BUSY_TX)
  ```
- 说明：位或结果恒非 0，函数永远返回 0。任何依赖它做 DMA/IT 连续发送的模块将永远不发。
- 修复：注意不能直接改“位与”——HAL 状态值中 `HAL_UART_STATE_READY=0x20`、`HAL_UART_STATE_BUSY_TX=0x21`，`0x20 & 0x21 = 0x20` 仍恒非 0。应改为状态相等判断：`(gState == HAL_UART_STATE_READY)`。
- 备注：当前全工程无调用方，修复后行为不变，仅修正 API 供后续连续发送使用。
- **修复记录（2026-08-08）：已修复（早期提交，待办补打勾）。** `USARTIsReady` 改为 `gState == HAL_UART_STATE_READY` 相等判断；当时无调用方，本次随 VISION-02 实际启用（`VisionSend` 忙时跳过）。

### BSPUART-02 [P1] 串口错误回调未先 Abort/清错误状态就重启 DMA 接收

- 位置：`bsp/usart/bsp_usart.c:127-135`
- 说明：HAL 出错后 `RxState` 仍为 `BUSY_RX`，直接 `HAL_UARTEx_ReceiveToIdle_DMA` 返回 `HAL_BUSY`，接收永久停摆（裁判、遥控、视觉断链后无法自恢复）。
- 修复：先 `HAL_UART_AbortReceive()`（或 `HAL_UART_Abort()`）再重启接收；`RefereeLostCallback/RCLostCallback/VisionOfflineCallback` 等离线恢复路径同样受益。

**修复记录（2026-08-07）：已修复（阻塞版）。** `HAL_UART_ErrorCallback` 中先 `HAL_UART_AbortReceive(huart)`（清错误标志、复位 `RxState`），再 `HAL_UARTEx_ReceiveToIdle_DMA` 重启；Abort 或重启失败均打日志（不做重试）。中断版 Abort 与重试机制已列入 P2 todolist 作为将来升级项。

### BSPUART-03 [P1] 模块回调拿不到“本次实际接收长度”

- 位置：`bsp/usart/bsp_usart.c:102-118`；`modules/master_machine/master_process.c:82`
- 说明：`HAL_UARTEx_RxEventCallback` 的 `Size` 被丢弃，模块回调无参数；`DecodeVision` 只能按 `recv_buff_size`（固定 128）整缓冲扫描，会把历史残留帧当新帧解析。
- 修复：给 `usart_module_callback` 增加长度参数（或把 `Size` 存到 `USARTInstance`），视觉/裁判等按实际长度解析。

**修复记录（2026-08-07）：已修复（方案 B）。** `USARTInstance` 新增 `last_recv_size`，`HAL_UARTEx_RxEventCallback` 回调前写入本次实际 `Size`；视觉 `DecodeVision` 改用 `vision_usart_instance->last_recv_size` 解析。回调签名升级（`void (*)(uint16_t size)`，让裁判/遥控等全部显式接收长度）作为将来升级项列入 P2 todolist。

### BSPUART-04 [P3] `recv_buff_size` 使用 uint8_t，缓冲上限 255

- 位置：`bsp/usart/bsp_usart.h:27`
- 说明：与 `USART_RXBUFF_LIMIT=256` 配合时若配置 256 会截断为 0。建议改为 `uint16_t` 并校验。

## 4. BSP-SPI

### BSPSPI-01 [P1] `SPIDeviceOnGoing` 只有索引 0 被初始化，SPI2 首次 `SPITransRecv` 死锁

- 位置：`bsp/spi/bsp_spi.c:8`

- 说明：C 初始化器只给 `[0]=1`，`[1]` 为 0；`SPITransRecv` 中 `while (!SPIDeviceOnGoing[1]) ;` 会永远等待。BMI088 新模块（`modules/BMI088/bmi088.c`）通过 SPI2 收发时必然卡死。
- 修复：`= {1, 1}` 或改用 `= { [0 ... SPI_DEVICE_CNT-1] = 1 }`。

**修复记录（2026-08-08）：已修复。** 改为 GCC 范围指定初始化 `{[0 ... SPI_DEVICE_CNT - 1] = 1}`，全部总线初始为空闲；自旋等待无超时问题另列 BSPSPI-04。

### BSPSPI-02 [P1] TX 完成回调缺失，DMA/IT 纯发送后片选不释放

- 位置：`bsp/spi/bsp_spi.c`（只重写了 `HAL_SPI_RxCpltCallback` 和 `HAL_SPI_TxRxCpltCallback`）

- 修复：实现 `HAL_SPI_TxCpltCallback`，复用与 RX 相同的 CS 释放逻辑。

**修复记录（2026-08-08）：已修复。** 新增 `HAL_SPI_TxCpltCallback`，直接复用 `HAL_SPI_RxCpltCallback` 的片选释放逻辑；与既有 `HAL_SPI_TxRxCpltCallback` 同构，无重复定义冲突。

### BSPSPI-03 [P2] `SPITransmit/SPIRecv` 不维护 `SPIDeviceOnGoing`，总线互斥不完整

- 位置：`bsp/spi/bsp_spi.c:36-92`
- 说明：仅 `SPITransRecv` 做等待/置位，另外两个接口不置忙标志，多从机共享总线时可能并发拉低 CS。

### VISION-06 [P1] 视觉通信端到端未跑通（已解决：正式链路为板载 USB CDC 虚拟串口）

- 发现时间：2026-08-07（CORE-07 上板验证期间）
- 现象：用虚拟串口发送 SP 视觉帧，`recv_data` 始终为 0。
- 根因（2026-08-08 核实）：
  - 正式机器人链路是**板载 STM32 USB CDC 虚拟串口**（`usb_device.c` 描述符 VID=0x0483/PID=0x5740 “STM32 Virtual ComPort”，主机侧为 COM10），并非 UART9/USART10；

  - 因此正确做法是启用 `VISION_USE_VCP`，走 `bsp_usb` + `CDC_Receive_HS` 回调，而不是临时改 UART 句柄/波特率。
- 修复与验证（2026-08-08）：
  - `robot_def.h` 正式启用 `VISION_USE_VCP`（UART 路径保留为备用宏）；
  - `VisionInit` 的 VCP 分支注册 `DecodeVision` 到 USB CDC 接收回调（VISION-04 此前已核实为误报，链路实际可用）；
  - 上板实测：从 COM10 发送 29 字节模拟 `Vision_Recv_s` 帧（S/P + mode=1 + 6×float + CRC16/X25），OpenOCD/GDB 读到 `recv_data` 完整正确（yaw=0.1、yaw_vel=0.2、yaw_acc=0.3、pitch=-0.4、pitch_vel=-0.5、pitch_acc=0.6、crc16=0xD8F0）；`send_data` 同时被 `VisionUpdateTx` 正常填充（四元数 + yaw≈2.807rad + 弹速 30）。
  - 临时补丁（USART10 波特率 115200、`VisionInit(&huart10)`）已还原；正式配置为 VCP + `VisionInit(&huart9)`（句柄在 VCP 分支下不使用）。

### VISION-07 [P2] VCP 发送忙检查/发送队列（升频预留）

- 位置：`modules/master_machine/master_process.c`（`VisionSend()` VCP 分支）；`bsp/usb/bsp_usb.c`（`USBTransmit`）；`USB_DEVICE/App/usbd_cdc_if.c`（`CDC_Transmit_HS`）

- 实测结果（USB-only，5Hz 刷新，P1 系统页）：

  | 项目 | 实测值 |
  |---|---|
  | 全系统任务占用（累计） | motortask 48.2%、instask 35.7%、**lcdtask 8.9%**、IDLE 5.9%、robottask 0.7%、USB(defaultTask) 0.36%、daemontask 0.15%、uitask ≈0 |
  | LCD 单帧刷新数据量 | 68.4KB（其中值区无条件清屏 172×16px×8 行 = 44KB，占 64%） |
  | LCD 单帧纯 SPI 时间 | 68.4KB×8/15MHz ≈ 36.5ms，加 HAL 行开销 ≈ 38ms（= 5Hz 下 19% CPU） |
  | LCD 行调用 | 289 次/帧；实测 176B/99us → SCK≈14.2Mbit/s（配置 15MHz，prescaler=8） |

  | LCD 初始化（一次性） | 816ms（含 RES/休眠退出 320ms 的 HAL_Delay） |
  | 按键/在位采样 | 7~9us / 50ms（≈0.02%） |
  | 生效刷新率 | 当前整机负载下 ~2.2Hz（LCD 是 osPriorityLow，需求 19% 但只拿到 8.9%） |

  - LCD 自身开销完全由 SPI 决定，占空比 = 5Hz × 38ms ≈ 19%（若 SPI 提到 30MHz 则 ≈9.5%，若改为“只在数值变化时重绘”可再降一个量级）；

  | CAN 发送/失败 | 22698 次全失败 | tx_ok≈1000/s、丢弃约 10~20/30s | 不再有超时等待 |
  | MotorControlTask 频率 | 250Hz | **997Hz** | 回到设计的 1kHz |
  | DWT 分段 | CAN 发送段 3068µs | **8.2µs**；PID 34.8µs | 98.9% 的浪费被消除 |

- 测量驱动的两个反直觉结论（已记入学习文档与本节）：
  1. **TX 完成/队列空中断不值得开**：实测每秒进 2 万多次中断（远多于实际帧数），而 `TXBTO` 是累计标志，用 popcount 统计会重复累加；信息与 `tx_ok` 重复。故默认关闭（回调保留，注释一行即可启用）。
  2. 空总线上 BusOff 仍会发生（TEC 涨到 ~250 → BusOff 每 30s 约 1 次）：这是**没有从机应答**的必然结果，现在已能自动恢复（`busoff_recover` 递增），系统不再卡死；接上电机或 CAN 分析仪后应归零。
- 待观察（下次接硬件时）：① USB-CAN 适配器不参与应答（见下条）；② CAN3 偶发 `MESSAGE_LOST`（该总线上当前没有任何设备），待有硬件时复核。

### 2026-09-21：USB-CAN 适配器接入验证（python-can 尝试）

- 环境：`python-can 4.6.1` + `pyserial 3.5` 已安装；适配器枚举为 `VID_2E88&PID_4603`（CDC，COM15，"CDC Config"）。
- 结论：
  - **不是 slcan/CANable**：对 `\r` / `C\r` / `S8\r` / `O\r` 等标准 ASCII 命令**零响应**，python-can 的 slcan 后端能"连上"但一帧都收不到 → **python-can 无法直接驱动该适配器**（它用的是私有二进制协议，需要厂商上位机或协议文档）。
  - **但能当"只听"监视器**：私有帧为 16 字节、同步字 `55 AA`，实测格式 `55 AA | 11 08 | ID_L ID_H | DATA0..7 | xx xx`。写了 `tools/usbcan_serial_monitor.py`（纯 pyserial）解帧，实测能看到 MCU 发的 `0x200` 帧（1.2~2.2k 帧/s）。
  - **判决性实验**：用 OpenOCD 暂停 MCU → 适配器数据流几乎归零；恢复 → 立刻回到 1.4k 帧/s。**证明它报的就是我们总线上的真实帧**，也就是说物理层、波特率（1Mbps）、接线都是对的。
  - **它不回 ACK**：MCU 侧 TEC 长期 190~250（接近 BusOff），所以三条总线都在周期性 BusOff→恢复。推测其"通道未打开/静默模式"，需要厂商命令打开。**这解释了为什么 CAN1 状态显示 OFF，不是 MCU 配置错误。**
- 附带修正（此前工具误读）：三条总线实际都在正常发送，每组 1 帧/ms：

  | 总线 | 使能的发送组 | 实测速率 |
  |---|---|---|
  | CAN1 | `0x200`（底盘 M3508 组） | 1000/s，丢弃≈0 |
  | CAN2 | `0x200` | 1000/s，丢弃 ≈1.7/s |
  | CAN3 | `0x1FF`（云台 GM6020：yaw+pitch） | 1000/s，丢弃≈0.1/s |

  → 同时确认了 `application/gimbal/gimbal.c` 里云台电机是**硬编码在 CAN3**（`tx_id=1/2`），而 `sentinel_config.c` 里写的 `gimbal_type=MINI_GIMBAL`、yaw/mini_yaw/pitch 在 CAN2 —— **配置文件与实际注册不一致**（对应既有待办 APP-10"配置框架接入或删除"，本次从实测确认）。
- 待办：拿到适配器型号/厂商上位机后，补"打开通道 + 发送"支持，才能进一步验证"发送成功路径"和"注入假电机反馈"。

### 2026-09-21：放弃该适配器，改用 FDCAN 回环自测（CAN-04）

- 用户决定：不再为那台私有协议适配器做逆向，改用 **MCU 自身回环**验证 CAN 收发链路。
- 新增：`CANRunLoopbackSelfTest()`（`bsp/can/bsp_can.c`）+ 开关 `CAN_SELFTEST_LOOPBACK`（默认 **0**，置 1 时在 daemon 任务首轮执行一次）。
- 测试内容（逐条总线）：切到回环模式 → 注册一个测试实例（真实占用一个滤镜 + 进入 `rx_lookup`）→ 连发 8 帧并逐帧校验 ID/DLC/数据 → 注销实例 → 恢复 NORMAL 模式 → **重装所有已注册实例的滤镜**（`HAL_FDCAN_Init` 会清空消息 RAM 里的滤镜，这一步不做会导致正式设备收不到帧）。
- **实测结果（2026-09-21，USB 供电、无电机）**：

  | 指标 | 结果 |
  |---|---|
  | `can_selftest_pass_mask` | **0x07（CAN1/CAN2/CAN3 全部通过）** |
  | `can_selftest_tx_ok / tx_fail` | 24 / 0（8 帧 × 3 总线，全部被硬件接受） |
  | `can_selftest_rx_ok / rx_bad` | **24 / 0**（每帧都通过滤镜 → 中断 → 查表派发 → 回调，且数据完全正确） |
  | `can_prof_rx_frames` / `can_prof_rx_isr.max_us` | 24 / **5µs**（RX 中断平均开销极小） |

  → 这是**这块板子上第一次验证 CAN 接收路径**（之前只有发送被测过）。
- 过程中发现并修掉的问题（都记进学习文档的"坑"清单）：
  1. **`HAL_FDCAN_Init()` 不会清 `CCCR.INIT`**：初始化完成后必须再调 `HAL_FDCAN_Start()`；而且 HAL 内部的 `hfdcan->State` 很容易与真实硬件状态失配（`Start()` 只在 `State==READY` 时才动作，否则直接返回错误、什么都不做）→ 新增 `CANForceMode()`：先对齐 State，启动后**回读 `CCCR.INIT` 校验**。
  2. **健康监控升级**：除 BusOff 外，现在还检测并恢复"`CCCR.INIT=1`（外设停在初始化状态）"的总线 —— 这种情况以前会静默失联。
  3. **启动阶段 `HAL_GetTick()` 不递增**（TIM23 时间基准此时还没工作，实测 `uwTick` 冻在 2）：任何在调度器启动前用 `HAL_GetTick()` 做超时的等待都会**死等**（自测第一版就卡在这里，靠 PC → addr2line 定位到等待循环）。启动阶段一律用 DWT 计时。
  4. **内部回环（Internal Loopback）在这颗 H7 上不自应答**：实测发送的帧被判 ACK 错误、进不了 RX FIFO（TEC 归零、RXF0S=0）。改用**外部回环**（会自己 ACK）才能做完整链路自测；测试 ID 用 `0x123`，不是任何电机指令，总线上有别的设备也安全。
  5. 自测必须**放在设备注册之后**（否则 `CANRegister → CANServiceInit` 会重新配置总线、把自测的接收配置覆盖掉）；并且**发送 ID 必须等于滤镜接收 ID**（开发中先踩了 `tx=0x123 / rx=0x321` 不匹配的坑，表现为"帧收到了但被滤镜挡掉"）。

### 2026-09-22：CPU 饱和排查 —— 第 4 步「热路径日志限速」（CPU-04）

- 新增统一限速组件：`bsp/log/bsp_log.h` 的 `LogRateLimit_t` + `LogRateLimitAllow(rl, period_ms)`（内部用 `HAL_GetTick`，打印时给出"累计次数 / 期间被限速条数"）。
- 应用位置：
  - **4 个任务超时日志**（INS/MOTOR/Daemon/ROBOT）：原来格式串是坏的 —— `%f` 传的却是 `&ins_dt`（指针），RTT 又不支持浮点，打出来一直是 `dt = []`；现在改成整数微秒 + 限速 1 条/秒，并把原来的 `DWT_GetTimeline_ms()`（内部 64bit 除法，1kHz 下不便宜）换成轻量周期探针；

- 顺带修工具：`tools/probe_snapshot.py` 的 `can_bus` 步长改为**从 ELF 符号大小自动推算**（`nm --print-size`），以后改结构体不会再出现"读错位"。

### 2026-09-22：`-O2` 再进一步 —— 复位源已锁定在"运行期看门狗 + 标定循环失控"

两轮干净实验的结果：

1. **逐轮喂狗实验**（标定循环里每轮 `BSP_WatchdogFeed()`）：`-O2` 仍然复位 → **复位源不是"启动期看门狗窗口不足"**；日志里 `reset reason: IWDG1` 属于**运行期**那次（`RobotInit()` 末尾设的 200ms）。
2. **临时把任务监控改成"无条件喂狗"**（`monitor_paused = 1`，只为实验）：复位停止，系统稳定停在卡死状态 → 说明复位链条是：
   `某个被监控任务/daemon 停喂 → TaskMonitor 不喂 → 200ms IWDG 复位 → 重新启动 → 再次卡死 → 循环`。
3. 在"不复位"的实验环境下读到：`cali_diag_outer`（标定外层重试次数）在 25s 内 **111 → 133 持续增长**，而

**本轮修改**

- 把标定循环的超时判断从 `DWT_GetTimeline_s()` 换成**周期计数器** `DWT_ProbeStart()/DWT_ProbeElapsedUs()`（与我们所有探针同一套、已验证在 `-O2` 下可用）；超时值仍为 12.01s，行为等价；
- 保留"标定循环逐轮喂狗"（对启动期看门狗是正确设计）；
- 实验用的 `monitor_paused = 1` 已**撤回**（恢复"关键任务健康才喂狗"的正式行为）。

**当前状态**

- `-Og`（Debug）生产固件已重新烧录并复测正常：`lcd_task_entered=1`、`lcd_init_done=1`、`lcd_heartbeat` 递增（≈4.5/s）、`cali_diag_finish=1`；
- `-O2` 仍未通过：换上周期计数超时后，30s 内标定仍未 `finish`（单次外层应约 3.3s）。**下一步**：① 在标定循环里同时记录"周期计数进度"和"外层重试次数"，确认是"内层确实很慢"还是"外层判据一直失败 + 超时仍未生效"；② 用 GPIO 翻转 + 示波器/逻辑分析仪给 `-O2` 一个**可信的独立时间基准**（避免再用可能有问题的软件计时互证）；③ 若定位到"在线标定本身就是启动瓶颈"，可采用 M1 方案：**启动直接用预标定参数，在线标定改成按需触发**（配合内部 Flash 参数区），这样启动可以缩短到毫秒级，`-O2` 的启动问题自然消失。

### 2026-09-22：预标定启动 + 通用参数存储 + 按需标定 + DWT 时间轴修复（PARAM-01/02、IMU-08、CALIB-01、CAN-08、CPU-05 结案）

这一段是"CPU-05 `-O2` 启动不了"的**收尾**：把根因彻底拆成两半，各修一处。

**改动 1：通用内部 Flash 参数存储（`bsp/param/`，新模块）**

- 物理布局：扇区 6（`0x080C0000`）/ 7（`0x080E0000`）各 128KB 做 A/B 双区；
  `STM32H723VGTx_FLASH.ld` 的 `FLASH` 由 1024K 收到 **768K**，把这两块从程序区挖掉
  （当前镜像仅 ~150KB，完全放得下）。
- 记录格式：记录头 32 字节（`magic`/`version`/`payload_len`/`seq`/`crc32`，正好一个 Flash Word），
  payload 是 TLV（`key u16 | len u16 | data`，每条 4 字节对齐）；软件 CRC32（HAL CRC 未使能）。
- 提交：擦**非活动区** → 按 32 字节 Flash Word 写入 → `SCB_InvalidateDCache_by_Addr` + 回读比对
  → 切活动区。任何一步失败都保留旧记录（A/B 的意义所在）。
- 看门狗：H7 单 bank 擦写期间 CPU 停摆（实测擦 1 扇区 0.83s、2 扇区 1.66s），
  所以提交前 `GetTimeout()` → `SetTimeout(8000)` → 擦写 → **恢复原值**（不是写死 200ms——
  启动期是 4s）。详见《07》第 9 节。
- `ParamInit()` 做成幂等（`s_inited` 保护）：启动时扫一次，之后各模块再调用只返回上次结果，
  避免把 `ParamSet` 改过的 RAM 缓存又用 Flash 老内容覆盖掉。

**改动 2：BMI088 标定流程重构（预标定启动 + 按需标定）**

- `BMI088Register()` 不再无条件跑 6000 次采样在线标定，改为 `BMI088CalibInit()`：

  ```
  Flash 有有效记录 → 直接应用 + RobotSafetySetCalibValid(1)      （启动 <1s）
  无记录           → 首次自动标定一次(最多 3 轮)，成功即写参数区
  标定失败         → 编译期默认值 + RobotSafetySetCalibValid(0)  （不阻塞启动，报警）
  ```

- `BMI088CalibrateIMU()` 改为**返回成败**（1/0），不再自己决定失败后用什么参数；
  外加重试轮数上限 `BMI088_CALI_MAX_ATTEMPTS=3`（原来是"12s 超时前无限重试"）。
- **顺带修掉一个真隐患**：原来结尾无条件 `acc_coef *= 9.805 / gNorm`，
  标定失败时 `gNorm` 可能是垃圾值甚至 0 → 算出 inf/NaN 污染整条加速度链路。
  现在只有判据通过才计算，失败直接回到 `BMI088_ACCEL_6G_SEN`。
- 新增按需标定接口 `BMI088CalibRequest/Service/GetState/AckResult/IsValid`：
  执行体放在 **INS 任务**里（IMU 的 SPI 只被该任务使用，避免和 `INS_Task` 抢总线），
  标定循环每 512 次采样 `osDelay(10)` 让出 CPU，让低优先级的 daemon/LCD 还能跑；
  进入前 `TaskMonitorPause()`（否则 INS/MOTOR 会被判超时把状态推到 FAULT），
  结束后 `TaskMonitorResume()`。

**改动 3：LCD 交互（长按 3s 触发标定）**

- 长按中键分两档（松开时判定）：**1.5~3s = 面板重初始化**（沿用原行为），**≥3s = 进入按需标定**。
- 流程：`RobotSafetyRequestCalib(1)`（进 CALIB，电机失能）→ `BMI088CalibRequest()`
  → LCD **立刻**显示「标定中 / 请保持静止」（不等标定跑起来，因为一开始 CPU 就被抢走）
  → 成功「标定成功」/ 失败「标定失败」保持 3s → `BMI088CalibAckResult()` + 回 SAFE。
- IMU 页新增 `CAL` 行：标定来源（`FLASH`/`AUTO`/`MAN`/`DEF`）+ 标定时温度。
  （注意：本工程用 `nano.specs`，`snprintf` 不支持 `%f`，所以是手算一位小数。）
- 中文字库由 `tools/lcd_font/gen_cn_font.py` 重新生成（93 字，新增 中/静/止/成/失/败/请/保/持），
  新增 `CALIB_RUN`/`CALIB_HOLD`/`CALIB_OK`/`CALIB_FAIL` 四组标签。

**改动 4：DWT 时间轴重写（`-O2` 卡死的直接原因之一）**

- 旧实现 `CYCCNT_RountCount * UINT32_MAX + cnt_now` 有三个问题：
  ① 模数写 `UINT32_MAX` 而不是 `2^32`，每次回绕少算 1；② 每次调用做 64bit 除法；
  ③ **`-O2` 下"读 CYCCNT → 比较 → 累加 → 写回"被编译器重排，实测返回值根本不前进**
  → EKF 的 `dt` 恒为 0、标定的 12s 超时永不触发 → 无限重标定 → 启动卡死。
- 改为增量累加：每次只读一次 `CYCCNT`，用 32bit 无符号减法拿到"距上次的周期数"
  （回绕天然正确），累加进 64bit 总数；读-改-写用临界区保护；
  `DWT_GetTimeline_s/ms` 改用预计算的 `1/f` 常数，热路径没有除法。
- LCD/CAN 的探针统一改用 `DWT_ProbeStart()/DWT_ProbeElapsedUs()`（直接读 CYCCNT，不经过时间轴）。

**改动 5：`-O2` 一上电就 HardFault 的真凶 —— `CANInstance` 非对齐访问**

修完时间轴后 `-O2` 仍然复位，但日志停在 `[bmi088] 使用 Flash 标定记录` 之后。
用「读故障寄存器 + GDB 回溯」定位（完整方法论见《09》）：

```
CFSR = 0x01000000  → bit24 = UFSR.UNALIGNED（非对齐访问）
HFSR = 0x40000000  → bit30 = FORCED
GDB bt:
  #2 FDCAN_CopyMessageToRAM (pTxData=0x2400035d ...)   ← 地址是奇数!
  #3 HAL_FDCAN_AddMessageToTxFifoQ
  #4 CANTransmit            (bsp_can.c:534)
  #5 DJIMotorControl        (dji_motor.c:404)
  #6 MotorControlTask
```

根因：`CANInstance` 原来有 `#pragma pack(1)`，`sizeof = 77`，于是
`static CANInstance sender_assignment[9]` 从 `[1]` 开始元素地址就不是 4 的倍数
（`0x240002E0 + 77 = 0x2400032D`），`tx_buff` 跟着变成 `0x2400035D`。
而 `-O2` 下 GCC 会把 `FDCAN_CopyMessageToRAM()` 里
`pTxData[3]<<24 | pTxData[2]<<16 | pTxData[1]<<8 | pTxData[0]` 合并成一条 32 位 `ldr`
→ 非对齐读 → UsageFault → HardFault。`-Og` 逐字节拷贝，所以这个问题一直没暴露。

修复：去掉 `pack(1)`（`sizeof` 77→80），并加三条 `_Static_assert`
（`sizeof` 是 4 的倍数、`txconf`/`tx_buff` 的偏移是 4 的倍数）防止将来再加回去。

### 2026-09-22（续）：修掉"日志把系统打崩"—— LOG-01

把上面那批改动烧上去、跑几十秒之后，板子又挂了一次。这次现场非常明确：

```
CFSR = 0x00008200   → BFSR: PRECISERR(精确总线错误) + BFARVALID
HFSR = 0x40000000   → FORCED(由可配置故障升级)
BFAR = 0xC0000000   → 出错地址落在 FMC/SDRAM 区(本板没接外存)
PC   = 0x080063D4   → addr2line: SEGGER_RTT_vprintf(), SEGGER_RTT_printf.c:428 → c = *s;
LR   = 0xFFFFFFE9   → 从异常上下文升级进来的
栈帧(对 MSP 手工解栈): R0..R3/R12/LR=0x08006411/PC=0x080063D4/xPSR=0x01000000
```

**根因**：`LOG_PROTO()` 拼出的格式串是 `"  %s%s" format "\r\n%s"`——
`format` 后面**永远还跟着一个 `%s`**（用来复位颜色）。而 SEGGER 的 RTT printf 是精简实现，
**不支持 `%f/%e/%g`，遇到它们时走 `default: break` 且不消费参数**。
于是：

```
%s        → color
%s        → type
%.4f      → 不支持, 不消费    ← 本该消费一个 double(2 个 32bit 槽)
%.5f ×3   → 同上
\r\n%s    → 取到的不是 RTT_CTRL_RESET, 而是第一个 double 的低 32 位(浮点位模式)
            → 被当成 const char* 解引用 → 读 0xC0000000 → BusFault → HardFault
```

之所以"以前没炸"，是因为错位后取到的位模式是随机值：
恰好是 `0x00000000` 时读的是 ITCM 别名区（可读）→ 侥幸通过；
落在没接外设的区域 → 崩。**典型的偶发、和"改一下打印内容就不崩"的特征。**

顺带说明：这些 `%f` 在 RTT 下**本来就打印不出东西**（之前日志里看到的就是 `gNorm= off=//`），
所以清掉它们没有任何信息损失。

**修法（两层）**

1. **治标**：清掉工程里所有日志中的 `%f`——
   `bmi088.c` 三处（online calib OK / FAILED / 使用 Flash 记录）+ `bsp_dwt.h` 的 `TIME_ELAPSE` 宏，
   统一改成"放大成整数"打印（`gNorm_x1000` / `off_x10000` / `temp_x100`）。
2. **治本**：在 `SEGGER_RTT_printf.c` 的 `default:` 分支里，对
   `f/F/e/E/g/G/a/A` 执行 `(void)va_arg(*pParamList, double);` ——
   即使将来再有人写 `%f`，也只是"这一项不显示"，**不会再破坏后面的参数表**。

**实测**：`-Og` 跑 45s、`-O2` 跑 45s，均 `CFSR=0 / HFSR=0`，
`[cpu] / [seg] / [can] / [lcd]` 四行汇总日志连续正常打印。

**新增学习文档**：《10-可变参数与格式串安全》（含完整解栈步骤与"日志自查清单"）。

**新增待办**：LOG-02（把 `LOG_PROTO` 改成先 `vsnprintf` 再输出，从机制上免疫格式串错误）、
LOG-03（`HardFault_Handler` 保存故障现场，不接调试器也能事后分析）。

### 2026-09-23：CAN 接收链路改造 —— 中断入队 + 任务逐帧派发（BSPCAN-02 / MOTOR-08 / MOTOR-09 结案）

**改动的动机**：CAN 接收中断里原来直接调用模块回调，对 DJI 电机来说就是
在中断里做"解析 + 两路浮点低通滤波 + 多圈角度累加"，而控制任务同时在读同一份
`measure` —— 属于典型"中断写 / 任务读"的数据竞争；而且 12 个电机 ×1kHz 反馈
= 每秒 1.2 万次 ISR 里各干这一串活。

**为什么不能"只把最新一帧丢给任务"**：低通滤波和多圈累加都有**跨帧状态**
（`last_ecd` / `speed_aps` / `total_round`）。跳过中间帧时，一旦两帧之间的
角度变化超过半圈（4096/8192 = 180°），`total_round` 就会算错且永久偏一圈。

**改法**：

- 每条总线一个 **SPSC 环形队列**（深度 32 ≈ 32ms 缓冲），中断只做
  "查表找实例 → 把 `{实例, 长度, 8 字节}` 入队"；
- 解析由 `CANProcessRx()` 在任务上下文**逐帧按到达顺序**执行；
- 消费点放在 `MotorControlTask()` 开头、**算控制之前** —— 拿到的仍是最新反馈，
  **端到端延迟与改造前相同**；
- 队列满时丢新帧 + 计数（`rxq_drop`），并记录历史峰值 `rxq_peak` 来判断深度；
- `CANInstance` 布局与回调签名完全不变，其余模块（LK/HT/DM/can_comm/super_cap）
  无需改动即自动受益。

**实现中自己发现并修掉的两个坑**：

1. **双消费者**：启动期自测跑在 daemon 任务里，而那时 motor 任务已在调用
   `CANProcessRx()`，两个任务同时推进 `tail` 会重复消费/漏消费。用
   `__disable_irq()` 包一个 test-and-set 互斥挡住第二个调用者（被挡方直接返回，帧不丢）。
2. **HAL_FDCAN_Init 会清滤镜**：注入自测切回环用的 `CANForceMode()` 内部会调
   `HAL_FDCAN_Init()`，它重配整块消息 RAM，把各电机实例原先注册的接收滤镜全清掉。
   第一次实测的现象是"5 项自测全失败、只发出 4 帧"（帧根本没被任何滤镜接收）。
   补一次 `CANReapplyFilters()` 后立刻全通过。

**顺带修的两项**：

- **MOTOR-09**：`set = (int16_t)pid_ref;` 之前先饱和到 ±16384（超出 int16 会回绕成
  反向大电流），加 `dji_current_sat_count` 观测；
- **ISR 内日志**：`FDCANFIFOxCallback` 里的 RxFIFO 溢出日志改为只计数，
  打印挪到 `CANHealthMonitor()`（任务上下文），并给接收侧单独一份限速状态
  （否则会被发送侧告警压掉）。

**验证（无真实电机，全部在板子上跑）**：

| 项目 | 方法 | 结果 |
|---|---|---|
| 回环自测 | `CAN_SELFTEST_LOOPBACK=1`，三条总线各发 8 帧 | `pass_mask=0x07`，24 发 24 收，坏帧 0 |
| 假反馈注入自测 | `CAN_DJI_INJECT_TEST=1`：单帧解码 / 正跨圈 / 反跨圈 / `total_angle` 一致性 / 连续 20 帧序列 | **5 项全通过**（pass=5、fail=0、多圈错误=0、共 23 帧，与设计帧数完全吻合） |

### 2026-09-23（续）：异常现场保存 —— 不接调试器也能知道崩在哪（LOG-03）

**动机**：这一轮里已经**两次靠接调试器**才把 HardFault 查出来（一次 `CANInstance`
非对齐、一次日志格式串打乱参数表），而且中途还遇到过调试器直接连不上
（`CMSIS-DAP command CMD_INFO failed`）。当时的 `HardFault_Handler` 只有一句
`while(1)`，不接调试器就只能看到"板子在反复复位"。

**改动**

- **新增 `.noinit` 段**（链接脚本，放在 `.bss` 之后）：启动的 `FillZerobss` 只清
  `_sbss.._ebss`，所以这一段能跨系统复位保留（掉电丢失，已确认接受）。
- **新增 `bsp/crash` 模块**：现场内容 = 类型 / `CFSR/HFSR/BFAR/MMFAR/DFSR` /
  异常压栈的 8 个字（`R0-R3/R12/LR/PC/xPSR`）/ `MSP/PSP` / 32 字栈快照 / 累计次数。
  `CrashLogRecord()` 只做"读寄存器 → 写 RAM → `NVIC_SystemReset()`"，
  **不调用函数、不写日志、不碰外设** —— 异常可能由内存/总线错误引起，
  任何额外动作都可能二次 fault 导致 Lockup，连现场都保不住。
  顺序上**先写数据、最后写 magic**，于是"magic 有效"就等价于"整份记录写完了"；
  另加 `progress` 字段记录写到第几步，用于诊断"写到一半就死了"。
- **五个异常入口改成 `naked`**：普通函数的序言会 push 寄存器、把 SP 挪走，
  那样 `mrs r0, msp` 拿到的就不是硬件压的那个帧了（会整体错位）。
  取帧时按 `EXC_RETURN` 的 bit2 选择 MSP/PSP。
- **断言与栈溢出**：`configASSERT` 从"关中断死循环"改成记录 `__FILE__` + `__LINE__`；
  打开 `configCHECK_FOR_STACK_OVERFLOW=2` 并实现 `vApplicationStackOverflowHook`
  记录任务名指针（字符串在 Flash 里，复位后依然可解析）。
- **LCD 系统页新增 CRASH 行**：显示 `类型@PC 次数`，没崩过显示 `--`。
- **可开关的崩溃自测**（`CRASH_TEST`，默认 0）：启动后依次故意触发
  BusFault / 断言失败 / 栈溢出，验证整条链路。

**实现中踩的两个坑（都很典型）**

1. **自测最初放在 `BSPInit()` 末尾** → 崩溃发生在 RTT 初始化之后**几毫秒内**，
   复位太频繁，几乎每次 halt 都落在"RTT 还没初始化"的窗口里，读不到日志。
   改到 daemon 任务里（数 300 轮循环 ≈ 3 秒）就稳定了。
2. **一开始用 `osDelay(3000)` 等系统稳定** → daemon 任务睡 3 秒**没人喂狗**，
   IWDG 200ms 先把板子复位了（实测复位原因是 `IWDG1` 而不是 `software`），
   自测根本跑不到。改成"在循环里数周期"，期间 `TaskMonitorTick` 照常喂狗。

**验证（`CRASH_TEST=1` 的独立构建，不动源码默认值）**

| 类型 | 记录到的现场 |
|---|---|
| `HARDFAULT` | `pc=0x08014DA0 lr=0x08014D91 sp=0x24003CB0`（有完整异常帧）+ `CFSR/HFSR/BFAR` |
| `ASSERT` | `pc=0x08014DC5` + **`assert: .../bsp/crash/bsp_crash.c:258`**（文件名+行号精确到自测那一行） |
| `STACKOVF` | **`任务 'selftest' 栈溢出`** + `MSP/PSP` + 栈快照（快照里能看到成片 `A5A5A5A5` —— FreeRTOS 的栈填充图案） |

另外两条关键证据：

- **复位原因从 `IWDG1` 变成 `software`**，证明 `NVIC_SystemReset()` 生效、
  不再需要等 200ms 看门狗；
- 正常固件跑数分钟 **0 条 crash 日志**，说明打开的栈溢出检测没有误报。

> 排查过程中还确认了一个容易误判的事实：`.noinit` 的地址由 `.bss` 大小决定，
> 所以**换了固件（比如 build-test → build）之后，之前留下的记录读不到** ——
> 这不是 bug，只是"跨固件不通用"。同一固件内的复位保留已反复验证。

### 2026-09-26：串口 + VCP 接收链路改造 —— ISR 只入队，解析搬到任务（BSPUART-02U1/02U2）

**动机**（三条实测依据）：

1. `HAL_UARTEx_RxEventCallback()`（**正常接收路径**，每包都进）在中断里直接调模块回调 ——
   裁判要在 255 字节里滑动找帧 + 逐帧 CRC8/CRC16 校验，可能一包里切出多帧；
2. `HAL_UART_ErrorCallback()` 在中断里调**阻塞版** `HAL_UART_AbortReceive()`（会轮询等
   UART/DMA 回 READY，DMA 卡住就等到超时）并写 RTT 日志；
3. 视觉的正式链路走 VCP，`DecodeVision()`（滑动找帧 + CRC16）也在 **USB 中断**里跑。

**改法**（与 CAN 改造同一套路数）：**中断只把数据拷进队列 + 重新武装接收，
解析/恢复/日志全部搬到 1kHz 的 `MotorControlTask` 里逐帧执行**。

- UART：每实例一个深度 4 的 SPSC 队列（项大小按各自 `recv_buff_size` 从**静态池**切分，
  不占 FreeRTOS 堆）；`HAL_UART_ErrorCallback` 只 `err_count++` + `need_recover = 1`；
  `USARTProcessRx()` 里做"重试 ≤3 次的 Abort + 重启"和限速错误日志。
- VCP：深度 8 的环形队列（项 128B），`CDC_Receive_HS` 改调 `VCPQueuePush()`；
  `VCPProcessRx()` 取出后拷回端点缓冲再调 `DecodeVision`（模块侧零改动）。
- 两个新消费者与 `CANProcessRx()` 并排放在 `MotorControlTask()` 开头，都带原子互斥。

**必须"拷贝"而不是传指针**：两条链路都是**同一个缓冲区被复用** ——
UART 的 DMA buffer 在重新武装后立刻被继续写入，VCP 的端点缓冲在
`ReceivePacket` 之后随时会被下一包覆盖。只传指针给任务就会读到半新半旧的数据。

**实测验证（板子上跑，全部通过）**

| 验证项 | 方法 | 结果 |
|---|---|---|
| VCP 视觉链路 | `tools/vision_sim.py` 经虚拟串口(COM14) 投喂 1600 帧 @200Hz | `vision_rx_count=1600`（**全收到**）、CRC 错误 **0**、丢帧 **0**、帧头/mode/yaw 解析正确、**中断侧 ≤1µs** |
| 串口错误路径 | USB-TTL(COM3) 用**错误波特率**灌 6 秒制造帧/噪声错误 | **err=4935 / recover=4924 / fail=0**；`usart_prof_rx_isr` **恒定 ≤5µs**；任务侧派发平均 2.9µs、最大 30µs（含恢复动作） |
| 串口正常路径 | 同口改用正确波特率投喂 250 帧 | `RxEventCallback` 调用次数 **+250**（完全对应）、错误计数不变、丢帧 0、ISR ≤6µs |
| 长跑与占用 | 自由运行 ≥25s 后再看 | **IDLE 52.2%**（改造前 52.1%，无退化）、无 task timeout、无 crash、`CFSR/HFSR=0` |

> 关于"改造前的对比数字"：改造前 `HAL_UART_ErrorCallback()` 里既没有探针、
> 现在也已经被替换掉，所以拿不到同口径的历史数据。不过从代码结构上很清楚 ——
> 原来每次错误都要在中断里做**阻塞 Abort + 重启 DMA + 写 RTT**，
> 现在中断里只剩两条语句；实测"4935 次错误、中断耗时恒定 ≤5µs"就是改造后的状态。

**顺带新增**：`tools/vision_sim.py`（通过虚拟串口投喂合法 SP 帧的模拟上位机，
以后验证视觉链路可以直接复用）。

### 2026-09-26（续）：LCD 性能优化 —— 按内容变化重绘 + SPI 提到 30MHz（LCD-12/LCD-08）

**现状与动机**：LCD 每帧（5Hz）无条件重画全部 9 行值区（先 `clear_value()` 清 172×16px，
再画文本），但大部分数值（电压、安全状态、任务在线位、CAN 状态）根本不变化。
实测 `lcdtask` 占用 **15.3%**（仅次于 instask 的 25.1%），是继 CAN 之后第二大 CPU 开销来源。

> 顺便纠正了报告里一个不准确的说法：`lcd_upd=58397µs`（58ms）是**墙钟时间**，
> LCD 任务优先级最低、刷新期间会被反复抢占；真正的 CPU 开销是 `[cpu]` 里的
> `lcdtask=153‰` 即 15.3%（约 30ms/帧）。

**改动**

- **值区按内容变化重绘**（`lcd_ui.c`）：新增逐页逐行的内容缓存（约 2.1KB RAM），
  三个绘制入口统一走它——ASCII 比字符串（**比截断后的最终文本**，不是原始入参）、
  中文标签**比指针**（同一内容本来就是同一个常量数组）、浮点值比"数值+小数位数"
  （本工程不用 `%f`，无法先格式化）。内容没变就整行跳过，连清屏都不做。
- **缓存失效点收敛到一处**：`LCD_UI_InvalidateValueCache()` 只在 `LCD_UI_DrawStatic()` 里调用。
  之所以选这里，是因为所有"整页重画/清屏"的路径（初始化、热插拔恢复、翻页、冻结切换、
  标定提示消失）都经过它——一处生效不会漏。这是本方案最容易出 bug 的地方：
  漏了就会变成"屏幕被清了但值一直不刷新"。
- **SPI1 分频 8→4**（`spi.c`）：已核实 SPI1 时钟源是 PLL1Q=120MHz（`main.c` 没配
  `PeriphClkInit`，用默认值），所以 15MHz → **30MHz**，一帧的 SPI 传输时间减半。
  加了醒目注释（CubeMX 重新生成会覆盖、花屏就回落到 8）。
- 新增观测：`lcd_rows_drawn` / `lcd_rows_skipped`，直接看"跳过率"；保留原有 `lcd_prof_*` 探针。

**实测对比（同一工况）**

| 指标 | 改造前 | 改造后 |
|---|---|---|
| `lcdtask` CPU 占用 | 15.3% | **1.0%** |
| IDLE 余量 | 52.2% | **66.2%**（+14 个百分点） |
| 每帧重画行数 | 9 行（全部） | **约 0.94 行** |
| 跳过率（`skipped/(skipped+drawn)`） | 0% | **88.6%** |
| SPI 时钟 / 刷新率 | 15MHz / 5Hz | 30MHz / 5Hz（不变） |

**数据可信性核对**：`lcd_module_absent=0`（模组在位）、连续两次采样间 `lcd_prof_cycles`
6 秒增长 31 次（5Hz × 6s = 30，吻合）、同期 `lcd_rows_drawn` 只增长 29 行 —— 说明
"LCD 确实在刷，而且每帧只重画了约 1 行"，不是"因为没插屏所以没开销"。

**遗留**：用户观察**有偶发显示异常但不影响正常使用**，已记录为 LCD-16 观察项。
若后续确认是偶发花屏/错位 → 回落 SPI 分频到 8（缓存优化仍在，占用预计 5~6%）；
若是值区偶发空白 → 属缓存失效漏洞，需按 LCD-16 的说明排查。

**新增学习文档**：《17-LCD 刷新的性能账》（SPI 带宽换算、墙钟 ≠ CPU 占用、
"画得快"与"画得少"的收益上限、缓存失效时机、帧缓冲/脏矩形的取舍）。

### 2026-09-26（续二）：消除按键时的整屏黑屏（LCD-16 定位 + LCD-17 修复）

**现象**：LCD 优化上线后用户反馈"按键时偶发黑屏然后重刷"，不影响使用但能看到。

**定位过程**（先排除硬件、再查代码）：

1. 从现象排除 30MHz 时序问题 —— 信号完整性问题表现为**雪花点/文字错位/颜色不对**，
   不会表现为"整块黑一下再刷回来"，而且黑屏只在**按键**时出现、平时不出现；
2. 顺着按键路径查下去，三条路都走到 `LCD_UI_DrawStatic()`，而它的第一件事就是
   `LCD_BufFill(0, 0, LCD_W-1, LCD_H-1, BLACK)` —— **整屏刷黑**，然后才重画标题和标签；
3. 所以每次按键都是"整屏黑 → 重画标题标签 → 逐行画值"。这一瞬间只有几毫秒
   （提到 30MHz 后更短），人眼有时捕捉得到有时捕捉不到，表现为"偶发"——实际上每次都会发生；
4. 结论：**不是这两轮改动引入的**（那句整屏填充从一开始就在），也不是硬件问题。

**修复**（核心思路：**按影响面决定重画范围**）

| 按键 | 实际影响的内容 | 改后的重画范围 |
|---|---|---|
| 上/下（翻页） | 标题 + 9 行标签 + 9 行值 | 标题栏（`draw_page_title` 覆盖）+ 标签列（清）+ 值区（逐行清画） |
| 中键短按（冻结/恢复） | 只有标题栏右上角的"冻结"标记 | **只重画标题栏**（原来走整页重画） |
| 中键长按（重初始化） | 屏幕内容未知 | **整屏清（保留）** |

具体改动：`DrawStatic` 只清标签列（x: 0~`COL_VALUE_X-1`）；抽出 `draw_page_title(page)`
统一画标题（四个页面的 static 函数不再各自画）；`LCD_UI_SetFrozen()` 从
`DrawStatic + UpdateValues` 改为只调 `draw_page_title()`。`LCD_UI_Init()` 与
`LCD_UI_Recover()` 里的整屏清屏**保留**——那两处是"模组刚上电、屏幕内容未知"的场合。

**用户实测确认**：翻页不再整屏黑、冻结/恢复完全不闪、长按重初始化仍按设计整屏重画，功能完整。

**学习文档**：合并进《17-LCD 刷新的性能账》第 5.1 节（"重画范围要按这次操作实际改变了什么来定"：
画少了留残影、画多了会闪，两边都是 bug）。
