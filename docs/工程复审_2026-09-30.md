# MC-02 工程复审（2026-09-30）

## 范围与结论

本次复审以当前工作树为准，检查了构建清单、自有源码的启动/任务/通信/控制链路，并核对了 [既有审查报告](代码审查报告_MC-02.md) 和 [原始待办](../.Doc/TODO.md)。`Drivers/`、`Middlewares/` 作为第三方代码，仅核对实际调用接口；没有逐行审计库实现。未连接整车执行器，以下运行结果均为**代码可达性推断**，不是实车复现。

工程是基于 **STM32H723VGT6 / 达妙 MC-02** 的 RoboMaster 哨兵机器人电控固件。默认 `ONE_BOARD`，由一块板运行底盘、云台、发射、遥控、裁判系统和视觉通信；`VISION_USE_VCP` 选择 USB CDC 虚拟串口。程序从 `Core/Src/main.c` 初始化 HAL/外设，经 `RobotInit()` 注册模块和任务，再启动 FreeRTOS。INS 与电机任务约 1 kHz，机器人命令任务约 200 Hz，守护任务约 100 Hz。

```text
main / CubeMX 外设初始化
  → BSPInit（DWT、看门狗、日志、ADC、参数、崩溃记录）
  → RobotCMDInit / GimbalInit / ShootInit / ChassisInit
  → FreeRTOS: INS、Motor、Robot、Daemon、UI、LCD、USB defaultTask
  → 遥控/视觉/裁判输入 → RobotSafety + RobotCMD → message_center
  → Gimbal / Shoot / Chassis → DJI 电机 PID → FDCAN 输出
```

## 新发现：运行安全与正确性

编号对应 `.Doc/TODO.md` 中的新增任务。P1 是上车前应关闭的风险；P2 是边界和可维护性问题。

### 既有待办仍重要

- **功率、热量、发射机构**：`Chassis::LimitChassisOutput()` 的功率限制仍为空，`power_manager` 是骨架；`ShootTask` 的档位目标仍为 0 或默认 30000，未使用裁判热量和电容状态。对应旧报告 APP-07、MISC-07 与路线图 Phase 2。
- **配置单一来源**：`sentinel_config.c` 的底盘/云台/发射电机 ID、总线、轮径和俯仰限位，与 `chassis.c/gimbal.c/shoot.c` 的实际硬编码不一致；对应旧报告 APP-10、PARAM-03。
- **通信和 RTOS**：消息中心目前 `QUEUE_SIZE=1`，没有时间戳或数据年龄；双板 CANComm 接收异常后的旧数据仍可被使用；旧报告已列 BSPUART-03U1、CAN-05/07、CORE-10。
- **并发说明**：原始 `.Doc/TODO.md` 曾建议用普通 `bool` 实现互斥，并以“数据短”为由省略保护；检查与赋值不是原子操作，抢占时依然有数据竞争。本轮已修正文档并加入 R25-14。
- **备用驱动**：LK/HT/DM/servo/SPI/IIC 等旧报告未完成项仍开着，默认主链路之外的驱动启用前应逐项验收。`seasky_protocol.c` 老协议接口没有长度参数，不宜直接对外部输入调用。

## 优化与重构顺序

1. **安全边界**：将输入验证、数据年龄、RobotSafety 判定和电机输出失能组成统一的最后一道输出门；先解决 R25-01~08 和 R25-15，再做整车通电测试。
2. **单一配置**：电机总线/ID/方向、PID、运动学参数、软限位从一份配置生成，启动时校验 ID 冲突和物理范围；移除应用层重复硬编码。
3. **通信接口**：UART/USB/CAN 的接收统一提供实际长度、校验结果、时间戳和在线态；把解析与控制快照分离，避免跨任务读到半更新数据。
4. **任务与内存**：将 CAN/串口/USB 解析从 1 kHz 电机任务中拆出可定界预算的服务任务或限额处理；记录队列峰值、每任务栈余量和周期最坏耗时。当前 Debug 构建主 RAM 使用 **106384/131072 B（81.16%）**，优先排查静态大缓冲和任务栈，不把可 DMA 的缓冲迁入 DTCM。
5. **构建/测试**：统一 Makefile 和 CMake；CI 增加主机侧协议/安全状态机/运动学测试，编译告警逐步清零。当前编译存在 `DWT_ProbeDone` 形参丢 `volatile` 等告警。
